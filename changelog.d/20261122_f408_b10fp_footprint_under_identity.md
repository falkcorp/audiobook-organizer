### Fixed

- The "Sign-ins & data" drawer (`GET /api/v1/users/:id/footprint`, the SPA's `?footprint=` link) works again once accounts live in core (identity flip, F4-08 B10fp). Under the flip it answered 409 `merge_unavailable_under_identity`, because the account, its sign-ins, its API keys and its sessions had moved to core and books had no read of them. It now answers HEAD's JSON (same member names and types): the account from core, the sign-ins from core with the subject masked exactly as before (first two and last two characters, the owner-address flag kept), the counts of API keys, sign-ins, invites and invite grants from core, the books-owned counts (listening state, positions, bookmarks, preferences, playback, playlists, collections) from books' store, and `active_sessions` from core (expired sessions and sessions an epoch bump outdated are not counted). The read is a new masked core admin call, `auth.AccountAdmin.AdminAccountFootprint`: it returns counts and masked values only, never a key, hash, token, session id or raw subject, and it checks `core:users.manage` and `core:admin` on the request's principal itself, so holding the handle grants nothing. The route keeps HEAD's refusals: a caller who is not an admin, an API key that may not act as admin, and a request with no principal still get 403 (or 401), before any core read. A server with core identity wired but without core's handles still answers 409. `usermerge.Service.Footprint` now takes the request context, and `CheckFootprintAvailable` is gone.
