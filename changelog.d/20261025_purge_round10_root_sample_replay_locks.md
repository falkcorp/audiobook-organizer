Fixes from the tenth review of the purge work (PR 4140, continued in PR 4165).

- The library-root check no longer asks whether the root directory is empty. On production the root is never empty while the application runs: the database (`.appdata`), the cover cache and the backups live inside `root_dir`, so "not empty" passed for an unmounted library. `libraryRootReady` now samples the database's own evidence: up to 50 live (not trashed) `book_file` paths under the root, taken from a window of books at a random offset, are stat-ed, and the root is ready only when more than half of them are there. A store error while sampling refuses. A library with no live file under the root is ready. Cost: a library that has really lost most of its live files (deleted by hand, moved out of the root) is also refused a delete-files purge until they are back or their books are dealt with, because that cannot be told from an unmounted share; each check is a window read plus one book_file read per book examined and up to 50 stats.
- A missing file counts as "already gone" only when the folder it would be in exists. With the folder missing too (nested ZFS datasets mount apart from the root, so the root can look populated and a folder under it still be absent) the file is undecided: a trashed book stays in the trash with a line saying so, and a journal record is kept for three passes and then cleared with "its folder is still missing". Cost: a trashed book whose whole folder has been removed cannot be purged with delete_files until the folder is readable again (a purge without delete_files is not affected), and a record for a file that was removed together with its folder, for instance by a concurrent single-book purge that also emptied the folder, costs up to three passes of one report line each.
- A pass trusts its start-of-pass root check for 15 seconds (`rootGuard`) and then checks again, so a mount lost in the middle of a long pass stops the books after the loss from being decided; before, the check was made once.
- The replay has its own lock (`replayMu`, held for the whole run) and takes the journal write lock (`pendingMu`) only while it reads the records. Before, it held the journal lock through every stat and unlink, so a single-book purge (which holds the shared side) waited for the whole replay. A test pins both orders: a purge is not blocked by a slow replay, and a replay is blocked while a purge sits between its journal write and its row delete.
- The replay honours its context: a cancelled run looks at no further path, keeps every record it did not reach and reports how many. The boot replay passes the server's background context, so shutdown stops it and waits for it before the database closes.
- A single-book purge whose delete fails and whose journal record then cannot be taken back reports both in the error, and logs it; the record outlives a book still in the trash, and the next replay finds that book at the path, keeps the file and clears the record.
- The purge dialog previews with "also delete files" as currently ticked, and again whenever the box is ticked or cleared, so the preview it asks the owner to confirm is the run it will start (before, ticking the box after the first preview ran a different pass from the one previewed).
