### Changed

- The core task executor's "finish" decision on a run waiting for one now does what the current operations registry's "finish without resuming" does. It re-queues the run with a finish-only marker on the run record, and the next attempt leases no work: it reads no source, runs no item and writes no chunk, and runs only the kind's Finish (a Batch) over the stored chunk ledger or its AfterApply (a Fixer) over the rows the run applied. The run ends succeeded, or failed when that step returns an error, and the marker is cleared when the run ends. Before, the decision ended the run succeeded at once and neither Finish nor AfterApply ever ran. A kind that is neither a Batch nor a Fixer is refused with a conflict (`tasks.not_finishable`), as the registry refuses it, and a restart in the middle of the finish returns the run to awaiting a decision with the marker kept (as the registry does), so the person chooses again: finish runs it finish-only, resume clears the marker and runs it normally, drop drops it. A start of the same kind is never folded into a finish-only run. Nothing registers a native kind or starts the executor yet, so no running system reaches this.
