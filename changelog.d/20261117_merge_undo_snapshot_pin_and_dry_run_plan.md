### Fixed

- The book version snapshot prune can no longer make an automatic merge impossible to undo. An undo restores both books from the saved snapshots its journal row names, and the prune kept only the newest N per book and exempted nothing, so N later edits and one prune (the per-book "Prune (keep 5)" button and its route, or the `prune-book-snapshots` job) left the undo with nothing to restore. The prune and its dry run now decide through one function (`planSnapshotPrune`) that asks one pin set, built once from the live `dedup:automerge:` journal rows and rebuilt only when a journal row is written, so a whole-library run does not scan the journal once per book. An entry that was undone releases its snapshots; an unreadable journal row makes the prune delete nothing for that call (fail closed). A merge still being journaled (a provisional entry, written before the merge and finalized after it) pins a range on each of its two books: every snapshot newer than the book's newest snapshot when the merge began, which the entry now records (`winner_baseline_ts`, `loser_baseline_ts`; an entry without them pins every snapshot of both books). The range is answered from the floor, so a snapshot written after the pin set was built is covered, and it has no expiry: a provisional entry whose merge failed keeps pinning for as long as the row exists, and the dry run counts those (`stale_provisional_merge_journals`, with ids capped at 200) instead of unpinning them.
- `Engine.UnmergeAuto` checks that both pre-merge snapshots still exist before it writes anything. When one is gone it returns an error naming the missing `book_ver:` key and says nothing was reverted. Before, it put the loser's siblings and the loser back first, then failed on the survivor with "version not found" and left the entry open, a half-applied undo no retry could finish.
- The `prune-book-snapshots` dry run reports `pinned_by_journal` (snapshots it would have deleted but keeps because a live merge journal row points at them) and, read-only, the live merge journal entries whose undo snapshots are already gone (`live_merge_journals`, `merge_journals_missing_snapshots`, `merge_journals_missing_ids` capped at 200, `merge_journals_missing_truncated`), so whether production has already lost any is known. Nothing is repaired. The job now stores a structured result (`GET /operations/:id/result`).
- The `dedup.auto-resolve` dry run keeps its plan. It stores, as the op result, the pairs a run would merge (cap 2000, with `plan_truncated`) and the pairs a guard refused (cap 500, with `refused_truncated`), with per-guard refusal counts. Each entry has the candidate id, both book ids, band, score, the signals as evaluated, the guard that decided, the reason, the rule id (`dedup.auto-resolve/tier1-certain/v1`), and `shares_book_with_rank` for a pair that names a book an earlier entry names. `planned_by_guard` counts every planned merge by the clause that admitted it, so the number resting on the whole-book-signature label fallback (`corroboration_signature_label`) is visible. No titles and no signal evidence text. `autoResolveEligible` returns a decision with a `Guard`; its eligibility rules are unchanged. The apply path, the `dedup.auto_resolve_enabled` flag and its default, and the per-candidate cost are unchanged: the dry run collects the plan in memory and adds no read or write per candidate.
