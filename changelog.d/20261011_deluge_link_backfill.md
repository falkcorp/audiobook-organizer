### Added

#### `deluge.link-backfill` — link library book files to the torrents they came from

New manual operation (permission `integrations.manage`, write set `book_files`) for library files organized before Deluge imports recorded their torrent. For each torrent under the discovery label (or `label`), it hashes every audio file with `filehash.BookFileHash` (head and tail above 100 MB, whole file below; no audio decoding) and looks for the library row in this order: `DelugeOriginalPath` equal to the torrent file's path, rows with that content hash, the file provenance chain (skipped and reported as `provenance_unavailable` when the store does not expose it), then same basename and size under the library root. A candidate is linked only when the hash equals its `FileHash`, its sampled `OriginalFileHash`, or the digest of its earliest provenance event with the same size (`SHA256Full`, which is what the provenance writers record, for files up to 100 MB; `SHA256Chunk` above that). A path match alone never writes. Only rows inside the library root are linked (a row still naming the seeding copy is counted `outside_library`). Empty torrent files (`empty_files`) and files Deluge was told not to download (`deselected`) are skipped. Rows of deleted books are dropped (`book_deleted`). A torrent file whose verified rows belong to more than one book links none of them, and a row two torrents resolve to (cross-seeded) is skipped for both; both count as `ambiguous`. A row already holding another torrent's hash is counted `conflict` and left alone. The op writes exactly one field, `BookFile.DelugeHash`, through `ModifyBookFile`. Under the row's lock it re-checks the path and content hashes that were verified. It never removes, moves or repoints anything. It previews unless `dry_run=false`. `limit` caps the torrents written and applies only after every listed torrent has been checked for cross-seeds; rows it holds back are counted in `deferred_by_limit`. `workers` defaults to the CPU count, max 8, and is run through `registry.RunItems` with `Concurrency` set. Its result reports `torrents`, `files`, `linked` / `would_link`, `already_linked`, `unverified`, `ambiguous`, `conflict`, `book_deleted`, `deferred_by_limit`, `relink_fixer_would_link`, `non_audio`, `empty_files`, `deselected`, `errors`, `provenance_unavailable`, `unmatched` and `outside_library`. When no torrent file it tried to hash is on disk, a note says Deluge's paths and this server's paths probably differ.

**Run order: apply `maintenance.relink-pre-fix-imports` first.** Files imported before 2026-10-10 recorded neither the torrent on the file nor on its version. That fixer links such a file to its book's version when both carry no torrent hash. Once this op sets the file's `DelugeHash`, the pair no longer matches, so the fixer reports the file as `hash_mismatch` and cannot link it. `relink_fixer_would_link` counts the files this run would do that to, and the result carries a note when it is not zero.

A linked row has `ImportedFromDelugeAt` unset, so it is listed once by `GetBookFilesNeedingDelugeImportCore` for `/discovery/import`, `deluge.centralize` and `maintenance.bulk-deluge-import`. Every linked row is already inside the library root, so all three resolve its destination to its own path and copy nothing. They mark it imported in place, setting only `ImportedFromDelugeAt`, and the row leaves the list. The exception is a protected path, such as a torrent seeding from inside the library: that row stays pending, as it would under `/discovery/import`.

### Fixed

#### `deluge.centralize` and `maintenance.bulk-deluge-import` no longer re-list files that are already in the library

A pending Deluge file whose library destination is its own path used to be skipped with nothing written. It stayed on the pending list and came back on every run, and bulk import counted it "imported" each time. Both now handle it the way `/discovery/import` has since 2026-09-14. If the path is protected, it is left pending and nothing is written. Protected here means under `protected_paths`, under the iTunes library directory, or under the save path of an active torrent (a torrent seeding from inside the library). All three importers share this check (`deluge.InPlaceProtection`). Otherwise the file is marked imported in place: `ImportedFromDelugeAt` is set and nothing else, under the row's lock and only while the row still names that path. They never copy, move or repoint the file. Bulk import reports such a file as `already_in_library`, or `protected` when it is left pending, in its preview too. `deluge.centralize` counts protected files in its summary.

#### Library directories whose names start with `..` count as inside the library

`/discovery/import` and `maintenance.bulk-deluge-import` treated a library directory named like `..Extras` as outside the root and copied its files to the top of the root. `deluge.centralize` and `deluge.link-backfill` treated it as inside. All four now share one check (`pathutil.RelEscapesBase`), so such a file is in the library for all of them.

### Removed

#### Deluge plugin: dead `importToLibrary`

`internal/plugins/deluge/import.go` had no callers (it carried a `lint:ignore U1000`) and was kept only until this change (owner decision D55). The live importer, `internal/deluge/importer_adapter.go`, is unchanged. `MarkFileImportedFromDeluge` left the plugin's store interface with it.
