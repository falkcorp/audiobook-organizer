### Fixed

- `reconcile.apply`: a book already at the matched file when the apply wrote it (another writer set the path after the plan) no longer leaves live journal rows for writes this operation never made. The hash clear still runs under the same check; rows for a clear that did not run are voided, and the path and file-row twin rows are voided when this operation moved no row. A book write that reported a failure but reads back at the matched path is classified by its cleared hashes (this operation wrote it, another writer did, or unproven) instead of assumed to be ours, and the hand-off runs only after a write that was ours. Before, reverting such an operation could undo the other writer's later change.
- `reconcile.apply`: finishing a stranded match with a hash match hands over the earlier operation's hash-clear rows, keyed on the hashes the book held under its lock when the apply wrote it (not the plan's read). A hash match checks no hash, so the plan's read could be stale, and a hash-match finish used to leave the earlier operation's rows live, so a later revert of it undid a later apply of the same match.
- `reconcile.apply` stamps every journal row it writes with Source `reconcile.apply`, and the twin and the hand-off copy and mark only rows with that Source. The operation row can be discarded while its journal survives, and `fs_regroup_xml` and the organizer journal `book_path_update` with no Source, so a row with no Source is not the apply's. A row journaled by the apply before it stamped a Source is no longer recognised: finish such a stranded match by reverting its operation.
- `reconcile.apply`: a match that landed but whose hand-off to an earlier operation, or whose void of rows for a write that did not run, failed is applied and named in the operation's errors (the operation ends with an error). Before, it was only logged.
- `reconcile.apply` refuses a stranded match whose journal cannot be read, with nothing written. Finishing it without the twin and the hand-off would leave a revert of the finish putting the book back while the row stays at the matched file.
- `POST /operations/reconcile` and the `reconcile.apply` precheck refuse a `match_type` the scan never produces (anything but `hash`, `original_hash`, `filename` or none) with a 400 naming the match; the apply also refuses it per match with nothing written. An unknown type used to apply as an unproven match and clear the hashes, so a typo of `hash` silently cleared the hashes of a match that proved the content.
- The `reconcile.apply` operation description said it moves files; it repoints a book and its file row at a file already on disk and moves, copies or deletes nothing.
- The store has an atomic "repoint unless held": `ModifyBookFileUnlessPathHeld` re-checks the single-owner path key at the commit, under the owner stripes and the single-owner index mutex, and refuses with `ErrBookFilePathHeld` when another row (live or retired) holds the new path. `reconcile.apply`'s row repoint uses it, closing the window the callback's own holder check left: a library scan that imported the matched file as a new book's row inside that window had its path key taken by the repoint, so two books held one file.
