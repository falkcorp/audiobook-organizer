### Fixed

- Settings saves keep every check the old save path made, now in the configuration Engine: the candidate is run through `Config.Validate` and refused when the write adds a problem (an unset is judged by the default it returns to); a removed setting is refused with the reason it was removed; a submitted `ai_endpoints` list is validated; a masked secret value (four or more asterisks) is refused for the secret fields and the metadata-source credentials the old save checked. Before this, only core's own schema bounds applied, so a bad vector backend, a negative scan count, an out-of-order dedup ladder, a duplicate AI endpoint id or a pasted mask was accepted (F3-07).
- A setting the operator's environment supplies and the settings blob also holds (the Deluge connection) takes the operator's value and is reported locked; a save that names it is refused with 409 instead of being stored and overridden at the next restart (F3-07).

### Changed

- The old environment-only settings `cf_account_id`, `cf_guests_policy_id`, the login-saturation pair, `public_base_url`, `allowed_peer_cidrs` and `tunnel_connector_addrs` are ordinary stored settings now (spec 05-config 1.3.7). The peer allow-list, trusted proxies and public base URL need an interactive admin session; an API key, the bootstrap key included, is refused. The SMTP block and the Cloudflare policy token stay operator-only (F3-07).
- `enabled_sort_indexes` is accepted and reported restart-pending instead of being refused, because it is a restart-bound key (F3-07).
