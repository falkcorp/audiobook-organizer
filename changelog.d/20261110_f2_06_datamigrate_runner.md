### Added

- Core: data migrations, shipped dark (platform-core F2-06). `core/storage/datamigrate` declares them (`DataMigration`, `StepWriter`, `VerifyReport`, `Blocker`, `DerivedBuildSpec` and `DerivedBuildTask`), and `core/internal/storagemigrate` runs the `BootBlocking` ones inside the boot's migration DAG. Each one has a persisted shard plan, persisted shard cursors and one batch per chunk, so a crash leaves every item of a chunk either untouched or done and a resume starts right after the last committed item, even when the machine has a different CPU count. Shards run in parallel through `tasks.ForEach` and never touch the same item. A chunk writes each key at most once. A write into another shard's range is allowed only below that shard's last committed item, so a crash cannot make a resumed shard step the migration's own write. A failed `Verify` leaves the migration `failed`, fails the boot with the checkpoint open and keeps the owner's later versions blocked. The `Online` mode is refused at registration (SIMP5-7). `core/kernel/migrate.go` builds the runner, records the `data_migration_items`, `data_migration_state` and P4b `boot_phase` metrics, and holds the seams that F3-04 fills: the quarantine writer, the preflight and the level step. Nothing calls it yet; the boot call is F2-16's.
- Core: `coretest/crashmatrix` can kill a data migration at every chunk boundary of every shard and inside a chunk, then reboot and check that no row was lost or doubled (`RunChunks`, `SyntheticCutover`). The boot crash matrix has a new row for the three data-migration writers (plan, chunk with cursor, state), and hello's `TestBootCrashMatrix` covers each one through the kernel entry point.

### Changed

- Core: `storage.Open` takes the build's data migrations as DAG nodes (`OpenOptions.DataSteps`), runs them in DAG order before the attempt's checkpoint is closed, and checks the DAG's shape at `Open` rather than at registration, because a versioned step may now name a data migration in `After`. The record of a data migration is keyed `c/storage/dm/<id>`. A data migration's `Barrier` must name one of its owner's registered versions. A boot whose pending data migration names a `Barrier` version the store has already applied fails with `ErrBarrierApplied`, because that version has already run. `storage.RewriteSidecars` checks the migration DAG's shape again. `storage.ErrBatchDone` is now exported, so a data-migration chunk can tell that a step committed or closed its batch.
