### Fixed

#### The apply gate's title check compares whole titles by one rule, and a partial match needs an agreeing runtime

`checkTitle` in `internal/applygate/evidence.go` scored title agreement 1.0 when the candidate's main title equalled ANY segment of the stored title. Two volumes of one storyline share the segment before the colon, so with the runtime inside 5% and the author agreeing a bulk apply wrote the wrong volume onto the book unattended ("Hush: Part 1" took the metadata of "Hush: Part 2" and the reverse, "Batman: Dark Victory" took "Batman: The Long Halloween"). Round 1 compared the whole title but decided agreement by removing text (series names, credited names, "of N", a parenthetical, fuzzy overlap), and each removal was a new way for two books to agree; it is replaced.

The rule lives in `internal/applygate/titlecompare.go` and is symmetric in its two sides. The check answers one of three things:

- AGREE: a whole form of the candidate equals a whole form of the book. A form is the declared fields joined and never trimmed (`{title}`, `{title subtitle}`, each also behind the series name); a side with a subtitle has no bare-title form; the book's file and folder names are forms of the book (never of the series). Equality is over a closed normalisation: NFKC, case, diacritics, "&", number words, roman numerals and digits as the same value, ordinals as a different kind of token, a closed edition-phrase list, a leading article per segment. "abridged" stays significant.
- DISAGREE (`title_disagrees`): only from the two title fields, and only when they share a whole segment and each has a segment of its own, or use the same words with different numbers. A series name, a credit, a path or a year never makes a pair agree or disagree. A title equal to a series name (candidate's or stored, edition tags ignored) still blocks unless a whole form agrees.
- NEUTRAL: everything else related. A neutral title confirms nothing, so `EvidenceVerdict.tally` applies it only when the runtime check AGREES (known on both sides and within 5%); narrator, ASIN and transcription agreement never substitute. Otherwise the refusal is `title_unconfirmed` ("title only partly matches ... and the runtime does not confirm it"), which is a structural refusal an owner review can lift, like `insufficient_evidence` (when the author is the only other agreement the count refuses first, as `insufficient_evidence`).

The same gate guards the metadata auto-upgrade (`metabatch/upgrade.go`), so that unattended path takes the same rule. Recall change: a subtitle, a bracketed tag, a series prefix or a leading list number ("08 - The Long Halloween") on one side only (for example "Hush: A Gotham Story" against "Hush") is now neutral, and applies only with an agreeing runtime.

Still open, as on main: a sequel with a one-sided word or number ("Hush" and "Hush 2"), word-form ordinals ("The Second Robin" and "The Third Robin"), one word changed in a long title, a franchise-only candidate with no series, a one-sided credit ("Year One" and "Grayson: Year One"), numbers swapped between segments (refused only by the sequence check), and the transcription lift path with no runtime (`transcribed_identity.go`). Tests: an oracle-based property test that draws titles, subtitles, series and file names from one word pool, symmetry and "added text never agrees" properties, and a table of 38 reproduction rows asserted at an agreeing, a 7% and a missing runtime.

#### Batch apply from candidate-fetch results no longer re-applies an applied book

`planOpResultApply` (the planner for `/metadata/batch-apply-candidates` and its preview) lacked the already-applied check `planCachedApply` has. The op result's own "applied" status is written only when this path applies the book, so a book applied since the fetch by the cached bulk apply, the review lane or the single-book dialog still had a "matched" result and was applied again: file work, a tag write, an iTunes write-back and a history entry. It now comes back `already_applied` (skipped, not an error), the preview reports it as skipped, and a queued apply skipped for this reason logs it. Undoing an apply restores the book's review status, so an undone book can be applied again.
