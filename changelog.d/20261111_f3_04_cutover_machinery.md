### Added

- Core: the storage cutover machinery, shipped dark (platform-core F3-04). `storage.LevelStep` and `storage.CoreLevelStep` build the level step that guards a cutover (M7), and `(*DB).RaiseLevel` is the data-migration runner's level-step seam. Like the cutover step it guards (06 A5), the level step runs for a disabled module. A cutover step's quarantine goes through `storage.QuarantineWriter`: a row from a `Sensitive` prefix is sealed through a `QuarantineSealer` in the chunk's batch and its record names only the sealed secret, and with no sealer such a row fails its step and its source row stays. `(*DB).Quarantine`, `ExportQuarantine` and `PurgeQuarantine` list, export and delete the records; the purge deletes the sealed secrets too and is audited in the same batch, so a store without `core/audit` refuses it. `kernel.CutoverPreflight` runs every pending cutover step's `Preflight` at P4a, before the checkpoint, and refuses the boot with `storage.ErrCutoverBlocked` having written nothing; `kernel.ExitCode` maps that, a second store-rewrite swap-back and a store too new for the build to exit 78. The quarantine shows in `core.storage`'s health Detail (never its Reason) and in the `storage_quarantine_rows{step,sensitive}` gauge (`kernel.QuarantineGauge`).
- Core: M8, the store rewrite (`storage.NewRewriteStep`, `kernel.DataMigrationsConfig.Rewrite` and `Swapper`). It compacts the store, copies it into a new directory and swaps it in as a `KindRewrite` swap of `core/internal/restoreswap`, in process, with the engine closed around the swap. The generation is kept, the old directory is deleted at once from where the swap moved it (failing closed if it is not there), and a failed swap swaps back and restarts once; a second swap-back refuses the boot (`storage.ErrRewriteSwappedBack`). P0a finishes or swaps back a `KindRewrite` journal a crash left in flight.
- Core: `kernel.DryRun` and the offline command `storage migrate --dry-run`: the store opened read-only is copied into the checkpoint area's `scratch/`, the copy runs the preflight and every pending step, and the report lists blockers, counts per outcome, held and would-quarantine rows and bytes written, never a value. The copy is deleted whatever the outcome. `--estimate` counts over the live store with every write discarded, and `--from-archive` copies from a backup archive. New offline commands `storage quarantine list`, `export` (a new 0600 file) and `purge --step --confirm`.
- Core: the boot crash matrix has a row for M8's writers, the data-migration row's chunk label also carries the quarantine sequence's lease, and hello's matrix kills M8 at each of its writes, on a first run and on the run after a swap-back, then reboots and checks that every row is there and no old store is left.
