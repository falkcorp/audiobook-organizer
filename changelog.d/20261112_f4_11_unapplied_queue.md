### Fixed

- core: a revocation line this build cannot apply (a kind a newer build wrote) is queued instead of stopping the boot re-apply (dark; F4-08 wires the re-apply). Each such line is recorded in `c/backup/journal_unapplied/<seq>` before anything can move the head, the head passes it, and the first build that knows the kind applies it (only when the verified journal holds that line with the same mac) and removes the entry in the batch that applies it. A rollback onto an older build no longer holds the head below the line, so later boots stop re-applying every line after it (which undid an admin's re-enable or a new password), and the journal is no longer refused for good (a restore boot writes its restore line again). The boot still fails closed once for each queued line, now recorded on the entry (`closed`) instead of in a fingerprint. `Component.Hold` and `Resume` replace the file-level hold; `File.Refuse`, `File.Hold`, `File.Resume` and `Component.Refuse` are removed.
- core: the restriction of a kept last admin runs after the whole tail has been applied and queued, and the line that kept the admin completes (its head, its queue entry's removal) only after it. The restriction is a journal append whose head sits above every line, so a crash right after it used to lose every later line for good (a queued kind of a newer build, or a plain user.disabled), and a crash between the keeping line and the restriction left an admin the journal proved was demoted with the role, unrestricted, and nothing to replay it. A boot that keeps an admin in an early chunk now resumes from that chunk after a crash instead of from the last committed one.
- core: audit's copy-forward records of a restore whose journal line could not be written are keyed on a per-run ID (`c/backup/restore_run`) and no longer on restore seq 0, so a second such restore no longer finds its records already written and skips them.
