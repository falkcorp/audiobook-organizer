### Fixed

#### Dedup vector index: a crash that kept the row count no longer leaves the index wrong

At startup the server trusted the saved vector index whenever the number of embedding rows still matched the number saved with it. A crash could change rows without changing that number (one book embedded and another deleted, a book re-embedded, a merge that changed which version is primary), and the index then stayed wrong until something rebuilt it.

A clean stop now leaves a marker beside the snapshot, and a startup that finds no marker brings the snapshot up to date against the database whatever the counts say. The marker is written only when both of these hold:

- the snapshot is exactly the index in memory (complete, undamaged, saved after its last change, and no write the index refused or failed to mirror during the run);
- nothing during the run changed what that update would read from the database: an embedding row, or a book's existence, primary flag or series fields. The check sits where every database write passes, so merges, primary changes, embedding cleanups and re-embeds all count. A run that embedded anything therefore leaves no marker, so only quiet runs let the next start skip the update.

It also records the embedding model, and a startup with another model brings the snapshot up to date. It is the last step of a stop, and is skipped when any stop step was still running or failed, a plugin's shutdown included. A backup restore replaces database files without going through the database layer, so the index counts as out of step from just before the restore writes its first file to the end of the run. A stop that lands while a restore is still writing therefore leaves no marker, even if the process exits before the restore finishes. Any marker beside the live database and beside the database it writes is removed before the restore writes its first file and again after it. A backup holds only the database folder, so a restore now refuses, before writing anything, an archive with anything in the index's snapshot folder beside it or with a file name that climbs out of the restore folder (even one that climbs back in), rather than restore a marker from a file that has no reason to match. A restore whose `target_path` is the snapshot folder, contains it or lies inside it is refused too (to restore over the live database, leave `target_path` out), and the extraction compares every folder on the way to each file with the snapshot folders by identity, so a symlink or a case-insensitive spelling of the folder counts, refuses a file that would land in either, and never writes a file through a symlink. A `target_path` is compared the same way. A snapshot folder whose path is a symlink that does not resolve (dangling or looping) cannot be compared, so such a restore is refused with a 409 before anything is marked or written. Each file is written as a new file beside its destination and renamed into place, so a file already there that is a hard link to a snapshot file is replaced, not written through, and a file cut short leaves the old one whole. Before it reports success, the restore flushes the folders it changed to disk, so a crash right after a successful restore cannot bring back a mix of old and new files. A clean-stop marker the restore can neither delete nor empty now fails the restore before it writes anything. The same check reads the whole archive before the restore starts writing, so a backup file that is cut short, damaged or empty, or that names a file outside the restore folder, is now refused with nothing written, where the restore used to write part of it and then fail; with checksum verification on, the check shares the checksum's read of the file. A restore refused before it wrote anything (the backup was not found, its checksum failed, the backup directory could not be read, the archive could not be read to its end or was empty, it had an entry in the snapshot folder or outside the restore folder, the target overlapped the snapshot folder, or a snapshot folder did not resolve) leaves the marker alone. Any process that opens the database removes the marker, so running a command-line tool between a stop and the next start costs that start one update. A marker that cannot be deleted is emptied, which makes it invalid. The short-lived worker processes that run a single operation leave the marker alone and check only the counts.

Not covered: a tool that writes those database rows without going through the server's database layer (none does today), writes made by a worker process (no operation runs in one today), and the index holding non-primary books that a startup leaves out. For that last one, a run that adds a non-primary book to the index from its stored embedding now leaves no marker; the fix that removes the cost is tracked in TODO.

#### Stop timeout: comments and the deploy example

Three code comments said the systemd unit's stop timeout was 30 s. The committed unit sets none, so the deploy drop-in's value (or systemd's default) applies, and production's drop-in sets 90 s. The comments now say where the value comes from, and `deploy/local.conf.example` uses 90 s.
