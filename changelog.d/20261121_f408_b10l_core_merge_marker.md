### Added

- Core identity records which account an admin user merge folded an account into (`auth.User.MergedInto`, `MergedAt`; `merged_into_user_id` and `merged_at` on the user JSON). `auth.Service.SetStatus` now refuses to enable such an account (`auth.ErrMergedAway`, HTTP 409 `merged_away`), as HEAD's reactivate route did, so a merged-away account cannot be turned back on to share sign-ins and data with the account that absorbed it. The HEAD import carries the marker over for rows merged before the cutover.
- `auth.Admin` gains `PlanUserMerge(ctx, source, target)`, which previews a user merge with every refusal the merge itself runs and returns an opaque `auth.UserMergePlan` (the stored bytes of the records it moves stay inside core; printing a plan shows two ids and a count) plus an `auth.MergeSummary` of ids, counts and outcome codes. `StageUserMerge` now takes that plan and stages, in the caller's batch, the roles the source holds and the target lacks (under the principal's dominance, with the role set claimed so a role edited before the commit fails it), HEAD's e-mail rule on core's one verified flag (the source's address is cleared; the target keeps its own, else takes the source's; a same-address merge whose only verified side was the source leaves the target verified; a verified address another account holds is refused), and the merged-into marker. A merge is refused, with an `auth.MergeRefusal`, when the source was already merged (`already_merged`), when the target would have no way to sign in (`no_sign_in`), and, narrower than HEAD, when a target that is not an admin and has no password would gain a verified address it did not hold verified (`email_linkable`), which an OIDC sign-in by address would otherwise auto-link to it. A plan whose users or records changed since the preview is refused with `auth.ErrMergeConflict`. `auth.Store` embeds a new `MergeStore` (`MergeRows`, and `StageMerge` now takes the two ids and the rows).

### Fixed

- A user merge whose plan went stale while the merge was being evaluated (another merge of the same source landed between the evaluation's reads) is now refused as `auth.ErrMergeConflict`, the true cause, and no longer as a misleading "another account holds the address" refusal. The import rule `auth.CheckImportUser` refuses a user marked merged into another that is not disabled, or that is merged into itself, so no import can hand the store a merged-away account that is open. A restore's replayed `user.enabled` line no longer re-enables a merged-away account, so a merged-away account stays disabled for good on every path.
