### Security

#### Content-Security-Policy and Permissions-Policy on every response

The web app was served with no Content-Security-Policy, so any injected script would have run unrestricted. Responses now carry a policy that allows scripts only from the app's own origin plus the one inline pre-paint theme script, allowed by hash (computed at startup from the `index.html` the binary actually serves, so it cannot drift from the build). Other sources are limited to same-origin (requests may also go to the one host of the configured Cloudflare Access team, `cf_access_team_domain`, so the app can still tell an expired Access session from an outage; nothing is added when it is unset, and no wildcard is ever allowed), with images also allowed from `data:`, `blob:` and `https:` (metadata search shows provider cover URLs), `object-src 'none'`, `base-uri 'none'`, and `frame-ancestors 'self'`. Styles keep `'unsafe-inline'` because the UI library injects them at runtime. A handler that sets its own policy (the OpenID browser page, the Cloudflare recovery page) keeps it. A `Permissions-Policy` turns off camera, microphone, geolocation, payment and USB. Checked in a real browser against the embedded build: no violations on the app's main routes.

The policy stays enforcing and now also reports: browsers send violations to an unauthenticated `POST /api/v1/csp-report` (via `report-uri`, and `report-to` with a `Reporting-Endpoints` header), which logs one line per violation with the directive, the blocked resource, the page and the source file. Every reported URL, with or without a scheme, goes through one reduction first: the query and fragment are dropped, secret path forms such as `/invite/<token>` are redacted, and the page the violation happened on is always cut to its first path segment, so a token in it never reaches the log, whatever Host the request carried. A blocked or source URL on the same site as that reported page (decided against the page's own host, never the request's Host header, which a proxy may rewrite), or a relative or schemeless one, is cut the same way; a third-party URL keeps its redacted path so a blocked script stays identifiable. "Same site" is compared by host name, ignoring case, a trailing dot and the port (`Books.Example.com.:443` is the same site as `books.example.com`), and when the page has no usable host at all every URL is cut, so a missing page can never make a path survive. The invite-route redaction matches case-insensitively and ignores empty path segments, so `/INVITE/<token>`, `/Invite/<token>` and `//invite/<token>` are redacted like `/invite/<token>`; the path is also read in its decoded form, so a path whose slashes are percent-encoded (`/api/v1/auth/invite%2F<token>`, `%2f`, and a doubly encoded `%252F`, decoded up to three times) is redacted too, in this log and in every place an invite page's path reaches a log or a span (the request log, panic recovery, the HTTPS redirect, error-response logging, the trace span path, and the Cloudflare service-token recovery middleware's three lines, which `/invite/<token>` reaches as a page navigation). A guard test fails the build when a log call in the middleware or response packages prints a raw request path outside a redactor. Request-path log lines outside the invite surface (the Audiobookshelf probe and audit records) are unchanged. The raw path is tried as written and then cleaned; then each of up to three decodings of the whole path is tried cleaned and then as decoded (the uncleaned decoded form matters: a dot segment after the token, `/invite%2F<token>/..`, would otherwise clean the route away before it is recognised); each form is matched anchored at its start, and the first match decides. Once the invite prefix is found, every remaining non-empty segment up to the query is redacted, not only the next one, so a decoy segment between the prefix and the token (`/invite/%2F/<token>`, `/invite/./<token>`, `/invite%2F%2E%2F<token>`) does not let the token through; the one segment kept is a trailing `resend` on the invites route. A malformed escape (`%zz`) never switches redaction off or makes decoding fail: it is kept literally and the rest is still decoded. When a path is an invite route only after decoding or cleaning, the logged form is that decoded path with its non-redacted segments re-escaped, so the original spelling is not preserved. If no form matched but some form has a `.` or `..` segment and some form has a segment equal to `invite` or `invites` (decoded once, ignoring case) followed by a non-empty segment, at any position (`/x/../invite/<token>/..`, `/api/v1/users/q/../invites/<token>/..`, `/api/x/../v1/users/invites/<token>/..`), the path is logged as `/[REDACTED]`, because a walked path cannot be redacted by position; the check is one linear pass over the segments, so a dot walk that splits the invites route cannot slip past a prefix test. The same happens when the escaping is nested deeper than three rounds and the last form still decodes to something different (`/invite%2525252F<token>`, and `/%2525252569nvite/<token>`, where even the route name is escaped, so no keyword is needed to decide); decoding is not repeated until stable, which would cost quadratic time on a long nested path. Paths that are not invite routes (`/books/invite/<token>`, `/books/../x`) are unchanged. A `?` inside a path is path text, never a query delimiter: `%3F` decodes to `?` in the parsed request path, so `/invite/%3F<token>` and `/x%3F/../invite/<token>` are redacted like any other invite path rather than cut at the `?` with the rest logged. The request log strips the request's real query first, writes any `?` left in the path as `%3F` and masks credential query values on the real query only, so `/books%3Fa=1?token=<x>` logs as `/books%3Fa=1?token=REDACTED`; if the logged path does not end in the request's query the line is `/[REDACTED]`. Only inputs that are a raw request target (panic recovery, the HTTPS redirect) cut at the first `?`. The path comes from an unauthenticated request line, so the work is bounded: a path over 8 KiB is logged as `/[REDACTED]` without being read, a path with no `%` and no "invite" in it is returned at once without any allocation, and for any other every step (cleaning, decoding, the check for an invite segment at any position) is linear in its length; a test counts allocations at two sizes four times apart and requires them equal, which a quadratic version fails. Values are logged quoted, so a crafted report cannot forge a log line, and truncation never splits a character. A report is capped at 8 KiB and ten violations, and the limits count violations, not requests: a burst of 30 then one every two seconds service-wide, and a burst of 10 then one every ten seconds per visitor (the visitor address, a public IPv6 visitor grouped per /48 so a caller owning a /48 cannot mint a fresh budget per /64). The service burst is deliberately above the visitor burst, so a visitor that has spent its own budget cannot drain the shared one and leave a real browser's reports unlogged, and a full batch of ten from one browser is logged. The decision is made under one lock, and if a charge ever refused after its tokens were verified the reports are dropped and the refusal is logged (fail closed; it cannot happen with the single writer today): a batch is logged up to the smaller of what the visitor's budget and the service's budget still hold, both budgets are charged exactly that many, and the rest are dropped and counted. A visitor with nothing left therefore never moves the service budget, even when many arrive at once (an earlier version reserved from both budgets and cancelled the unused part, which under concurrent requests could lose the refund, so the statements that a refused request spends neither budget and that one caller cannot use up the budget did not hold under load; they hold now, and a concurrent test checks it). Reports over a limit are dropped, counted, and the count is logged with the next one.
