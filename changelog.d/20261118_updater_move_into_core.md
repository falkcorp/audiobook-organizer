### Added

- `make rollback-restore RELEASE=<tag>` now fetches the named release and installs it as `.prev` instead of refusing. After the restore source (the latest checkpoint, or `ROLLBACK_ARCHIVE`) is read, the running binary's new `updater fetch-release --version <tag> --out <file>` downloads that release's binary for the host's platform to the helpers' `stage_bin`, runs it once with `--version-json` to check it is this app at that release, and the recipe compares its store levels with the source's. Only when they are equal does a new `install-staged prev` helper operation put it in place as `.prev` (replacing any `.prev`, never touching the running binary); any refusal before that deletes the fetched file and leaves `.prev` as it was. Without `RELEASE`, a `.prev` at other levels than the source now refuses with the exact `make rollback-restore RELEASE=<tag>` to run, taken from the checkpoint's `from_release`. `updater fetch-release` is also a command of its own, capped at 512 MiB, with no store and no restart.
- The rollback helper `deploy/rollback-helpers/rollback_helper.py` gained `install prev`, and `rollback.conf` needs `stage_bin` for `RELEASE=`. The helpers are root-owned on the host, so the new operation reaches it only when the bundle is reinstalled (see "Rollback helpers" in `docs/system/deploy-and-gpu-ops.md`).

### Changed

- The self-updater now lives in the shared core module (`core/updater`), parameterised by the release source, the binary name and the app name, and with a GitHub release source (`core/updater/github`). Its behaviour on the existing `/api/v1/update/*` routes is unchanged: the same check, the same download of `audiobook-organizer-<os>-<arch>`, the same swap that keeps the old binary as `.prev`, the same exit status 75. What the move adds underneath, none of it mounted yet: a check that cannot offer a downgrade, a self-test that runs the downloaded binary's `--version-json` before it replaces anything (skipped on the existing routes, so a release from before that flag still applies), the five updater metrics, three background task definitions and four HTTP routes that a later release turns on.
