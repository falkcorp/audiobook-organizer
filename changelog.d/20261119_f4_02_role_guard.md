### Fixed

- The last-admin rule of core's auth service, and the writes that give a user a role, now guard the whole set of role definitions instead of one role. Every role write raises a role-set generation in its own batch; `keepAnAdmin` reads it before any role and stages an Expect on it, which covers all three exits of the rule and a role deleted and created again under the same name. `rbac.Service.DeleteRole` now applies the last-admin rule to the role it deletes. `CreateUser`, `SetRoles`, `AcceptInvite` and the OIDC first sign-in decide on the stored role (`rbac.Service.CanAssignCommitted`), guard the generation and raise a role-claim counter that `DeleteRole` guards before it reads the holders, so assigning a role and deleting it conflict in both commit orders and no user is left holding a role that no longer exists. `CanAssignCommitted` refuses a role the store does not hold for every actor, `core:admin` holders included (the cache check `CanAssign` keeps its admin exemption, which removals need), so an admin's assignment of a deleted role is refused, and so is the accept of an admin's invite to a role deleted since (the invite is spent, like any refused one). A failed read of a role under that check is returned as the read error, never as `ErrEscalation`, so `CreateUser` and `SetRoles` answer a server fault and not a 403 `scope_escalation`, and `AcceptInvite` does not spend the invite on a storage fault. The role store gains an optional guard (`rbac.RoleGuarder`, implemented by the native store); a store without one makes the write fail closed. A write that loses every retry is a typed 503 busy (`rbac.ErrContended`, `auth.ErrContended`), not a 500 or a 412; `rbac.Service.write` retries sixteen times with backoff instead of three. Nothing wires the role-holder source yet, so none of this is reachable today.
