### Fixed

#### M6 (dark, unregistered): the synthesised ai/openai row follows enable_ai_parsing, local rows carry no url

M6 is not registered, so nothing here runs in the app yet; these are the fixes the review of the integrations migration asked for before it is wired. The `ai/openai` row M6 synthesises for HEAD's legacy OpenAI path is now ticked with the four capabilities the sites that read the scalar key served (`books.author_review`, `books.author_discovery`, `books.author_dedup_batch`, `books.diagnostics`) and is written enabled only when `enable_ai_parsing` is on, where it was tickless and always enabled, so it was health-probed with the key and served nothing even with AI off. `Config` gains a required `EnableAIParsing` reader, since M2 moves the setting out of the blob. A `local_process` endpoint is written with no `url`: `books.whisper_local` declares none and core refuses a destination-named setting that is no URL, so the record was refused at Put and the row served misconfigured; the test now Puts the record through a real Registry with the whisper adapters registered. The exact `openai` row binds the stored key (and pairs with the operator's key) only when its `auth_ref` is `openai_api_key`, as HEAD sent the key to no other row. A refused row no longer reports that the key was bound to it, a sub-root path alias listed after an alias that contains its root is reported as never having been used by HEAD rather than as a lost rendering, and the m6 tables are now pinned against the books capability and topic catalogs.
