### Fixed

#### `core/tasks` — a parent waiting in `rc.Await` is no longer stopped by the watchdog

`rc.Await` was documented as relaying the child's liveness to the waiting run, but the executor's `await` never stamped the parent's liveness. A Task that enqueued a child and waited on it went silent, the watchdog struck it once it passed its `ProgressTimeout` and stopped it as a cancel, and a cancelled run is never resumed. Any kind whose watchdog limit was shorter than its longest child was affected. This was not a live bug and changes nothing in production today: the kernel builds no executor before F5, and the one production-path caller (the maintenance-window run in `core/internal/scheduler/window.go`) is not registered yet. The fix makes the documented contract true before the F5 kinds rely on it.

While the child is queued, waiting on its dependencies, running, stopping or quiesced by a stand-down, `await` now stamps the parent's liveness three times per `ProgressTimeout` from the waiting goroutine itself (in memory, no store write, no extra goroutine), so the stamps end with the wait. The stamp is liveness only: it is not progress for `ErrContinueInPlace` and does not mark the run as having reported. A child that needs a restart or a person's decision (interrupted, awaiting a decision) does not keep the parent alive. The wait is still bounded by the parent's own `Timeout`, and the child's own watchdog still stops a stalled child, which ends the wait.

A child that can never start while its parent runs (same `ConcurrencyKey`, overlapping write set, or a `NotWhile` naming the parent's kind) is refused at once with `ErrAwaitSelfBlocked` naming the cause, instead of holding the parent until its `Timeout` now that the relay keeps the watchdog from breaking that deadlock. `await` also returns the stop's cause (cancel or timeout) rather than a bare context error when its run read loses a race with the stop, and the `rc.Await` doc comment now states the behaviour as implemented.
