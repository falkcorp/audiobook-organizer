- Four whole-library operations that ran on a single core now use a worker pool: the LSH fingerprint index backfill and the file-clearing pass of the AcoustID reset (both sized to the CPU count), and the Deluge centralize job (4 workers, one book per worker so a book's own files are still copied one after another). The Deluge path update is one book's versions, of which at most one is active, so it stays sequential and says why. The AcoustID reset's candidate-dropping pass is not a worker pool either: each single delete held the candidate store's one lock, so a pool only queued on it; it now drops candidates 500 at a time in one locked batch, which is the actual speed-up. In production the reset clears fingerprints with the bulk clear, so only the candidate pass runs there. The two AcoustID ops now read the one book file they are about to rewrite instead of loading every file of its book, which matters once several run side by side. Deluge centralize no longer stores a resume position: a restarted run lists the files still pending, which is exactly what is left to do, so a restart cannot skip a pending file. Its checkpoint now holds only counts and the last error. A new test, TestRunItemsCallsDeclareConcurrency, fails the build when any RunItemsOptions literal omits Concurrency, a RunItems call has no options, or RunItems is used as a function value, unless a `// runitems:sequential <reason>` comment covers it.
