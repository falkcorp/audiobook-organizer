### Changed

- Under core identity the invite and admin set-email routes are wrappers over core: creating, resending, listing and deleting an invite, and changing a user's email, call core with the request's own principal, so every core rule runs for the caller. A new invite is mailed through the existing delivery code with core's absolute `/invite#token=...` link, and the invite is flagged to bind its address on accept only after the mailer reported success. The token is returned to the admin as before and is never stored by books. Books keeps only a token-free delivery record per core invite id (recipient and send time) for the Users page; it is never a gate.
- Resending an invite under core identity rotates it: the old invite is deleted and a new one is created and mailed, so the old link stops working. The new invite expires when the old one would have, an expired invite is refused (404), and the per-invite and per-admin resend limits survive the rotation. The new invite is flagged to bind its address only if the old one was flagged, so a resend by an admin never makes an address verify where the original invite would not have.
- Under core identity `POST /api/v1/auth/accept-invite` and `GET /api/v1/auth/invite/:token` answer 410 and name core's invitation routes. An identity with no account handle answers 503 on these routes and never falls back to books' own store.
