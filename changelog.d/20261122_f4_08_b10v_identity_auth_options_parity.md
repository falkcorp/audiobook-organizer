### Fixed

- Existing API keys keep working after the switch to core identity. Every key the app has ever issued (the `abk_` keys, including the ones used by the owner's own automation and the audiobook-app surface) is now accepted after the identity cutover imports it, by its stored hash and under core's expiry, revoke and disabled-owner rules; a key that was never issued, or one that is expired, revoked or owned by a disabled account, is still refused. New keys are core's `mck_` keys.
- Under core identity, the OAuth start and callback addresses (`/api/v1/auth/oauth/{provider}/start` and `/callback`) stay where identity providers already have them registered, and core answers them. A server with sign-in switched off and reachable from other machines boots as it did before and reports itself degraded instead of refusing to start, unless an operator sets `core.auth.disabled_allow_remote` to false. The revocation journal sits in the backup directory under the archive prefix existing installs already hold (`audiobooks_pebble_`), so it shares a name space with the archives already there.
