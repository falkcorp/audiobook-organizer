### Fixed

- `POST /api/v1/operations/reconcile` (the legacy `reconcile.apply` route) now needs `settings.manage`, the permission the `reconcile.apply` operation definition declares. The route was mounted on `scan.trigger`, which the seeded editor role holds, so an editor could repoint books there while the generic `POST /operations/v2` trigger refused the same operation. The change moves four cells of the route's reach: the editor session, an editor-role key with every scope, and an editor-role key with none lose the route (allowed to refused), and an admin key scoped to `settings.manage` alone gains it (refused to allowed). They are recorded as two named post-R0 decisions in the reach oracle (`reachPostR0Decisions`), with 4 golden cells and the "cells that differ" pin moved 217 to 221.
- `reconcile.apply` (`ExecuteReconcile`) now repoints the book's `book_file` row in the same apply, instead of writing the book row alone and leaving the row at the old path still flagged Missing. The row keeps its id and is rewritten to the matched file: path, Missing cleared, size from the file, hash cleared (the match type is not known, so the old hash is not carried). A row is never deleted or recreated. The single-owner path index follows, so the matched file stops being "untracked". A book with no file rows moves alone as before. Per match, nothing is written until every check passes; then the book's path change and the row's repoint are journaled, the row is written under its compare-and-swap, and the book is written only while it still points at the path the plan read. If the book write fails the row is put back, and a rollback that itself fails is named in the result. A failed match counts as skipped, never applied, and a rerun finishes a half-done one (the row already at the matched file).
- The match is refused, with nothing written, when the book's rows are not exactly one at its path and none at the matched file, when another book's row or a retired row holds the matched file, when the path lookup is incomplete (memdb warming up), or when the store cannot rewrite file rows.
- `reconcile.apply` journals the book's path change as `book_path_update` instead of `file_path_update`. The revert engine cannot reverse `file_path_update`, so beside the row's (reversible) repoint row a revert would have put the row back and left the book at the matched file. With both reversible, reverting the operation restores the book and its row together. Operations journaled before this change keep their `file_path_update` rows and stay not revertible.

### Removed

- `GET /api/v1/operations/reconcile/preview`. It ran a full-library stat, directory walk and hash sweep inline on the request goroutine, was admitted by `library.view`, and bypassed the `reconcile.scan` ConcurrencyKey, so a read-only user could start it beside a scan. Nothing called it (the Reconcile tab is gone from the UI; `POST /operations/reconcile/scan` and `scan/latest` cover the same ground).
