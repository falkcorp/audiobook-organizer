### Fixed

- The M6 cutover no longer leaves the metadata sources that held a stored `credentials` entry unserveable (F7-09, dark: M6 is not wired into a boot yet). M2 stores a source's credentials under `integrations.metadata.<id>.credentials.<key>` and M6 bound each as a dotted setting, which core's closed settings schema refuses, so the whole instance read `integration_settings_invalid` and sent nothing, including a key it held under a declared field. M6 now folds the credential HEAD actually sent into the one field the books adapter declares (google-books `api_key`; hardcover `api_token`), by HEAD's own precedence (the operator's value, then `credentials.api_token`, then `credentials.apiKey`), and drops every other `credentials.<key>`: those are quarantined by secret name (sealed, never the value), reported, and the secret stays in the store. A source renamed onto a metadata ID folds nothing, since HEAD never sent an unknown source a credential. `m6.RepairMetadataCredentials` applies the same plan to a store an earlier M6 already wrote (the importer is create-only, so re-running M6 cannot), one audited write per row and idempotent. Cells cover every rule, and a real Registry loads the migrated sources healthy.
