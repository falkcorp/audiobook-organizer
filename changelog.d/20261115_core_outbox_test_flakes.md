### Fixed

- core/outbox: two intermittent test failures of `Go Tests (short, race) shard core/4` are removed, and neither needed a production change. `TestOutbox_StatusSurvivesAnUnreadableRowAndNamesIt` planted a corrupt or newer-build message row by staging a valid one and overwriting it while the rig's relay was running; the relay could deliver the valid row in between, the cursor then passed it, and `Status` (which reads above the cursor only) rightly found nothing unreadable to name (`Stopped = []`). The test now stops the relay first (`rig.stopRelay`), so the planted row is the only thing the status read can meet. `TestOutbox_RelayRestartsAfterCancel` timed out after ten seconds when a redelivered message reached the new relay's third delivery between two polls of its `== 2` wait, which hid the duplicate behind a relay that looked as if it never restarted; the duplicate itself was the lost ack fixed by the settle-past-cancel change, and the test now waits for at least two deliveries and checks the delivered sequence, so a regression names the duplicate.
- core/outbox: `core.outbox` no longer stays Degraded for up to fifteen seconds after an operator retries or discards a dead letter that the relay had committed a moment earlier. The relay counted a new dead letter in memory after its commit, so a retry that ran between the commit and the count was undone by the late increment, and only the relay's next status refresh (every fifteen seconds) corrected it; `TestOutbox_RetryDeadLetter` timed out on exactly that. Every writer of the count (the relay's dead-lettering for ordered and unordered consumers, `RefreshStatus`, and the operator actions) now publishes it through one recount (`syncDead`) that reads the count inside the lock that publishes it, so the last report always reflects the newest store state. The in-memory increment is gone: a recount that fails is logged and left to the next refresh.
- core/outbox: the dead-letter count is a stored counter, not a scan. Recounting after every dead letter by scanning all of `dead/` was quadratic (a backlog of ten thousand read about fifty million keys, under the lock) and could outlast the five-second settle deadline. A new Serialized family `deadn/<consumer>/<topic>/<pp>` holds one counter per pair, changed in the SAME batch as every letter written (`StageDead`) or removed (`StageDeleteDead`, which now takes a context and reads the letter itself to find its pair), so a recount reads at most one row per partition. The first start after an upgrade builds the counters from the stored letters in one batch (idempotent; a crash before its commit writes nothing and the next start repeats it), and every status refresh checks the counters against the letters once and rewrites a drifted counter from them, logging both numbers at warn. `core/outbox`'s storage claim gains the `deadn/` Serialized prefix (the outbox is not wired into the boot yet, so no ledger is affected).
- core/outbox: `core.outbox` health reports are now published while the health state's lock is held, so an older result can no longer land after a newer one and stick; the result's time is never earlier than the previous one's.
