### Fixed

- Under core identity the Audiobookshelf-compatible surface accepts an API key core minted after the flip (`mck_`), by `Authorization: Bearer` and by `?token=` on GET and HEAD, as it already accepted an imported `abk_` key. Such a key used to be handed to the ABS access-token parser and refused as an invalid token. The key is still judged entirely by core (status, expiry, owner, the fingerprint-worker confinement and the route's credential check), and it is never read as an ABS access token: `GET /api/me` mints the legacy token for a key caller exactly as it does for an `abk_` key and never echoes the key. A server not running under core identity treats tokens exactly as before.
- Under core identity the API-key page's routes (`/api/v1/auth/api-keys`: create, list including `?all=true`, read, enable/disable, revoke) work again. Core holds the keys after the cutover, so creating a key used to answer 500 and the list was empty. Each route keeps its HEAD path, checks and response shape and now reads and writes core's keys as the signed-in caller (new `auth.KeyAdmin` methods on core's admin handle). A new key's scopes come from the same rule the cutover applies to every imported key (`m3.KeyScoper`, now one function shared by both), so a key created after the flip holds exactly what an imported key with the same HEAD row holds, and every request still limits a key to its owner's current roles. Recorded differences: a key no longer grows when its owner is promoted; reading or listing another owner's keys also needs dominance over that owner's roles; a key's scopes are listed as the HEAD permissions its core scopes reach.
