### Added

- core: the authenticated revocation journal and the boot re-apply that keeps revocations revoked across restores (dark; F4-08 calls both at boot). Every journal line now ends in an HMAC-SHA256 over its exact stored bytes, chained to the previous line's mac and keyed by a derive key (`journal.Keys`, so the journal never imports `secrets`); the header names the install, the app and the derive key. A line edited anywhere, a line dropped, a seq out of order, a retired derive key, a journal of another install and a file that ends below the store's committed `journal_head` all fail verification (`journal.ReadChain`, `journal.Break`); a rotation of the derive key mid-journal does not break the chain. `backup.location.json` (0600, temp file and rename) records the journal path, backup directory, install ID, store identity, the `c/backup/served_boot` pair and the committed head. The new `journal.Component` keeps that head current, reports the four `revocation_journal_*` health tokens and refuses with `ErrNotBound` before it is bound, so callers record gaps. `kernel.reapplyRevocations` is P4d step 2: it classifies the store (same, relocated, replaced, restore boot) from the content marker, the committed-head anchor and the journal's own evidence, sets aside a journal of another install and starts a new one, re-applies the verified tail in ordered batches that also stage the journal head, keeps the last admin and restricts them, appends the restore line (find-or-append by restore ID, aborted restores excluded), and fails closed once per broken chain. `kernel.runRestoreHooks` is P4d step 3: `auth.PostRestore`, the new `rbac.PostRestore` and the new `audit.RestoreHook` run with coverage from `Chain.Cover`, their lines stamped with the restore line's seq, and `restore_hooked` is written after them. `restoreswap` gains the `restore_line` and `hooks_done` edges, `auth.StageReapply` and `rbac.StageReapply` stage journaled revocations on a caller's batch, and `storage.Admin.StoreIdentity` returns the identity the location file compares.
- core: the revocation re-apply keeps every revocation (hardening in the same PR). A user with both an auth line (disabled, deleted, password) and a role line in one chunk had the second overwrite the first because both were staged in one batch; the tail now commits auth's batch and then rbac's, and `authstore` and `rbacstore` fail with `ErrDoubleWrite` on a second stage of a key in one batch. A replaced store's restore line is written before the head moves, and the head is held until the hooks finish when it cannot be written, so a crash can no longer erase the evidence the store was replaced. A journal that fails verification, is truncated below the location file's committed head, or holds a line a newer build wrote still applies the lines that did verify, then fails closed once; a journal of another install and a forked one apply nothing. A forged line appended after a break no longer mints a new fail-closed fingerprint. The journal is opened, read, moved and set aside without following a symlink and only as a regular file. Known revocations journaled after a line a newer build wrote are still applied (the head stays below that line, including when the boot itself journals the restriction of a kept last admin); a named pipe at the journal path is refused without blocking the boot; a journal file over 256 MiB is refused as corrupt; the hold on a replaced store's journal ends when its hooks complete; a replaced store with an unknown line fails closed once, not twice.

### Changed

- core: `journal.OpenFile` now verifies the chain and needs a `Keys` and an install ID. It returns a broken `File` (whose `Gap` still works) on any failure, and `journal.Append` and `journal.Gap` keep their signatures.
