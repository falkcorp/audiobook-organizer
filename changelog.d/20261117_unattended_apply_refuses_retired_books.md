### Fixed

- No unattended metadata apply writes onto a retired book any more. A retired book is one in the trash (`MarkedForDeletion`) or merged into another book (`MergedIntoBookID` set); `database.Book.IsRetired()` is the one definition of it. A replay of 4,000 review-lane pairs had shown 30 outcomes where the certainty gate said "apply" for a retired book, and the cached bulk apply, the op-result apply (`batch-apply-candidates`, `apply-when-scanned`), the nightly metadata upgrade and every other automatic apply had no check for either field.
- The two plan functions every bulk apply is decided by, `planCachedApply` and `planOpResultApply`, now refuse a retired book with the reason `book_retired` (one shared function, `refuseRetired`). The preview shows the row as skipped with that reason and counts it ("skipped as retired"); the apply op's summary counts it ("retired N"); a queued `apply-when-scanned` result skips it instead of reporting an error. A single review-row pin (the owner approving one book on its own row) is the one exception and still applies, as before; no pin, a review-page bulk pin and the hashless select-all marker do not.
- `metafetch.ApplyMetadataCandidateWithOptions` refuses an automatic apply (fill-only, or an overwrite of a candidate nobody was shown) of a retired book with `metafetch.ErrBookRetired`, at the start and again under the write lock, next to the existing `no_match` refusal. This covers the callers that never go through a plan function (metadata upgrade, auto-match-transcribed). The metadata upgrade skips a retired book before its search, so it spends no provider quota on it.
- The candidate fetch no longer spends provider quota on retired books. `fetchCandidateForBook` skips one ("skipped: retired book") before any provider call; the explicit-id and selection lists of `POST /metadata/batch-fetch-candidates` drop retired books and report the count as `retired_skipped` (separate from `skipped`, which still means "already being fetched"); the stale refetch set and the stale count leave them out (`cacheRowStale`); the scheduled unfetched selection now skips books merged into another book as well as trashed ones, and its log line reports "N retired books left out". A person's "Search again" on one book is unchanged and still searches a retired book.
- `metafetch.Service.FetchMetadataForBook` and `FetchMetadataForBookByTitle`, which search the providers and apply the best record themselves, now take a required `metafetch.FetchIntent` argument: `metafetch.Interactive` (a person's own action on one book) or `metafetch.Unattended`. There is no default and no zero-value fallback (an unstated intent is an error). An `Unattended` call refuses a retired book with `metafetch.ErrBookRetired` before any provider is searched, and again under the write lock if the book was retired while the search ran. Callers: the owner's Fetch button and its queued form are `Interactive`; organize's fetch-first, the iTunes import enrichment and the production-author resolver (`entities.resolve-production-author`, through `Server.FetchMetadataByTitle`) are `Unattended` and each counts a retired book as a skip (organize and the iTunes import in their summary lines, the resolver in its result message) rather than a failure; `maintenance.resolve-production-authors` has no AI pass and writes no publisher or author, so it is not changed. None of them stops the run or trips the iTunes rate-limit breaker. The organizer package cannot import metafetch, so the organize wiring hands it `organizer.ErrFetchSkippedRetired`.
- Unchanged on purpose: a manual single-book apply by the owner (the single-book dialog) still applies to any book, including a retired one.
- Review round 2. `metafetch.ApplyOptions.AllowRetired` (zero value refuses) is set only for a single review-row pin or the single-book dialog (`metafetch.PinAllowsRetired` is the one rule); a pinless preview carries false by construction, so a preview can no longer say "apply" for a book the apply would refuse. The automatic Audible-id backfill (`internal/plugins/metafetch/asin_backfill.go`) re-reads the book under the lock in both of its writes and counts a retired skip instead of writing.
- More callers now leave retired books out before spending anything on them: `maintenance.auto-match-transcribed` (before search, eligibility and the per-run cap; its summary ends "retired skipped N"), the lost-candidates repair (plan and replan, with its own `retired` skip kind), `bulk_metadata_fetch` (both the id-list and the whole-library forms; no provider call, counted in the log line and the "all books already cached" message), and the production-author dry run, which no longer counts retired books. `claimBook` treats a merged-away sibling like a trashed one. The identification-advance job records `retired` rather than "marked no match" for a retired skip. A version-twin metadata write whose primary is retired between the plan and the write reports `repairs.ErrChangedSincePlan`.
- `POST /metadata/batch-fetch-candidates` answers every outcome with one body (`batchFetchStartResponse`), so `retired_skipped` is on the "all selected books already have matched candidates" reply as well as the started, all-retired and all-already-fetching ones. `dropRetiredBookIDs` takes the request's context and stops its store reads when the client goes away. The candidate-fetch op itself refuses `Interactive` with more than one book id (or with `Unfetched`), not only the HTTP route. The web `BatchFetchStartResponse` gains `retired_skipped`; "Search again" on several books counts the books searched (not selected), names the retired ones left out, and an all-retired set starts nothing and says why.
- Review round 3. Three more places could write onto a book retired a moment earlier, and now check the fresh row under the lock. The production-author and production-publisher writes of `entities.resolve-production-author` re-read the book before the AI parse on the no-result path and refuse a retired row inside both write closures (`errResolveBookRetired`, counted as a retired skip; the author join is not read or written). The library-copy sync that follows every metadata apply (`syncMetadataToLibraryCopy`) refuses a trashed or merged copy under the lock and returns an error wrapping `errFileTargetChanged`, and `libraryCopyGone` treats any retired copy as gone; write-back stops on that error instead of writing the file. The iTunes import enrichment replaces the author credit through `replaceSingleAuthorCredit`, which re-checks the book under its lock and skips a book retired after the fetch committed.
- Review round 3, smaller items. The Audible-id backfill's start-of-run check and the version-twin fixer's live check (`vtLive`, `vtStillNeeds`) now call `IsRetired` instead of spelling the merged half themselves (a merged-into id of only whitespace now counts as merged, as `IsRetired` has always said). The lost-candidates repair reports a book retired between its replan and its refetch as `repairs.ErrChangedSincePlan` (the fetch result carries a typed `Retired` flag), not as a failure. "Search again" names both causes when books were left out as retired and as already being searched.
- Review round 4. Two places still wrote a join after the lock that checked the book had been released, and both now do it in a second locked pass that rechecks the row: `entities.resolve-production-author` rewrites the `book_authors` join through `ModifyBookAuthors` nested in a second `ModifyBook` (a book retired after its `AuthorID` write is refused with `errResolveBookRetired`, so no write lands after it retired; the column and the join then disagree on that retired row, and round 5 counts that book as resolved, below), and `syncMetadataToLibraryCopy` writes the copy's author and narrator joins in a second `ModifyBook` that refuses a retired copy with `errFileTargetChanged`. `authorAssignStore` and `serverAuthorLinkStore` gain `ModifyBookAuthors`.
- Review round 4, library-copy lookup. `librarySiblingMatchingIn` now skips a retired sibling, so a live organized copy behind a merged primary is found (a merged row keeps its primary flag and sorted first). When a protected book's only library copy is retired, `resolveLibraryCopy` no longer creates a second one: the file work is skipped with an error wrapping `errLibraryCopyRetired` ("its only library copy, book X, was merged away, so no audio files were written and no new copy was made"), and the metadata is still applied. (Superseded in round 5: organize refuses in that case too, see below.)
- Review round 4, write-back. `writeBackForBook` refused a retired book that is its own file-work target with `ErrBookRetired` and wrote no tag, as it already did for a retired library copy (round 5 moves this check, see below). The check reads the row outside any store lock (tag writing is file I/O), so a book retired after it still has that one call's tags written. The iTunes import now counts a book retired after its fetch as enriched with its author join left alone (its own count in the summary line), not as a skipped book.
- Review round 5, organize. Organizing a protected book (one whose files are in the iTunes folder) whose only library copy was merged away no longer creates a second copy beside the merged one. `metafetch.ExistingLibraryCopyOfFile` now reports the retired copy separately from "no copy", and organize refuses with a new 409 category `library_copy_retired` that names the merged row (`copy_book_id`, `copy_path`) and says to revive or un-merge it first. The single-book organize, its preview, the organize op queued behind a scan and the batch `library.organize` op (which counts the book as skipped under the same collision category and records an `organize_skipped` change) all take this path, and the handler core re-asks the resolver under the lock. A live copy behind the merged one is still used, tagged or not. A book whose only copy is in the trash (not merged) is not covered and still gets a fresh copy (filed in `todo.d`).
- Review round 5, file work. The retired-self refusal now lives in `fileWorkTarget`, so for an unattended job the rename, the cover embed and the tag write all stop together on a retired book, instead of only the tag write. The refusal is keyed on an intent carried with the file-work job (`metafetch.FetchIntent`, reused): `FinishApplyFileWork`, `FinishApplyFileWorkTimed`, `FinishAutoFetchFileWork`, `ApplyMetadataFileIO`, `WriteBackMetadataForBook`/`WriteBackMetadataForBookContext`, `RunApplyPipelineRenameOnly` and the file-IO pool's `Submit`/`SubmitTyped` all take it, and the pool persists it with the job record so a restart replays the same intent; a record with no intent (written before this change) or an unrecognised one replays as `Unattended`. A person's own actions stay attended and still write all three: the single-book apply dialog (including the one queued behind a scan), `fetchCore`'s queued job and the single-book write-back. Everything else is unattended: bulk write-back, batch save, the batch apply, apply-when-scanned and batch-apply-candidates, the iTunes enrichment and a legacy replay. Bulk write-back now re-reads each book after waiting for its file gate and skips a retired one before its rename, counting it skipped rather than failed (also when the refusal comes from the rename or the tag write after a retirement in the window). Where the refusal is reported: the single-book dialog logs one warning line and the UI shows the apply as a success; bulk write-back counts it skipped with an info log line; the batch apply counts it through its write-back failure counter.
- Review round 5, smaller items. `entities.resolve-production-author` now counts a book retired between its two locked passes as resolved (its author column was written while it was live), and reports the skipped join on its own line in the result message, instead of as a retired book skipped. The `errLibraryCopyRetired` text says "merged away" (the lookup cannot see trashed rows). The `syncMetadataToLibraryCopy` comment now names what its second locked pass does not cover: the store's own narrator junction sync runs after the column pass and checks the Narrator column, not the retired flag.
