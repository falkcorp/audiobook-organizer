### Fixed

- The cleanup-series maintenance job no longer deletes a series row unconditionally. Both phases (the single-book collapse and the duplicate merge) now delete through the store's check-and-delete (`DeleteSeriesIfUnreferenced`), which counts the book rows that name the series and deletes it while holding every book write lock. A book another writer linked into the series after the job read its membership (and its reference counts) used to be left naming a deleted series; the series is now kept, counted and reported. The job's warn line and its "Done" log report these as their own counts, apart from the start-of-run reference guard: series kept because a book references them now, series kept because they were renamed, re-authored or held after the job read them, series already deleted by someone else, and series whose delete failed because the store could not count their references. A store that cannot answer fails the delete closed (the series stays, the failure is counted, no fallback to a plain delete). A live run on a store without the check-and-delete refuses before it reads or writes anything; a dry run does not need it. The start-of-run reference guard in the duplicate merge is kept: it still refuses early, with a count of the rows the run could not reach.
- cleanup-series keeps every series it made a delete decision about out of the duplicate merge. A single-book series the delete kept (a book linked in, a rename, a failed delete) used to be grouped again by the merge, refused a second time by the start-of-run reference guard, and counted twice, the second time under the wrong cause ("rows this run could not reach"). It is now counted once, under its real cause.
- A store that has the check-and-delete but cannot count references right now (its memdb is not serving, or is known to be missing rows) used to get its books unlinked before every delete was refused. A live run now asks the store once, before it reads or writes anything (`SeriesDeleteReadiness`), and refuses; and each phase stops at the first delete that shows the store cannot count references to any series (its memdb is missing rows or is not serving), so nothing more is unlinked or re-homed. The warn line says where it stopped.
- The "Done" log line and the warn line account for every candidate: single-book series whose unlink failed, merged-from series left unprocessed by an error that stopped their group, and, after a stop, the single-book candidates and the duplicate groups the run never got to (`singleNotReached`, `dupGroupsNotReached`) each have their own count. After a stop the run finishes reading the selection, without writing, to count what it left.
- The plain `DeleteSeries` is gone from the job store contract (`maintenance.JobStore` and `jobs.Store`), so a job cannot delete a series unconditionally.
- A run that stops because the store cannot verify a delete now returns an error wrapping `jobs.ErrCleanupSeriesStopped` (with the phase and the store's own error), so the op shows as failed in the ops list instead of succeeding with only a warn line. The counts and the warn line are still logged first.
- A delete that fails for a reason about one series row (a row that will not decode, a failed write) no longer stops the run or fails the op: the series is counted as failed, the error is logged with its real cause, and the run goes on to the next series. Only a store-wide cause stops it (`ErrMemdbIncomplete`, or the new exported `ErrSeriesDeleteMemdbNotServing`, which the store's `DeleteSeriesIfUnreferenced` documents as the two errors that are about the whole store).
- When phase 1 unlinks some of a series' books and then fails on another (a transient write error), phase 2's reference guard now subtracts the books phase 1 verified off the series. It used to count them as stranded, refuse the series under the wrong cause (trashed or unhydratable rows) and leave it for the next run.
