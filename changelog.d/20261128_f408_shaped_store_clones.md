### Fixed

- Test tooling: the production-shaped test store's generator no longer pads the longest text field of each cloned row. That field was often a typed value, so cloned API keys got a token hash that is not a SHA-256 and a cloned sign-in link got a timestamp that does not parse, and the upgrade's identity step refused the store before any upgrade check ran on it. Each family now names the one free-text field that may grow (an error message, a log message, a summary), identity rows are cloned unchanged, and every cloned API key gets its own valid token hash. Cloned rows are now named with a lowercase "z" and hex digits instead of "~", which the upgrade checks split IDs on, so cloned API keys no longer looked lost after the upgrade; the generator refuses a store that already holds a key in that name space. Rows that belong to an upgrade step's narrower range (sign-in name and email indexes, API key and session indexes, the four stored secrets, the settings blob, the bootstrap rows) are no longer used as templates: their clones landed outside that range, where the step never looks, still pointing at the old system account. A new test grows a store a tenth of production size and runs it through the same upgrade checks as the full-size job in about a minute; the full-size job runs it first, so a broken generator fails there instead of half an hour in.
