### Fixed

- The identity upgrade no longer leaves the server unable to start because of the built-in system account. The old release stores that account under a generated ID, while everything it attributes to the account (the organizer's checkpoints, the maintenance jobs' preferences) uses the name `_system`, and the new core also looks the account up by that name. Importing it under its generated ID made the new core's startup fail on a duplicate user name and refuse to serve. The upgrade now imports it as `_system`, still with the system status that cannot sign in by password, key, session, Cloudflare Access or Audiobookshelf, and every key, linked login and merged-user pointer that named its old ID follows it. A database with two accounts that both claim to be the system account, or an ordinary account named `_system`, stops the upgrade and names the rows, as the other upgrade blockers do.
