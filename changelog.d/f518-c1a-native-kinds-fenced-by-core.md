### Fixed

#### Native kinds are fenced by core, not by HEAD's fence

With the tasks flip on, a native kind run by core's executor was checked against HEAD's `opswriter.FenceFromContext(ctx)`. Core never puts a HEAD fence on the run's context, and with none there that check answers "always writable", so a write after a cancel, timeout or lease loss would not have been refused by it. The native repairs kind now refuses with `tasks.ErrFenced` only (its fence reads the run context, which core ends with a cause on cancel, timeout, shutdown, quiesce and abandon; the `opswriter.ErrFenced` case of its error mapping is gone), and the native window-index-build kind gets the same fence on its env (`nativeFence`), where it had none. HEAD's own paths keep HEAD's fence; the repairs writer still wraps `opswriter.Writer` because its journal and evidence engine has no equivalent in core or the books writer (listed as a frozen dual use). A new architecture test (`TestNativeKindsAreFencedByCore`) fails if a native file references `opswriter.FenceFromContext`, `opswriter.New`, `opswriter.ErrFenced` or `opswriter.WithFence`, and cells run the real executor and stop a run by cancel, timeout and (repairs) hold lapse and assert the next write is refused and leaves the row as planned. A lapse does not end the run context at the base, so a write inside a row's own apply after a lapse waits for the next `Do`; that cell is skipped until the lapse-cancel change lands. The flip is still off in production.
