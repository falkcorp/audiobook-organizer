### Fixed

- A restore run with no restore intent of its own (a replaced or external store) now keys its idempotent work on a run ID the live host holds. The ID is a crypto/rand value kept in `restore_hook_run.json` in the state directory, bound to the replaced store's state and removed when the run finishes. It used to live in the restorable store keyspace (`c/backup/restore_run`), where an archive taken mid-run could carry it back. A run that crashes after the kept-admin restriction lines and resumes now appends no second set of lines and does not bump the credential epoch twice, and a second external run gets a new key. A stale `restore_run` row from an older build or an archive is ignored and deleted.
- audit's restore hook keys its records on the same live-host key as auth (the restore intent's ID with the line's seq, or the host run ID) instead of the restore line's seq. A restore whose line reused an earlier restore's seq used to find that restore's records in its archive and write none of its own. The hook now refuses to run without a key. The target ID of the `core.restore.*` records changes from the seq to `restore:<intent ID>:seq:<N>` or `run:<hex>`.
