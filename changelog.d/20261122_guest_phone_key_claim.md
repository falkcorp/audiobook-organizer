### Added

- Under core identity a guest's one-time phone-app key is claimed with `POST /api/v1/auth/phone-key/claim`, called by the accept page with the session core's accept just gave it (core's accept response cannot carry a books secret). The claim is bound to the accepted invitation and to the session's own user: it is single use, expires 15 minutes after the accept, mints through the same code as before (Cloudflare token, access policy, hashed record, audit entries, optional e-mail copy) and answers every refusal (nothing offered, a second claim, another user's claim, an expired one) with the same no-store 404. It is limited by the same `/api` rate limiter as the other credential routes, and an API key or ABS token is refused before it runs. The entitlement is written only by `OfferGuestKeyClaim`, which the invitation-accepted hook calls for an invitation that was e-mailed to the address by an administrator; nothing mints a key until that hook is wired, so production refuses every claim for now. A restart inside the 15 minutes means asking the administrator to reissue the key.

### Changed

- The phone-app key code (the admin Reissue route, the Phone app keys panel and the mint's deactivation re-check) reads accounts through one seam: books' own store as before, and under core identity the caller's own record through its principal and every other account through an actor-checked reader that core re-checks for `core:users.manage`. A server without that reader refuses these routes rather than reading books' empty user store.
