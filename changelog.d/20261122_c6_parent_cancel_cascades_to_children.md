### Fixed

- Cancelling a run now cancels the runs it enqueued, as HEAD's cancel stopped the work a job had started (F5-18 C6). Before this a cancelled batch parent stopped after its current child, and that child kept writing until its own timeout. The executor now ends the unfinished descendants of the cancelled run that the cancel reaches: the child's context is cancelled with a cause that names its parent, its writer refuses from the next write, and its row ends canceled. Children are found level by level, each level read after the one above it has been stopped (so a grandchild a child enqueued just before its own stop is not missed) and stopped by a bounded pool of eight workers. A child queued while the cancel was being applied is cancelled at dispatch instead of started, and after a restart in the middle of a cancel no child is resumed: each is ended canceled at boot. Only a cancel cascades (not the watchdog, a timeout or a shutdown).
- What a cancel reaches is limited by its caller, per kind of run. A cancel reaches a descendant only if the descendant carries the cancelled run's own actor and the caller may cancel runs of its kind by the rule a direct cancel applies (the run's own actor, `core:tasks.manage`, or the kind's cancel permission). This is narrower than "everything the caller could cancel directly" in two ways: a descendant that carries a different actor is never reached, and a kind whose module is disabled is reached only by a caller who holds one of the two kind-independent grants (the run's own actor, `core:tasks.manage`), because a disabled module has no definition to read the permission from. A run the cancel does not reach keeps running, as before the cascade existed; the runs beneath it are not walked; the cancel counts them in the parent's run log (no id or kind there, which the log's readers may not be allowed to see) and names them in the `core.task.cancel` audit record (`skipped`) and the server log. A child of a disabled module is left for its module and is not reported as skipped.
- The verdict is stored with the cancel, per kind of child, on the cancelled run and on every run the cascade ends (a new `CancelReach` field on the run record; a run row written before it decodes with none, and with none nothing is cascaded), so a child queued after the cancel, or one still unfinished at a restart, is judged by the original caller's authority. A repeat or racing cancel is limited to what both the stored verdict and its own caller cover: it cannot lend the first caller's authority to the second, nor reach further than the first stored. A kernel-internal cancel stores "all kinds". The HTTP route writes the `core.task.cancel` audit record whenever the cancel acted or skipped a run, even if it then returns an error (a repeat that finished a cascade still answers "not found"), and treats the same user over an API key as a different actor from the session that started the run, as the executor does.
