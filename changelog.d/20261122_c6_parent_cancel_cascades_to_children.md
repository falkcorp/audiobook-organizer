### Fixed

- Cancelling a run now cancels the runs it enqueued, as HEAD's cancel stopped the work a job had started (F5-18 C6). Before this a cancelled batch parent stopped after its current child, and that child kept writing until its own timeout. The executor now ends every unfinished child of the cancelled run (and theirs): the child's context is cancelled with a cause that names its parent, its writer refuses from the next write, and its row ends canceled. A child queued while the cancel was being applied is cancelled at dispatch instead of started, and after a restart in the middle of a cancel no child is resumed: each is ended canceled at boot. Only a cancel cascades (not the watchdog, a timeout or a shutdown), and only down to the run's own children that the person cancelling could cancel directly: a child whose kind needs a permission they lack is left running, and the cancel names it in the parent's run log and in the `core.task.cancel` audit record (`skipped`). The cancel stores that verdict, per kind of child, on the cancelled run and on every run the cascade ends (a new `CancelReach` field on the run record; a run row written before it decodes with none, and with none nothing is cascaded without a live caller), so a child queued after the cancel, or one still unfinished at a restart, is judged by the original caller's authority: it is ended only if its kind is in the set and it carries the same actor, and otherwise it is left alone, as before any cascade existed. A kernel-internal cancel stores "all kinds".
