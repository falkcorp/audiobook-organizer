### Added

- The admin user merge runs on core once accounts are core's (identity flip, F4-08 B10l). The preview shows core's masked summary (roles that transfer, e-mail outcome, API-key ids, sign-in provider names, allow-list row count) beside the books rows, and its digest covers both, so a preview that drifted is refused. Apply stages the books rows, the merge journal and core's half into one storage batch under the same locks the merge always took, checks every books row against the preview before it writes, commits once, and only then lets core publish its invalidations. A merge whose estimated batch is over 64 MiB (a provisional cap, one named constant) answers 409 `merge_too_large` and writes nothing. The merge runs as the admin who started it: the request's own session principal rides in the single-use grant (never in the operation's stored parameters, never logged), is re-checked through core when the operation starts, and is refused if the session was revoked or the admin lost the right in between. Core refusals keep their own codes (`already_merged`, `no_sign_in`, `email_linkable`, `last_admin`, `email_in_use`, `inactive_user`). Resume and undo stay `merge_permanent` under identity; the sign-in footprint route stays unavailable.

### Fixed

- Core's `merged_away` answer (409 on enabling an account an admin merge folded into another) no longer tells the admin to undo the merge; it says the account was merged into another and stays disabled, and `ErrMergedAway`'s comment says the same. Enabling a merged-away account is refused either way.
