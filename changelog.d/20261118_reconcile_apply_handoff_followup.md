### Fixed

- `reconcile.apply`: a rerun that finishes a stranded match (the row already at the matched file, the book at the old path) now hands the earlier operation's rows over. Its live rows for the match (the book's path change, the row's repoint, and any hash clear) are marked reverted with no write, the way the Missing files fixer's hand-off does. Before, the rerun journaled a copy of the earlier operation's repoint, so reverting the rerun alone worked, but the earlier operation's own rows stayed live: revert the rerun, apply the match again, then revert the first operation, and that last revert undid the second apply. The hand-off runs after the book write landed and is best effort: a store that cannot mark rows, or a failed mark, is logged and leaves the match applied. It copies and marks only rows the apply itself wrote (no `Source`), so another writer's rows are never copied or marked.
- `reconcile.apply` documents what it cannot cover: a crash between the journal rows and the writes leaves live rows for writes that never landed, and `reconcile.apply` is `ResumeDrop`, so nothing voids them. Reverting such an operation after a later apply of the same match undoes that apply. The `ExecuteReconcile` doc said a revert "cannot act on a write that never landed"; that holds for failures the process survives, and the doc now says so and names the residual. The hand-off closes it only for a stranded match. Filed as RECONCILE-APPLY-CRASH-RESIDUAL.
- `reconcile.apply` reads the book back before it rolls the row back. When the book write reported a failure but the book is at the matched path, the write landed: the row is kept, the match counts as applied (with a logged warning), and the rows stay live. Rolling the row back first left the book at the matched file and the row at the old path, a state a rerun cannot finish. When the book cannot be read back at all, nothing is undone and nothing is voided: the row stays at the matched file (a stranded match a rerun or a revert finishes), and the message says to check the book.
- `reconcile.apply` refuses a book trashed between the plan and the write inside the book's write callback, under its lock, with its own error. The row is put back and the rows voided. A book already at the matched path is skipped before the trash check, so a trashed book that already holds the file is not rolled back. The "another writer changed the book's path" advice is no longer printed for it.
- `reconcile.apply` accepts a row already at the matched file beside the book's other rows only when a live journal row of an earlier apply says it repointed that row from the book's path to the matched file. Before, a multi-file book with one chapter row at the matched path had its path set to that one file, with nothing said about its other rows. A book whose only row is at the matched file is accepted as before.
- `reconcile.apply` checks again who holds the matched file inside the row's compare-and-swap, and refuses while any row (live or retired) holds it. A library scan that imports the still-untracked file as a new book's row between the plan and the write used to have its single-owner path key taken by the repoint, so two books held one file. The store has no atomic "repoint unless held", so a row created within the callback itself is still not seen. The repoint row also records the row that held the path key (`KeyOwnerBook`/`KeyOwnerRow`), as the Missing files fixer's writer does.
- `reconcile.apply` carries the scan's match type (`match_type` on each item of `POST /operations/reconcile`, optional) and keeps hashes only for a hash match. Any other type, or none, clears the book's `FileHash` and `OrganizedFileHash` along with the row's, journaled as restorable `metadata_update` rows (a revert puts them back), refused if another writer changed them since the plan. A hash match keeps the book's hashes and the row's hash. `OriginalFileHash` is never cleared. The type is the confirming caller's claim about the scan's match, not re-derived by hashing the file.
