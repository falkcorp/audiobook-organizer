### Added

- core: config binds a `secrets.Ref` inside a list entry (F3-OIDC-SECRET, dark). A list key whose entries have a string `id` may give each entry `secrets.Ref` fields; each is a secret key of its own, `<list parent>.<id>.<field>`, with its own protection and reload class, listed by `Lookup`/`Keys` and writable through `Apply` only while an entry names it. The OIDC provider list declares its `client_secret` this way, so each provider gets `core.auth.oidc.<id>.client_secret` (live, `ProtectAdmin`) beside the owner-protected `core.auth.oidc.providers` list (05-authn §8, 05-config §1.12.3). An entry with no id, an id that is not a path segment, an id equal to a sibling key's name (`providers`, `redirect_base_url`), a repeated id, or a reference naming another secret is refused at validation. Removing or renaming an entry deletes its secret in the same commit, so no later entry inherits it; such a removal is refused when an operator layer sets that secret. A list holding entry secrets is redacted like a sensitive key: its validation errors, the quarantine report, the logs and its section's Validator messages never quote a value, and the redacted operator file drops the list. Nothing reads the client secret before F3-07 wires OIDC sign-in.
