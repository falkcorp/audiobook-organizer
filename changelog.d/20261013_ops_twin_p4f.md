### Changed

- `scheduler.cleanup-old-backups` is merged into `maintenance.cleanup-old-backups`. The two copies ran the same sweep (remove `.bak-*` backups older than the retention window, never descending into the backup and OpenLibrary dump directories) and already shared one retention setting, so the sweep itself is unchanged. The surviving op now requires `settings.manage` and keeps the 1 hour budget (up from 30 minutes), so it neither widens who can trigger a deleting op nor shortens the budget production runs were sized against. The old ID keeps working as an alias, so stored rows and API callers still resolve. The nightly `cleanup_old_backups` task now enqueues the surviving op, and the two IDs no longer have separate concurrency keys, so a manual run and the nightly run cannot overlap. The surviving op is now re-queued after a restart instead of dropped, because the sweep is safe to run again: files an interrupted run already removed are simply absent the second time. The sweep also no longer treats every file with `.bak-` in its name as a backup: it deletes only the names the app writes (`<file>.bak-<unix>`, with an optional `-N`, and the older `<file>.bak-YYYYMMDD-HHMMSS`), aged by the time in the name. Before, a file such as `x.bak-notes.m4b` or any other name with `.bak-` in it and no recognised stamp was aged by its modification time and deleted once that was old enough, whether or not it was a backup. Such files are now left alone at any age.
