### Fixed

- The book_atpath and opchange_by_book index key builders now check their operands (path, book id, journal key suffix) against fixed upper bounds before sizing the key buffer, and return an error for an over-limit operand instead of computing an unchecked allocation size. This clears the CodeQL go/allocation-size-overflow alerts; keys for valid inputs are byte-for-byte unchanged.
- CreateBook and UpdateBook refuse an over-limit path or id. The book_atpath backfill and verify and the opchange_by_book backfill and verify skip such an existing row instead of aborting the pass: they count it (`skipped_overlong_rows`, `overlong_rows`, `skipped_overlong`) and log one warning with lengths only.
- A skipped overlong book row also gets the existing id-keyed undecodable marker, so path lookups fail closed for it and never report its path as free; the verify counts it without asking for a rebuild.
- Existing overlong rows stay usable: DeleteBook, metadata-only UpdateBook and the old-path side of an update tolerate an overlong path or id (a shortening update writes the key and clears the marker); only a new overlong value is refused. The opchange journal refuses a new row with an over-limit book id or key suffix, treats an over-limit book id as not indexable so reads scan, keeps the index untrusted while a legacy overlong-suffix row exists so GetBookChanges scans and returns every row, and prune and rewrite delete or rewrite such rows without an index entry. The at-path verify reports a stale key left for an overlong row as an extra.
- The opchange index trust gate no longer depends on a verify run having walked an overlong-suffix row: such rows get a durable opchange_overlong marker (written by the backfill, the verify and any rewrite, removed with the row), and the resumable verify counts live markers, so a cursor-based tail verify on a later boot keeps the index untrusted until the last one is gone. A kept legacy overlong at-path book also has its marker re-written on update if missing.
