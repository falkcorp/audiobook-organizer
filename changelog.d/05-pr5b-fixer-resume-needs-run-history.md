- A v3 Fixer that resumes after a crash or a deploy now reports a row as "already applied" only when the run's own earlier attempt left history for every book and book file the row names: a metadata history batch of that run, or an operation journal row under its op id. Before, a row that someone else had changed to the same values between the two attempts was also reported as applied and handed to the fixer's after-apply step. Such a row is now skipped as changed since plan. A row written by the interrupted attempt is still reported applied and is not written again. The new `Writer.Wrote` read backs this check. It reads a book's whole metadata history, because the existing per-book read cuts off at its limit by field name rather than by age. Nothing in production registers a v3 Fixer yet (05-PR7).
