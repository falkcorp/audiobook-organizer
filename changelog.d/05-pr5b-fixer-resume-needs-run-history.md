### Fixed

- A v3 Fixer that resumes after a crash or a deploy now reports a row as "already applied" only when that row's own apply marker is there: a record the run writes as soon as the row's apply step succeeds, naming the history entries that step recorded. Before, a row that someone else had changed to the same values between the two attempts was also reported as applied and handed to the fixer's after-apply step. Such a row is now skipped as changed since plan, also when the run itself changed another field of the same book. The marker counts only while everything it names is still the latest change: a book field the run set and someone later edited (even back to the run's value), undid, or reverted with the run's operation no longer counts, however the clocks of the two writes compare; nor does a book-file or credits entry that was voided, reverted, or followed by a later entry on the same file or credits. If any of the book's history entries cannot be read, the row is not counted either. A row written by the interrupted attempt is still reported applied and is not written again; if the process stops between a row's write and its marker, or part of the row's history could not be recorded, the resume skips that row rather than writing it twice. The markers live under the run (`opv3:rowmark:`) and are deleted when the run finishes or is discarded. Nothing in production registers a v3 Fixer yet (05-PR7).
