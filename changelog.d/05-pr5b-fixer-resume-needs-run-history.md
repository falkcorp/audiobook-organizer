### Fixed

- A v3 Fixer that resumes after a crash or a deploy now reports a row as "already applied" only when that row's own apply marker is there: a record the run writes as soon as the row's apply step succeeds, naming the history entries that step recorded. Before, a row that someone else had changed to the same values between the two attempts was also reported as applied and handed to the fixer's after-apply step. Such a row is now skipped as changed since plan, also when the run itself changed another field of the same book. The marker counts only while everything it names is still the latest change. A change the run made stops counting when a later change to the same thing is recorded in either the book's change history or the operations journal, whoever made it and even if it set the run's value back. That includes changes those writers record under other names: a series override, an author merge or credit rewrite, a repoint recorded under the bare file id, and a manual track edit. A name the check does not recognize counts as a change to everything on that book. "Later" is judged by the two entries' timestamps. Three things are seen whatever the timestamps say: an "undo last apply" of the run's change, a revert of the run's whole operation, and a voided or reverted journal entry. Undoing one field by hand is an ordinary later change, judged by its timestamp like any other. If any of the book's history or journal entries cannot be read, the row is not counted either. A row written by the interrupted attempt is still reported applied and is not written again; if the process stops between a row's write and its marker, or part of the row's history could not be recorded, the resume skips that row rather than writing it twice. The markers live under the run (`opv3:rowmark:`) and are deleted when the run finishes or is discarded. Nothing in production registers a v3 Fixer yet (05-PR7).
