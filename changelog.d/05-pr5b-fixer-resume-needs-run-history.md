- A v3 Fixer that resumes after a crash or a deploy now reports a row as "already applied" only when that row's own apply marker is there: a record the run writes as soon as the row's apply step succeeds, naming the history entries that step recorded. Before, a row that someone else had changed to the same values between the two attempts was also reported as applied and handed to the fixer's after-apply step, and an earlier draft of this fix still did so when the run had changed another field of the same book. Such a row is now skipped as changed since plan. A marker whose history was taken back since (an undo of the change, a reverted or voided journal entry) no longer counts either. A row written by the interrupted attempt is still reported applied and is not written again; if the process stops between a row's write and its marker, the resume skips that row rather than writing it twice. The markers live under the run (`opv3:rowmark:`) and are deleted when the run is discarded. Nothing in production registers a v3 Fixer yet (05-PR7).
