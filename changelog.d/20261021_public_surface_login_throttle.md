### Security

#### Login failure throttle now counts each visitor behind the tunnel separately

The web login and the Audiobookshelf-compatible `/login` and `/auth/refresh` throttled failed attempts per peer address. Behind the Cloudflare tunnel the peer is always the connector, so one visitor failing 15 times locked every other visitor out, and a visitor could not be told apart from another. The throttle now keys on the visitor address (`CF-Connecting-IP`, believed only from a configured tunnel connector or a verified Access assertion; a public IPv6 visitor counts per /64). A request from any other peer is still keyed on its own address, so a spoofed header cannot pick a bucket. Session and audit records are unchanged.

The per-visitor budget does nothing against a caller with many addresses, so password login now has aggregate ceilings in front of it, checked before any password work: 150 failures per 15 minutes through any one configured tunnel connector, and 500 across the whole service, shared by the web `POST /api/v1/auth/login` and the Audiobookshelf-compatible `POST /login`. Only failed (401) attempts and attempts still in flight count; a successful login or a per-visitor refusal hands its slot back. A flood that spends a ceiling refuses password logins with 429 until the window ends, which can include the owner's; sessions already issued are unaffected and a restart clears it. `POST /auth/refresh` stays outside the ceilings because it does no password work. The per-visitor and per-account failure tables are also capped at 10,000 keys each with the oldest window evicted first, and expired entries are swept once a minute instead of on every failure.
