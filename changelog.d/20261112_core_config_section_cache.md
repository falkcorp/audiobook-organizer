### Changed

- core/config: a section's schema, key table and validators are now built once per distinct section spec per process, not once per store. `Store.Register` takes its own instance of a frozen template (fresh `section` and `keyInfo` values and private copies of every byte slice and map; only the reflected schema trees and the resolved validators, which nothing writes after the build, are shared). The template is keyed by the section's type, path, marshaled defaults, permissions and its Docs, ProtectionWaivers, EnvBinding and FailClosed options. Builds are single-flight, failed builds are not cached, and the cache holds at most 1024 templates (a spec with a computed default, like `core.paths` in a test that boots in a fresh directory, is built uncached past that). This removes the cost F2-16 added to every kernel boot: the hello example's level-step crash-matrix cell under `-race` went from about 36s of CPU back to about 6s. `sectionSpec.schemaFor` is gone: the schema is `jsonschemax.ForType` of the spec's type, so the build is a function of the spec's data alone.
- core/config: `Store.register` no longer re-derives every registered section's claimed paths for each new section. A section's claims are computed once in its template and shared (they are immutable), and `checkOverlap` consults an index of the claims and paths registered so far (exact and ancestor sets) instead of scanning every section and key, so the check is proportional to the new section's own keys. The refusal and its error text are unchanged: the index only picks candidates and the original pairwise comparison decides. This takes the hello level-step cell from about 13s to about 11.6s of CPU under `-race`.
