### Added

- maintenance: the 34 maintenance jobs now have native Task kinds `books.maintenance.<job id>`, dark (nothing registers them until the tasks flip, F5-18; the existing maintenance operations run exactly as before). One shell in `internal/maintenance/jobs/kinds.go` serves all of them: it hands each job its own `Run(ctx, store, reporter, dryRun)` a store the owner declares per run (`KindDeps.NewStore`, whose writes go through the run's writer), maps the run's mode to `dryRun` (only an explicit live mode writes), refuses a `dry_run` key in params, captures the job's result, carries the run ID and params, turns a job's restart-in-place request into the core sentinel, and reports progress and log lines through the run. Each kind keeps its job's title, description, resume policy, timeout and concurrency key, requires the same permission HEAD's operation does (`settings.manage`), declares the books resources the job writes (five report-only jobs are read-only and refuse a preview, as HEAD gives them none), and waits for the library index like HEAD's operation does. The two jobs that checkpoint (`backfill-file-hashes`, `recompute-book-aggregates`) save and restore through the run, with HEAD's own checkpoint struct so a run imported from HEAD resumes from the bytes HEAD wrote; under HEAD's wrapper they keep the existing checkpoint calls.

### Changed

- maintenance: `scan-composer-tags` records a rewritten file's new hash through the store its run was handed, not through the store `internal/metadata` installs at startup, and a live run whose store cannot record file hashes is refused before any file is touched. `internal/metadata` gains `WriteSingleTagContextVia`, the same single-tag write recording through a store the caller names; `WriteSingleTagContext` is unchanged and still records through the installed store. In production the two stores are the same object, so nothing observable changes.
