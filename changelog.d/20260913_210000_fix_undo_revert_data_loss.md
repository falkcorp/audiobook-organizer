### Fixed

- Undoing an organize no longer erases the tags it wrote. The organizer now reads each file's tags before writing and records the real pre-write value per book_file; a tag the file did not carry is recorded as absent, and the revert removes it again. The revert writes the value back by book_file id, only while the file still holds what the organize wrote (a later write-back is kept and the row reported as changed since), and under the same per-path write lock write-back uses. Rows with no known pre-write value, including every older `tag_write` row, are reported as not restorable. Multi-file books get their tags written per file instead of to the folder path, including books copied out of a protected source.
- "Undo last apply" now puts the book row back instead of storing the old value as a user override. Each field is restored inside `ModifyBook` only while it still holds what the apply wrote; fields edited since, locked fields and already-restored fields are reported. The apply is found by a batch id recorded on every history row, not a ±2s window. Only the newest apply is ever undone: a second click is refused with 409 instead of undoing the apply before it. The author is restored only together with its book_authors credits, never on its own, and the bulk-fetch path now records those credits. History recorded before batch ids existed is refused with 409.
- The single-field metadata undo works the same way: it puts the book row back with a compare-and-set, creates no override, and refuses with 409 when the field has changed since.
- Metadata apply history is recorded after the write commits, from the committed row, so values the apply refused are no longer recorded, and every field the apply can change (description, genre, ASIN, ISBNs, subtitle, years, secondary series, page count, abridged, and the rest) is recorded so undo can restore it. The auto-fetch paths write only the fields they changed through `ModifyBook`, so an edit made during the provider search is no longer overwritten.
- Operation revert writes every book change through `ModifyBook` with a compare-and-set instead of a whole-row `UpdateBook` of an earlier read. Reverting a file move takes the per-path write lock, repoints every book_file row (and its iTunes path), refuses when the book was repointed since, and moves the file back if the book write fails. `file_copy` rows are listed as not restorable, because deleting the library copy is not a safe reversal.
