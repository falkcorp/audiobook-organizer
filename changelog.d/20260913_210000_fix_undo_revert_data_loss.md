### Fixed

- Undoing an organize no longer erases the tags it wrote. The organizer now reads each file's tags before writing and records the real pre-write value per book_file; the revert writes that value back to the file by its book_file id and never writes an empty or unknown value (such rows, including every older `tag_write` row, are reported as not restorable). Multi-file books get their tags written per file instead of to the folder path.
- "Undo last apply" now puts the book row back instead of storing the old value as a user override. Each field is restored inside `ModifyBook` only while it still holds what the apply wrote; fields edited since, locked fields and already-restored fields are reported. The apply is found by a batch id recorded on every history row, not a ±2s window, and write-back is queued only when a field actually changed. History recorded before batch ids existed is refused with 409.
- Metadata apply history is recorded after the write commits, from the committed diff, so values the apply refused are no longer recorded, and every field the apply can change (description, genre, ASIN, ISBNs, subtitle, years, secondary series, page count, abridged, and the rest) is recorded so undo can restore it. The bulk-fetch path had been recording the new values against themselves.
- Operation revert writes every book change through `ModifyBook` with a compare-and-set instead of a whole-row `UpdateBook` of an earlier read. Reverting a file move also repoints every book_file row, refuses when the book was repointed since, and moves the file back if the book write fails. `file_copy` rows are listed as not restorable, because deleting the library copy is not a safe reversal.
