### Changed

- The relocation follow-up (`books.book.relocated.v1`) is staged only by the organized copy of the single-book organize request, in the same batch as the copy's row (`CreateBookWithRelocation`), where the events flip first staged it on every committed `file_path` change. That restores what `NotifyDelugeAfterOrganize` did (the request still calls it directly while the tasks switch is off) and nothing wider: no repair, scanner, quarantine, revert, edit or version-swap write moves a torrent, and in-place organize still moves none. The message carries `book_id` (the original) and `target_book_id` (the copy), never a path; the `books.deluge.path-update` run moves the original's Active torrents to the copy's stored path as read when it runs, and does nothing if the copy is gone.
