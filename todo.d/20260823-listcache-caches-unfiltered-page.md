- [ ] **`listCache` caches the UNFILTERED page under a filtered key when the store cannot push down.** In `GetAudiobooksWithTotal` (`internal/audiobooks/service_query.go`, light-filter arm), `svc.listCache.Set(cacheKey, books)` runs unconditionally right after `bookSummariesToBooks(summaries)`. But `didPushdown` — the flag that says whether the store actually applied `IsPrimaryVersion` — is not consulted until several lines further down, where it gates the in-Go post-filter. So when `summariesPushdown` falls back (`didPushdown=false`), the raw unfiltered projection is written to the cache under a key that encodes `p=true`, while the post-filter builds a *new* slice for the caller. The first request answers correctly; every subsequent identical request is served from `listCache.Get` and returns rows the filter excluded. Measured on a 3-book fixture with a store lacking `HonorsEveryBookSummaryFilter`: miss returned `{explicit-true, nil-flag}`, hit returned `{explicit-true, explicit-false, nil-flag}`. This is a **membership** bug, not a field-value one — it mis-serves explicitly-non-primary books, so it is unrelated to nil semantics. It needs a non-pushdown store to reproduce, which in production is the ~2-minute memdb warmup window after startup, so it is a live path and not a mock-only curiosity. Likely fix: move the `Set` below the post-filter, or gate it on `didPushdown`. Found while doing TASK-002 (PR #2805) and deliberately left unfixed there to keep an API-contract change from being buried under a second behaviour change.
