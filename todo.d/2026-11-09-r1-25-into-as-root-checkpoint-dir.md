- [ ] **core: `storage restore-offline --into` run as root leaves files in the checkpoint directory that the service cannot open** R1-25 review B-1 made the offline writes run only as the state directory's owner (seams note D29), and kept `--into` open to any user. `--into` still writes inside the checkpoint directory, which belongs to the service. `restoreInto` (`core/kernel/restore.go`) creates the scratch area and its parents with `mkdirPrivate` (0700) when they are absent, and puts its copy and `<copy>.state` under it. `Checkpoints.Lock` creates `<checkpoints>/.sweep.lock` (`core/storage/checkpoint_sweep.go`) when no sweep has run yet. Run as root, each of those belongs to root.
  - A root-owned `.sweep.lock` makes every later sweep fail to open it. `sweeper.runOnce` logs that at INFO as "another sweep or prune holds the checkpoint directory" and skips, so retention stops with no error, and `storage prune-checkpoints` run as the service refuses as busy. A root-owned scratch area or copy is one the sweeper cannot list or remove.
  - R1-27 runs the restore as the service user (`systemd-run --uid`), so it is not affected.
  - Fix: refuse `--into` as a non-owner too. Drop the `req.Into == ""` condition before `refuseNotOwner` in `RestoreOffline`, flip the `--into` half of `TestOfflineWritesRefuseANonOwner`, and update D29, the changelog line and the executive summary (about ten lines of code and test). The partial alternative, a non-owner `--into` that creates nothing shared, still leaves its root-owned copy where the sweeper cannot remove it. Either way this reverses the review's "`--into` stays unrestricted", so it needs the owner's call.
