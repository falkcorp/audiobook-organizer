- [ ] **LOCK-METADATA-STATE-ORDER-AUDIT** `ModifyBookRespectingLocks`, `ModifyBookCreditsRespectingLocks` and the maintenance sites built on them read a book's field locks inside the book's write stripe, but the lock WRITERS (`RecordUserOverrides`, the field-state upserts) take `LockMetadataState`, not the book stripe. So the window in which a lock saved just before a write can lose is one batch wide, not closed: a lock saved while a commit's callback is running lands after the callback read the lock set. Closing it means choosing one acquisition order for the two locks (book stripe then `LockMetadataState`, or the reverse) and auditing every site that takes both for a deadlock, including the user-edit handlers that hold the metadata-state lock while they write the book. Own PR with its own plan; until then the helper docs and the changelog say "narrowed", not "closed".
