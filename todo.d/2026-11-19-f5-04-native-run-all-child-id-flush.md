- [ ] **F5-18-RUN-ALL-CHILD-ID-DURABLE** (owed by F5-18 or core) the native `books.dedup.run-all` does not make its child's run id durable while it waits. `runChainChild` (`internal/plugins/dedup/chain.go`) records the id with `rc.Checkpoint` right after `rc.Enqueue`, but the kernel holds a checkpoint in memory until `MinCheckpointInterval` (30 s) has passed since the last flush (`core/internal/executor/attempt.go`), and the plan-freeze or step-done save has just flushed, so this one is held. The native wait never records again (its driver reports one `childWaiting` frame and no row changes). A graceful stop flushes in `finish`; a hard kill or a fenced attempt does not, so after F5-18 switches the kind on, a resumed run-all re-enters step i with no child id and starts a second child (a second full-scan queued behind the first on the shared ConcurrencyKey: wasted CPU, no data loss; if the old child is still queued the two fold). Fix before F5-18 flips run-all: either core grows a flush-now checkpoint (`rc.CheckpointNow` or an option on `Checkpoint`) that the forced `record` uses, or the native driver calls `record(false)` on a timer while it awaits. Add a test that kills the attempt between the enqueue and the first throttled flush and resumes with the child id. Found by the F5-04 review (round 2, m2).
