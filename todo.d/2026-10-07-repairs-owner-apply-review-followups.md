- [ ] **Repairs owner apply (#3810) review follow-ups (SHOULD-FIX)**
  - [ ] Bind the owner grant to the op it was minted for. `OwnerGrants.Issue` records user, fixer, plan and rows but not the `repairs.apply` op id, so any apply op whose params carry the token and name the same fixer/plan/row consumes it. Op params are not in the v2 response today and the grant is now consumed before any failing step, but the binding should not depend on that: attach the enqueued op id to the grant (or check the op's `ActorUserID` against the grant's user) in `ResolveOwnerApproval`.
  - [ ] A credential that can manage users can make itself an "interactive" admin. `POST /users/:id/reset-password` is fine (it mints a temp-login link, recorded `session_delegated`), but `PUT /auth/me/password` with `user_id` set (`ChangePassword` admin reset) lets any caller whose USER holds `users.manage` set another user's password, checking the user's roles and not the API key's scopes or the auth method; the caller then signs in with that password and gets a `password`-origin session that `auth.Method.Interactive()` accepts. Creating a user with a password and an admin role is the same path. This widens the plan's "Open risk (owner's call)" (`scripts/manage-credentials.sh` logins) from Claude's own users to any admin API key. Limiting owner apply to named owner user ids does NOT close it: the key can create an admin, sign in as it, admin-reset the owner's password through the same branch, and sign in as the owner. Only an identity the server cannot mint closes it: owner apply only for a Cloudflare Access SSO identity, or a second factor at the click. Refusing user/password/role management to non-interactive methods narrows it but breaks API-key user provisioning. Owner decides.
  - [ ] `CloudflareAccessAuth` binds a user before `RequireAuth` looks at the bearer token, so a request carrying both a CF Access assertion and an `abk_` key is recorded `cf_access` (interactive). Only an SSO user's own browser or `cloudflared access` holds that assertion, so this is low risk, but record the stronger fact: when an `Authorization: Bearer abk_...` header is also present, mark the method `api_key` (WithMethod's downgrade rule already allows it).
  - [ ] The engine journals the owner audit note on every fragment before the fixer's Apply, and the fixer's under-lock checks (ownerRetireRefusal) can still refuse the row after that, leaving ledger-only `repair_owner_apply` notes on an op that wrote nothing. Journal the notes from the fixer after its pre-checks pass (or void them on a refusal) so the operation's history only names the owner on a row that was written.
