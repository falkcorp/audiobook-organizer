# 05 — AI integration (`integrations/ai`)

Evidence commit `748fd787a`. Raw inputs: [`raw/11-integrations.md`](../../plans/platform-core/raw/11-integrations.md) §1-§2, §6;
[`raw/12-cross-cutting.md`](../../plans/platform-core/raw/12-cross-cutting.md) §9.
Builds on the instance base, error taxonomy and `providerhttp` in [05-metadata](05-metadata.md) §M1-§M2.

## 1. Purpose & scope

A provider-neutral AI contract for three kinds of work — **text generation** (including vision input and
structured JSON output), **embeddings**, and **transcription** — plus a per-`App` **router** that sends each
piece of work to an endpoint explicitly allowed to do it, with failover, per-endpoint concurrency, health
cooldowns, privacy locality rules, batch jobs and usage **metrics** (OTel counters, as at HEAD).

**v1 scope (SIMP-11, cross-cutting resolution 1).** v1 = the contract, the router moved from
`internal/aidispatch` with its globals removed, the `core.openai_compat` adapter, batch jobs, and usage
metrics. The persisted usage ledger, the `Router.Usage` query, the monthly token cap, user-entered pricing
with cost estimates, and the `/ai/usage` route are **deferred** (§11): ABO is the only AI consumer, HEAD has
none of them, and TV/Movies consume no AI. Modules reach the router as `module.Deps.AI` (06, COR-1).

Hard requirement (D9): **core works with zero paid providers.** No AI is required for any core function; a
capability with no capable endpoint fails closed with a typed error and the module degrades. The first-class
adapter speaks the **OpenAI-compatible HTTP API**, which local servers expose (Ollama, llama.cpp's server,
and transcription servers implementing `POST /v1/audio/transcriptions`); a paid cloud endpoint is just another
instance with a secret. Conformance against each named local server is run at implementation (§10), not
asserted here.

Out of scope: prompts, schemas and result handling (module code); agents/tool loops (not needed by any
current caller — `Feature` reserves `tools` so it can be added without a contract break).

// labels: Status is the HTTP status (0 when no response arrived); Quota is a
// 429 whose error type or code is a quota marker (the router's quota rule,

	Status    int
	Quota     bool
	Err       error
	Retried   bool
	InBackoff bool
	Elapsed   time.Duration
	Usage     Usage

// JobStore persists batch jobs. SDK surface, frozen by the API-stability
// gate. Core ships NativeJobStore (§4 "Native store"); an app whose jobs
// predate core passes its legacy implementation in the AIJobs field of
// legacy.Stores, set on Manifest.LegacyStores (06; R6-3). JobStore has no
// legacy-only capability, so package legacy holds nothing of ai but that
// field, and a legacy implementation runs the native suite (§9) with its own
// fixtures. Store model: EXCLUSIVE (05-storage
// §5S.3.11, SIMP5-1): when the app supplies a legacy store it serves every
// job, pre-core and new, so an older build can see and finish a job after a
// rollback; there is no per-record routing between it and the native store.
// Writes stage into the caller's batch, so a job's state change commits with
// the poll step, apply run or cancel that caused it.
//
// EVERY write is checked at commit (R6-1, R5-4, DATA5-1, DATA6-1). Create
// and Transition are the only writing methods, so no write is unconditioned:
// there is no progress tick, count, attempt, error-text or timestamp update
// outside a Transition. Create expects the job absent. Transition reads the
// stored job (for a legacy store: its legacy row) through b.GetForUpdate, returns ErrJobConflict when its State is not from,
// and otherwise stages next, derived from that read; a write that keeps the
// state (an apply run's raised attempt count, its recorded outcome) is a
// Transition with from == next.State and the same precondition. A concurrent
// commit to any key it read fails b with storage.ErrConflict, so a poll, an
// apply run and an HTTP cancel racing on one job never both commit, and a
// same-state write can never revert a cancel. A failed write is DROPPED:
// nothing of its batch applies, and its writer re-reads and decides again
// from the new state (§4 step 5); no caller re-stages a row derived from the
// stale read, and no implementation retries one internally. None relies on a
// lock held between calls (HEAD's aijobWriteMu,
// internal/database/pebble_store_aijobs.go:18-23) for its correctness. An
// implementation therefore keeps jobs only in Serialized families:
// c/ai/jobs/ and c/ai/ix/open/ natively, which are also CheckedWrites so
// storage refuses a blind write (ErrBlindWrite); for a legacy store the
// families it reads or writes here (05-storage §5S.9.1 row 19), which are not
// CheckedWrites: HEAD's single-writer ratchet keeps any other writer off them
// (A-3), and its own writes carry the Expect. Such a store offers no
// legacy.WriteLock (R9-1): HEAD's aijobWriteMu guarded HEAD's direct
// read-modify-write commits, which books' store no longer makes, so the
// commit-time Expect, not a mutex, decides every race. Every batch a JobStore
// stages into commits through storage.CommitLocked (05-storage; R9-1), with
// the locks of the other legacy stores that staged into it (§4 step 5).
type JobStore interface {
	Get(ctx context.Context, id BatchJobID) (StoredJob, error)
	Open(ctx context.Context) iter.Seq2[StoredJob, error] // non-terminal jobs, payload omitted
	Create(ctx context.Context, b *storage.Batch, j StoredJob) error // j.State == JobPending; payload included
	Transition(ctx context.Context, b *storage.Batch, id BatchJobID, from JobState, next StoredJob) error // ErrJobConflict
}

## 4. Lifecycle

1. **Register**: modules call `AICapability` and register one `ai.BatchApplyTask` per batch capability with
   `r.Tasks`; the kernel rejects a duplicate ID, an ID
   outside the module's prefix, a missing `Description/DataSent/TypicalRequest`, or a `FormerIDs` collision.
   The catalog is **frozen** before `Run`; there is no runtime registration (the review-gated property of
   `newCapability`, `capabilities.go:93-97`, kept by construction: a capability exists only if a module's
   code registers it).
2. **Endpoints** are `ai/<id>` records in the one instance registry (05-metadata §M1, SIMP-4); the API key is the
   secret `integrations.ai.<id>.api_key` (05-config §2.3 grammar). During the extraction ABO's endpoints are
   legacy-backed: served in place by the app's legacy `integrations.InstanceStore` (05-metadata M1.4 step 2a, R4-1;
   books code for ABO, §10), which the Registry routes to per record (05-metadata M1.3, SIMP5-1); ABO's one endpoint
   key (`ai/openai`) stays in HEAD's encrypted row until the secrets cutover (§10, R5-1(b), A-2). A stored tick for an ID the catalog does not know is **kept and ignored**
   (rollback-safe, `ParseCapability` rule `capabilities.go:285-293`); a PUT containing one is rejected (422). The
   Registry hands ticks to the store as catalog IDs; a legacy store writes them in its own vocabulary — ABO's stores a
   capability that has a `FormerIDs` entry under its HEAD ID, so an older build still sees its ticks, and a
   capability new with core under its own ID, which HEAD keeps and ignores
   (`internal/config/ai_endpoints.go:53-55` @748fd787a). Reads accept both through `Lookup`. Rewriting the stored
   ticks to native IDs belongs to the AI family's cutover.
3. **Per call**: snapshot endpoints → refuse (disabled, not ticked, kind/protocol, missing required
   feature, missing label/GPU, no model, pinned-model mismatch, locality, cooldown) → order by
   priority then current depth → free-slot spill → attempt with per-attempt timeout started after the slot
   → classify → mark health → fail over or return (the `Call` algorithm, `dispatch.go:347-500`, kept).
4. **Health**: cooldown = `cooldown_base × consecutive failures`, capped; quota → `quota_cooldown`; success
   resets. The `core.integrations.health` task additionally probes benched endpoints with `GET /v1/models`
   (no tokens spent — unlike HEAD's Test, `openai_parser.go:878-889`) and clears the bench on success.
5. **Batch**: `SubmitBatch` stores the job (`JobPending`, `JobStore.Create`) **before** the remote call, tags
   the remote batch with the job ID, then records the handle (`Transition` from `JobPending` to `JobSubmitted`). The
   store is `NativeJobStore`, or — when the app passes a legacy `JobStore` (R4-1) — the app's, which then holds open
   pre-core jobs and every new one (exclusive model, §3).
   **Every write is a commit-time compare-and-set (R6-1, R5-4, DATA5-1).** `SubmitBatch`'s recording of the remote
   handle (`JobPending` → `JobSubmitted`, with ABO's batch-ID index row in the same batch), the poll's recording of
   an orphan it found by tag and its move to `JobApplying` (with the staged apply run), an apply run's `JobCompleted`, `JobFailed`, raised
   attempt count or recorded outcome (the last two keep the state: a `Transition` from `JobApplying` to
   `JobApplying`), and `CancelBatch`'s `JobCanceled` are each a `Transition` from the state the writer read,
   derived from that read and staged in that writer's batch. No writer stages anything else on a job's rows: there
   is no progress tick and no unconditioned status, count or timestamp write. The apply run's own progress is a
   `tasks` run write, checked at commit by 05-tasks (R6-1). When two of
   them race on one job, exactly one commits; the other's batch fails with `storage.ErrConflict` (or `Transition`
   returns `ErrJobConflict` before staging) and nothing of it is applied. The loser re-reads: the poll skips the job
   until its next pass, so a cancelled job never gets an apply run staged; an apply run whose job is now terminal
   stops and marks nothing (handler writes it already committed are idempotent and stay; no later apply run is
   staged for a terminal job, so a completed job is never applied twice); a `CancelBatch` that loses re-reads once and cancels from the new state while the job is non-terminal,
   else returns 409. The remote cancel is sent only after the
   `JobCanceled` transition commits. The families these transitions read and write are therefore `Serialized`:
   `c/ai/jobs/` and `c/ai/ix/open/` natively, which are also `CheckedWrites` from S7, when they land, so a blind
   write fails with `ErrBlindWrite`; and for ABO HEAD's `aijob:`, `aijob_batch:` and `aijob_payload:` families
   (05-storage §5S.9.1 row 19), which are not `CheckedWrites` during the extraction (A-3): from S7 books' `JobStore`
   is their only writer, kept so by HEAD's single-writer ratchet, and its own writes carry the precondition. The
   router holds no in-process job lock.
   **Books' legacy `JobStore` keeps none of HEAD's read-modify-write shapes (R6-1).** HEAD's writers each read the
   row and write it back whole under `aijobWriteMu` (`updateAIJob`, `pebble_store_aijobs.go:120-140`, used by
   `MarkAIJobApplied`, which records counts with the status unchanged, `MarkAIJobCompleted`, `MarkAIJobFailed` and
   `MarkAIJobApplyFailed`; `MarkAIJobSubmitted`, `:95-118`, which also writes the `aijob_batch:` index). In books'
   store each becomes the `Transition` its caller stages: the row read with `GetForUpdate`, the mutation applied
   to that read, the result staged with the index rows it touches.
   ABO's legacy `JobStore` is books code over HEAD's job rows (§10): its job type is the HEAD feature type when the capability has one,
   so an older build can still finish the job with its own idempotent callback after a rollback
   (`internal/ai/aijobs/aijobs.go:68-80`), and it reports an unknown type as an apply failure (`aijobs.go:303-308`).
   Core holds no key name or row format of it and no storage grant; open pre-core jobs are not copied anywhere.
   **Nothing is stored beside HEAD's row (A-2).** Books' store maps `StoredJob` onto HEAD's `aijob:` row
   (`internal/database/ai_jobs_types.go:22-56` @748fd787a) and derives what the row does not hold:

   | `StoredJob` | HEAD's row |
   |---|---|
   | `Capability` | `type`: the HEAD feature type for a capability that has one (its `FormerIDs` entry), else the catalog ID, which an older build reports as an apply failure (`aijobs.go:303-308`) |
   | `Module`, `ApplyKind` | not stored: derived from the capability (its registering module and that module's `ai.BatchApplyTask` kind) |
   | `Endpoint` | not stored: the one endpoint HEAD's batch path submits to (`ai/openai`, `aijobs.go:106-170`); books' store refuses `Create` for any other endpoint before the remote is called |
   | `Handle` | `batch_id`, with the `aijob_batch:` index row in the same batch |
   | `State` | `pending` ↔ `JobPending`; `submitted` ↔ `JobSubmitted`; `apply_failed` ↔ `JobApplying` (results ready, apply to be retried); `completed`, `completed_with_errors` ↔ `JobCompleted`; `failed`, `expired` ↔ `JobFailed`; `JobCanceled` is written as `failed` with `error_msg` `canceled`, which reads back as `JobCanceled` |
   | `ApplyAttempts` | `apply_attempts` |
   | `Payload` | the `aijob_payload:` row |

   HEAD's row has no state for "apply run staged, not yet failed", so books' store writes the poll's move from
   `JobSubmitted` to `JobApplying` as the unchanged `submitted` row, under the same precondition, and reads it back
   as `JobSubmitted`. A later poll pass that finds the results ready again stages another apply run; the apply
   task's queued-run dedupe on the job ID (05-tasks `DedupePolicy`) merges it with one still queued, and one staged
   while the first runs is serialised behind it by the conflict rule and, finding the job terminal, marks nothing.
   This is HEAD's interrupted-apply replay (`aijobs.go:68-80`), and idempotent handlers make it safe. A failed apply
   run writes `apply_failed` with `apply_attempts` raised, which reads back as `JobApplying`, so retries and
   `batch_max_apply_attempts` work as on a native store. A job an older build polled, finished or failed while
   rolled back reads in the state its row now holds: a terminal one is final and never re-staged, and a non-terminal
   one continues from it.
   **No result-journal store (SIMP5-3, COR5-10, DATA5-15).** `ai` persists batch jobs only. ABO's
   `internal/ai/resultjournal` (the `aijournal:` family, `internal/ai/resultjournal/journal.go:50-51` @748fd787a)
   is books code that books' own callers use (`internal/transcribe`, `internal/scanner`,
   `internal/plugins/maintenance`, `internal/reconcile`; no core service persists through it): it stays ABO over
   books' own `aijournal:` claim. There is no `ai` result-journal interface, no `LegacyStores` field for it and no
   core re-implementation of the mechanism; a module that wants to journal its batch results does so in its own
   apply handler, which runs as a module task (`ai.BatchApplyTask`).
   `core.ai.batch-poll` (a core kind,
   `Effects: tasks.Writes(tasks.Res("core", "ai"))`), scheduled by
   `tasks.ScheduleFromConfig("core.ai.schedules.batch_poll")` (the one schedule-key rule, R2-7), advances job
   states over `JobStore.Open` and reconciles orphans by tag. It **never calls a module handler** (COR2-11): for each
   job whose results are ready it moves the job to `JobApplying` and, in the same batch, stages the module's apply run
   (`<module>.ai.batch-apply.<name>`, `ai.BatchApplyTask`) through `tasks.Stager.StartIn`, the stage-only handle
   the kernel gives the router at construction (05-tasks; core services never hold the `Executor`, COR3-8), with
   `ModeLive`; the kernel stamps the owning module's system actor. The poll builds and commits that batch inside
   `Stager.WriteRuns` (05-tasks 5T.7), which retries it under `storage.RetryOnConflict` and is a use of
   `storage.CommitLocked(ctx, b, locks...)` (05-storage; R9-1): on books' legacy run store it holds HEAD's `opsMu`
   through that store's `legacy.WriteLock` from the batch's first run-store read until its commit returns.
   **One commit path (R9-1).** Every other batch here that a legacy store stages into (`SubmitBatch`'s `Create` and
   its `JobSubmitted` transition, `CancelBatch`'s `JobCanceled`) commits through `storage.CommitLocked`, naming the
   `legacy.WriteLock` of each legacy store that staged into it; books' `JobStore` names none (§3), so on ABO these
   commits hold no HEAD mutex and rely on the `Expect`. The apply run's `JobCompleted` commits with the run's own
   write, inside the executor's `WriteRuns`. The `JobStore` the router uses is the one instance the kernel builds per
   process (`TestLegacyStoresAreSingletons`, R9-1). That run
   executes the handler under the module's own `Effects`, fence and ref locks, records the results' token
   counts in the usage metrics (`mode=batch`; HEAD records none) and marks the job `JobCompleted` in its own
   fenced write (`Transition` from `JobApplying`). A failed apply run leaves the job `JobApplying`; the next poll
   starts a new apply run (`Transition` from `JobApplying` with the attempt count raised) until
   `batch_max_apply_attempts`, then `JobFailed`.
6. **Shutdown**: stop accepting calls (ctx), drain in-flight within the App's bounded drain. Nothing to flush:
   usage is metrics only.

## 5. Error semantics

| Error path | Fail-open / closed | Why |
|---|---|---|
| No capable endpoint | **closed**: `*NoCapableEndpointError` listing every refusal; the caller must mark the item failed, never skipped or done | Default-deny is the point (`capabilities.go:6-13`; contract `dispatch.go:339-341`). |
| Capability ID unknown to catalog at call time | closed (`ErrUnknownCapability`) | Unreachable with handles; guards hand-built IDs from storage. |
| Embed call without pinned model | closed (`ErrEmbedModelNotPinned`) | Mixing vector spaces corrupts every similarity score (`capabilities.go:208-210`). |
| `ClassTransient`, `ClassRateLimited`, `ClassAuth` on an attempt | fail over; bench endpoint | Credentials and capacity are per endpoint; another may serve (`classify.go:136-147`). |
| `ClassQuota` (quota marker in `type` **or** `code`) | fail over; long bench | The next request cannot clear it (`retry.go:59-96`). |
| Per-attempt deadline on a live parent | fail over once; a second deadline ends the call | `classify.go:43-45` (PLAN decision 7). |
| `ClassBadOutput`/`ClassInvalid` | return as-is, no failover | Another endpoint would reject it too, or hide the problem (`classify.go:148-152`). |
| `ClassUnknown` | no failover | Safe answer to "send it again?" is no (`classify.go:87-92`). |
| Parent ctx done / slot wait canceled | stop (`ClassCanceled`) | Our budget, not the endpoint. |
| Secret referenced but unset | `ClassAuth` on that endpoint → fail over | Never send an unauthenticated request (`pool_routing.go:90-103`). |
| Structured output invalid after repair turns | closed (`*QualityError`) | Quality problems must surface, not spread. |
| Batch handler returns error (apply run fails) | job stays `Applying`; the next poll starts a new apply run; after `batch_max_apply_attempts` → `Failed` | Idempotent handlers make replay safe. |
| `SubmitBatch` for a capability with no `BatchApplyTask` | closed (`ErrNoBatchApply`, nothing submitted) | Results nobody can apply would be paid for and dropped. |
| A legacy job an older build changed while rolled back | terminal legacy status: final, never re-staged; otherwise the job continues from its legacy status and attempt count (§4 step 5) | An older build may already have applied or abandoned it; a terminal job is never applied twice (R4-1, DATA4-8). |
| `Create` on a legacy store for an endpoint its format cannot record (ABO: other than `ai/openai`) | closed: refused before the remote call, nothing stored | An older build could not poll a batch it cannot attribute (§4 step 5, A-2). |
| `JobStore` read fails during a poll | closed for that poll (nothing staged; next poll retries) | A job that cannot be read must not be treated as absent and resubmitted. |
| `core.integrations.disabled` true (a staging copy, R6-7; 05-metadata M1.4) | closed: every endpoint is refused (refusal "integrations disabled"), so a call fails with `*NoCapableEndpointError` and `SubmitBatch` stores nothing; the batch poll makes no remote call and changes no job. A schedule that fires against a disabled integration fails closed, but its run is enqueued and its clock advances (the `core.ai.schedules.batch_poll` run included). At every stage, `staging-scrub` (09 §9.3, A-12) also clears every legacy integration URL, so an older build booted on the copy, which ignores the switch, has no endpoint to call (R7-6); native endpoints are not cleared, because only S7+ binaries read them and every such staging boot carries the switch (R8-3) | A copy of a production store must never spend a production provider's budget or fetch its batches (OPS6-4, SEC7-6); schedules must still fire there (DATA5-8). |
| `Transition` loses a race (`ErrJobConflict`, or `storage.ErrConflict` at commit), including a same-state write (attempt count, outcome) | closed for the loser: nothing of its batch applied (dropped, never re-staged from the stale read); poll skips the job until its next pass, an apply run on a now-terminal job ends without applying, `CancelBatch` on a now-terminal job returns 409 | One state change per job wins; a cancelled job never gets an apply run and a completed one is never applied twice (R5-4, DATA5-1). |
| LocalOnly capability or call and only cloud endpoints | closed (refusal "cloud endpoint excluded") | Privacy floors fail closed. |

## 6. Concurrency contract

`Router` is goroutine-safe: endpoint snapshot is immutable per call; health, slots and attribution sit behind
their own mutexes (as `Dispatcher`, `dispatch.go:91-93`). Every endpoint has a hard in-flight cap
(`Concurrency ≥ 1`); kinds may have a pool-wide cap (`core.ai.kind_limits.<kind>`), which **restores the
production setter** that HEAD lacks for `whisper_max_in_flight` (`dispatch.go:99-104`). Slot acquisition
honours ctx; the attempt timeout starts after the slot. Depths are snapshotted once per selection (sort
stability, `dispatch.go:274-279`). Slot release, in-flight gauge decrement and attempt-ctx cancel run in
`defer` inside one closure per attempt (panic-safe, `dispatch.go:437-449`). Library-scale callers size their
worker pools from `Capacity(c)` and run through `tasks.RunItems` with declared parallelism (03 R7).
Batch polling processes at most `core.ai.batch_parallelism` jobs at once (`tasks.Fixed(n, "provider batch
API calls")`); apply runs are separate module runs, serialised against conflicting module runs by the
dispatch conflict rule over their declared `Effects` (05-tasks §5T.3.4). Writers of one job (poll, apply run,
`CancelBatch`) are not serialised by any lock: each job state change is a `JobStore.Transition` checked at
commit over a `Serialized` family (§3, §4 step 5), so the loser of a race applies nothing and re-reads.
