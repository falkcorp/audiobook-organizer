# 14 — Risks, migration hazards, open questions

Every item has an owner section and a recommendation. "Owner" means the repository owner must decide;
everything else is resolved inside the named spec file during review. Review findings are cited by
ID (`docs/plans/platform-core/reviews/spec-round-{1,2,3,4,5,6,7}-*.md`; dispositions in
`spec-round-{1,2,3,4,5,6,7}-dispositions.md`; round-2 to round-7 resolutions are cited as R2-n, R3-n, R4-n,
R5-n, R6-n and R7-n). Round 3's R3-1 replaced the dual-format rollback machinery of rounds 1–2 (adoption copies,
mirrors, side records, Teach-build floors); risks that existed only for that machinery are withdrawn
below, not kept as history. Round 4's R4-1 refines R3-1: core reaches ABO's data through store
interfaces whose implementation is books code, so the core-side legacy-format adapters and the storage
grants of the extraction are gone (grants return with the deferred cutover).

Its signals: (1) a **content marker**: every journaling boot writes `c/backup/served_boot = {n, nonce}` into the store and then the same pair into `backup.location.json`, and backup's `Create` writes a fresh pair after taking each archive's checkpoint, so from S8, when `backup` makes the archives, every archive carries a pair older than the file (SEC6-6); until S8 ABO's `internal/backup` makes them and they carry the current pair, so an in-place restore of one is caught by the anchored head (2), not by the marker (DATA7-16); a store whose pair is older than the file's (a lower `n`, or the same `n` with another nonce) was replaced, whatever its directory identity; (2) an **anchored journal end**: `backup.location.json` also holds the journal's committed `head {seq, mac}`, rewritten after each revoking commit (it may lag, never lead) by the file's one writer, the journal component, which holds a mutex across every read-modify-write while `Create` hands its pair to it (DATA7-14) and never rewrites the anchor on a restore boot or while a restore journal is between `swapped` and `applied` (R7-4, DATA7-5), so a store whose `head_before` is below it was replaced whatever its marker — this catches the common case the marker alone missed, an in-place restore of last night's archive taken during the last journaling boot (DATA6-4); (3) a **generation or directory identity** that differs from the recorded one, with no staged restore, means replaced only with journal evidence — the head is below the journal's last revocation line, a gap or `restore` line follows the head, the store has no head while the journal has revocation lines, or this boot's own owed `journal` entry or foreign-open verdict says so; otherwise the store was relocated (a cross-device move, a new disk, a volume migration), its new identity is recorded and no hook runs (DATA5-7). Markers, head and lineage are compared only when the file's `db_path` (and install id, when present) matches the store, so two stores that share one state directory — the image job's second volume, a staging copy — never trip each other's hooks (SEC6-8). **A staged restore is not a foreign open (R6-4):** the restore-pending record names the boot that applies it, which records the identity of the `.storage-format` it rewrote, reads the lineage as `restored` (never `behind`), appends no `gap` line for its own swap, forces no key confirmation (DATA6-2) and writes `c/storage/boot` and `storage.boot.json` in its `marker_written` batch before the journal reads `applied`, so a failure later in that boot does not leave a `behind` lineage (R7-4, DATA7-4); a restore whose hooks fail swaps back, restores the `backup.location.json` it saved at step c and appends `restore_aborted`, so the original store is the same store on the next boot and runs no hook (DATA6-3). A lagging head on the same store only re-applies the tail, with no hooks (DATA4-7), and a non-empty store with no install marker at the recorded path (an in-place restore of a pre-S0 archive) inherits the **lineage file's** `install_id`, so its verified tail is re-applied instead of the journal being set aside (DATA5-13, DATA6-10). A core build's own factory reset only **stages** (R7-2): from S2b until S4 r2 books' gin handler, behind HEAD's chain, calls `legacy.Maintenance.StageFactoryReset`, and from S4 r2 the core route in `internal/storagehttp` does, with the legacy path as its `Alias`; nothing destructive runs before the restart. The intent records the live Pebble open stamp and is rejected when it moved; a staged reset and a staged restore refuse each other; `CheckReader`'s tokens `reset_pending` (while `reset/pending.json` exists) and `reset_inflight` (while a `reset/<id>/inflight.json` exists, from the set-aside until the post-reset hook journals `hook_done`) make `make rollback`, `deploy` and the updater refuse (`ROLLBACK_IGNORE_RESET=1` overrides). An empty store is exempt from the upgrade floor, so the fresh install the reset leaves passes it (R7-2, DATA7-7). The next boot boots a fresh install with a new `install_id` and sets the journal aside (05-storage §5S.3.15, 05-backup; DATA6-6; the keyring is kept, Q-J decided (a), §14.3.1); HEAD's side effects run afterwards in a books post-reset hook, only once the reset journal reads `applied` (Q-K). The kernel re-applies every verified revocation line after the head (the journal's end is its last **revocation** line; gap and `restore` lines are bookkeeping and never count) through the auth and rbac stores (books' legacy implementations during the extraction), so known revocations hold, and runs the hooks with `KindExternal` and `Revocations == nil`: every active or disabled API key needs confirmation, a revoked key stays terminal, and the owed-`auth` consumer deletes every legacy sign-in (`DeleteLegacySignIns`), so no undetected interval can honour a pre-cut-off legacy session (DATA6-4). When a staged restore's pre-swap store exists (`rc.Previous`), rbac's hook keeps the most restrictive of the restored and pre-swap state for every role row and assignment, whatever the coverage, so a demotion the journal does not cover (made on an older build, or whose `Append` failed) is not undone (SEC5-10, SEC6-4). A replaced store has no pre-swap store; there the residual is stated: such an unjournaled demotion can come back with the restored role rows until an admin re-checks the accounts holding `core:admin`. The restriction applied to them meanwhile is 05-rbac §7.1's **weaker rule, which the lead accepted in round 5** (05-rbac §14 item 8): every `core:admin` holder is listed in the restore report and in health (`restore_admins_review`, `degraded`) until an interactive admin acknowledges each one, and auth's fallback has already bumped their epochs and set their keys `needs_confirmation`, so a restored admin needs a fresh sign-in; the stronger option (sign-in restriction for every admin until an owner-verified reset) is recorded there and not taken. (c) A **whole-volume snapshot rollback** — store, backup directory and fallback state directory on one volume, the default on Docker and launchd — reverts the store, the journal, `backup.location.json`, `storage.boot.json` and the markers together, so every check reads "same store" and revocations and demotions made after the snapshot come back undetected (SEC6-10); rollback runbooks say to restore with the staged restore, never with a volume snapshot, and 05-backup recommends a `core.backup.dir` on another volume (health `info` `revocation_journal_colocated` while the journal shares the store's device).
