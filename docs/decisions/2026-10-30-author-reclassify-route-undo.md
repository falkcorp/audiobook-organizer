# AUTHOR-RECLASSIFY-ROUTE-UNDO: run the reclassify route as an operation

## Decision log

Context: `POST /authors/:id/reclassify-as-narrator` ran `entities.ReclassifyAuthorAsNarrator` in the request with no `ReclassifyJournal`, so the Authors view's button deleted the author and moved its credits with no way back. The AI scan apply passes a journal and is undoable.

- Chosen: a new op `entities.author-reclassify` (params `entities.AuthorReclassifyOpParams{AuthorID}`, defined once in `handlers/entities` and aliased in package server like `AuthorMergeOpParams`). The route validates the id, answers 404 for a missing or tombstoned author (the tombstone check `author.ID != authorID` moved into the route, since the op would otherwise turn the surviving author into a narrator), enqueues, and answers 202 with the bare `{id, type, status}` shape `POST /authors/merge` uses. The op passes `ReclassifyOptions.Journal` under its own op id; no new undo code was needed, the existing revert path already handles both change types.
- Chosen: `ConcurrencyKey: "entities.author-merge"` (shared with the merge and the AI apply: all three rewrite `book_authors` and delete authors), `ResumeDrop` (a re-run would double-journal under one op id), `Permissions: PermLibraryEditMetadata` (the route's own gate, unchanged), `Capabilities: library.read + library.write`, `NoWarmupWait` (a person is waiting), not cancellable (the move is one author). Goldens: `op_ids.golden` appended and `write_op_modes.golden` records `no-mode`, like `entities.author-merge` (the op acts on one named author and has no `{}` that writes anything).
- Chosen: no `SkipBook`. This is a person's explicit action on one author; the AI apply's author_name / narrator lock skip stays the AI apply's. Behaviour is unchanged from the old route.
- Chosen: scan stand-down held once before any write and renewed before each book through a new `ReclassifyOptions.Lease func() bool`; a lost lease returns `ErrReclassifyLeaseLost` before the delete, so the author is kept (a delete would strand the books not yet moved) and what moved stays journaled. Fails closed like the series ops: an empty op id or an acquire error refuses the run before any write. A hold that is not renewed would lapse during a long author, which is why the per-book renew exists.
- Chosen (duplication, to remove later): PR #4302 (`fix/author-merge-holds-scan-standdown`) adds `Server.holdAuthorMergeStandDown` and `scanLeaseRenewer` but is not on main, and it edits `entities_ops.go` / `ai_scan_apply_op.go`, which this change avoids. The same check is implemented locally as `Server.holdReclassifyStandDown` in `author_reclassify_op.go` (and the test gate is named `reclassifyTestGate`, not `recordingStandDown`) so neither lands a name clash. After #4302 merges, replace `holdReclassifyStandDown` with `holdAuthorMergeStandDown`.
- Chosen: the web client waits for the operation. `api.reclassifyAuthorAsNarrator` returns the queued `Operation`; the lane's new `reclassifyOne(id, life)` polls it with `pollOperationV2` and throws when it did not complete, at all three call sites (single merge, series merge, split-composite). Every caller goes on to a merge or a list edit that assumes the reclassify finished, and a bare 202 would report success for an operation that fails. The rejected alternative was to rely on the operations bell like a fire-and-forget start; it fits no caller here. The UX is otherwise unchanged (same toasts, same "N narrator reclassifications failed" wording, now also for a failed operation). The `unconfirmedRef` bookkeeping the merge keeps was not copied: it is keyed by group and used to re-check a merge after the lane is left, and a reclassify that was queued before the lane was left still runs server-side to completion.
- Not done: the "related, left as it was" sentence in the TODO entry (a scan result whose keep author cannot be chosen is re-evaluated on every read instead of remembered). It needs the scan read path to store a remembered state on the result, which is a schema and read-path change, not a one-line change. It is filed as its own task in `todo.d/` (`AI-SCAN-UNPICKABLE-KEEP-REREAD`).
- Rejected: passing an operation id into the synchronous route and journaling under it. There is no operation row to attach the revert to, so the Activity undo would have nothing to show.
- Found, not done: nothing filters the revert by op id or def (`POST /operations/:id/revert` reads the journal rows only), so the new op is undoable there like `entities.author-merge` and `ai.author-scan-apply`. But the web has no Undo button for any author op: ActivityLog.tsx only offers one on `organize_completed` / `metadata_applied` entries, and the operations bell only on organize ops. Adding one is a separate UI change.
