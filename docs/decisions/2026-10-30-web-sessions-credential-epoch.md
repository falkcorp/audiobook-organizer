# Web sessions end on a credential change (CredentialEpoch)

## Decision log

- Chosen: the web session store gets the same treatment #4081 gave ABS sessions. `Session.CredentialEpoch` is stamped at sign-in, `RequireAuth` (and the open-stream re-check `sessionStillStands`) refuses a mismatch, and a cleanup revoke follows the write. A refused session is treated exactly as an expired one: `RevokeSession` plus 401 "session expired", with no new message or cookie behaviour (the middleware does not clear the cookie for an expired session today, and still does not).
- Chosen: the stamp is the epoch of the user record the sign-in verified against, passed by the caller as a new trailing argument of `CreateSession` / `CreateSessionWithOrigin`. Rejected: the store re-reading the user inside `CreateSession`. That would stamp a login that checked the old password and wrote its session after the change with the NEW epoch and let it through, which is the exact "created mid-change" hole the ABS stamp closes. Changing the signature (about 70 test call sites, three mocks) was accepted as the price; the compiler now finds every caller that would otherwise forget.
- Chosen: a session with no stamp reads as epoch 0 (same as ABS). It stays valid for an account whose epoch is 0 (no one who never changed credentials is signed out on deploy) and is refused for an account whose epoch is above 0, which means users who changed a password or were deactivated since 2026-10-19 sign in once more after deploy. Rejected: back-filling a stamp onto every live session at startup (it would launder exactly the sessions that survived a past change); rejected: treating unstamped as always valid (it would leave those sessions alive through the next change, defeating the point for them).
- Chosen: on a self-service change the caller stays signed in, by passing `keepSessionID` to `UserCredentialWriter.SetUserPassword`, which re-stamps that one session inside `mutateUserCredentials`, in the same Pebble batch as the user row. Rejected: re-stamping in a separate write after the bump. A parallel request from the same browser landing in the gap would be refused and revoke the caller's own session; with real SPA request fan-out that is a spurious sign-out after changing a password. Rejected: signing the caller out too (simplest, but a product regression on every password change). The re-stamp runs only for a live, unrevoked session of the same user that was current under the epoch being replaced, so it cannot launder a stale session. An admin reset keeps nothing.
- Chosen: the cleanup (`RevokeStaleWebSessions`) revokes only sessions stamped below the epoch the write produced, not "every session but the caller's". A sign-in with the new password that completes between the bump and the cleanup is current and must not be revoked; a session stamped newer comes from a later change racing this one. Cleanup failure is logged and does not fail the request (the stamp check is what makes the change safe).
- Chosen: reactivation also revokes (parity with the ABS `user-reactivated` path); its bump already makes pre-deactivation sessions unusable.
- Chosen: `SetUserPassword` gained the `keepSessionID` parameter instead of a second method, so there is one entry point for a password write.
- Not done, by instruction: ADMIN-COMPROMISED-ACCOUNT-RESET stays an owner decision. The old password still works after an admin reset link; only the sessions end.
- Chosen: `sessionWriteMu` serializes the two read-modify-write paths on a `sess:` row, `RevokeSession` and the `keepSessionID` re-stamp (lock order `userWriteMu`, then `sessionWriteMu`). Without it a revoke that lands between the re-stamp's read and its batch write is overwritten and the session comes back to life (`TestRevokeSession_IsNotLostToAConcurrentReStamp` fails on iteration 0 with the lock removed). Rejected: leaving it as a documented race; `RevokeSession` predates this change but the new re-stamp is what makes the interleaving reachable.
- Chosen: temp-login links carry the user's `CredentialEpoch` from the moment they are minted (`tempLoginEntry.Epoch`), and `consumeTempLoginToken` refuses a link whose epoch no longer matches (redirect to `/login?error=invalid_or_expired_token`, no cookie). The reset-link handler mints from the row its own bump returned, so its link is redeemable while any later change, including a second reset, kills it. This matches the ABS OIDC pending code, which already carries its epoch. Rejected: leaving links epoch-blind (a link from before a password change or deactivation would still have signed in, with a current stamp).
- Conflict noted, brief followed: the brief's "401 plus cleared cookie" was matched to what an expired session does today (401 "session expired", cookie not cleared by the middleware). `docs/executive-summaries/2026-10-executive-summary.md` says later-October work is added there as a new section, but the brief named a dated file, so the dated file was written; fold it in at the monthly combine.
- Edited, not acted on: the ADMIN-COMPROMISED-ACCOUNT-RESET entry in `TODO.md` only had its stale "Web sessions have the same gap" cross-reference rewritten.
