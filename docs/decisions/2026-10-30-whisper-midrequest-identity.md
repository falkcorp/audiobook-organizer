# Whisper worker swapped for another machine mid-request

Implements the TODO.md entry TODO-WHISPER-MIDREQUEST-IDENTITY. Code: `internal/transcribe/workerswap.go`, `liveness.go`, and the two `send` call sites in `dispatcher.go`.

## Decision log

1. **The frozen identity reaches the poller through the request context, not a parameter.** `withFrozenWorker` is set where the dispatcher calls `send` (the pool round loop and `dispatchSingle`); `pollWorkerLiveness` reads it. Rejected: adding the key to `superviseRequest` / `transcribeRemoteWithHealth` / `transcribePathChunks` and the `TranscribeByPathBatch` sender closure. That threads a new argument through every transport and edits `TranscribeByPathBatch`, which PR #4285 is changing. A request sent without the value (any other caller) is simply not checked.
2. **The comparison reuses `reprobed` and `resolveMachine`, the rules `regate` applies after a cooldown wait.** The pool rule is "any identity different from the frozen one", the lone endpoint additionally keeps a worker that gained its machine id (`lone`). A frozen identity of "" or "?" has nothing to compare. A worker that missed its id and answers "u:" resolves to the machine last seen at the URL, so it is not a swap; with no such link it stands for itself and is one, exactly as at the gate. Rejected: a looser rule for mid-request (treat any "u:" as unchanged). It would let a non-id-capable worker that took the URL over keep the old machine's name.
3. **The swap check runs before the stuck check in the poll.** A decode past its deadline on the new machine says nothing about the old one; checked after, it would be recorded as a stuck request of the old key (`soloStuck`), which is the misattribution this fixes.
4. **A new error kind, `WorkerSwappedError` / `ErrWorkerSwapped`, that does not wrap the request's own error.** The cancelled call's error is a `*url.Error`, which `isTransportishError` reads as an outage the ops count toward stopping a run; the new kind is excluded there as worker faults are, and its text avoids every transport wording. `Is(errPortChangedHands)` is true so the pool-emptied and lone-endpoint deferrals read the same as a port found changed after a wait.
5. **The whole request is withheld.** The dispatcher stores none of the sender's results for a swapped request, earlier chunks included: they cannot be told from the swapped-in machine's. A response that raced the poll's cancel (the call returned nil after the cause was set) is withheld too. Rejected: keeping earlier chunks. The swap could have happened before the first poll saw it.
6. **No bench, no recorded failure, port dropped from the dispatch.** No `markEndpointFailure` (it is process-wide and the port is not down), nothing in `lastErr`, `soloStuck`, `faultedOn`, sick or canary state. The jobs stay in `remaining` and go to the other ports; the port gets a `ChangedHands` refusal and is dropped through `heldDrops`, applied at the next round start, because dropping mid-round changes `soloLimit` under answers still being judged. No process-wide "re-probe before use" flag is set: the entry asks for the port to be dropped and the next dispatch's gate to key it, and a flag would need new shared state. A pool emptied this way ends as `errPortChangedHands`. The lone endpoint defers its jobs with the same error.
7. **The journal is invalidated, not buffered (follow-up review).** The journal is keyed by clip content and model, not by machine or URL, so an entry written by a swapped send is replayed to any endpoint running that model. Each chunk's results are journalled as the chunk completes (the restart protection the journal exists for), so a swapped send has already written the chunks before the one that was caught. `endpointJournal` records the key of every entry it wrote, and a send that ends as `WorkerSwappedError` removes them (`ResultJournal.Invalidate`, one synced batch on `resultjournal.Journal`). Rejected: buffering the writes until the send ends. A kill part-way through a send (hours of chunks for a large share) would then lose every chunk's journal entry, where today it loses one; the invalidation keeps the kill-safety. The cost is a window between a chunk's write and the invalidation in which a kill leaves the entry; the entries written there are of chunks that passed the post-response probe (decision 9), so they are the frozen machine's. An entry another call wrote for the same clip is removed with it, which costs a repeated decode.
8. **The lone endpoint's learned machine is pinned (follow-up review).** `reprobed` lets a lone endpoint frozen as "u:" accept a worker that gained its machine id, without knowing whether it is the machine that was behind the URL. The earlier rule (`!lone && now != key`) then accepted any strong id. `workerPin` makes it consistent: seeded with `gatedEndpoint.learned` when the dispatch learned one, else the first strong id any poll sees, held for the whole `dispatchSingle` (across chunks and sends), and a different strong id is a swap, so no answer is stored under a learned machine the poll contradicted. A pool port still takes no such allowance. A worker that missed its id again resolves to a weak identity and is not a contradiction.
9. **A successful response is verified before it is accepted (follow-up review).** The poll misses a swap in the window after its last probe (up to `livenessInterval`) and never runs for a worker without `busy_seconds`. `verifyAfterResponse` makes one synchronous `/health` probe after each successful response on a request with a comparable frozen identity and judges it with `swappedTo`; a mismatch withholds it as a swap. An unreadable probe withholds the answer too (`WorkerSwappedError.Unverified`): nothing says it came from the frozen machine, the cost is a re-send elsewhere, and accepting would risk a strike or transcript under a machine that never saw the file; it is the rule `regate` applies to a port it cannot read. The probe ignores the op's cancellation (bounded by `healthProbeTimeout`) so a cancelled op does not store an unverified answer. Because every chunk is verified at its end, the chunks before the one a swap is caught in are in fact the frozen machine's; they are still withheld, as the TODO entry says ("withhold the whole request's answers"), which keeps the dispatcher, the journal and the entry consistent at the cost of re-decoding them. Rejected: one retry of an unreadable probe. It adds latency to every chunk for a blip the next dispatch absorbs.
10. **Durable fix filed, not built.** The worker echoing `machine_id` in its batch response closes the remaining window (a swap between the response being produced and the probe) because the answer names the machine that produced it. It needs a `whisper_mlx_server.py` change; filed as `todo.d/2026-10-30-whisper-batch-response-echoes-machine-id.md`.

## Residuals

- A swap between the response being produced and the post-response probe, or one that is gone again by then, is not seen. The durable fix is the worker echoing its machine id in the response (todo.d fragment).
- Workers older than whisper_mlx_server.py 1.8.0 (no `busy_seconds`) are not polled during a request; they are checked once, after each response.
- The poll reads the canary memory (`byURL`) and never writes it; a concurrent dispatch's refused probe of the same URL can end the link, so a "u:" can then read as a swap. That costs a re-dispatch of the jobs elsewhere, never a wrong strike.
