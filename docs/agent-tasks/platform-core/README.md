# Workstream — platform core (mediacore extraction, R0–R3)

ABO becomes *app = core + module `books`* in four releases: R0 hotfixes, R1 the core runtime with no user-data
change, R2 the one-way cutover (the dark foundation PRs F2, then the flips F3–F9 and a last runbook PR), and
R3 cleanup with the upgrade floor. The plan, its gates, critical path and risks are in
[`docs/plans/platform-core/implementation-plan.md`](../../plans/platform-core/implementation-plan.md); the
design is `docs/specs/platform-core/` (03 normative, 09 the release plan).

**134 rows: 128 agent tasks (one PR each) and 6 owner checkpoints, in 46 waves.**
By tier: T0 2, T1 11, T2 35, T3 47, T4 33, OWNER 6. By release: R0 6, R1 37, F2 17, F3 8, F4 11, F5 18, F6 5, F7 10, F8 4, F9 5, R2 2, R3 5, OWNER 6.

**Gate (every task):** plan, then execute autonomously in a worktree with its own PR. **OWNER-* rows are NOT
AGENT WORK**: no agent may complete, tick or simulate one; a task that depends on one waits for the owner's
recorded answer.

## Wave legend

`Wnn` is the task's wave. Tasks of one wave run at the same time: each has every dependency merged in an
earlier wave, and no two of them touch the same file (a path ending in `/` is a whole directory). Both are
checked mechanically. A wave's PRs merge one at a time; after each merge the open siblings rebase onto
`main`, which is conflict-free because their files are disjoint. Owner rows sit in the wave where they
become due and have no files. The table of waves, with why each is safe, is §(d) of the plan.

A file several tasks need has one owner per wave; the table below names it. The kernel's wiring files
(`core/kernel/boot.go`, `core/kernel/kernel.go`) and the SDK member files (`core/module/*.go`) are created by
R1-13; from R2 on a dark task adds only its own files, and its stage's wiring task (F2-16) or flip adds the boot
calls, members and mounts. Each F5 conversion task deletes only its own entry file in `tasklint`'s exemption
directory (`internal/books/testdata/tasklint_exempt.d/`, read as one union), so conversion tasks can share a wave. Importer and caller lists were computed at the plan's base commit; a brief re-greps at its own base, and
any further importer it finds is its file too.

## How to run a wave

1. **Check the gate.** Every dependency of the wave's tasks is merged, and every OWNER row they depend on
   is recorded. `git worktree list` shows no live worktree of an earlier wave, and no other open PR of this
   workstream touches a file of the wave. A wave with a move or rename task announces its move window in the
   tracking issue at least one working day ahead and holds feature PRs on the frozen packages until the move
   merges (09 §9.2.10); other feature PRs rebase as usual.
2. **Fix the base.** Fetch `origin/main` and record the base commit; every brief reruns its re-verify greps
   there and stops on a zero-hit edit target or a moved count. Done-check counts are generated at the base
   commit (09 §9.3).
3. **Dispatch.** One worktree and branch per task off fresh `origin/main`:
   `git -C "$REPO" worktree add "$REPO/.worktrees/<slug>" -b <branch> origin/main` with `REPO=<your clone>`,
   then `npm ci --prefix web` (or `make web-deps` once R1-05 has merged). Three or more mechanically similar
   tasks of one wave may run under `/parallel-sweep`, partitioned by their files; it merges only in the mode
   OWNER-01's Q-I answer allows, never with `--admin` past a required check; the F5 conversion groups qualify.
4. **Merge.** Each PR is green on every required check of 09 §9.2.1 on an up-to-date branch, then
   `gh pr merge <n> --rebase` (never squash). Every commit ends with
   `Co-Authored-By: Claude <noreply@anthropic.com>`; 09 defines no release or flip trailer. A flip PR merges
   alone; its siblings rebase after it.
5. **Hand off.** When a release's last task merges, the lead prepares the release-note lines its tables
   give (prepended to the generated notes) and hands off to the release's OWNER row.
6. **Report** with exact counts and the closing lines `COMPLETED: <n> — <list>`, `REMAINING: <n> — <list>`,
   `BLOCKED: <n> — <list>`; a subagent silent for more than 10 minutes is surfaced (CLAUDE.md).

## Repo rules every brief repeats

- Never edit `main` or the primary checkout; one worktree per task (CLAUDE.md "Worktree Discipline"); never
  run `go work init` in a checkout (CLAUDE.md; 03 §3.2 item 1).
- File headers on every created or modified file, version bumped (`.standards/instructions/file-headers.md`);
  `changelog.d/` and `todo.d/` fragments carry no header.
- Conventional commits; `gh pr merge <n> --rebase`; one `changelog.d/` fragment per PR (always allowed, though no row's file list names it); a tracked
  item is checked off in `TODO.md` in the PR that finishes it.
- The plan's §(n) execution rules apply to every task: the brief is the approved plan (put `PLAN.md` content
  in the PR body); T4 and flip PRs get an independent review before merge; executive summaries and TODO
  check-offs go in the release-closing PRs; coined names go in `seams.d/<ID>.md`; a path added to a file list
  is added to `docs/plans/platform-core/tools/inventory.json` and the checker re-run first.
- CLAUDE.md concurrency rules for any loop over library-scale collections: a bounded worker pool, disjoint
  shards, and an explicit `Concurrency`/`Parallelism` (`registry.RunItems` is sequential by default).
- Move PRs list their `old ==> new` paths in the description, build at every commit
  (`scripts/ci/check_commits_build.py`), and apply `go fix` to the files they move (04 §2.2).
