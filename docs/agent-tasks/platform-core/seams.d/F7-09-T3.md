# F7-09 T3 seams and coined names

This file lists what F7-09 slice T3 added to `core/integrations`, `core/integrations/ai`, `core/internal/integrationhttp` and `core/storage`, the readings it took, and what F7-09 must do to wire it. T3 ships dark: no production code installs a validator, passes `Options.Probed` or builds a Router.

## Names beyond the spec

| Name | What it is |
|---|---|
| `integrations.SettingsValidator`, `Registry.SetValidator(kind, v)` | A kind's own rule over an instance's settings, installed once per kind. A second install, a nil validator and an invalid kind are `ErrInvalid`. Valid before or after `Load`. |
| `integrations.ImportValidator(reg)` | An `ImporterOption`. The importer runs the kind validator over each imported record. |
| `integrations.Options.Probed func(Ref, Health)` | Called on every probe result, in `observe`, after the `HealthChanged` block. `HealthChanged` still fires only on a status move. |
| `ai.Router.ObserveProbe(ref, h)` | The consumer of `Options.Probed`: a `HealthOK` probe of an ai instance calls `ClearBench`. |
| `ai.RouterOptions.ValidateEndpoints` | Installs `Router.ValidateEndpoint` as the ai kind's validator. Temporary: see the first obligation below. |
| `integrationhttp.ErrHoldChanged` | Deleted. The hold route recognises `providerhttp.ErrHoldChanged` directly, with a compile-time assertion that `*providerhttp.Registry` is a `HoldReleaser`. The route needs no wrapper, and `integrationhttp` declares no sentinel of its own (an alias var is a package-level variable that core's no-mutable-globals guard refuses). The F7-10 seam row that asked F7-09 for a wrapper is updated. |

## Readings taken

- **The validator runs on Put, Test and import; never on the serve path.** A stored row is served whatever a validator would say of it (M1.4 step 2), so installing a validator refuses no existing instance. Put and Test share `shape()`, which now also runs the kind's validator over the effective non-secret layer, after the schema check. A refusal wraps `ErrInvalid` and the validator's own error, so the instance routes answer 422 `validation_failed` and store nothing.
- **An import is judged only when its adapter is registered and of the record's kind.** Otherwise it is kept and reported, as before. The validator is handed the non-secret fields and no stored row. A refusal stages nothing and returns an error wrapping `ErrInvalid`; M6 quarantines on an importer error.
- **`ClearBench` no longer clears a quota bench still in force.** The probe is `GET /v1/models`, which succeeds on a spent balance. A quota bench past its window is cleared, a failure bench is cleared, and a real successful call (`markSuccess`) still ends every bench. A benching failure that lands while a quota bench is in force (a call that was already in flight when the quota answer came back) keeps the bench a quota bench and keeps the later of the two end times, so a probe can never clear a quota bench still in force and the quota window is never shortened. Two known limits remain and are not fixed here: a probe that started before a failure can still clear the failure bench that failure set (`Health.CheckedAt` is the probe's start), and for an endpoint whose `/v1/models` answers while completions fail, every OK probe resets the consecutive-failure run, so the backoff never grows past one `cooldown_base`. A real call that was accepted before the balance ran out and succeeds after a sibling's quota bench ends that bench (`markSuccess`, as 05-ai section 4 step 4 says), costing one wasted request. `Registry.Test` reaches neither `observe` nor `Probed`, so an operator's Test of an endpoint clears no bench unless F7-09 wires it. This is a behaviour change in a shipped function, but nothing in ABO calls `ClearBench` yet (ABO builds no Router before F7-09).
- **The "stored" layer a validator is handed is what the row serves, not the bare stored layer.** It is the stored layer with the operator overlay applied, nil for a create. The ai `capabilities` field can be locked by an operator value (`integrations.ai.<id>.capabilities`: every non-secret field of the adapter's schema can, and the ai adapters carry `capabilities` among the endpoint routing fields). A locked field keeps its stored value in the stored layer, so a tick the operator locks, retired since, would be in no layer the rule reads as already there, and every Put of that instance would be refused with a 422 over a field only the operator can change. Handing the rule the effective previous layer grandfathers a locked tick like a stored one. It does not help a locked wildcard (the rule refuses a wildcard first, so every Put of an instance whose operator-locked ticks include `*` is refused until the operator fixes the config), and a create is still handed nil, so an operator-only instance created over a locked retired tick is refused. `TestKindValidator_StoredIsWhatTheRowServes` (core) and `TestAIInstancePut_OperatorLockedTickIsGrandfathered` (ai) pin both.
- **`Registry.validators` has its own lock (`vmu`).** The ai Router is built from the Registry, so the validator is installed after construction, and the map is read both on the Put path, which already holds `r.mu`, and in `Test`, which does not, so `r.mu` is the wrong guard. `validateImport` still reads the adapter map under `r.mu`, which is frozen after `Load`: an import waits behind a long Put, and a caller holding `r.mu` would deadlock it. Neither happens today (the importer runs before Load, outside a Put); reading a post-Load copy would remove both and is not done here.
- **`specProblems` checks `Spec.Derived`.** Each entry through `DerivedIndex.Validate()`, a name declared twice, and any declaration on a core subsystem (`DB.Derived` issues handles to modules only). This closes the F7-07 seam that said `specProblems` did not call `Validate` yet. It changes what `Open` accepts: a spec that declared a bad entry used to boot and now fails with a `SpecError`. No spec in the repo declares one (the three declarations are on module owners with valid entries).

## What F7-09 must do

1. **Delete `RouterOptions.ValidateEndpoints` and make the ai validator unconditional.** The option exists only because installing the validator by default would change what a Put accepts before the flip. It must not outlive the flip: the point of the hook is that nobody has to remember to turn validation on. In the same change, remove the `if opts.ValidateEndpoints` guard in `NewRouter`, delete `withEndpointValidation` from `ai/harness_test.go`, and update `TestNewRouter_ValidationIsOptIn`.
2. **Fix the 7 ai tests that the unconditional validator refuses at `Put`.** They fail for two different reasons, read from the tests, not guessed:
   - Two store a row the rule exists to refuse, and exist to prove the router tolerates such a row. Each must build its row through an importer built without `ImportValidator` (the path for rows that predate the rule), or assert the refusal: `TestRouter_WildcardRejectedOnPut` (a `"*"` tick, router_test.go) and `TestCatalog_UnknownTickKept` (the unregistered `retired.capability`, catalog_test.go).
   - Five Put a capability before it is registered, an ordering slip the old Put never noticed, and only need the registration moved first. `TestRouter_DefaultDenyEmptyTicks` (router_test.go) calls `h.capability("cipher")` after the Put that ticks `gotham.cipher`. The other four (`TestOpenAICompat_ARouterCooldownEndsWithTheHold`, `TestOpenAICompat_HealthProbeEndsAHold`, `TestOpenAICompat_RetryAfterIsHonouredUpToTheRoutersCap`, `TestOpenAICompat_GateAndAdapterAgreeOnQuota`, all in openai_egress_test.go) go through `newRecoveryRig`, which Puts `gotham.riddle` and registers it in the return statement; registering it before the Put fixes all four at once.
3. **Wire `Options.Probed` with a closure.** `Router.ObserveProbe` needs the Router and the Router needs the Registry, so `integrations.New(Options{Probed: func(ref, h) { router.ObserveProbe(ref, h) }})` with `router` assigned after `NewRouter` (guard the nil window, or install it under a mutex).
   **Owner decision needed before wiring it: three limits of `ObserveProbe` go live with it** (details under "Readings taken", `ClearBench`). (a) A probe that started before a failure can still clear the failure bench that failure set. (b) A probe that answers OK ends the failure bench outright and resets the consecutive-failure run, so for an endpoint whose `/v1/models` answers while completions fail, the backoff ladder restarts (30s, 1m, ... up to the 5m cap) after every probe. The cost is about one failed attempt per OK probe, each a wasted request plus failover latency on a user call, and a restarted ladder instead of one that climbs to the cap; the probe interval is F7-09's choice, so the multiplier is too. (c) A real success that was accepted before the balance ran out ends a sibling's fresh quota bench (one wasted request, as 05-ai section 4 step 4 specifies). Options: keep the run count on a probe (`clearTransient` stops resetting `consecFails`; about 2 lines and a changed `TestRouter_ClearBenchLeavesQuotaBench`), which shortens the cycle but leaves one failed attempt per OK probe; compare a bench-set time with `Health.CheckedAt` (fixes only (a)); or have `ObserveProbe` decline to clear a long failure run, the only option that stops the per-probe retry.
4. **Build the M6 importer with `ImportValidator(reg)`, after two preconditions hold.** The validator is looked up when a record is imported, not when the importer is built, so the order of construction does not matter, but before M6 imports its first ai record: (a) `NewRouter` has run (or that record is judged by nothing), (b) **every module has registered its AI capabilities** (`Router.RegisterCapability`), or the catalog is frozen (`FreezeCatalog`). `ValidateEndpoint` refuses every tick the catalog does not know and the stored row does not carry, and an import has no stored row, so an import that runs before the modules register refuses every ticked ai record and M6 quarantines every ai endpoint. And (c) **the Registry has its ai adapters registered** (`Register` before `Load`): `validateImport` silently skips a record whose adapter is not registered, so a missing adapter makes the records go in unjudged, which would hide the omission.
5. **Keep `Options.Probed` cheap.** It fires on every probe, not only on a status move; `ObserveProbe` is one map lookup under the bench mutex.

## Production data the flip has to survive

Can production store a retired or wildcard tick through `Put` today? Not through the HEAD write path: `config.validateAIEndpoints` (`internal/config/ai_endpoints.go`, called from `update_service.go` on a PUT that carries `ai_endpoints`) refuses a wildcard (`"wildcard ... is not allowed"`) and an unknown capability (`"unknown capability ..."`). It runs only on a PUT that carries the key, on purpose: the comment on it says rows stored by a newer binary, with capability IDs this one does not know, must not block an unrelated save, and `AIEndpoint.UnknownCapabilities` exists to report them. So an `ai_endpoints` row can still hold an unknown tick when it was written by a newer or different binary, by a capability retired after the row was stored, or by any path that skips the PUT (a config file, a restore). A wildcard can only arrive that way. HEAD concurrency 0 is valid ("0 means 1") and M6 already maps it with `max(ep.Concurrency, 1)`.

I could not read the production rows (no prod access in this task), so this is from the code, not a count. What it means for the flip:

- **M6 would quarantine a whole endpoint for one retired tick.** `ImportValidator` makes the importer refuse the record, and M6 quarantines the member on an importer error. The ai validator refuses an unknown or wildcard tick. HEAD's rule for the same row is "selection ignores it and the status API reports it", and the spec says unknown ticks are kept and ignored. So an endpoint with `["gotham.riddle", "retired.capability"]` serves at HEAD and would be quarantined after the flip, taking its known capabilities with it.
- **Needed before the flip, one of:** (a) M6 drops the unknown and wildcard ticks from `settings["capabilities"]` before building the record and reports each dropped tick in its migration report (the tick is ignored at HEAD anyway, so nothing that served stops serving), or (b) the ai validator, when called for an import, accepts unknown ticks and only refuses wildcards. (a) keeps the Put rule strict and the stored rows clean, and is the recommendation. Either needs a census first: a dry run of M6 over the production `ai_endpoints` listing every tick `UnknownCapabilities` reports and every `*`, and every operator-sourced ai `capabilities` value (an `integrations.ai.<id>.capabilities` overlay holding `*` or an unknown tick blocks every Put of that instance, disabling it and rotating its key included, until the config is edited). That dry run is the owner-side gate for this flip; it must not be skipped because the unit tests pass.
- **A row that is already in the registry (imported before the validator existed, or by an importer without the option) is served as it is, and a retired tick it carries is kept by every later Put.** The serve path never validates. The rule accepts a tick the catalog does not know when the stored row already carries it (`ValidateEndpoint` is handed the stored layer), so a Put of such a row is accepted and the retired tick stays. Only a wildcard (checked first), a concurrency below 1, a bad locality or an unknown feature is refused on that Put. An import has no stored row, so the same retired tick is refused at import (and quarantined by M6) and grandfathered on every later Put. A wildcard is refused on both. `TestAIEndpoint_RetiredTickKeptOnPutRefusedOnImport` pins the asymmetry. F7-09 decides whether an import should get a grandfathering rule too, which is recommendation (b) above in other words.
