# F5-03 seams and coined names

F5-03 adds four core task kinds and one books kind, all dark: `core.storage.compact` and `core.storage.census` (new package `core/internal/storagetasks`), `core.tasks.prune` (`core/internal/executor/prune.go`), `core.log.journal.prune` (`core/internal/logjournal/prune.go`) and `books.maintenance.aux-store-compact` (`internal/plugins/maintenance/db.go`). Nothing registers them: F5-18 does. HEAD's `maintenance.db-optimize` keeps its behaviour and now shares its steps 2 and 3 with the books kind.

## Review fix: journal retention overflow

The automated security review flagged `cutoff := now.Add(-time.Duration(s.RetentionDays) * day)` in `core/internal/logjournal/prune.go`: a `retention_days` past about 106,000 overflows `time.Duration`, and a wrapped cutoff in the future deletes the whole journal. Fixed in the same PR: the cutoff is `now.AddDate(0, 0, -days)` (as HEAD's `PruneOldLogs` computes it), the task refuses a retention outside 1 to `MaxRetentionDays` and a cutoff that is not strictly before now (`ErrRetentionOutOfRange`, nothing deleted), and `Settings.RetentionDays` carries `maximum=36500` in its schema tag (`TestSettings_RetentionDaysSchemaMaximumMatchesTheTask` pins the tag to the constant). A zero or negative retention keeps everything, as the brief says of zero. `core.tasks.prune` does `now.Add(-keep)` with a positive duration, which cannot wrap (a duration is at most about 292 years), and `TestPrune_HugeRetentionNeverYieldsAFutureCutoff` pins it.

The line was not ported from HEAD. HEAD's `PruneOldLogs` (`internal/logger/retention.go`) uses `AddDate`, but it has a different gap: no upper bound on `log_retention_days`, and at 1<<60 days `AddDate` returns a cutoff equal to now (at `math.MaxInt` the day after), so the purge would delete everything. That file is outside this row's set, so it is filed as `todo.d/2026-11-18-log-retention-days-no-upper-bound.md`.
