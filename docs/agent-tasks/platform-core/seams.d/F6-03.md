# F6-03 seams and coined names (slice E6a: the task topic specs)

E6a declares the three `core.task.*` catalog entries in `core/tasks/topics.go` and lists them in `kernel.coreTopics()`. It is dark: nothing declares the core catalog until F4-08 wires `declareCore`, and nothing publishes the topics until the executor does (the publisher half, E6b, belongs to F5-18).

## What the specs fix and what E6a chose

- Names, permission and channel are the 05-events §5E.3.1 table rows: `core.task.run-changed.v1` (bus, `Realtime{Coalesce}`, `Redact = tasks.RunViewRedactor()`), `core.task.log-appended.v1` (bus, `Realtime`), `core.task.finished.v1` (bus plus `Notify`, "as run-changed"). All three are `AnyAuthenticated` and bus only. Payload of run-changed and finished is `tasks.RunPayload`, the wire form of a `RunView` (the terminal view for finished, the value `Options.OnTerminal` receives, 05-tasks §5T.4), see below; payload of log-appended is "log line" (05-realtime §4.7), see `LogAppended` below. Every envelope is keyed by the run ID.
- `tasks.RunPayload` (new; lower-case JSON tags, `mode` as a word, built only by `tasks.NewRunPayload(RunView)`) is the run-changed and finished payload. Round-1 review M1: `RunView` has no JSON tags, so publishing it directly would put PascalCase keys and a numeric `Mode` on the stream while `GET /runs/{id}` serves lower-case keys and a string mode. `RunView` stays untagged (`RunRecord` embeds it and its stored rows decode through it, so a tag would rename on-disk keys). `taskhttp`'s `runDTO` and `actorDTO` are now aliases of `tasks.RunPayload` and `tasks.ActorPayload`, so the REST body and the stream payload are one type; `TestGetRun_SameJSONAsTheTopicPayload` pins that a `RunView` marshals to the same JSON both ways (after the topic's own `Redact`). The keys are exactly the ones #4813's `web/src/services/coreEvents/types.ts` declares for `core.task.run-changed.v1` (`id`, `kind`, `state`, `done`, `total`, `current`), so that client needs no change. 05-tasks §5T.3 documents `RunPayload`, `NewRunPayload` and `RedactRunPayload`.
- `tasks.LogAppended` (new, lower-case JSON tags, `fields` omitted when empty, as `GET /runs/{id}/log` spells a line) is the log-appended payload, with `tasks.NewLogAppended(LogLine)`. It is not `LogLine` because that type has no JSON tags and a line with no Fields marshals `"Fields":null`, which the reflected schema refuses, so the bus would drop the common line. `LogLine`'s stored shape cannot take tags without changing the keys on disk. Coordinator ruling 2026-11-20: accepted.

## Coordinator rulings, 2026-11-20

1. **Log redaction rule (accepted as conservative).** `tasks.RedactLogAppended(who, line)` blanks `Message` and every `Fields` value unless `who` holds `core:users.view`; `At`, `Level` and the `Fields` keys survive. It is the `Redact` of `core.task.log-appended.v1` (via `tasks.LogAppendedRedactor()`) and the same function `taskhttp`'s `GET /runs/{id}/log` now applies per line, so the stream and REST agree. This reads 05-tasks §5T.3.10 `Client.Log` ("each line redacted by RedactRunView's rule"); the spec names no field list, so the rule is the coordinator's.
2. **Visible fails closed.** `declareCore` has no access to the definition registry (`coreTopics()` takes no arguments), so each spec carries `Visible = visibleToAdmins`: only a holder of `core:admin` (`rbac.CoreAdmin`, the "Perms.View or admin" of the ruling) sees a task envelope; a plain signed-in user, a holder of `core:system.manage` alone and a nil checker see none. Round-1 review M2: the first cut gated on `core:system.manage`, which is assignable to a custom role, so a forgotten swap would have shown every run to such a role; `core:admin` is the superuser scope. **F4-08 / the executor wiring must replace `Visible` on each returned spec with the definition's `Perms.View` rule** (COR-20: for run-changed and finished, decode the `RunPayload` and look up its `kind`; for log-appended, look up the run from the envelope key). Forgetting hides the stream; it never exposes it. `TestTaskTopics_VisibleFailsClosed` pins the default.
3. **Coalesce window.** `runChangedCoalesce` = 250 ms (named constant in `topics.go`), the window `books.book.changed.v1` uses (05-realtime §4.7); 05-events §5E.3.1 says only "`Realtime{Coalesce}`". Coalescing keeps the latest envelope per key, so the terminal view wins.

## Hand-offs

- **`Visible` covers realtime only (round-1 m2).** Notify rules (`notify/rule.go:143-150`) check the topic's `Permission` only, never `Visible`, so `core.task.finished.v1`'s `Visible` gates nothing that a notify rule delivers: a rule on it reaches every authenticated rule owner whatever the run's kind View rule says. Closing that gap belongs to the `OnTerminal` wiring (F5-18 / F4-08): either the notify side consults the definition's View rule for the run, or the finished topic's `Permission` is narrowed there. E6a does not claim finished is access-controlled beyond realtime.
- **Exclude 400 (round-1 m3).** The `exclude` 400 that #4813's `manager.ts` and `manager.test.ts` attribute to F5-18 is resolved by F4-08's `declareCore` wiring (the declaration that makes the catalog real), not by F5-18. E6a registers the specs in `coreTopics()`; #4813's branch is untouched.
- **Redaction placement (round-1 m1, follow-up, out of scope here).** 05-tasks §5T.3.10 puts the log redaction inside `Client.Log` ("each line redacted by RedactRunView's rule"); today `executor.Log` (`core/tasks/control.go`) yields raw lines and `taskhttp.getLog` applies `RedactLogAppended`, so a second caller of `Client.Log` must redact too. Follow-up: move `RedactLogAppended` into `Client.Log` and make `getLog` a plain serialiser.
- F5-18 / E6b: publish with `events.Publish(scope, ctx, tasks.RunChangedTopic(), string(runID), tasks.NewRunPayload(view))` (and the log and finished equivalents) after each run commit; use `tasks.NewLogAppended` for the log line. A `RunView` or `LogLine` payload is refused by type.
- F6-03 flip: rerun the run-redaction and `TestHub_TaskTopicVisibleWithoutTasksView`-shaped cells over these real topics once `Visible` is the definition rule (F6-02 hand-off).
