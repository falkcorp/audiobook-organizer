# F6-03 seams and coined names

What the F6-03 server pre-slice (#4795, dark) added, the readings it took, and what the F6-03 flip must know. The pre-slice stages `books.book.relocated.v1` and adds the Deluge consumer. Nothing installs the outbox writer, declares the topic or registers the consumer before the flip.

## Shape

- `internal/books/store/book_relocated_outbox.go` declares the topic: `books.book.relocated.v1`, payload `{book_id, from_path, to_path}`, keyed by book, 16 partitions, `books:view`. `PebbleStore.SetRelocationOutbox(w)` switches staging on, and the store has one writer. The topic lives in the store package, not `internal/books/topics`.
- Staging happens in `updateBookLockedMode`'s `FilePath`-change branch, in the batch that writes the path and under the per-book stripe, so stage order is commit order per book. A refused stage refuses the move. A raw pebble batch is refused (`errRelocationNeedsCoreBatch`), so books must be on core storage before the flip calls `SetRelocationOutbox`.
- **No event when the old path is empty.** A book getting its first path is a create, not a relocation, and staging it would start a path-update run for every newly imported book. There is also no event when the path is unchanged or the new path is empty (a retire or detach). A side effect: path → "" → path emits nothing.
- `internal/plugins/deluge/relocation_consumer.go`: `RelocationConsumer` (`books.deluge.book-relocated`) is a `ConsumeIntoTask` that starts one Live `books.deluge.path-update` run, carrying the book ID only. `path-update` dedupes by book: a new start folds only into a queued run for the same book, never into a running one.

## What the consumer replaces (round 1, M1)

**It replaces only `NotifyDelugeAfterOrganize`.** The version-swap and import moves are not replaced and stay in-process until the flip designs their events:

- **Version swap.** The swap moves the from-version to `.versions/<id>`. `pathUpdateCore` skips any version that is not Active (`path_update.go`), so a relocation event would not move that torrent. A same-path swap returns `ErrSkipBookWrite`, so it writes no book row and stages nothing. The event is staged in `swap.go` before finalization.
- **Import.** An import is not a create of `Book.FilePath`. It is `UpdateBookFile` plus `bookFile.DelugeHash`, and no caller writes `Book.FilePath`, so the book update path never sees it.

The flip has two options: keep both moves in-process, or stage events from the version-status and `book_file` writes and teach path-update about Alt slots and `DelugeHash`.

## Queued for the flip (round 1 minors)

- m1: the flip makes `pathUpdateNative` `ResumeFromZero` plus a retryable `MoveStorage` error, pinned by the `kinds_test` parity test.
- m2: `from_path` and `to_path` in the payload are unused by the consumer. Drop them, or document why they stay.
- m3: path → "" → path emits nothing.
- m4: `stageFold` decodes O(N²) times on a bulk organize.
- m5: `TestRelocationFollowUpDurable` must pin Live. The `consumer_preview` mutant cannot be killed before the flip, because the run mode is only visible once the relay delivers through the core executor.
- Pre-existing: `createBook` with an existing ID overwrites the row without a guard.

## Left for the flip

`SetRelocationOutbox`, the topic declaration (F4-08's `Registrar.Topics`), the outbox owner in storage owners, consumer registration (`Manifest.OutboxConsumers`, `Registrar.OutboxHandler`, `Deps.Outbox`), deleting `NotifyDelugeAfterOrganize` and the `handleBookRelocated` placeholder in `path_update.go`, and `TestRelocationFollowUpDurable`.
