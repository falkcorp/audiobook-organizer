# R1-16 seams and coined names

This file lists what the sdnotify PR added beyond the brief and 05-health §5H.3.4, §5H.10 and 06 §6.4.5: names the spec does not have, readings it took where the spec or brief is silent, the risks it leaves, and the seams later rows (R1-23, R1-28, F2, F8) build on.

old ==> new: `internal/sdnotify` ==> `github.com/falkcorp/mediacore/internal/sdnotify` (core-internal).

## Names beyond the spec

| Name | What it is |
|---|---|
| `lifecycle.NotifySocketEnv` | `"NOTIFY_SOCKET"`. It replaces HEAD's `sdnotify.SocketEnv`, which is deleted (one source). The registry's child-environment scrub and core's notifier both read it. |
| `app.FastExit(args, stdout) (handled bool, err error)` | The brief's "app serves `--print-capabilities`". It answers the one flag when `args` is exactly `[prog, "--print-capabilities"]`, and prints `sd_notify` plus a newline, byte-identical to HEAD. `main` calls it after `--print-storage-format` and before cobra. A write error is returned so `main` exits 1. The flag is core's, so another host binary gets it for free. |
| `kernel.systemdNotifier` | `Config.Notifier`'s default (the no-op notifier is deleted). Stateless: each call is one datagram on its own connection, so `Run`'s goroutine and the hooks' `ExtendStart` never contend. |
| `statusServing`, `statusStopping` | HEAD's two `STATUS=` lines, byte for byte, now sent by the kernel: after `READY=1` at start step 8 and after `STOPPING=1` at the first stop step. `TestSupervisor_DefaultNotifierSpeaksSystemd` pins the bytes. |
| `kernel.startWindow`, `startCtx` | The hook start window (below). `startWin` is a `Kernel` field. |
| `Config.ExtendStart` (meaning changed) | It now replaces only the service-manager half of `Deps.ExtendStart` (tests). The window extension always happens. nil sends `EXTEND_TIMEOUT_USEC` over `NOTIFY_SOCKET`, but only when the window was extended or the call precedes `Run` (Register time): never after READY or during stop, where systemd would push `TimeoutStopSec` out. |
| `database.SetStartExtender(func(step string))` | How `serve` hands the store `app.ExtendStart` (`cmd.injectStartExtender`, called before `initializeStore`). It is a package-level atomic, because the store opens before `app.New` until R1-23 and `InitializeStore` has no options. **R1-23 deletes it** when the store opens inside the App. Every other command, child mode and every test run without one, so they send nothing. |
| `search.IndexService.SetStartExtender`, `server.Server.SetStartExtender` | The injected `func(step string)`. `books.Register` calls the server's, which reaches the service through the container. books passes `Deps.ExtendStart`, and its start hook calls it once more up front. `search` imports no `module` (MOD4-18). |

## Readings and decisions

| Topic | Reading |
|---|---|
| The R1-15 risk "60 s hook start timeout" | Closed here. The kernel abandoned a hook's `Start` at `startTimeout` whatever the hook did, and `Deps.ExtendStart` was a no-op. Now each hook's `Start` runs in a window that its own module's `Deps.ExtendStart` moves to at least `StartupStepBudget` (10 min) from the call, never earlier. Another module's call, and a call outside a `Start`, change nothing (and send nothing to systemd once `Run` has begun). A hung step is still abandoned once its own budget runs out: no ticker, as in HEAD. books' start hook calls it first, before `StartHook`'s steps (HEAD ran them under the unit's `TimeoutStartSec=300`, the kernel's initial window is 60 s), and the search-index step calls it again before its long open. So books' whole start has 10 minutes from the hook's start, and the index open gets a fresh 10 from its own call. |
| Hook ctx | A context's deadline cannot move, so the hook's ctx has none. The window cancels it with the cause `DeadlineExceeded` and `startCtx.Err()` reports `DeadlineExceeded`, as a deadline context does, so a `Start` that returns `ctx.Err()` returns what it always did. `ctx.Deadline()` now reports none. A child made with `context.WithTimeout(ctx, ...)` sees `Canceled` with cause `DeadlineExceeded` when the window closes. |
| Window owner | Keyed by module ID. Hooks start one at a time, so one window serves the boot. |
| READY and STOPPING order | HEAD sent `READY=1` from the server's `afterListen`, after the bind, concurrently with serving. The kernel sends it after `Listen` returns and `Serve` is launched, which is the same instant. HEAD sent `STOPPING=1` first in `beforeDrain`. The kernel sends it first in `stop`, before the drain and before the scheduler stops. `TestComposedApp_SystemdSignals` runs the composed App and pins the order and the two extensions (books' start, the search-index open) before `READY=1`. |
| `STATUS=starting` | `Run` already sent it (R1-13). HEAD did not. It is the only new datagram. |
| Child-env scrub | Kept. No child path sends a datagram now (only `serve` injects the extender), so the scrub is defence in depth. Its comment says so. |
| Tests that moved | `internal/server`'s `TestStartNotifyReadyAfterBindAndStoppingOnShutdown` and the socket half of `TestStartListenFailureFailsStartWithoutReady` asserted the server's own sends. They moved to `core/kernel` (`TestSupervisor_*`, including `TestSupervisor_NoReadyWhenListenerFails`) and to `books`. `TestStartListenFailureFailsStart` keeps the bind-error half. The `search` and `database` extension tests assert the injected func instead of a datagram. |
| core tests are standard library only | The moved `sdnotify_test.go` used testify. The move commit kept its call sites through a shim so it stays a 90 %+ rename, and the next commit rewrote it and deleted the shim. |

## Risks

| Risk | Cost of the fix |
|---|---|
| **A start step that runs longer than 10 minutes between two `ExtendStart` calls** is abandoned by the kernel (and by systemd). HEAD was bounded the same way: `TimeoutStartSec`, then 10 minutes per extension. Nothing here measures prod's start; the 130-200 s warmup is after readiness. | If a prod measurement shows a step near 10 minutes, add an `ExtendStart` call inside it. |
| **`EXTEND_TIMEOUT_USEC` is sent only by `serve`'s injected extender and books' start hook and search step.** A future slow step must call `Deps.ExtendStart` (modules) or `app.ExtendStart` (before `New`) itself. | None; this is HEAD's rule. |
