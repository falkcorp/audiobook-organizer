# F2-01 seams and coined names

This file lists what the `core/tasks` public API PR added beyond the Go blocks of 05-tasks §5T.3.1–§5T.3.13, the readings it took where the spec or the brief is silent, and the seams later rows build on. Everything not listed here follows the spec as written.

## Names beyond the spec

| Name | What it is |
|---|---|
| `tasks.NewRC(h RunHost) *RC`, `tasks.RunHost` | Builds a run context over the exported `RunHost` interface. It is not app-facing: a test double implements it by embedding `taskstest.FakeRun`, because it may grow methods in any release. Its methods are (`Context`, `RunID`, `Kind`, `Mode`, `Trigger`, `Actor`, `Log`, `Writer`, `Resumed`, `Deadline`, `ShouldYield`, `Phase`, `Checkpoint`, `Restore`, `ReportProgress`, `Note`, `Touch`, `Enqueue`, `Await`, `StandDown`, `LockRefs`, `Lane`, `CapWorkers`, `AwaitUnpaused`, `AcquireCPU`, `RenewHold`, `ItemsProgress`). ## Readings

| Topic | Reading |
|---|---|
| Nil run context | `RunItems`/`RunSeq`/`ForEach` with a nil `*RC` return `*ItemsError` wrapping `ErrNoRunContext`; `LockRefs` on a context without a host returns `ErrNoRunContext`. |
| Options | More than one `ItemsOptions` value is refused. |
| `RunSeq` watermark | Needs a `Key`; the keyed watermark `{n, key}` verifies order on resume. |
| Watermark persist error | Stops the loop and is recorded in `Errs` with `FirstIndex` -1; the host decides fatality per `ResumePolicy`. |
| Resumed items | Counted in `Done`. The checkpoint is absolute (`ProgressBase` + prefix). A resumed `RunItems` skips, and a resumed `RunSeq` drains, `N - ProgressBase` items of this call's input. |
| Gate errors | When `AwaitUnpaused`, `LockRefs` or `AcquireCPU` returns an error while the loop's context is live, the item fails (`Failed`, `FirstIndex` = the item) and the loop stops in both error modes, because the run's gate is broken. With the context done, the item is only `NotStarted`. |
| Panics | A panic in `fn`, `Label`, `Key` or `ExclusiveRefs` fails that item with `fmt.Errorf("tasks: <what>: %w", *PanicError)`. `PanicError{Value, Stack}` gives a one-line `Error()` ("panic: <value>") and `Unwrap()` when `Value` is an error. Inside a run the stack is logged once through the run's logger at Error level. The innermost loop with a run logs it and marks the `PanicError` logged (an unexported flag), so an enclosing loop that sees it again does not log it. A plain `ForEach` has no run logger and leaves the logging to the enclosing run's loop. The loop carries on per `OnError`. |
| `ItemsError.Cause` | Set when the run's end changed the outcome: items were left `NotStarted`, a stream was not drained, or an item failed after the run's context ended. That last case is recorded in `complete()` at the moment the item fails, so a shutdown with every item in flight still reports `ErrShutdown`. An item that failed on its own before the cancel gets no Cause, and a loop whose items all succeeded returns no error even if the run was cancelled afterwards. |
| Definitions own their `Common` | `newSpec` and `CommonOf` deep-copy `Schedule`, `Approval`, `Debounce`, `NotWhile`, `Ready` and `Lanes`. Each `*Schedule` builder returns a changed copy, so one base schedule can seed a Live and a Preview definition. |
| `BatchSpec.OnItemError` | It is a `BatchErrorPolicy`, a type of its own (05-tasks v1.15.0): the zero value `BatchContinue` counts the item failed and goes on (v3 `Continue`), and `BatchStop` must be stated. `ErrorMode`'s zero value stays `FailFast` for `ItemsOptions.OnError`. |
| `FromParam` in `RunItems` | Without run params it resolves to its default. |
| Constructor problems | Include a scheduled writer with neither Live nor Preview, and one with both. |
| Left to the kernel (F2-16) | Module prefix of the kind, view-class scope, `Every` outside the relay, `PrioritySystem` on a module kind, undeclared exclusive keys and resources. |
| ABO citations | Doc comments cite HEAD's v2 registry and v3 ops files by file name only, so `grep 'internal/operations\|pkg/ops' core/tasks/` stays 0. |
| `ErrShutdown` | Re-exports `lifecycle.ErrShutdown` under `//archtest:allow-var`. |
| Interface width | `Client`, `Executor`, `RunStore` and `runHost` carry `//nolint:interfacebloat` with the reason: their method sets are the spec's. |

## Seams for later rows

- **F2-03 (executor):** the constructors do not store type-erased runners in the `Definition`. F2-03 must add unexported closures in `Task`, `Batch` and `Fixer` that run the typed spec, and build the `ItemRC` for the Batch runner. The executor-backed tests the brief lists (`TestRunItems_WatermarkResume`, `TestRunItems_CPUBudgetShared`, `TestRunItems_PauseParksBeforeItemClock`, `TestForEach_JoinsRunBudgetWhenCtxFromRC`, `TestExclusiveRefs_*`, `TestLockRefs_*`, `TestParallelismCap_LowersDeclared`) and `Conformance`'s runtime assertions (preview writes nothing, no write after the fence, crash and resume at least once) join there.
- **F2-03 (nested CPU slots):** a `CPU()` item's context carries an unexported mark saying it holds a `core.tasks.cpu_slots` slot. A `CPU()` `ForEach`/`RunItems` whose context carries the mark runs on the inherited slot with one worker. A marked nested loop does not call `AcquireCPU`, so the executor's semaphore needs no special handling.
- **F2-03 (nested ref locks, revised by the F2-01 follow-up):**
  - An item that took `ExclusiveRefs` carries, in its context, its refs and one lock table of its own (one per item, not per loop).
  - Every nested lock under the item is taken in that table: a nested loop's `ExclusiveRefs`, `ic.LockRefs` and `tasks.LockRefs`. So two nested loops, or two goroutines of one item, never hold the same ref at once.
  - A nested request may name only refs the item holds or that a held ref covers. A ref that overlaps a held one without being covered by it is refused with `ErrHeldOverlap`; any other ref with `ErrNestedLockNotHeld`. It fails closed because locks taken in stages (A holds X and waits for Y, while B holds Y and waits for X) deadlock.
  - The item's table is not re-entrant.
  - A nested item's own hold replaces its parent's, so a nested item's nested locks may name only that nested item's refs.
  - The result for F2-03: the executor's lock table only ever sees top-level item locks and `RC.LockRefs`/`ic.LockRefs` calls outside any hold, all taken at once. It needs no re-entrancy and no owner tracking.
- **F2-03 / F2-17 (lock rule for kinds):** an item must declare every ref it will ever need in its own `ExclusiveRefs`. The F5 conversions must follow this; a v3 batch that locked more refs inside an item now gets `ErrNestedLockNotHeld`. F2-17's tasklint should flag two call shapes: `rc.LockRefs` inside a `RunItems`/`RunSeq`/`ForEach` callback, which waits on the item's own refs (`RC.LockRefs`'s doc says to use `ic.LockRefs`), and a nested loop or `ic.LockRefs` naming a ref not in the enclosing `ExclusiveRefs`.
- **F2-03 / F2-17 (one `LockRefs` call per item, second follow-up):**
  - Every item now has a lock state in its context (`itemHold`), whether or not it declared `ExclusiveRefs`. It records the item's one outstanding `ic.LockRefs` / `tasks.LockRefs` call, reserved before the lock is taken.
  - A second call while the first is held, or still waiting, is refused with `ErrLockAlreadyHeld`, from any goroutine of the item.
  - While that call's refs are held, a nested loop may lock only refs the call covers. They are locked in the item's table, so nested items exclude each other. Anything else gets `ErrNestedLockNotHeld`.
  - Release-then-relock works, and the release function is idempotent.
  - What this costs: two goroutines of one item can no longer each hold an `ic.LockRefs` lock at the same time; the second is refused, depending on timing. Concurrent work inside an item that needs its own locks belongs in a nested loop, whose items each get one call.
  - The executor's lock table still sees only all-at-once requests. F2-03 needs nothing new.
  - F2-17's tasklint should flag a second `ic.LockRefs` / `tasks.LockRefs` in one item callback while the first release has not run (lock X, then lock Y without releasing X), and `ic.LockRefs` called from goroutines an item starts.
  - One self-wait remains, documented rather than refused: an item with `ExclusiveRefs` that holds X through `ic.LockRefs` and then, in the same goroutine, runs a nested loop on X waits on itself. That is the item's table acting as a mutex. It is a tasklint candidate too.
- **Mark lifetime (CPU and refs):** both marks live on in every context derived from the item's. A goroutine an item starts and leaves running after the item returns would still claim the slot or refs the item has released. Goroutines must not outlive their item. F2-17's tasklint is where that rule can be checked. Only a loop given the item's context (`ic.Context()`) sees the mark; a nested `RunItems` over the outer `*RC` would still wait for a second slot. F2-17's `tasklint` could flag that call shape. A non-blocking try-acquire of extra slots for a nested loop is allowed but not built.
- **F2-03 (Batch `OnItemError`):** the Batch runner passes `s.OnItemError.itemsMode()` as the item loop's `ItemsOptions.OnError`: `BatchContinue` (and the zero value) maps to `Collect`, `BatchStop` to `FailFast`. The helper is unexported because the runner closures F2-03 adds live in package `tasks`; `TestBatchErrorPolicy_ItemsMode` pins the mapping. There is no special case for an unset field. A v3 `Stop` migrates to `BatchStop`; the only v3 user is `internal/operations/registry/batch_runner_test.go`.
- **Later row (actor naming):** `tasks.Actor.AuthMethod` and `audit.Actor.Method` name the same `auth.Method` value differently. The row that first maps a run's actor into an audit record should reconcile the two names. `tasks.Actor` is coined here; 05-tasks has no Go block for Actor.
- **F2-02:** the store records above are the shapes `NativeStores` persists.
- **F2-09:** `tasksKindDial` can be replaced by `tasks.KindDial`.
- **Spec-block harness (`core/examples/hello/specblocks_test.go`):** once `core/tasks` exists the hello blocks wait on identifiers, not packages. The harness now compiles with `-gcflags=-e`, classifies each error line as a missing core identifier (three patterns: `undefined: pkg.X`, unknown struct-literal field, missing method/field on a core type) or a real error, and pins the exact missing set. The rows that add `config.Handle`, `ui.Bundle`, `module.Manifest.{Permissions,Settings,TaskLedger}`, `module.Registrar.{Resources,Tasks}` and `module.Setting/Settings/SettingsSection` must shrink that pin in their own PR; when it is empty the blocks compile and boot. The pin names each identifier's owner: `config.Handle` F3-01, `ui.Bundle` F9-03, `Manifest.TaskLedger` and `Registrar.Resources` F2-16/F5-18, `Registrar.Tasks` F2-17. Five have no owner (`module.Setting`, `module.Settings`, `module.SettingsSection`, `Manifest.Permissions`, `Manifest.Settings`); a todo.d fragment tracks them. Only existing core packages count as "core": a name missing from a snapshot package (another spec block) is a compile error, not a wait. A missing identifier never hides an independent compile error. An error downstream of a missing type surfaces in the row that lands the type.
