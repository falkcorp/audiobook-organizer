# F8-04 A2 (journal trim) seams and coined names

A2 is the revocation journal's retention: a trim function `Options.PruneJournal` can call, in `core/backup/journal`. It is dark. Nothing calls `File.Trim` or `Component.Trim`, no boot binds the journal until F4-08, and no running binary changes.

## Overlap with other rows (read before touching `core/backup/journal`)

A2 writes into the package that two other rows also change. The brief for A2 asks the F4-08 lead first; a builder cannot, so the overlap is stated here and in the PR body for the coordinator to sequence.

## Names beyond the spec

| Name | What it is |
|---|---|
| `journal.File.Trim(ctx, seq) (TrimResult, error)` | Drops the lines at or below `seq`. It rewrites the journal to `<path>.trimming` and renames it over the journal. |
| `journal.Component.Trim`, `journal.ErrTrimRefused` | The bound journal's trim. It refuses while the component is held or frozen (a restore is in flight) and before `Bind` (`ErrNotBound`); a broken file answers with its own error, as `Append` does. |
| `journal.TrimResult{Requested, Base, Dropped, Kept, Limit}`, `journal.TrimLimit` | What a trim did, and what held it back (`tail`, `head`, `unapplied`, `gap`, `restore`, or none). |
| `Header.ChainBase` (wire `chain_base`, omitted when false) | A header that chains its first line from `base_mac` instead of its own mac. See Decisions 1. |
| `journal.LabelTrimClear`, `LabelTrimCopy`, `LabelTrimRename`, `LabelTrimDirSync`, `LabelTrimCleanup` | Five writer labels, so `FSLabels()` is 25. One writer-table row, `Unbound` until F4-08 and G2. |
| `memFS` lock follows the file through a rename (`core/internal/journalfs`) | The trim locks its temporary file, then renames it over the journal it also holds locked. The adapter's lock was keyed by path, which cannot model that. It now belongs to the open file, as `flock(2)` does (`TestMemFS_LockFollowsARename`). |

## Decisions

1. **Kept lines are not re-signed.** `journal_head` names a line by `(seq, mac)`, the unapplied queue and the location file's anchor do the same, and a line's mac depends on the previous line's. Re-signing the kept lines would change every one of those and read as a replaced file at the next open. The trim copies them byte for byte, and the new header names the last dropped line as its base (`base_seq`, `base_mac`), with `chain_base` set so the first kept line verifies against `base_mac`, which is what it was signed with. `chain_base` is part of the header's signed body, so flipping it breaks the chain at the header (`TestTrim_ARewrittenHeaderThatForgesChainBaseDoesNotVerify`).
2. **Older builds fail closed on a trimmed journal.** A build without `chain_base` verifies the first kept line against the header's own mac and reads a break. That is the safe direction, but it makes a trim a one-way step for a binary rollback; the first trim in production happens when G2 binds `PruneJournal`, so the rollback window the owner accepts for that flip covers it.
3. **The cut is the boundary entry.** A trim to `seq` drops the line at `seq` too and keeps it as the base, so `MACAt(seq)` still answers and a restore whose boundary is exactly `seq` is still covered (`Cover`). A restore with a lower boundary is refused ("starts after"), which is retention's contract: `seq` is the smallest boundary any retained archive records.
4. **The cut only ever goes down.** A trim lowers `seq` to the lowest of: the last line, the store's committed `journal_head`, the line before the oldest `journal_unapplied/` entry, the line before a gap line whose `journal_gap/` record is still in the store, and the line before a restore line that is neither hooked (`restore_hooked/<seq>`) nor closed by a `restore_aborted` line. It keeps more than asked and says why in `TrimResult.Limit`. A cut at or below the header's base is a no-op that writes nothing.
5. **A kid stays in use while a kept line carries it.** Kept lines keep the kid they were signed under; the new header is signed under the active kid. After a trim that drops every line of a derive key, that key can be retired and the journal still verifies (`TestTrim_RetiredKeyAfterTheCut`, DATA3-13), and while a kept line is signed under it, retiring it still breaks the chain, as it should.
6. **Failure model.** The temporary file is created exclusively, locked, written, fsynced, read back and verified (same bytes, a chain that verifies, the same last line and mac as the journal's) before the rename. A failure before the rename removes it and leaves the journal and the `File` untouched and usable. After the rename the `File` swaps to the new file at once (a line written to the old descriptor would be lost) and then syncs the directory; if that fails the `File` is broken (every `Append` fails and callers record gaps) until the boot reopens it, the trimmed file being whole. A file that is not the chain this `File` holds (rewritten under the lock) is never rewritten: the `File` is broken with `ErrCorrupt`.
7. **No worker pool.** The journal is one MAC chain, each line signed over the previous mac, and the trim is one sequential read and one write under the file's mutex. There is nothing to shard. Appends wait for the rewrite, which is a cost of the file's size (capped at 256 MiB by `maxJournalBytes`), and the trim is a once-per-retention-run call.

## Caller contract for G2

- `Manifest.JournalSeq` is the archive's own boundary, but the hook's boundary at restore is the lower of that and the swapped-in head. Retention's `trimJournal` takes the minimum of `Manifest.JournalSeq` over retained archives. G2 should confirm the two agree for every archive a restore can still use before it passes that minimum to `Component.Trim`; the trim cannot see archives.
- `Options.PruneJournal` returns only an error, so a clamped trim reports success. G2 may want `TrimResult.Limit` in its log line.

## Tests

`core/backup/journal/trim_test.go`: exact survivors and byte identity, the boundary entry and `Cover`, trim to head then append, appends after a trim and a reopen, no-ops, a second trim, every clamp, closed and broken files, a file rewritten under the lock, key rotation and retirement, the wire format, `Component.Trim`, failure injection at each label (create, write, fsync, rename, directory fsync, a silently corrupt copy, a leftover that cannot be cleared), a crash at each step over the real filesystem, and appends racing a trim.

`core/internal/journalfs`: six site rows (success, leftover cleared, nothing to drop, fsync failed, rename failed, directory fsync failed) and `TestKill_TrimLeavesAWholeJournal`, which crashes before every durable step on the minimal clone and sixteen mixed clones and on the settled clone, and fails unless the old journal, the trimmed one, a leftover temporary file and the settled state were each reached.
