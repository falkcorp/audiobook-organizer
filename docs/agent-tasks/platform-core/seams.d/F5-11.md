# F5-11 seams and coined names

F5-11 converts the 14 T6 group 6 maintenance definitions to native `books.<ID>` kinds (`internal/plugins/maintenance/kinds_t6_g6.go`). They are dark: nothing registers them before the tasks flip (F5-18). This file lists the readings the row took where the brief is silent, the helpers it added, and what later rows build on.

## Seams

- `t6g6Store` and `t6g6Writer` are composed by embedding each definition's own narrow interface, not one hand-written interface. Every core takes only its narrow piece; the composition is what `t6g6Deps` carries.
- `t6g6Deps` is wider than the brief's two fields. Besides `Store` and `NewWriter` it carries `ActivityLogFullDetailDays`, `StandDownKey`, `RootDir`, `ResolveReportPath` and `ITunesRoots`. F5-18 fills them. A native shell refuses at the top when a dep it needs is nil, instead of panicking inside a worker.
- `StandDownKey` empty refuses a live apply that needs the stand-down (recover-missing-files with repoints, repoint-book-file-rows). A native apply never runs without the lease. The native stand-down `Lost()` reports false: a lost lease is caught by the writer fence.
- Effects use only resources declared in `pkg/ops/effects.go` on origin/main: books, book_files, files, operations, activity, review_items, user_state. No resource name was coined. `operations` is the undo journal only (opchange, heal, repoint), never the activity log (that is `activity`).
- Native params drop `dry_run` and `apply`: the run's mode carries them (Preview reports, Live applies). Every native kind that writes refuses those keys, in any case, before it builds a writer (`t6g6RefuseModeKeys`, one test row per kind per spelling). Live-only writers (nightly compaction, recompact digests, iTunes heal) refuse Preview with `<kind>: preview not supported; start with mode live`.
- repair-merged-user-state reads through `env.Store` and writes through `env.Writer`. `merge.RepairMergedUserState` takes one store and probes it for the sync-identity, bookmark, bookmark-copier and position-timestamp capabilities, so the core composes that object from the two halves (`t6g6ComposeUserState`). A capability is present only when both halves carry it. Layers embed the concrete type below them; embedding the interface would hide the lower layers (found by CI, pinned by `TestT6G6More_ComposedUserStateStacksCapabilities`).
- iTunes heal's body now lives in `internal/reconcile` (`RunITunesHealVia` over `HealReader` and `HealWriter`); the HEAD shell calls it through `NewHeadHealWriter`. The native writer adapts the run to the three writes it makes (`CollapseHealDuplicates`, `HealTrack`, `HealWhisperJournal`).
- Resume, per kind (standing ruling: a HEAD `ResumeRestart` maps to `ResumeContinue` only if HEAD reads its checkpoint on restart, else `ResumeFromZero`; `ResumeDrop` maps to `ResumeDrop`). `TestT6G6Kinds_MatchHEADDefs` writes the expected policy out per kind.

  The opchange exception: by the letter of the ruling HEAD reads no registry checkpoint, so FromZero. But a native yield (`tasks.ErrContinueInPlace`, which the verify takes at its time budget) is honoured only for `ResumeContinue` (`core/tasks/rc.go:125-129`; the executor fails any other policy with `yield_not_continue`, `core/internal/executor/attempt.go:679-680`), so FromZero would turn the yield into a failed run. After a restart the Continue kind behaves as HEAD did: Run re-enters the ensure and the store's cursor continues it (the core never calls Restore (the resume point is the store cursor, not the registry checkpoint), so its Continue rests on the yield rule alone and is the one place a Continue kind reads no checkpoint; `TestT6G6OpChange_YieldWritesMarkerAndSecondAttemptReentersEnsure`). Ruling (review r3): opchange keeps `ResumeContinue` as a NAMED exception to the standing rule. Its restart behaviour is the same under FromZero and Continue (the core never calls Restore; the store cursor is the resume point, `core/tasks/resume.go:14-15`), and only Continue lets its yield through. Cost: every attempt that runs longer than 90s without yielding records an `uncheckpointed` strike (`core/internal/executor/watchdog.go:60-62`), which is a ledger entry only (`attempt.go:516-523`), so it is noise, not a stop.
- Optimize: `Resume` is `ResumeContinue` and `Timeout` is `tasks.MaxTimeout` (24h), against HEAD's 36h chain budget. Deviation from R5: the kernel only honours `tasks.ErrContinueInPlace` for `ResumeContinue`. The native sweep keeps HEAD's 36h across attempts: (1) it waits for each child under a context ending at the attempt deadline minus five minutes (`rc.Await` takes no context, so the native wait runs it in a goroutine and returns when that context ends; the goroutine returns when the attempt context ends); (2) when the wait expires with the child still running it checkpoints the finished children and the in-flight child's run id and returns `ErrContinueInPlace`; (3) the resumed attempt re-attaches to that run and never launches it twice, and a child that finished in between answers at once; (4) it checkpoints after enqueuing a child (the run id) and after every child that ends, so a crash resumes at the next child or re-attaches; (5) the 36h budget is checked at every child boundary and bounds every wait, and a checkpoint with no start time is refused as corrupt; (6) while it waits it stamps the run's liveness on a timer, every `optimizeLivenessEvery` (a quarter of the 65-minute `ProgressTimeout`), because the kernel's await does not (see the liveness seam below); (7) native progress is a step counter persisted in the checkpoint (`Steps`: two per child, one more for each attempt that re-attaches to a child still in flight), so a yield in an attempt that finished no child still reports progress past where the attempt began, which the executor requires (`attempt.go:671-686`: `done > rec.Done`); (8) a child recorded in flight that today's flags no longer list is waited on first and counted, not left running beside the children that start after it; (9) a re-attach checkpoints at once, so the attempt is not struck as uncheckpointed. Behaviour change from HEAD: HEAD dropped an interrupted sweep (ResumeDrop); the native kind resumes it at boot from the checkpoint. A child enqueue failure is counted, recorded as finished and the sweep carries on, as HEAD did. Tests: `TestT6G6Optimize_ChildOutlivesDeadlineYieldsAndResumeReattaches`, `_CrashAfterAChildResumesAtTheNext`, `_BudgetIsHeldAtEveryBoundary`, `_EnqueueFailureIsRecordedAndSweepContinues`, `_YieldsBeforeStartingAChildNearTheDeadline`, `_WaitTicksLivenessAndStopsWithTheWait`, `_NativeSweepStampsLivenessWhileAChildRuns`, `_YieldWithNoChildFinishedStillReportsProgress`, `_InFlightChildNoLongerListedIsWaitedOn`, `_FailedChildIsCheckpointedAtOnce`, `_LostInFlightRecordRestartsTheChildWithIdenticalParams`.
- Optimize, double launch (known residue): the in-flight run id is checkpointed right after `Enqueue` returns, but `rc.Checkpoint` flushes at most every 30s (`core/internal/executor/attempt.go:154-160`, `options.go:70`), so on a hard crash that record can be lost for the child's whole wait, not just an instant. What bounds the damage is the kernel's start dedupe (`core/internal/executor/start.go:497-562`, `stageFold`): a start with no dedupe key and byte-identical params folds into a queued or running run of the same kind, and optimize's child params are constants (`TestT6G6Optimize_LostInFlightRecordRestartsTheChildWithIdenticalParams` pins that a resumed sweep re-starts a child with params identical to its first start's). So after a crash the re-enqueue returns the child already there; the residue is at most one extra back-to-back run of an idempotent child that had already ended. An idempotency key is refused for children (`attempt.go:305-310`), so the window cannot be closed here. HEAD dropped the whole sweep on the same crash, so native is no worse.
- Optimize's children are `books.maintenance.temp-file-cleanup`, `books.acoustid.fingerprint-rescan`, `books.acoustid.scan` and `books.acoustid.backfill` (test-pinned). No row on origin/main or a sibling branch declares those kinds yet; the native optimize cannot run before the owning rows land. It has no progress relay (HEAD's `relayChildProgress` fed its watchdog from the child's observations); the native run reports steps instead (above).
- Await liveness, **an F5-18 blocker, core fix filed separately** (review r3 M1): the doc on `rc.Await` (`core/tasks/rc.go:264`) says it keeps the parent alive, but the executor's await (`core/internal/executor/dispatch.go:582-598`) never touches liveness; the only touches are progress, Note and the writer (`attempt.go:246`, `:268`; `writer.go:60`). A sweep waiting on a child for over the 65-minute `ProgressTimeout` would be stopped as a cancel, which is never resumed (`watchdog.go:67-79`). F5-11 does not change core: the native wait ticks liveness itself (`optimizeAwaitTicking`, pinned by the two tick tests above), which stays correct once core's await touches. The earlier version of this note repeated the doc, not the code. Filed as `todo.d/2026-11-15-f5-11-await-liveness-before-native-flip.md` beside the hold-renew item.
- The opchange ensure's yield is `tasks.ErrContinueInPlace` natively, written after a checkpoint marker (pinned by `TestT6G6OpChange_YieldWritesMarkerAndSecondAttemptReentersEnsure`, which stops at the host: the executor's own handling of the yield is core's, not proven here).
- Hold renewal and liveness (review MINOR 2), **an F5-18 blocker**: a native apply holds the stand-down for the whole run, and core's `Hold` has no renew call, so a long recover or repoint relies on the lease outliving the run; at HEAD the registry renewed it, and the HEAD heartbeat also stamped liveness. The native heartbeat does neither. The 14 kinds must not be registered native until core has `Hold.Renew` and the native shells renew the hold and stamp liveness from their progress. Filed as `todo.d/2026-11-14-f5-11-hold-renew-before-native-flip.md`.
- Optimize's child kinds (review MINOR 7): `optimize.go` names the four def IDs it launches as constants (`optimizeChildTempFileCleanup` and three acoustid ones), the kind launched for each is `books.` plus the ID, and `TestT6G6Optimize_ChildKindsAreTheLaunchedConstants` pins the constants, the kind strings and, for the one def this package owns (`maintenance.temp-file-cleanup`, `cleanup.go:141`), its HEAD def ID. Cross-row part, not pinned here: `books.acoustid.fingerprint-rescan` (`internal/plugins/acoustid/fingerprint_rescan.go:52`), `books.acoustid.scan` (`scan.go:20`) and `books.acoustid.backfill` (`backfill.go:270`) must be declared with exactly those kinds by the row that converts the acoustid plugin, or that row changes the constants in the same PR.
- Effects are traced, not hand-picked (review N1). `t6g6WriterResource` in `kinds_t6_g6_test.go` maps each writer method to the full set of resources its call chain writes, with the chain cited, and `t6g6AssertWritesDeclared` requires every one of them in the kind's declared write set. heal declares `books`, `external_ids`, `files`, `indexes`, `operations`, `user_state` (it writes no `book_file` row: the merge moves files only on the combine path, and the earlier `book_files` declaration had no traced writer; coordinator, say if you want it kept as a precaution): its duplicate collapse is a full `merge.Service.MergeBooksWithOptions` (loser rows soft-deleted, external ids moved, undo pointer and sibling journal, the losers' progress and read status followed onto the survivor, the identification dirty mark). The sibling journal's raw keys are classed `operations` (the undo journal); the group redirect's are `books` (ruling: path_history and group-redirect keys are `books`).
- Stacking list for the coordinator, resources that do not exist on this branch (`sync_identity` and `ai_journal` arrive with F5-06): `books.itunes.heal` adds `ops.ResSyncIdentity` (the merge follow mints and records sync ids, `service.go:1467`, `1486`) and `ops.ResAIJournal`; `books.maintenance.repair-merged-user-state` adds `ops.ResSyncIdentity` (`MintOrGetSyncID` and `RecordSyncMerge` through `t6g6SyncWrites`). Add each to the kind's Effects and to its row in `TestT6G6Kinds_MatchHEADDefs`, and re-map `MintOrGetSyncID`, `RecordSyncMerge` and `CollapseHealDuplicates` in `t6g6WriterResource`.
- Progress labels: the pool carries HEAD's index-only labels natively (`t6g6ItemsOptions.PureLabel`, handed to the item-only `tasks.ItemsOptions.Label`: relink phase 1, probe phases 1 and 2, regroup phase 1, transcribe pages). The labels that read running counters (recover's three loops, heal's per-track line) are dropped natively, because the kernel's label is pure and cannot read a counter; HEAD's pool still shows them. A seam, not a regression of the HEAD shells.
- Native repoint decodes strictly as HEAD did (`decodeStrictParams` after the mode-key refusal).
- Arch guard: the opchange `restartWithoutCheckpoint` entry is gone because the static scan finds the native-only `env.Checkpoint` call; the HEAD def still never checkpoints, so the store-anchored reason (a restart re-enters the ensure and the cursor continues it) is no longer enforced by the guard until F5-18 deletes the HEAD def (review n1).
- `ai_journal` writes (coordinator adds the resource at stacking): sibling F5-06 adds `ops.ResAIJournal` (`"ai_journal"`), which is not on this branch. The one F5-11 kind that writes `aijournal:` keys is `books.itunes.heal`: its ambiguous-track resolver journals Whisper results (`HealWhisperJournal`, `internal/reconcile/itunes_heal.go:921`, kind `resultjournal.KindWhisperIntro`). Its Effects cannot declare the resource here; add `ops.ResAIJournal` to its write set, and to the heal row of `TestT6G6Kinds_MatchHEADDefs`, when F5-06 is stacked. No other kind in this row touches that keyspace.

## Deviations

- Via variants are the shared cores; the old test-only wrappers were deleted with their baseline lines and the tests call the cores (coordinator ruling 1): `findOrphanBookFiles`, `planOrphanRepoints`, `probeAll`, `planRecoverMissingFiles`, `reconcileStaleHolds`, `staleRegroupHolds`, `decidedRegroupHolds`, `opChangeIndexProgressTo`, the opchange wrappers, three loopless `*Parallelism` functions. Tests use `t6g6TestPlanRecover`, `t6g6OrphanFixture` and `t6g6RecoverFixture` (`t6g6_head_fixtures_test.go`), which build the env a HEAD run hands the core.
- `internal/reconcile/itunes_heal.go` and four of its tests changed (outside the maintenance package), for the heal reader and writer split.
- `internal/arch/resume_restart_guard_test.go`: the opchange `restartWithoutCheckpoint` entry was removed, because the native shell now has a checkpoint call the static scan finds. The HEAD def still never checkpoints (`env.Checkpoint` is nil there).
- The nightly core holds an inlined copy of F5-08's `compactAndRecordCore` (`nightlyCompactAndRecord`, one function). Swap once F5-08 merges: replace its body with `return compactAndRecordCore(ctx, cutoff, startMsg, nightlyCompactRecordEnv{env})`, where the adapter maps `env.Log`, `env.Progress` and `env.Writer.CompactActivityEntries` to `compactRecordEnv`. The recompact core has no such twin. F5-18 removes the copy with the HEAD shells.
- Schedules dropped: the HEAD defs declared `10 0 * * *` (nightly compaction) and `15 2 * * *` (orphan scan) in the scheduler tables; the native definitions carry no schedule (the shell takes one through `sched`; F5-18 supplies them).
- Wider write sets than HEAD declared: probe-directory-books and relink-unlinked-books also write `books` (the aggregate recompute); iTunes heal writes books, external_ids, files, indexes, operations and user_state (traced above); repair-merged writes books and user_state; recover writes book_files, books and files; repoint adds books and operations.
- ReadOnly: optimize (its children write), orphan book_file scan and orphan book_file repoint plan.
- Writes the cores make to the file system (reflinks, the heal journal, recover's file operations) are file I/O and bypass the gated writer; the database writes go through it.

## Follow-ups

- Hold renewal in core and the native liveness stamp (above; an F5-18 blocker).
- Core's `await` touching liveness (above; an F5-18 blocker, filed by the coordinator as a core fix).
- F5-18 removes the HEAD v2 shells, the `t6g6Head*` adapters and the `var _ = t6g6KindList` and `var _ = (*Plugin).t6g6Kinds` lines, and the dark baseline lines for the native helpers (`t6g6DecodeNative`, `t6g6DecodeParams`, `t6g6NeedDep`, `t6g6NewWriter`, `t6g6RefuseModeKeys`, `itunesHealCore`).
- The wiring that builds `t6g6Deps` from the server (F5-18) is not proven here; the tests use fakes.
- A drift test between `t6g6SettingsManageScopes` and the settings.manage atom in `internal/books/atoms.go`: `internal/books` imports this package, so the test reads each definition's declared requirement and compares it to the scope list written out by hand; the real atom is not read.
- Deviation from R9: tasklint's unregistered-kind rule counts only package-level list functions as roots, never a method. `t6g6Kinds` delegates to the package-level `t6g6KindList(p, deps, sched)`, and `var _ = t6g6KindList` is the root. Same shape as F5-07's `t6g2KindList`.
