# F3-03 seams and coined names

This file lists what the core secrets PR added beyond 05-config §2 and the F3-03 brief: names the spec does not have, readings it took where the spec or the brief is silent, and the seams later rows (F3-04, F3-06, F3-07, F8-01) build on. Everything not listed here follows 05-config §2.3's code contract as the brief copies it.

Nothing here runs on `main`: no boot calls `secrets.Open`, creates `secrets.keyring` or writes `c/secrets/` until F3-07 (`grep -rn 'openSecrets(' core/kernel/ | grep -v _test.go | grep -vc 'func openSecrets'` prints 0).

## Names beyond the spec

| Name | What it is |
|---|---|
| `secrets.Options.InstallID` | The open store's `c/storage/install` marker. `Open` writes it into the keyring header when the header has none, and rewrites the header to it on `ResetBoot`. The spec has `Open` read the marker itself, but `secrets` cannot reach `storage.DB.Admin()` through a `storage.Keyspace`, so the caller passes it. `openSecrets` passes `db.Admin().InstallID()`. |
| `(*Store).Instrument(*metrics.Scope) error` | Registers the store's otel instruments on the `mediacore.secrets` scope. `Open` runs before P5, which is when scopes exist, so the kernel calls it after P5 instead of passing `Options.Metrics` at P4b. `Close` unregisters the callback. |
| `(*Store).UnexportedKeys() ([]string, error)` | The key IDs that `secrets.keyring.exported` does not hold with the same material digest, read from disk on each call. It feeds `secrets_keyring_not_exported`. Comparing the digest, not only the ID, keeps a record written for a lost keyring from vouching for a new `k1`. |
| `(*Store).RetireBlocked() []string` | The verify keys past `retire_after` that the last `RetireUnused` kept, because the in-use check said yes or failed. It feeds `derive_key_retire_blocked`. |
| `(*Store).Undecryptable(ctx) ([]Name, error)` | The names whose record carries `Meta.Err`. It feeds `secrets_undecryptable`. |
| `(*Store).KeyFile() string`, `(*Store).KeyIDs() []string` | The keyring's path relative to the state directory, and the key IDs it holds. Read by the health detail and the offline commands. |
| `secrets.ExportKeyring`, `secrets.RotateDerive`, `secrets.SetInstallID`, `ExportResult`, `RotateResult` | The library halves of the three offline commands. Each works on an `*os.Root` state directory and opens no store. |
| `kernel.RotateDeriveOffline(ctx, c, now)`, `kernel.SetInstallIDOffline(ctx, c, id)` | The kernel halves. Each refuses unless the caller is the state directory's owner, then opens the store read-only through `OpenOffline`, which refuses while the service holds the lock. |
| `openSecrets`, `secretsInput`, `kernelSecrets` | The unexported P4b helper (the brief coins `openSecrets`), its input, and what it returns: the store plus the `*os.Root` it holds. |
| `core/internal/keyedmutex` | A copy of ABO's reference-counted per-key mutex. It imports only `sync`. |
| Test names | `TestKeyedMutex_SerializesPerKey` and `TestSecretsSeries_Golden` (the brief coins both), `TestKeyMaterial_NeverFormats`, `TestKeyring_Invariants`, `TestOpen_FirstRunKeyring`, `TestOpen_RefusesBadOptions`, `TestAll_NeverValues`, `TestKeyIDsReferenced`, `TestPut_SerializesPerName`, `TestClose_WipesAndRefuses`, `TestNoSecretInLogsOrErrors`, `TestMeta_StorageErrorIsAnError`, `TestRotateDerive_Refusals`, `TestExportKeyring_CopiesWithoutTheStore`, `TestExportKeyring_RefusesLooseOrOwnTargets`, `TestSecretsOwnerSpec`, `TestOpenSecrets_ScratchStateDir`, `TestSecretsHealth_Tokens`, `TestSecretsMetrics_Golden`, `TestRotateDerive_RefusedWhileServed`, `TestCoreSections_SecretKeys`, `TestValidatorAddedEntryNeverKeepsItsPath`, `TestExportKeyring_RefusesFIFOTarget`, `TestKnownAnswer_KeyringAndRecord`, `TestSeal_FreshNonceEveryTime`, `TestOpen_BadNonceLengthIsCorrupt`, `TestExportRecord_VouchesOnlyForItsMaterial`, `TestOpen_NumbersPastKnownKeys`, `TestReadExportRecord_RegularAndBounded`, `TestExportKeyring_RefusesSymlinkedKeyring`, `TestWriteKeyringNew_NeverReplaces`, `TestOpen_RemovesStaleKeyringTemps`, `TestStore_NeverFormatsSecrets`; F3-OIDC-SECRET adds `TestEntrySecret_RegisterShapes`, `TestEntrySecret_NamespaceOverlap`, `TestEntrySecret_KeysAndBinding`, `TestEntrySecret_EntriesRefused`, `TestEntrySecret_Writes`, `TestEntrySecret_RemovalDeletes`, `TestEntrySecret_RemovalRefusals`, `TestEntrySecret_QuarantinedRowIDsDeleted`, `TestEntrySecret_NeverLeaks`, `TestEntrySecret_MetaFollowsEntries`, `TestEntrySecret_HealthDetailRedacted`, `TestCoreSections_OIDCClientSecretPerProvider`. |

## Spec readings and deviations

| Topic | Reading |
|---|---|
| `Stage` and `StageUnreadable` take `ctx` | §2.3 has `Stage(b *storage.Batch, w Write)` and `StageUnreadable(b, n, reason, by)`. Both read the current record (create-only check, per-name lock), and every storage read takes a context, so both take `ctx` first. The importer's methods already had one. |
| `storage.ErrImportConflict` | Declared in `core/storage/import_errors.go`, because `secrets.Importer` is the first importer that returns it. F3-04 keeps it where it is and adds §5S.3.13's other sentinels beside it. |
| Importer semantics | Create-only. A record that already holds the same value, or the same unreadable marker, counts as already current and stages nothing. Anything else is `storage.ErrImportConflict`: another value, a cleared marker, a record that cannot be read. The importer bypasses the `Ephemeral` lock, because it writes the stored layer that an operator value hides. There is no import of a delete. |
| `Meta` | `Meta` returns a nil error for a name that is unset or whose record does not decrypt (the state is in `Meta.Set` and `Meta.Err`). A storage error is still an error (`TestMeta_StorageErrorIsAnError`). |
| `RetireUnused` | The decision lives in memory and never reaches the keyring file, so every boot decides again. When the in-use check returns true or fails, the key stays and is listed by `RetireBlocked`. Only a nil check or a cancelled context is returned as an error. |
| Missing keyring with records | `ErrKeyMissing` counts sealed and malformed records only. A cleared marker or an unreadable marker carries no ciphertext, so it does not block a first-run keyring. |
| Key numbering (review MAJOR-1) | A new keyring, first-run or regenerated, is `k<n>` and `d<n>` with n past every key number known: the sealed records' kids, the export record's IDs, and `c/secrets/meta`'s `max_key_id` (coined). Every `Open` raises `max_key_id` to its keyring's highest key number, writing meta (with an `Expect` on the bytes it read) only when the number rises: on the first boot after rotate-derive, and on a regen. Every key a running service derived or sealed under was in a keyring some `Open` loaded, so new material never takes an old key's ID, exported or not. A truly fresh install (no meta, no export record) still starts at `k1`/`d1`. A keyring replaced when meta already knew keys is logged as a loss (Warn), because what was derived under the old derive keys no longer verifies. A derive key added by rotate-derive and lost before any boot loaded it can have its ID reused; nothing was derived under it. |
| Exclusive keyring creation | A first or regenerated keyring is created with a hard link from its temp file (`os.Root.Link`), which fails when the keyring appeared meanwhile; it never replaces one. On a filesystem without hard links it falls back to a check and a rename, safe because `Open` runs under the store lock. Rewrites of a present keyring (install_id, rotate-derive, set-install-id) still rename over it. |
| Stale temporary files | `Open` removes `<key file>.tmp-<12 hex>` regular files, which a crash between create and rename leaves holding key material at 0600. Only the keyring's lock-holding writers make them (`Open`, rotate-derive, set-install-id), so any found under the lock is stale. Links of that name, near misses and the export record's temporaries are left alone, because export-keyring runs without the lock. |
| Formatting | `*Store`, the keyring and its keys implement `String`, `GoString`, `Format` and `LogValue`. fmt prints unexported fields raw, bypassing `Value`'s and `keyMaterial`'s own redaction, so before this `%v` of an open store printed its operator values and `%v` of the keyring printed key material. `*Store` prints its app ID and key file only. |
| `export-keyring` target rules | It runs only as the state directory's owner. It writes mode 0600 through a temp file and a rename, and refuses an `--out` that exists looser than 0600, that is not a regular file (a symlink, a FIFO, a directory), or that is the keyring or the export record, by path or as a hard link to either. The bytes are the keyring file's bytes. The record `secrets.keyring.exported` is `{"format":"mediacore-keyring-export/1","keys":[{"id":…,"sha256":…}],"at":…}`. Each `sha256` is the hex SHA-256 of `"mediacore/secrets/export-digest/v1\x00"` followed by the key material (domain-separated, so it matches no other hash of the material). It holds no key material, and a digest of 32 random bytes reveals nothing of them. The reader takes only a regular file of at most 1 MiB. |
| `rotate-derive` window | `retire_after` = now + max(`core.backup.retention.max_age`, `core.auth.session.remember_ttl`). It reads those keys' defaults through a throwaway `config.Store` over the core sections, because no stored override is readable offline until F3-07. The default is 168h. |
| `rotate-derive` and `set-install-id` open read-only | Both use a read-only `OpenOffline` plus an explicit `RefuseNotStateDirOwner`. They write the keyring file, not the store, and read-only mode still takes the lock, so a running service refuses them ("lock held by current process" in-process). |
| Offline key file | All three commands use the default `secrets.keyring`. `core.secrets.key_file` is not readable offline until the config flip hands these commands the app's config (F3-07). |
| Health | `core.secrets` reports one reason by precedence: `secrets_undecryptable` > `derive_key_retire_blocked` > `secrets_keyring_not_exported`, all `Degraded`. `Detail` lists every condition that holds. When the undecryptable check itself fails, the component reports `secrets_undecryptable` with the failure in `Detail`. A multi-reason `health.Result` is a todo (F8). |
| Owner spec | `secretsOwnerSpec()` (keyspace `c/secrets/`, `Serialized: [""]`) lives in `core/kernel/secrets.go` and is not added to `storageOwners`, so no boot lists the keyspace before F3-07. |
| `core.auth.oidc.<id>.client_secret` | **Declared by F3-OIDC-SECRET** as `authOIDCProvider.ClientSecret secrets.Ref \`json:"client_secret" protect:"admin"\``, through a config engine change ("Entry secrets" below). `core.http.basic_gate.password` is declared (`protect:"admin"`, no `reload` tag, not `FailClosed`). |
| Entry secrets: the shape (F3-OIDC-SECRET) | 05-config names no mechanism for a secret inside a list entry. config accepts exactly one shape: a list key (`[]T`, T a struct that does not encode itself) below the section root, in a struct section, not `reload:"boot"`, whose element has an exported string field with json name `id`, holding each `secrets.Ref` as a direct, exported field with a json name. Every other shape (a Ref nested below an entry field, `[]*T`, an array, a map, a root list, a map section, a list of Refs) stays refused. Two entry lists under one parent object are refused (their IDs would share one namespace). |
| Entry secrets: the name | `<list parent>.<id>.<ref json name>`: for `core.auth.oidc.providers`, `core.auth.oidc.<id>.client_secret`, 05-authn §8's name. The ID grammar is config's path segment `[a-z][a-z0-9_]{0,47}` (05-authn's id grammar, stricter than secrets' `[a-z][a-z0-9_-]{0,63}`), so every derived name is also a valid config path. |
| Entry secrets: protection | The Ref's own tags, not its list's: `client_secret` is `ProtectAdmin` under a `ProtectOwner` list (05-config §1.3.7's FieldSignIn row). Register **refuses an entry Ref without an explicit `protect` tag**: inheriting the list's class, or defaulting to none, would be a silent choice either way. `checkNested` skips Ref fields (their tags are their own key's, so a Ref stricter than its list is honoured, not ignored). |
| Entry secrets: the list's value | The list's canonical value carries each entry's reference `{"secret": "<derived name>"}`, never a value. An entry may omit it or supply `{"secret": ""}` or its own derived name; a reference naming anything else is refused (an owner writing the list must not point an entry at another key's secret). The list's entry schema is rewritten to that reference shape, not required, with the coined vendor keyword `x-mediacore-entry-secret` naming the template path. The decoder binds each Ref from the entry's ID whatever the bytes say. |
| Entry secrets: validation | An entry with no id, an id that is not a path segment, an id equal to a json name of the list's parent object (computed at Register: `providers`, `redirect_base_url`), or a repeated id is refused in the key's canonical check, so Apply refuses it (`ErrInvalid`), a stored row is quarantined at Attach, and an operator value fails boot. These messages name the entry index, never the id. |
| Entry secrets: redaction | A list holding entry secrets redacts like a `sensitive` key, failing closed (#4564's rule): its schema, type and decode errors are replaced by a fixed message (only the entry checks' own, value-free messages are kept), its section's Validator messages are redacted, `flagJSON` redacts, and `RedactedConfigFile` drops the whole list (an operator may paste a secret into it on disk), with `ConfigFileHasSecrets` true for a file that sets it. |
| Entry secrets: lifetime | A derived key exists (Lookup, Keys, Apply) only while the stored or effective list has an entry naming it. An Apply naming one for an ID no entry holds is `ErrUnknownKey`, so an entry is added first and its secret set in a second Apply. |
| Entry secrets: removal (spec silent; fail closed) | When an Apply changes the list, every ID of the stored list (and of its stored row, even a quarantined one) that the new value lacks has each entry secret deleted (`secrets.Write{Delete: true}`) in the same commit. A rename is a removal: the secret is deleted, never carried to the new ID. Each deletion is a write to the derived key, so it is refused when the actor does not meet that key's protection (`ErrProtected`), when an operator layer sets it (`ErrLocked`; the secrets store refuses to write a locked name), or when the same patch sets it (`ErrInvalid`); a patch that unsets it deletes it once. Not covered: an entry removed by an operator layer (env, file) leaves its stored record, because config writes nothing at boot (C13); config binds no Ref and lists no key for it, so it is unreachable through config, and an entry that takes the ID again finds it. The same holds for a list row quarantined at boot. |
| Entry secrets: operator layers | `sourceQuery.entrySecret` (coined) reports whether a path is an entry secret for any valid, unreserved ID, so F3-02's env and file sources can place `CORE_AUTH_OIDC_GITHUB_CLIENT_SECRET`-style values; config records them as operator values (the key reads locked, source env). A flag never sets one. A stored `c/config/` row at a derived path is quarantined like any secret key's row. |

## Spec questions

- **Fingerprint stability across rotate-derive.** `Meta.Fingerprint` is HMAC-SHA256 under a subkey of the **active derive key** (05-config §2.3 names the info string `mediacore/secrets/fingerprint/v1`, not the key it derives from). So `secrets rotate-derive` changes every secret's fingerprint, though no value changed. A UI or audit that compares fingerprints across the rotation sees every secret as changed. Options for 05-config's owner: (a) keep it and document that fingerprints are stable only within one derive key, (b) derive the fingerprint subkey from the active data key (stable across derive rotation, changes on data-key rotation, which is deferred by §2.11 item 1), or (c) a dedicated fingerprint key that never rotates. This PR keeps (a) and pins the current derivation in `TestKnownAnswer_KeyringAndRecord`.
