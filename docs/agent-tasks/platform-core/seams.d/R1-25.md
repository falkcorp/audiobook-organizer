# R1-25 seams and coined names

This file covers what the "offline restore and reset" PR added beyond 05-storage §5S.3.12 and §5S.3.15, 05-backup §5B.3.4, 05-updater §5U.12 and 06 §6.4.5, §6.4.6 and §6.5.2. It lists:

- names the spec does not have;
- the decisions the row took where the spec or the brief is silent, or offers a choice;
- the files it touched outside its inventory;
- how the brief's test names map to tests;
- what it left for later rows, with the fragment that tracks each item.

From this row nothing restores or resets the live store while the service runs. A restore from Settings stages an archive restore in the one journaled swap slot and the service exits 75. `storage restore-offline` and `storage reset` run with the service stopped, and the swap lock makes that a rule rather than an instruction: they refuse while the service is running or starting, and the service refuses to start while either runs. They run only as the state directory's owner, the user the service runs as (D29). Every target is checked at staging. Every CLI command that opens the store goes through `app.OpenOffline`.

## Decisions

Each took the recommended option. The owner asked for no checkpoints.

- **D1. The live restore stages through `restorejournal`, not the kernel's swapper.** The kernel's offline stager refuses a store that a process holds, and the live restore runs inside the process that holds it. `backup.StageRestore` writes the same intent that the offline stager writes: `KindArchive`, the staged store as the one Target, `StagedByBuild` (the kernel's binary ID), `InstallID`, `ArchiveID` and a 24 h expiry. The next boot's P0a applies it. Its order:
  1. a listing lookup;
  2. verify without a sidecar is refused before any work;
  3. a slot read;
  4. `ValidateTargets`, then `Validate` over the set-asides and the placement;
  5. extraction (`ExtractStore`: one read that checks the archive, then the writes; D27);
  6. `VerifyStore`;
  7. `BeforeStage` (D8);
  8. a synced journal directory;
  9. `CreateIntent`.

  Every refusal removes what it made. The stager touches neither the live store nor its settings.
- **D2. Verification.** A sidecar that exists is always checked. With verify, the extraction must have checked one: a sidecar removed after the listing refuses (`ErrVerificationUnsupported`). The sidecar is read once, in the extraction (`extractStore` reports whether it verified).
- **D3. The restart.** The handler answers 202, then calls `Lifecycle.RequestRestart`, so the stop order drains the listener and the 202 reaches the client before exit 75. The SPA does not reload. The server's `system.shutdown` event shows the reconnect overlay, which reloads once the server answers again.
- **D4. `target_path` is refused (400)**, and the error names `storage restore-offline --archive <file> --into <dir>`. A restore into another directory while serving has no swap to run.
- **D5. An offline restore supersedes a pending live restore.** This follows 05-storage §5S.3.12 "In place": the pending intent is journaled `rejected`, never run as a second swap. `storage reset` refuses a pending intent (`TestSwapSlotExclusive`).
- **D6. The standalone opener refuses, rather than completing, a staged or in-flight swap** (the brief allowed either). It has no P0a, and the error names the fix: boot the app once. `cmd/pid-census` and the tools keep `StateDir` empty. The op runner's child passes it (fragment `2026-11-09-r1-25-child-mode-pending-swap.md`).
- **D7. `VerifyStoreOpens` uses books as the only owner.** At R1, ABO has one owner with storage.
- **D8. The HNSW clean-stop marker.** #4512 (which superseded #4506 and #4496) merged before this PR's last rebase, so the PR does the cross-seam work its first rounds left to a fragment, and the work #4512's round-9 review asked for:
  1. Every swap this row stages discards the marker first, once every check has passed and before anything is staged or moved: the offline commands through `R1BeforeSwap` (`database.DiscardHNSWCleanStop`, which takes the marker and refuses with `ErrCleanStopNotDiscarded` when one may still vouch), the live stager in `BeforeStage` (`TestDiscardHNSWCleanStop`).
  2. The live stager runs inside the serving process, whose clean stop at exit 75 would write the marker again. Its `BeforeStage` first marks the running HNSW store diverged (`StageRestore`'s `diverged`, the handler's `markANNSnapshotDiverged`), so this run's stop writes none, then discards the marker, both before `CreateIntent`. A restore the checks refuse marks nothing. A marker the discard cannot remove refuses the restore with nothing staged and the store left marked diverged, which costs only this run's stop its marker (`TestRestoreStagerMarksDivergedBeforeTheMarkerAndTheIntent`, `TestRestoreBackupMarksTheHNSWStoreDiverged`, `TestRestoreBackup_NoCleanStopMarkerAfterARestore`).
  3. `ExtractStore` carries #4512's archive refusals, and the in-place restore's helpers are deleted (D27).
  4. A read-write CLI open discards the marker after `OpenOffline` returns (under the store lock) and before books' boot repairs, its first write. A read-only open leaves it. A marker that may still vouch refuses the open and closes the store (`TestCLISubcommandsUseOfflineOpen`).
  5. The claim moved from books' `Options`, before the open, to books' `Register`, under the store lock (`(*PebbleStore).ClaimHNSWCleanStop`). A boot refused beside another process that holds the store no longer takes the marker that process may still write (`TestCleanStopClaimWaitsForTheStoreLock`). Books' first migration step discards the marker durably before it writes (`BooksSpec(ran)`, `beforeMigration`), and a failed discard fails the step, so no migration writes under a marker that may still vouch (`TestServedBootRefusesAMigrationOverAMarkerThatMayStillVouch`, legacy and versioned steps; `TestBeforeMigrationDiscardsTheMarkerOnce`). A boot that ran a step voids its claim (`HNSWCleanStopVoidMigrated`), as #4512's did. A marker the take itself can neither remove nor empty (`ErrCleanStopNotDiscarded`) fails the boot as it fails the first step, and fails ABO's standalone open, which closes the store; round 6 logged it and went on, leaving it vouching on disk through a run that writes the rows (review S-1; `TestServedBootRefusesAClaimOfAMarkerThatMayStillVouch`, `TestClaimHNSWCleanStop`, `TestOpenStandalone_TakesTheMarkerBeforePrepare`).
  6. A swap boot voids the claim. P0a replaces the store and leaves `hnsw/` beside it alone, so a marker on disk describes the rows from before the swap: one written after the stager's discard, by a build from before the swap slot run between the stage and the boot, say. `swapVoidReason` reads the slot in `Options`, before P0a empties it, and a staged, in-flight or unreadable slot voids the claim, so the boot reconciles (`TestSwapBootVoidsTheCleanStopClaim`, with a control that trusts; `TestSwapVoidReason`, whose in-flight case is review N-1's). Core tells modules nothing of what P0a did, so the read is books' own (fragment `2026-11-09-r1-25-p0a-outcome-to-modules.md`). #4512's fragment `2026-11-09-hnsw-clean-stop-p0a-swap.md` is deleted, because this closes it, and R1-15's seams note marks its P0a cross-seam row resolved.
  7. #4512's doc comments named `Merge` among the writes the verdict watch sees (`hnsw_verdict_watch.go`) and `Merge` and `LogData` among the gate's write paths (`pebble_gate.go`). The gate has neither method at this base, so both comments were fixed.
- **D9. `pebble-inject-skip` became `transcode-skip`.** TestLayering lets only `.`, `cmd` and `internal/books` import `mediacore/app`, so the separate `main` could not open through `app.OpenOffline`. The cobra subcommand writes the same `transcode_skip_<hash>` rows through `openCLIStore`.
- **D10. A read-only books store closes cleanly.** `syncWALForShutdown` maps `storage.ErrReadOnly` from a read-only legacy range to nil (`TestReadOnlyBooksStoreClosesClean`). Every read-only CLI open hit this.
- **D11. R1-23's fragment `2026-11-08-r1-23-standalone-opener-pre-boot-swap.md` is deleted**, because step 7 closes it.
- **D12. Phase 2 e2e setup navigates to `use.baseURL`, and a failed navigation fails the test.** `setupPhase2Interactive` went to `page.context().baseURL || 'http://127.0.0.1:8484'`. `BrowserContext` has no `baseURL`, so it always went to 8484, where nothing listens. The swallowed failure left a late `chrome-error://chromewebdata/` commit, which the deleted `resetToFactoryDefaults` call used to wait out, and which then interrupted the spec's first `goto`. The helper now navigates to a relative `'/'`.
- **D13. The CLI opener returns a role interface, and the op-runner child passes its state directory at the call site.** `openOfflineStore` returns `cliStore`, the union of each subcommand's own role: `seedStore` (with `authorUpserter`, `seriesUpserter` and `purgeStore`), `diagnosticsCLIStore`, `benchAuthorReader` and `SetSetting`. That is twelve methods, each one a call a subcommand makes; `TestCLIStoreIsTheSubcommandsCalls` holds the count. The review found the first cut embedding the author and series stores, some forty methods, so `upsertAuthor`, `upsertSeries` and `extractAuthorData` now take the narrow roles too. It does not return `database.Store`. The child's opener is `database.InitializeStoreWith` itself, given the resolved state directory where the child calls it, rather than a closure typed with `database.Store`. Spelling out `database.Store` in those two signatures took `TestStoreReferenceCount` from 26 to 28, and its baseline may only go down. `TestRunOperationRunner_StagedSwapRefusesTheOpen` runs the child over a store with a staged restore, and fails if the state directory is dropped.
- **D14. The swap lock.** The review's blocker: nothing stopped `storage restore-offline` or `storage reset` from running while the service was starting, and a service started during an in-place restore ran P0a on the same intent. Every opener of the live store now holds `<state dir>/swap.lock` shared: a serve boot from the end of P0a for the life of the process (it holds the lock exclusively through P0a, D25), `OpenOffline` until `Close`, and ABO's standalone opener with a state directory until its store closes. The in-place restore, the checkpoint escape and the reset take it exclusively, before they read the slot or move anything, and refuse with `ErrServiceRunning`. A boot or an open refused by an exclusive holder says a restore or reset is running. Choices:
  1. It lives in `core/storage`, not in `restorejournal` or `restoreswap`: `TestSwapSlotExclusive`'s no-mutex guard keeps locks out of those two.
  2. It is `flock(2)` (`syscall.Flock`), so a shell script can test it with `flock(1)`. R1-27's `make rollback-restore` calls `restore-offline`, which refuses through it while the service runs.
  3. Both sides are non-blocking: a refusal names what holds it, rather than a command hanging behind a running service.
  4. `--into` takes no lock, neither exclusive nor shared: it writes only a new directory in the scratch area and never touches the live store, so it runs while the service runs. R1-27's `make rollback-restore` depends on this: it runs `restore-offline --archive --into` with the service up, as the service user (D29), to read the archive's storage levels. `TestRestoreOfflineIntoBesideARunningService` (archive) and `TestRestoreOfflineIntoEmptyPath` (checkpoint) run it under a booted service, and a comment at the lock site in `kernel.RestoreOffline` says not to move the lock above the `--into` branch.
  5. A filesystem other than the real one takes no lock (the crash kit's MemFS). Where `flock` does not exist, both modes are one exclusive lock, which refuses more, never less.
  6. `refuseHeldStore` stays for an opener without the lock: a kernel or standalone open without a state directory, or an older binary (D26).
  7. The lock file's mode, owner and refusals are D24.
  The fragment `2026-11-09-r1-25-offline-swap-vs-starting-service.md` is deleted, because this closes it.
- **D15. An interrupted escape can be rerun.** The escape sets the live checkpoint pointer aside, so a rerun finds the latest checkpoint through the set-aside pointer (`escapedPointer`, `Checkpoints.LatestFrom`). The place loop skips a target the first run already placed, which would otherwise be `ErrSwapAmbiguous`. `TestEscapeKillMatrix` kills the escape at every step and reruns it.
- **D16. A refused in-place restore leaves no staging.** The slot is checked (`CheckOffline`) before anything is extracted or copied. When the swap fails before staging is linked into it (`OfflineResult.Linked`), the staging directory is removed. After linking, the next start applies the swap, so an interrupted `restore-offline` after staging is finished by the next service start.
- **D17. A checkpoint source is verified like an archive.** `stageSource` opens a checkpoint's store read-only through `verifyStore` before staging it. A store this build cannot open is refused (`TestOfflineRestoreRefusesUnopenableSources`).
- **D18. The reset hook stops at its timeout.** The hook's context is cancelled when its run ends, and the confined state files it was given refuse every call after that (`endedFiles`, `storage.ErrConfined`). A hook goroutine that ignores its context cannot delete anything after `hook_done` is journaled (`TestResetHookStopsAtTheTimeout`).
- **D19. A factory reset refuses a library root that holds the store or the state.** `refuseStoreRoot` refuses a root equal to the database's parent directory (backups, checkpoints and the HNSW directory beside the store) or to the state directory (the encryption key), before the preflight. The kept-path rule keeps either one only when an entry is or holds it, so a wipe of either one's own entries would remove what the restore and the next boot need. A root that holds either is still allowed: that entry is kept whole.
- **D20. The restore route's `verified` says whether verification ran.** `StagedRestore.Verified` is true when a sidecar was checked, with or without "verify", and false when there was no sidecar and verify was off.
- **D21. The updater checks the slot again just before the rename.** A restore or reset staged while the release downloaded refuses the apply, and the downloaded binary is removed.
- **D22. The CLI probe and the op-runner child resolve the state directory first.** `refuseBusySwapSlot` and `RunOperationRunner` call `config.EnsureSecureStateDir` before they read the slot. Where the default directory cannot be created, the directory falls back to the database's parent, and that is where `restore-offline` staged the swap and where the swap lock is. With the lock in the standalone opener, the unresolved default failed every child open on such a host at the lock's `mkdir`.

- **D23. The swap lock is a kept path (review B1).** A factory reset's hook, or the kernel's removal when no hook runs, could delete `swap.lock` from a state directory it was allowed to clear. The next taker would then lock a new file that a holder of the old one never sees, so the exclusion would end without anyone noticing. `restorejournal.Kept` keeps `SwapLockPath(stateDir)` like the slot (`TestKeptPaths`; the confinement test's kept paths).
- **D24. The lock file stays 0600, and a take checks it before it changes it (review B2 and the security review that followed).** Under `flock(2)`:
  1. The file is created 0600 by the open itself, so no stranger can open it between creation and a later `fchmod` (`TestSwapLockIsCreated0600`).
  2. The state directory is opened as an `os.Root` and the file opened relative to it, and the name is then checked to be the file opened (`Lstat` and `SameFile`), so a symbolic link at the name is refused whether it leaves the directory or not.
  3. The open is `O_NONBLOCK`, so a FIFO planted at the name cannot hang it.
  4. Before any change, a take refuses a file that is not regular, has more than one link (a hard link planted at the name could name any file on the filesystem), or is not owned by the state directory's owner (`TestPlanSwapLock`, `TestSwapLockRefusesUnsafeLockFiles`).
  5. Only the state directory's owner creates the file, and only the owner sets a wrong mode back to 0600, through the descriptor. Any other taker (root running a read-only command) opens the owner's file without `O_CREATE` and changes nothing: it locks the file as it is, or refuses a file that is absent or has the wrong mode and names the user to run as (`TestPlanSwapLock`, `TestSwapLockNonOwnerChangesNothing`, `TestStateDirOwner`). Round 6 had a root take create the file and `fchown` it to the owner; review B-1 removed that, because no command that writes runs as another user any more (D29), and a take that never changes another user's file never has to give one back.
  6. A state directory that group or others can write is refused, because whoever can write it can create or replace the lock file (`TestSwapLockRefusesAWritableStateDir`).

  **Deviation from the review.** The review asked to assert that the state directory is 0700, on the premise that `config.EnsureSecureStateDir` already makes it so. It does not: `EnsureSecureStateDir` (`internal/config/state_dir.go`) and `app.ResolveStateDir` (`core/app/app.go`) only `MkdirAll(0o700)`, which leaves an existing directory's mode alone, and `deploy/audiobook-organizer.service` creates the production directory with a bare `mkdir -p` (0755); that directory is also the service's home and the database's parent. An exact-0700 rule would refuse production boots and the database-directory fallback, so the take refuses only group or other write, which is what lets another user take the lock. The gap is filed (`2026-11-09-r1-25-state-dir-never-tightened.md`).

  Core uses only the standard library here: `golang.org/x/sys/unix` is not on core's import allowlist, and package-level mutable variables are banned, so the effective uid is a parameter of the take (tests pass 0 and another uid to drive a non-owner's take unprivileged).
- **D25. A serve boot's P0a holds the swap lock exclusively (review B3).** A shared take let two serve boots, or a serve boot and an offline or standalone opener, run beside each other's P0a, which may rename the store, and a second boot's P0a would resume the first boot's in-flight swap as a crashed one. P0a now takes the lock exclusively and turns it shared on the same descriptor once the swap step is done (`ExclusiveSwapLock.Downgrade`). A refused boot says which kind of holder it met, read from one shared take: one that succeeds means an opener (another service, an offline or standalone open, an op-runner child), one that fails means an offline swap. `flock(2)` does not promise an atomic conversion, so a failed `Downgrade` may hold nothing, and the boot stops there, as a crash would, with the journal as far as P0a wrote it. Where the lock is not `flock(2)` it is one exclusive lock in both modes, and `Downgrade` keeps it exclusive (`TestP0aTakesTheSwapLockAlone`, `TestSwapLockDowngrade`).
- **D26. `refuseHeldStore` is a check at one instant (review B4).** Its comment claimed more than it does. It takes Pebble's `<db>/LOCK` once and refuses an opener that has the store open while it runs, and no other: an opener without the swap lock that starts after it, or that is still booting toward its open, is not seen. The exclusion is the swap lock. The updater's last slot check before its rename has a window of the same kind against the in-process live stager (`2026-11-09-r1-25-updater-slot-check-window.md`).
- **D27. The in-place restore's helpers are deleted, and their archive refusals moved into `ExtractStore`.** `ExtractStore` reads the archive once before it writes (`scanArchive`): the SHA-256, checked against the sidecar when there is one, a mismatch winning over anything the scan found; an entry that climbs out of the target (`ErrArchiveEntryEscapes`); an `hnsw` component at any depth, compared without case and with the long s folded (`ErrArchiveCarriesHNSWSnapshot`); an archive with no entry the extraction counts, or one it cannot read to the end (`ErrArchiveEmpty`). The extraction repeats the entry checks as it writes. `PrepareRestoreIn`, `PreparedRestore` (`Extract`, `Root`), `CheckPathsApart` (`ErrPathsOverlap`), `CheckSnapshotDirs`, `ErrBackupNotFound` and the handler's `SetBeforeRestoreExtractHook` had no caller left, so they are gone with their tests. The extractor's identity keep-out of the snapshot directories (`keepOutDir`, `statKeepOut(s)`, `landsIn`, `physicalPath`) stays in `extractArchive`, though `ExtractStore`, whose directory is new and private, passes it nothing; removing it is an owner call (`2026-11-09-r1-25-restore-keep-out-machinery.md`).
- **D28. The restore route maps the archive refusals as the in-place restore did.** An escaping entry and an HNSW entry answer 400, since the archive is at fault and retrying cannot help; an empty or truncated archive stays 500.
- **D29. Offline writes run only as the state directory's owner (review B-1).** A root `storage restore-offline` left files the service could not read: the swap's journal directories (`restore/` and `restore/<id>/`, 0700 from `MkdirAllSynced`), the state files `copyVerified` puts back (`.encryption_key` among them), the extracted store, and whatever Pebble writes. The service's next boot then failed closed, and the unit reached its start limit. The review's decision, the smaller and safer of the two fixes (refuse the run, rather than chown everything a root run writes), is what the PR does. `refuseNotOwner` compares the effective uid with the owner of the state directory (`storage.StateDirOwner`), the user the service runs as, and refuses with `kernel.ErrNotStateDirOwner` and the command to run instead, `sudo -u <owner> audiobook-organizer storage restore-offline ...`. It runs first, before the command builds its kernel, takes the swap lock or reads the slot, so a refused command has touched nothing. It covers:
  1. `storage restore-offline` in place, the checkpoint escape included;
  2. `storage restore-offline --into`. The review first kept it open to any user. It writes no state file and takes no swap lock, but it writes inside the checkpoint directory, which belongs to the service: the scratch area and its parents (0700) when they are absent, its copy and `<copy>.state` under it, and `<checkpoints>/.sweep.lock` when no sweep has run yet. Run as root, a root-owned `.sweep.lock` makes every later sweep fail to open it, which the sweeper logs at INFO as "another sweep or prune holds the checkpoint directory" and skips, so retention would stop with no error; a root-owned copy is one the sweeper cannot remove. The review's follow-up decision refuses it too;
  3. `storage reset`;
  4. a read-write `OpenOffline`. The review did not name it, but a read-write CLI command writes Pebble files and runs books' boot repairs, so a root run leaves root-owned files the same way. This extension is the PR's own.

  A read-only open runs as any user. A read-only open as another user takes the swap lock shared without creating or changing the file (D24), so it works once the service has created the lock and refuses, naming the user, before that. The check reads the real filesystem only: on the crash kit's MemFS, files have no owner. The effective uid and the swap lock are seams on the context (`bootseam.Seams.Euid`, `bootseam.Seams.SwapLock`), so the tests run a command as root and as a stranger without privileges and check that nothing changed (`TestOfflineWritesRefuseANonOwner`), and fail P0a's `Downgrade` to show the boot stops (`TestP0aFailedDowngradeStopsTheBoot`, review S-2). R1-27 runs the in-place restore and its `--into` check as the service user (`systemd-run --uid`), so the rule does not affect it. A serve boot run as root is not checked here: which user the service runs as is the unit's `User=`, outside this row.
