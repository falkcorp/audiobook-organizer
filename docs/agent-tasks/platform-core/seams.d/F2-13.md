# F2-13 seams and coined names

Names this task added that later rows may rely on (implementation plan §(n) rule 5).

| Name | Where | What it is |
|---|---|---|
| overlay/blocker manifest entry | `internal/books/testdata/r2corpus/manifest.json` `overlay`, `blockers` | `{"case", "label", "family", "step", "key_prefix", "keys", "removed_keys", "corrupt_keys", "outcome", "reported", "expected", "spec", "store"}`, plus `imported_as` on the cases that have one. `case` = `label`. `keys` is every key the case added or changed, sorted, found by iterating the whole store before and after the case (no hand-kept list: the writers' indexes, counters, audit rows and shared rows such as `opv3:meta:counts` are in it); `setting:config_blob#<field>` names one changed field of the settings blob (the row is `setting:config_blob`, the part before `#`). `removed_keys`: keys the case deleted (none today). `corrupt_keys`: the subset of `keys` whose value the case wrote not to decode (torn JSON) or not to decrypt. `store` is the repo-relative store directory, a key of `stores`. `TestR2Corpus_ManifestMatchesFiles` ignores these fields; `TestR2CorpusStage2_StoresHoldTheirCases` reads `keys`, `removed_keys`, `corrupt_keys`, `outcome` and `store` against the committed bytes. It also asserts the lists are complete: a store's rows that differ from stage 1 are exactly the union of its cases' `keys` (with `#<field>` mapped to `setting:config_blob`, and the blob's changed fields exactly the named ones), and its rows missing from stage 1 exactly the union of `removed_keys`. No background row is exempt (there are none today; `opv3:meta:counts` is listed under each case that bumps it); a row no case causes belongs in the manifest under a case, not in an exemption. |

## Rules later rows inherit

- **No undecodable `setting:` row and no ill-typed or invalid settings-blob field can sit in a store R0 boots on.**
  R0 refuses to boot on an undecodable `setting:` row (`collectSettings`), on a blob field whose JSON type does
  not match its config field (`internal/config/persistence.go` at the tag), and on a value its validator rejects
  (an unknown `backup_compression`); every plugin setting is a string. M2's quarantine cases are therefore a secret
  whose ciphertext does not decrypt (`corrupt-settings-secret`, the `basic_auth_password` row, below) and a blob
  field no rename-table row names (`blob-field-unmapped`), and M6's integration case is an `ai_endpoints` row whose URL does not parse, kept and
  reported (`integration-field-invalid`, 05-metadata M1.10), not quarantined: HEAD validates `ai_endpoints` only on
  a PUT that carries them, so the stored row boots. It is not the Deluge URL because `DELUGE_WEB_URL` is env-locked
  in the corpus' boot and would mask the stored value in R0's answers. M6's undecodable rows are
  `corrupt-import-root` and `corrupt-aijob`.
- **R0's boot rewrites the encrypted secret rows the gap-fill file names; a cutover test reads the committed store,
  never one R0 has booted.** At boot R0 reads `<db parent>/config.yaml` and, where a stored value is empty, applies
  the file's value and saves it back, re-encrypting the row; a row that does not decrypt reads as empty. The corpus'
  gap-fill file names `openai_api_key`, `google_books_api_key` and `hardcover_api_token`, so an undecryptable copy
  of any of those three is overwritten with a fresh ciphertext the first time R0 boots on the store (seen in the
  first recording of this overlay: R0's answer showed the corrupted OpenAI key as set). `corrupt-settings-secret`
  therefore corrupts `setting:basic_auth_password`, which the file does not name, and R0's answer on the overlay
  shows it unset. The store under `overlay/` is the one built before R0 booted (the recorder boots a copy), and
  `TestR2CorpusStage2_StoresHoldTheirCases` asserts the row still fails to decrypt. Whether M2 treats an
  undecryptable row as "empty" for gap fill (imports the file's value) or quarantines it is open for 05-config's
  owner (F3; todo.d).
- **05-config §1.12.2's third stage-2 config case ("a blob value that R0's own validation refuses, which
  `Importer.Stage` must refuse too") is not in the overlay.** R0 runs `Config.Validate()` at `serve` boot and stops
  on an error (`cmd/root.go`, step `config.Validate`; it includes the dedup ladder's `ScoreConfig`), and the backup
  codec stops it on an unknown compression, so such a value in a rename-table key makes the overlay unbootable and
  R0 records no answers. R0's only PUT-only validation of a stored value is `validateAIEndpoints`, and
  `ai_endpoints` is an integration field (class `i`, M6), not `Importer.Stage`'s. A test of that case needs a store
  of its own that R0 is not booted on (a blocker-style store), which is a decision for 05-config's owner (F3; todo.d).
- **R0 answers on the overlay are R0's degraded reads.** R0 skips the undecodable rows in its listings (import
  roots, roles, AI jobs, syslog, v3 runs), so the torn `import_path:9` is invisible in the library answer. Its path
  (`import/Selina Kyle`) prefixes the Hush book's rows, which R0 still reaches through `import_path:1`: the books
  rows that reference the quarantined root by path prefix (05-storage
  `TestCutoverQuarantinedParentKeepsReferencingRows`).
- **A replay on the overlay waits for R0's dependency sweep.** `run-queued-deps` stays `queued` until the
  registry's deps sweep fires, a fixed 5 minutes after boot at the tag (`registry.go`, `SweepInterval` has no
  config surface), and then runs to `succeeded`. The recorder's settle wait is therefore longer on the overlay
  (`record_r0_answers.py --settle-timeout`, which `build_overlay.py` sets); a replay that compares answers waits
  the same way.
- **Stage 2 is rebuilt after stage 1.** `write_r0_corpus.py --regenerate` writes a manifest with empty `overlay`
  and `blockers` and only stage 1's store (and drops `stage2` and `overlay_answers`), and every stage-2 store is a
  copy of stage 1, so a stage-1 re-cut is followed by `build_overlay.py --regenerate` in the same PR.
- **Stage 1's committed search answer for `^The ` is stale; the overlay's is correct.** The overlay answers 4 books
  (The Killing Joke and The Long Halloween, each in `import/` and `library/`), which is what the corpus holds; stage
  1's committed answer has 0. The overlay adds no book; its recording starts after a 5-minute settle (above),
  stage 1's within seconds of boot, and the corpus carries `db/library.bleve.rebuilding`, so R0 rebuilds the search
  index at every boot and stage 1's answer was most likely recorded mid-rebuild. A replay that compares search
  answers against stage 1 sees a false difference (the overlay's `search` entry in `overlay_answers` carries a
  `note` saying so); F2-12's recorder should settle on the index rebuild, and stage 1's answers re-recorded with it
  before F2-15 compares against them (todo.d).
- **`corrupt-run` relies on M4 not rebuilding a run from its opv2 mirror.** The run's `opv3:run:` row is torn
  while its progress row and `opv2:` mirror stay intact and current, so HEAD's `ReconcileOpsV3WithV2` neither
  rebuilds nor deletes it. If F5 decides M4 rebuilds an undecodable v3 run from the mirror, this case's outcome
  changes to `imported`.
- **R0's merge-journal statuses are `applying`, `applied`, `undoing`, `undone`.** The spec's "done" is `applied`.
  The unfinished journals were written by HEAD's own `usermerge.Service` with a canceled context (cancel at the
  first `merging` step; undo with a pre-canceled context), not hand-encoded.
- **`stopping{watchdog}`:** 05-tasks §5T.8.3 maps it to `failed` (reason watchdog); R0's own `StopTerminal`
  says `timed_out`. The manifest (`expected`, `imported_as`) records the spec's mapping; which one wins is open
  against 05-tasks' owner (F5; todo.d).
- **An empty (or all-space) username is an `auth.Importer` rejection.** `blocker-identity-user-rejected` is a
  decodable `u:` row with username `""` (HEAD's own `CreateUser` writes it), and the corpus treats it as a row `ErrImportRejected` refuses
  (`TestR2CorpusStage2_StoresHoldTheirCases`'s `r2Blocking` counts it). 05-authn §3.4's list of Store invariants
  (unknown status, key with no scopes, key or identity whose user was not imported) does not name it yet; F4-06's
  importer must reject it, and the §3.4 sentence is proposed to 05-authn's owner (todo.d).
- **No API key in the corpus has a usable raw secret.** Stage 1's and the overlay's keys alike are stored as HEAD
  stores them, by hash; the overlay's raw tokens were generated by `database.GenerateAPIKeyToken` and discarded.
  The answer files hold `<api-key:NAME>` placeholders, never a key, and a replay mints its own key through the
  bootstrap exchange (`record_r0_answers.py`), as the recorder did.
- **Cases that build on another case's rows check their order.** The key cases (`key-outside-owner`,
  `key-every-atom-custom-owner`, `key-empty-custom-owner`, the `status-edge-key-*` cases) use the users the role
  cases created, and `run-interrupted-apply-rowmarks` applies `run-awaiting-decision`'s plan (its `PlanOpID`); the
  program stops if the case that writes them has not run first (`userFrom`, `planRunID`), and a table-driven case
  stops if its label has no table row.
- The program opens the store copy with `database.NewPebbleStore` and writes through HEAD's writers wherever one
  exists; a value no writer produces (a status no handler accepts) is HEAD's own type JSON-encoded and written
  with `SetRaw`; a corrupt row is a torn JSON prefix ending in `,"torn":`, except `corrupt-settings-secret`, a
  well-formed secret setting record whose value is not a ciphertext under the store's `state/.encryption_key`
  (R0 refuses to boot on an undecodable `setting:` row, above).
