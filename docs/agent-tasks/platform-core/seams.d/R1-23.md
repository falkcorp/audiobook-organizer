# R1-23 seams and coined names

This file covers what the "storage flip: strict claims" PR added beyond 05-storage §5S.3.4, §5S.3.5, §5S.3.7, §5S.9.3 and §5S.9.4, 04 §4.5 and 06 §6.11.1. It lists:

- names the spec does not have;
- the decisions the row took where the spec or the brief is silent, or wrong;
- every `old ==> new` path;
- what it left for later rows, with the fragment that tracks each item;
- the seams later rows build on.

From this row the kernel opens ABO's one Pebble store at P2. Books reaches its rows only through strict claims on `storage.LegacyRange`, and `serve` runs no pre-server step of its own.

## Decisions and deviations

Each took the recommended option; the owner was asleep and the coordinator asked for no gates.

| # | Decision |
|---|---|
| D1 | HEAD's pre-server steps leave `serve` (06 §6.11.1 step 2). The store open, upgrades and checkpoint move to the kernel (P2, P4a, P4b), and `initializeStore` leaves `startup.Table`. `EnsureSecureStateDir` runs in `books.Options`. The key guard, `initEncryption`, the settings load with its env sync, and `config.Validate` run in books' `Register` (`bootSettings`), each Fatal as before. They run in `Register` and not in a start hook because `NewServer` reads the effective config, and `Register` builds the server the legacy mount needs before P7. |
| D2 | `Register` commits no write (05-storage §5S.4 step 12). The settings load runs over `deferredSettings`, and its writes commit in the `books.repairs` start hook (`startRepairs`: `apply()` as the step `settingsWrites`, then `RunBootRepairs`), after Run's served write. `TestBooksConstructorWritesNothing` proves this under the production loader. |
| D3 | Settings writes are the Degraded startup step `settingsWrites` (review S2; the first cut failed the boot). HEAD logged a failure to save the blob's new layout, the maintenance-window marker or a reset of an unreadable secret, and served on, and the same upgrade ran again on every boot. Now a failed commit is logged, `settings_writes` joins `/health`'s degraded list, and the boot goes on: the effective config is already loaded, validated and served, the writes from the failed one on stay uncommitted for the next boot's load to stage again, and the first settings save persists the whole effective config anyway. `TestRepairsHook_SettingsWriteFailureDegrades`. |
| D4 | `Module()` fixes the manifest's legacy prefixes from the environment's `ABS_API_ENABLED` before the store opens, and `Register` refuses a boot whose loaded settings disagree (`errABSFlagDrift`). The real loader cannot cause that: `applyEnvAuthoritativeConfig` reapplies viper's value over the blob (`internal/config` `TestABSConfig_BlobCannotEnableOrCredentialTheABSAPI`). The check is defensive. |
| D5 | ABO resolves its own state directory and passes it as `Options.StateDir`. `books.Options` refuses when core's `ResolveStateDir` would name a different one. It also refuses an empty `database_path`, and runs `ValidateDatabaseType` before anything opens. |
| D6 | The memdb warmup is deferred to `RunBootRepairs` (`warmDeferred`), so a boot that fails between `Register` and the start hooks leaves no goroutine reading the store the kernel is closing. The repairs hook's `Stop` closes books' store, and the kernel closes the core DB after every module has stopped. |
| D7 | Projection kept (09 §9.2.2 "R0 and R1 raise no level"): every owner's level is 0, `<db>.storage-format` stays HEAD's 1, and the `db_version` row keeps its record ID. So `scripts/storage_format_guard.py` and `make rollback` are unchanged. It runs in the open-time repairs, after the pre-migration checkpoint (HEAD ran it inside its open, before any checkpoint existed). `TestStampWrittenAfterTheCheckpoint`; `storage_format_test.go`'s stamp assertions are HEAD's again (a fresh store and an unstamped store with data are stamped at 1, and a refused preference write leaves the stamp as it was). |
| D8 | `--print-storage-levels` prints JSON (`{"books":0,"core":0}`), as the brief's code contract and the image probe require. §5S.3.7's table says "`<owner> <level>` per line"; this follows the brief. The flag reads manifests only and opens nothing (§5S.3.7), so a trailing `--db PATH` or `--db=PATH` is accepted and ignored (`fastExitArgs`, review NIT) and the brief's acceptance line passes as written; any other trailing argument still goes to cobra. Its callers are the image probe and, from R1-27, the rollback guard; today's `make rollback` reads `--print-storage-format`. |
| D9 | R0 is `v0.223.0` (STATE.md, W03 OWNER-02). `TestR0OpensR1Store` downloads the release archive and checks it against pinned SHA-256 values, or uses `ABO_R0_BINARY`. CI's `boot-crash-matrix-abo` job builds the binary from the tag when the download fails. |
| D10 | `TestBootCrashMatrix_ABO` is partial. It boots books' storage declaration with a no-op `Register` (books' `Register` and `NewServer` share process globals the kit's concurrent boots would collide on). It covers every writer label from P0a up to Run's start step (0) over 7 fixtures, and `TestBootCrashMatrix_ABOCoversEveryWriter` lists the labels no fixture reaches, with reasons. Books' start-hook writes have no writer label in core yet. Tracked in `todo.d/2026-11-08-crash-matrix-abo-start-hooks.md`. |

Core storage never runs it: 66 entries (64 `nil`), `migration059Down`, `migration065Down` and `setVersion`, which only `migration065Down` called. `migration065Down`'s notes on what happens to opv3 records while an older binary runs (still true for a rollback to R0) moved onto `migration065Up`. 04-package-mapping.md:1332's `export_test.go` row for `migration065Down` is now moot. |
