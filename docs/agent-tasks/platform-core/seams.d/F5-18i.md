# F5-18i seams and coined names

F5-18i makes a write-set (or key) deferral visible in the dark executor. Nothing here runs in ABO before the
tasks flip (F5-18): the executor is not started, and its `<ns>.ops` instruments are off in ABO's App until F5-18
wires them.

## Names beyond the spec

| Name | Where | What it is |
|---|---|---|
| `RunView.Deferred`, `BlockedBy`, `DeferredSince` | `core/tasks/client.go` | Read-time, never stored (like `Held`; `putRun` blanks them). The gate's reason token, the running run behind a `key` or `writeset` deferral, and the start of the run's unbroken deferral. Set only on a queued run the last dispatch pass deferred. |
| `RunPayload.Deferred`, `BlockedBy`, `DeferredSince` | `core/tasks/topics.go` | Wire keys `deferred`, `blocked_by`, `deferred_since`; also on GET /runs (taskhttp's `runDTO` is an alias). Added to `TaskRunWire` in the shell's `taskRuns.ts`. |
| `wait`, `newWait`, `waitsNow`, `publishWaits`, `executor.waits` | `core/internal/executor/dispatch.go`, `executor.go` | The per-pass deferral record. Rebuilt every pass beside the counter's dedupe map (`e.deferred`, untouched), replaced whole under `e.mu` and read without it. A run that leaves the queue is simply absent from the next pass. |
| `gate` returns `(reason, blocker, blocked)`, `blocker{id, kind}` | `dispatch.go` | The middle value is new; the reason and the blocked decision are unchanged. The blocker's kind rides with its ID for the view's authorization check. |
| `executor.view` (no caller) and `executor.viewAs(who, rec)` | `executor.go` | `view` never sets `BlockedBy`; `viewAs`, used by `Get`/`Runs`/`Timeline`, sets it only when `mayView(who, blocker.kind)`. `RedactRunPayload` (the stream) blanks it unconditionally. |
| `<ns>.ops.dispatch_wait` (`insDispatchWait`), `attrTrigger` | `instruments.go` | Float gauge (s): longest wait per `def_id`, `reason`, `trigger` of a registered kind. 19th instrument; `Attributes()` gains `trigger`, `InstrumentNames()` gains the name. 05-tasks 5T.11 has its row. |

## Seams for F5-18

- **The alert is NOT in this PR; it belongs in F5-18's commit 7.** `TestDeployReferencedSeriesServed` fails any
  rule under `deploy/prometheus/` that names a series the seeded ABO scrape does not serve, and
  `audiobook_organizer_ops_dispatch_wait_seconds` is served only once F5-18 starts the executor with its
  instruments on (ABO's golden has HEAD's ten `ops_*` families). Measured on this branch with the rule and its
  promtool test below added: `promtool check rules` and `promtool test rules` pass, and the series test fails
  with "referenced but not served by the seeded /metrics scrape: audiobook_organizer_ops_dispatch_wait_seconds
  (alert-rules.yml)" and the same for `alert-rules.test.yml`. Seeding the series, a `foreignSeries` entry or a
  rule file the walker skips would each let a rule name a series the binary does not serve, so none was done.
  F5-18 adds the rule and the test below in the same commit that adds the family to `series.golden` and the
  seeding table (M6: the deploy files follow the family in one PR).
- **Threshold.** The alert uses a fixed 6h, not the kind's schedule interval: `Schedule.Interval()` is 0 for a
  `ScheduleFromConfig` schedule (the interval is a config value the scheduler resolves), so the executor cannot
  see it. Taking the threshold from the interval needs the scheduler to expose it as a series (a core scheduler
  change, not in this slice). Say which in F5-18.
- **`blocked_by` is authorization-checked.** It is the ID of another run, so it is shown only to a caller who may view that run's kind (`mayView`, the rule `Get`/`Runs` apply to the run itself). The realtime stream has a checker and a payload but no way to resolve the blocker's kind, so it never carries the field (`RedactRunPayload`). Whoever builds a run-changed publisher at F5-18 must build it from `executor.view`, never from a view that has had `BlockedBy` set.
- **Manual versus scheduled** is the run's `Trigger`, as the `trigger` label.
- **Realtime.** The run view carries the fields on GET /runs. `core.task.run-changed.v1` is published on a
  run's own state or progress change, and a deferral changes neither, so the stream does not push a deferral;
  the Activity page sees it on its next list fetch.
- **Existing counter behaviour, not changed here.** `deferRun` re-adds `e.deferred[id]` for a run a pass had
  already read when Cancel finished it (the terminal move deleted the entry), so `dispatch_deferred` counts such a
  run once more and the entry is never deleted. The new pass record does not share that: it is rebuilt each pass.

### Rule to add to `deploy/prometheus/alert-rules.yml` (group `audiobook-organizer`)

```yaml
      # F5-18i: a scheduled run held by the dispatcher's write-set gate. Once the
      # executor holds runs by write set, a scheduled kind queues behind any
      # manual job whose declared writes overlap its own (purge-deleted,
      # tombstone-cleanup, author-split-scan, trash-cleanup are the known
      # ones). ops_dispatch_wait_seconds is the longest wait of a queued run of
      # a def_id, by the gate that holds it and the trigger that queued it; a
      # manual start is not alerted on (its starter is watching it). The
      # threshold is 6h, not the kind's schedule interval: schedule intervals
      # are config values the executor does not see (Schedule.Interval() is 0
      # for a config-keyed schedule). Unit test: alert-rules.test.yml.
      - alert: AudiobookOrganizerScheduledRunWriteSetWaiting
        expr: >-
          max by (def_id) (audiobook_organizer_ops_dispatch_wait_seconds{reason="writeset", trigger="schedule"}) > 21600
        for: 5m
        labels:
          severity: warning
        annotations:
          summary: "a scheduled audiobook-organizer operation is stuck behind another job"
          description: >-
            The scheduled run of {{ $labels.def_id }} has waited
            {{ $value | humanizeDuration }} for a job whose declared writes
            overlap its own. The run's blocked_by field on the Activity page
            names the job holding it.
```

### Test to append to `deploy/prometheus/alert-rules.test.yml`

```yaml
  # AudiobookOrganizerScheduledRunWriteSetWaiting: samples every minute. The
  # scheduled tombstone-cleanup run has waited on the write-set gate since
  # minute 0 (the gauge climbs 60 s a sample), so it is past the 6h line at
  # 361m and, with for: 5m, fires from 366m. A manual run of the same kind
  # waits just as long and never fires; a scheduled run held by another gate
  # (module_cap) never fires; a scheduled run that waited only 1h stays quiet.
  - interval: 1m
    input_series:
      - series: 'audiobook_organizer_ops_dispatch_wait_seconds{def_id="maintenance.tombstone-cleanup",reason="writeset",trigger="schedule"}'
        values: '0+60x400'

        values: '0+60x400'

        values: '0+60x400'
```
