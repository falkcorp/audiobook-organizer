# R1-15 seams and coined names

This file lists what the composition-root PR added beyond 06 §6.4.5, §6.5.2 and §6.11.1, 05-metrics §6, 05-logging §3 and 05-rbac §6.1: names the spec does not have, readings it took where the spec or brief is silent, the risks it leaves, and the seams later rows (R1-16, R1-17, R1-18, R1-23, F2, F3, F4) build on.

## Deployability

**Verdict: deployable: shim parity test.** `TestPerimeterShim_ParityWithHEAD` sends every kind of answer through HEAD's listener stack and through R1's (peer gate, perimeter shim, kernel, books' mount) and compares status, headers and body. It covers an engine route, the SPA, gin's and the kernel's legacy 404, the /api redirect, an unmatched method, core's group, health, the Engine.IO probe and CORS preflights. It runs open, with gzip accepted, behind the Basic gate (refused, and signed in with and without gzip), and from an allowed and a denied peer. `TestPerimeter_ThroughTheRunningApp` runs the kinds core answers itself through the running App's own listener (books' R1Listen over `app.Handler()`), with gzip and a same origin. `TestPerimeterShim_UnmatchedMethodMatchesGin` repeats the unmatched-method scan through the shim, OPTIONS included. `TestComposedApp_UnmatchedMethodMatchesGin` runs it against the real composed App. Parity holds everywhere but one place. Under `/api/core/` the kernel answers core's problem 404 where HEAD's NoRoute wrote its legacy 404. Status and perimeter headers still match there, and no ABO client calls that group.

Two risks are not perimeter parity, so the verdict does not cover them. They are listed under **Risks** below: the 60 s hook start timeout and the periodic HNSW export.

## Readings and decisions

| Topic | Reading |
|---|---|
| NewServer in Register | `Register` must do no I/O (06 §6.4.1). The brief says `books.Register` builds today's `*server.Server`, and books has no other place to build the engine `MountLegacy` needs before P7. So Register runs `NewServer`, which opens the service container and sets package globals (the scanner's store, the global store). Consequence: `app.Describe` over books would do that I/O. ABO calls Describe nowhere today. R1-23 and the rows that split the server retire the exception. |
| A built server nobody starts | Building in Register opens a window HEAD did not have: boot can fail after the server exists. That covers app.New refusing at P7, `InstallProcessDefaults` or `Attach` failing, and Run failing before the start hook. serve calls `books.Release` on every path out, and Release closes `Stopped`. |
| Stop budget and store close (review m2) | StopHook clamps every wait to the kernel's shutdown deadline, keeping a reserve for the steps after it that never increases down the order: ops registry 8 s, background goroutines 5 s, file I/O pool 4 s, iTunes 4 s, container 3 s, activity flush 2 s, ollama 1 s, scheduler tasks 0. The steps whose APIs take no deadline (the file I/O pool, the container's Stoppers, the scheduler's tasks) run under `stopWithin`, which leaves a wedged step running and goes on. The container's and ollama's calls also get a context ending at their share, where HEAD passed `context.Background()` and the first R1-15 cut `context.WithoutCancel(ctx)`, which drops the deadline. HEAD waited for these with no bound (the pool had its own 30 s cap). With no abandon in HEAD's path that only cost time; under the kernel's budget it got the hook abandoned mid-order (`TestStopHook_WedgedStepsStayWithinTheBudget`). Not clamped: the flight recorder's own 5 s cap, and the plugins' `Shutdown(ctx)`, which gets the deadline with no reserve. serve no longer waits after Run. The old 30 s `storeCloseWait` spent 30 s after the budget that no stop setting reserves for it: 05-health §5H.4 sizes the supervisor's stop timeout against the budget, and a SIGKILL inside that wait lands before the store's Close and its WAL sync. The review read the unit's `TimeoutStopSec` as 30 s from a code comment. It is not: the committed unit sets none, only `deploy/local.conf.example` said 30, and the production drop-in sets 90 (`systemctl show`: `TimeoutStopUSec=1min 30s`). In production the 25 s budget plus the 30 s wait fitted, so the change rests on §5H.4's sizing rule, not on a measured overrun (the follow-up PR corrected the comments and set the example to 90). serve closes the store at once and logs ERROR when the hook was abandoned. That is safe because every Pebble access holds a lease on the main GatedDB, and every side store (activity, embedding, AI scan) shares it and closes as a no-op. PebbleStore.Close refuses new leases, syncs the WAL, drains, and leaves the engine open with the WAL synced if a lease outlives the drain; a later write gets an error wrapping `pebble.ErrClosed` (`TestStoreCloseUnderAbandonedStop`; the database package's `TestPebbleStoreClose_*` for the gate). A step left running when the process exits ends as it would have under HEAD's SIGKILL: file jobs re-queue at boot (`RecoverInterruptedFileOps`), and books the index worker did not pop are marked dirty for the reconciler. The 25 s default budget plus `DefaultCloseDrainTimeout` (10 s) is 35 s when a lease is still held at close: inside production's 90 s and inside 5H.4's planned 60 s for the committed unit. It overruns only a supervisor stop timeout under 35 s (Docker's 10 s default, launchd's), which R1-33's stop settings cover. The hand-off to R1-33 that said it exceeded `TimeoutStopSec=30` rested on the same wrong 30 s. |
| Claims | books declares the subtree of every manifest route's first segment (or `/api/<seg>/`), plus every top segment and `login`, whether or not a route sits there. The kernel requires each TopSegments and SPAShared entry to be a declared prefix (P7), and an unmatched path under a claim gets the legacy 404 HEAD's NoRoute gave. `/socket.io/` is claimed with no route, so the Engine.IO probe keeps HEAD's legacy 404. |
| ReservedAPINamespaces | Every unversioned `/api/<seg>` the ABS surface can register, ABS on or off, so no module takes a name that enabling ABS would need. |
| HNSW stop export (decision 1) | A periodic export runs every 10 minutes when the graph changed (`ExportIfDirty`, on bgWG). The stop-time export runs only when what is left of the budget covers the last export's duration plus a margin. Otherwise an INFO line gives the snapshot's age. The 25 s budget is not raised. A snapshot is written only from a complete graph (`ErrHNSWIncomplete`). HEAD exported a partially hydrated graph with the current truth count, so the next boot took it as fresh. A recovered library panic in Upsert, Delete or Reconcile marks the graph damaged, and `SetComplete(true)` is refused until the graphs are replaced, so a hydrate that finishes afterwards cannot re-enable its export. |
| Stale snapshot (decision 1c, review B2) | A stale or unverifiable snapshot is no longer discarded. It is installed (it serves queries at once) but incomplete, pending a reconcile, and PostInit runs `runANNReconcile` in the background **before** its "already populated" check. Every Pebble embedding row is classified with the hydrate rules, the book lookups on a `runtime.NumCPU()` pool. `Reconcile` then: adds a missing indexed key (coder/hnsw v0.6.1 adds new keys safely; the reviewer's probe ran 300 with no panic); tombstones a graph key whose row is gone or now skipped (Delete and re-Add corrupt the graph); restores a tombstone whose row is indexed again; refreshes stale metadata; and leaves a key alone when its book lookup failed (the store then stays incomplete, as a hydrate with lookup errors does). It asks for the full async rebuild only when an indexed key's vector changed, the graph is damaged, the rows miss an entity type, or tombstones exceed 10% of a graph; the WARN line names the keys (10, then a count). Live writes after the import are recorded and win over the rows read. Vectors are compared at Pebble's float16 precision, because the live embed paths mirror the API's float32 vector while the EmbeddingStore keeps float16; a bit-exact compare made every live-mirrored key look changed (`TestPostInit_ReconcilesStaleSnapshot` caught it). A stale snapshot whose metadata does not list exactly the graph's keys is still discarded, every type. Lazy mode (`ChromemLazy`) keeps HEAD's behaviour: the stale snapshot is dropped and queries use the SQLite scan. |
| B2: two deliberate departures from the brief | **(1) No new keys sidecar.** The brief asked for a sidecar of the graph's keys plus the keys hydrate skips on purpose, then a key-only diff at boot. Reconcile instead classifies every Pebble row with the hydrate rules. A key-only diff misses book changes in the crash window that leave the embedding row alone: a book deleted or merged, made non-primary, made primary again, or moved to another series. A rebuild picks those up; the key diff never would, and the error would then persist across exports. The cost is the book lookups HydrateChromem already does (about 40K Pebble point reads on prod, pooled), without the Adds that make a rebuild slow (4.09 ms per Add at 1024 dimensions: 73.6 s for 18,000 nodes in the reviewer's bench). With every row classified, the skipped-keys list adds nothing, and `hnsw-<type>.meta.json` already lists the graph's keys (import checks that it matches the graph exactly). If the sidecar is still wanted, it is an add-on of about 30 lines. **(2) Tombstone ceiling.** Past 10% tombstones in a graph, Reconcile asks for a rebuild even with no changed vector. Tombstones are graph nodes: FindSimilar over-fetches `limit*4` and drops them afterwards, so their share comes straight out of recall, and only a rebuild removes them. |
| Clean-stop marker (follow-up PR, reviews MAJOR-1 and the second round) | **What it vouches for.** `hnsw.clean-stop` (JSON `{"version":1,"model":...,"at":...}`, file and directory fsynced) says two things: the snapshot on disk is the graph, and the graph is the Pebble rows as the reconcile classifies them. The first round's marker checked only the first, so a merge written to Pebble after the last snapshot left a marker the next boot trusted (`TestHNSWCleanStop_APebbleOnlyMerge`, red before the fix). **Graph side.** `MarkCleanStop` writes it only when the graph is complete, undamaged, not pending a reconcile, not diverged, and the last successful export to that directory (or the fresh import from it) recorded the current gen. A stop-time export skipped for the budget, or one that failed before changing the directory, still gets the marker when nothing changed since the last successful snapshot. An export that fails after it began changing the directory (sidecars removed, the graph or the metadata rename failed) drops the baseline. **Pebble side.** Every Set, Delete, Merge and DeleteRange through a `GatedDB` or `GatedBatch` that touches an `emb:v:*` key or a `book:<id>` row counts as a verdict write, before it reaches the engine (`hnsw_verdict_watch.go`). `UpdateBook` counts only when the effective primary flag, SeriesID, SeriesSequence, or (with no sequence) the Title changed; the signature-sidecar migration never counts. `MarkCleanStop` refuses after any verdict write since the store opened, the import treats the snapshot as stale after one, and one made while this process's marker is on disk removes it. Because the watch sits on the gate, it covers every chokepoint without a list of callers: `EmbeddingStore.Upsert` (the `embed_async` ingest in `batch_poller.go`, `EmbedBook`/`EmbedBooks`/`EmbedAuthor`), `EmbeddingStore.Delete` (the orphan and orphan-author cleanup ops, the re-embed op, the empty-title delete), `CreateBook`, `DeleteBook` (row and embedding), `UpdateBook`/`ModifyBook` (merges, primary changes, revert, the credits store), the embedding re-encode, `SetRaw`/`ApplyRawBatch`, and migrations. **Restore.** `POST /backup/restore` writes Pebble files behind the gate, so the handler marks the live store diverged and, after the extraction, removes the marker beside the live database and beside the database it wrote. Running after the extraction also removes a marker an archive carried; `addToArchive` writes only the database directory today, so that case guards a hand-made archive. A restore that failed partway counts as a restore; only one `backup.RefusedBeforeWriting` reports (not found, verification failed) does not (`TestRestoreBackup_NoCleanStopMarkerAfterARestore`, red before the fix; `TestRestoreBackup_DistrustsTheHNSWSnapshot`). **Divergence.** A vector the graph refuses (other dimensions, a reserved metadata key), and any mirror the dedup engine reports failed outside `HydrateChromem`, mark the store diverged (`MarkDiverged`), and the marker is refused for the rest of the process. `HydrateChromem` counts its own failures, which keep the graph incomplete. **Model.** The marker records the dedup engine's embedding model, and a boot that classifies against another reconciles. **Stop.** StopHook writes the marker as its last step, after the scheduler wait, and not at all when a step did not finish: an ops registry Shutdown error, background goroutines still running after their wait (the index worker among them), the file I/O pool, an iTunes Shutdown error, a plugin Shutdown error (`ShutdownAll` returns them joined, each naming its plugin, a timeout on its context included), the container left running or failing to stop, the scheduler's tasks. The iTunes line has no test: its Shutdown returns nil unconditionally today. Not tracked: the ASIN backfill queue (stopped before the registry drains, so the runs it enqueued are the registry's), the flight recorder (its own 5 s cap; it writes trace files, not Pebble), the activity store close, the file watchers (their scans run on the registry and the file I/O pool, both tracked), the embed queue (its drain only starts and stops ollama), ollama's stop, and the embedding and AI scan store closes (no-ops over the shared GatedDB). None of them writes an `emb:v:*` key, a `book:<id>` row or the graph. Nor does the marker rest on the list: a verdict write made after the marker removes it (the hook, counted before the write reaches the engine), and so does a graph write. The list keeps the marker from being written while a step is known to be unfinished, before such a writer has had the chance to write. **Boot.** Every open of a database on disk takes the marker from `database.HNSWSnapshotDir` beside it (`initPebbleStore`, `claimCleanStop`), so a CLI command or tool (`cmd/pid-census`, `tools/cmd/reconcile-book-counts`, `tools/cmd/dedup-dataset-audit`, any `initializeStore` command) run between a clean stop and the next boot costs that boot a reconcile; the server's import gets what its own open took. A marker that cannot be removed is emptied, and an empty marker does not parse. With no marker that vouches, the snapshot is reconciled whatever the counts say; with one, the counts are still checked. A boot whose vector store is not HNSW takes the marker too. A crashed run's next boot always reconciles. **Child.** An operation-runner child's open does not take the marker (`DisableHNSWCleanStopClaim`), and its import checks the row counts only (`ImportCountChecked`), so a moved count reconciles in the child and the parent's marker stays. No production op sets `Isolate` today, so these paths guard unused code. **Not covered.** (1) A write to those keys from a process that opens Pebble without a `GatedDB`: the raw-pebble tools under `cmd/` write settings or only read. (2) An `Isolate` child's verdict writes count in the child's process, not the parent's, so the parent's stop could vouch after them. (3) The live mirror indexes non-primary books, which hydrate and the reconcile skip, so the graph a run builds is not the graph a boot builds (todo.d fragment). The stopgap keeps the marker from vouching for such a graph: a fresh embed writes the embedding row, a verdict write, and a cache hit, which writes nothing to Pebble, marks the graph diverged when it mirrors a row `classifyBookRow` would skip (`mirrorCachedBook`, `TestEngineMirror_ACachedNonPrimaryBookMarksTheGraphDiverged`). **Refuses more than it must, by design.** Any verdict write during a run, an embedding upsert included, means no marker, so the marker helps only quiet runs. An empty-vector mirror failure marks divergence although the reconcile skips that row anyway. |

(b) The live `Delete` (`deleteBookFromChromem`, book merge or removal) still calls coder/hnsw's Delete, the corruption class the reviewer's probe showed. A tombstone there would remove it. (c) A live re-embed of a key already in the graph is a re-Add, the same class. (b) and (c) predate this PR. |

## Risks

| Risk | Cost of the fix |
|---|---|
| **60 s hook start timeout.** The kernel abandons a hook Start after `startTimeout` (60 s, `core.lifecycle.start_timeout`) and fails boot. books' StartHook is HEAD's start up to the listener (op registration gate, container start, op catalog gate, search index, warmers), which ran unbounded in HEAD. It has not been measured at prod's size. `Deps.ExtendStart` is a no-op until R1-16 wires sdnotify into core. | Measure StartHook on prod before deploying. If it can exceed 60 s, either make the kernel honour `ExtendStart` in `startHooks` (a core change, plus a kernel test) or move the slow steps after readiness. |
| **Periodic HNSW export.** At prod's size an export took about 40 s before the buffering fix. It now runs every 10 minutes while the graph changes, on bgWG. | Measure the buffered export's duration on prod. If it is still long, raise `hnswSnapshotInterval` or export only on idle. |
