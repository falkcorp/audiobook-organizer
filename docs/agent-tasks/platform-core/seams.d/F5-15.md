# F5-15 seams and coined names

F5-15 adds the log journal dark: `log.JournalStore`, `log.Importer` and `logtest.JournalStoreSuite` in `core/log`, the native store, importer and tap in `core/internal/logjournal`, two journal series in `core/kernel`, and books' step M5 in `internal/books/cutover/m5`. Nothing is registered or started: F5-18 wires it. This file lists what the row added beyond 05-logging §5 and §9, the readings it took where the brief or the tree differed, and what F5-18, F5-19 and F6-05 build on.

## Names beyond the spec

| Name | What it is |
|---|---|
| `logjournal.Owner`, `logjournal.StorageSpec()` | The storage owner (`core/log`) and its declaration (`Spec{Keyspace: true}`, no `Serialized`: rows are appended, never updated, so a write carries no `Expect`). F5-18 registers it. |
| `logjournal.New(ks, ...Options{Now, Entropy})` | The native store. `Options` exists for tests (a fixed clock and entropy). |
| `logjournal.NewImporter(store)` | The `log.Importer`. Its key is `ULID(ms of Time, sha256("mediacore/logjournal/import\x00"+SourceID)[:10])`, so a record imported twice rewrites its own row. A record with no `SourceID` is refused (`ErrNoSourceID`), as is a zero, pre-1970 or post-9999 time (`ErrInvalidTime`). |
| `logjournal.StartTap(l, store, Settings, ...TapOptions)`, `Tap.Flush`, `Tap.Stop`, `Tap.Counters()` | The sink that feeds the journal. Name `logjournal.TapName = "journal"` (05-logging §9's sink label), not `core.log.journal` as the brief says. `Counters()` returns `TapCounters{WriteErrors, Lag, Degraded, Pending}`. |
| `logjournal.Settings`, `logjournal.Schedules`, `logjournal.SchedulesPath` | The two types `core.log.journal` and `core.log.schedules` now name. The kernel's own copies are deleted. `Schedules.Validate` replaced the kernel's `logSchedules.Validate`. |
| `logjournal.ParseLevel` | The settings' `min_level` text to a `slog.Level`. A bad value is an error, not a default. |
| `kernel.withJournalCounters` | An unexported option on `registerLogMetrics` that hands the bridge the tap's counters. Without it the two series are served at 0. See "Metrics" below. |
| `m5.New(cfg, id, raisesLevel, after)`, `m5.Config{Importer, Logger}`, `m5.Prefix`, `m5.Module`, `m5.UserIDAttr`, `m5.SourceRanges()` | M5. The step ID, the flip's level and the level step's `StepRef` are parameters: see "M5's constructor". |

## Readings taken where the brief and the tree differ

| Topic | Reading |
|---|---|
| Brief checks 6 and 7 (`Manifest.Cutover`, `Importers`) | `core/module` has neither (F3-07 has not landed), and there is no `internal/books/cutover/steps.go` to register M5 in. M5's constructor takes a `log.Importer` directly. This row does not add `Importers` to `core/module`; that is F5-18's. |
| `internal/database` | It no longer exists. HEAD's syslog code is `internal/books/store/pebble_store_activity.go` (`AddSystemActivityLog`, `syslog:<RFC3339Nano>:<source>`). |
| "One `Importer.Import` per chunk" | `datamigrate.DataMigration.Step` runs per key and has no end-of-chunk hook, so M5 calls `Import` once per row and then stages the row's delete. The import returns, durable, before the chunk batch that holds the delete commits, so a crash between the two leaves the row to be imported again onto the same key. Buffering imports across `Step` calls to import a chunk at a time would invert that order (a delete could commit before its import), so M5 does not. See the throughput note below and the follow-up. |
| Shards | The runner shards the key range itself from `Parallelism` (`PlanShards`, key quantiles, 64 samples per shard). M5 is stateless across `Step` calls, unlike M3, so shards need no coordination. `Parallelism` is `tasks.Fixed(8, ...)`: the work is one synced commit per row, which is disk-bound, and concurrent commits share an fsync. |
| Quarantine | The runner's `w.Quarantine` deletes the source key itself. The rig passes `storage.QuarantineWriter(nil)`: M5 is not `Sensitive`, so no sealer is needed. |
| `Enabled` setting | Keeps the kernel's existing `reload:"restart"` tag; the brief's struct omitted it. |
| Level strings | HEAD writes only `info`, `warn` and `error` (the logger gates at `LevelInfo`, and `Level.String()` is lower-case). M5 accepts exactly those and quarantines any other (`debug`, `INFO`, empty). |
| Row time | The record's time is `created_at`. When that is zero or outside 1970..9999 the key's time stands in: HEAD's key time is `time.Now().Format(RFC3339Nano)` in the server's zone, with colons inside, so `parseKey` cuts it by shape (`T`, then `Z` or a signed `hh:mm`, then `:` and the source) and not on the delimiter. A row with neither is quarantined as "no usable time". |
| `user_id` | HEAD's row carries one, and the corpus's rows do not, so the field mapping is checked over synthetic rows. It becomes the `user_id` attribute, and a row without one has no attributes. |
| Import cycle and the `internal` rule | m5's non-test code cannot import `internal/books/cutover` (which will import m5) and cannot import `core/internal/logjournal` (Go's internal rule across modules). Its tests, in `package m5_test`, import `cutover`. They run M5 over a test double of `log.Importer` over a `core/log` keyspace of the same store, which derives its key from time and `SourceID` the way the contract says and counts Import calls. The real importer's idempotence is proven in core (`TestImporter_IdempotentKeyAndRejections`); wiring the real one under M5 is F5-18's integration test. |
| Journal key order | A key is a 26-character ULID with millisecond precision and a per-millisecond random part drawn so that, within one process, a later append in the same millisecond sorts earlier (newest first). Across a restart within one millisecond the order is not guaranteed. `Query` and `Prune` judge sub-millisecond precision on the row's own `Time`, not on its key. |
| Time bounds | A record whose time is zero, before 1970 or after year 9999 is refused (`ErrInvalidTime`). |
| `core/kernel` edits outside the brief's file list | `core_sections_validate.go` (the kernel's `logSchedules.Validate` had no struct left to hang on, so it is removed and `logjournal.Schedules.Validate` replaces it) and `logmetrics_test.go` (the served-families list is five names, not three, and `TestLogMetrics_JournalFamiliesReadTheTap` is new). | `internal/arch/layering_test.go` | One line: `internal/books/cutover/m5` at layer 0 (computed: it imports only core packages), beside m3's. `TestLayering` refuses a package with no entry. It is not in `inventory.json`'s file list for this row: F7-02 lists the same file in the same wave, and `check_waves.py` refuses two rows that share one. Whichever of the two merges second keeps both entries when it rebases. |
| Commit trailer | `builder-rules.md` names "Claude Opus 5.5"; the session's attribution reminder names Sonnet 5.5, which is the model that wrote this. The commits carry the reminder's. |

## Metrics

`registerLogMetrics` now registers `mediacore_log_journal_write_errors_total` (an observable counter) and `mediacore_log_journal_lag_seconds` (an observable gauge, unit `s`). `testdata/log/series.golden` has the two new rows. When no tap is wired (`boot.go` is not touched by this row, so today none is) the callbacks report 0, which keeps the series present from boot. The series reading a live tap is proven by a fake counter source (`TestLogMetrics_JournalFamiliesReadTheTap`); with a real tap it is F5-18's.

## Throughput

`TestM5_ParallelShardsDisjoint` logs rows per second: 3000 synthetic rows, 8 workers, `-race`, in-memory filesystem. Two runs on the development Mac, one with the machine loaded by other builds and one quiet, logged 413 and 5,692 rows/s. The in-memory filesystem has no fsync, so the number is M5's own cost per row (one `Import` commit and one staged delete), a floor on what a real disk adds to, not a measure of it. HEAD's corpus holds two syslog rows, so M5's runtime on the owner's store is the number of syslog rows it has at cutover divided by the real fsync rate.

## For F5-18

- **Gate: count prod's `syslog:` rows before registering M5.** M5 commits once per row (one `Import`, then the row's staged delete lands with the chunk), and one synced commit per row is about 800 to 8,000 rows per second. Count the rows first. If the count implies minutes of boot time, land the `datamigrate` chunk-end hook (see Follow-ups) before registering M5, because M5 is `BootBlocking` and the server does not serve until it finishes.
- Register M5 in `internal/books/cutover/steps.go` with `m5.New(m5.Config{Importer: <module.Importers.Log>, Logger: ...}, LogCutoverID, BooksCutoverLevel, []storage.StepRef{BooksLevelStepRef(version)})` and add `Importers.Log` to `core/module`'s manifest type (F3-07's, once it lands).
- Register the `core/log` owner with `logjournal.StorageSpec()`, build the store with `logjournal.New(ks)` and the importer with `logjournal.NewImporter(store)`.
- Start the tap with `logjournal.StartTap(logging, store, settings)` and pass `withJournalCounters(tap.Counters)` to `registerLogMetrics`.
- Shutdown order: `Logging.Close` (drains the tap's queue) and then `Tap.Flush`. A tap that is `Degraded` is the source for the health token `log_journal_degraded`.
- `core/internal/logjournal/ulid.go` is one more Crockford ULID encoder in core (`core/internal/taskstore/ulid.go`, `core/outbox/stage.go`, `core/audit/store.go` and `core/library/journal.go` each declare their own Crockford alphabet); a row that touches them should fold them into one.

## Follow-ups

- A chunk-end hook in `datamigrate` (a `Chunk` callback with the chunk's rows) would let M5 import a whole chunk in one commit before the chunk's delete batch, as the brief wrote it. Measure first: rows per second on a real disk with fsync decides whether it is worth the API.
- `Verify`'s counts are the resumed boot's own (a boot that resumed after a crash reports only the rows it stepped); a durable per-step count in the checkpoint would make them whole-run. No gate reads them.
- Review nits left as follow-ups, not changed here: (a) `Tap.Degraded` is a bare flag, so the health token reports a failed write without the error that caused it; keeping the last error (and when) would let `log_journal_degraded` say why. (b) In `core/internal/logjournal/store.go` the per-millisecond entropy map is emptied with `clear(s.last)` when it reaches 4096 entries, and the current millisecond's entry is stored again straight after, so the current millisecond keeps its order. What the clear drops is the entry of every other millisecond, so a record that arrives later for an older millisecond (an imported record, or an out-of-order clock) starts from fresh entropy and can sort before an earlier record of that same millisecond. Evicting only the oldest entries would keep that order; the effect is limited to records of one millisecond at the moment the map fills, and order within a millisecond is already not guaranteed across restarts (deviation 12).
- `Verify` probes with `Reader.NewIterator` and `First()` instead of ranging over `Reader.Scan`. `TestTasklint_F518ListsOnlyFlaggedFiles` (`internal/books`, `-race`) type-checks every `internal/books/...` package concurrently through `go/packages`, and a `range` over `Scan`'s `iter.Seq2` in two packages at once is a data race inside `go/types` (the shared instance is expanded lazily by whichever checker touches it first). With `range` in m5 the test failed 3 of 3 local runs and CI; with the probe it passed 4 of 4, and main passed 3 of 3. The race is still there for every other package that ranges over `Scan` in that set (`cutover/m3`, `cutover`, `books/store`, `books`), so it can reappear when one more does. The complete fix is in `core/archtest/tasklint/run.go`: stop type-checking roots concurrently (for example by loading the module's roots with a loader whose `GOMAXPROCS` is 1, or by pre-expanding the shared instances before `packages.Load` returns), at the price of a slower tasklint test. It is not in this row.
