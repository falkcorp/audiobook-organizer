# F7-06 seams and coined names

F7-06 completes `core/library` and builds it dark: the roots registry and sentinel, the crash-safe transfer engine, quarantine, hashing, the watcher, the per-owner `Scope`, the recovery task, the metrics and the live config binding. It adds `core/internal/libfs` (the byte-level layer) and `core/internal/libraryhttp` (one route). Nothing imports any of it from the kernel until the F2-16/F7 wiring. This file lists what the row added beyond 05-library, the readings it took where the spec or the brief says nothing, what review changed, and what is owed.

## Readings taken

- **Every mutation is gated by the sentinel.** `Mounted` is identity-checked (the directory is the one opened, the sentinel names this install and this root) and runs under the path locks of each transfer. A bootstrap root gets its sentinel when the non-dot-content heuristic passes. `WriteSentinel` never overwrites.
- **Publishing never overwrites.** A copy goes to a temp name (`O_EXCL`) and is published without ever replacing a name, by the first of three steps the filesystem supports: a hard link (the temp stays and is removed after); a no-replace rename (`renameat2` `RENAME_NOREPLACE`, `renameatx_np` `RENAME_EXCL`, or for a regular file link-then-unlink); and, where there is neither (exFAT, FAT, SMB or FUSE without hard links), a reservation: the destination is created exclusively (an empty mode-0 file, or an empty `0700` directory for a directory Move), the journal row says first that a placeholder may exist (`Placing`, with the path that is to replace it), the placeholder's identity is read from the descriptor that created it, and the temp is renamed over it only while the entry is still that one. A Move on one device, Replace's restore, recovery and Release use the same protocol; a Quarantine's holding name and a replaced file's aside are fresh ULID names and take a checked rename. Replace is a compare-and-swap through an aside file that is hashed again after it moves. A Hardlink asked for on a filesystem without links is `ErrNotSupported` with the cause in the chain.
- **Reservations are the last resort and have a window.** Another process that deletes the placeholder and creates its own file in the two syscalls between the identity check and the rename-over would lose that file. Only a writer to the same directory can do it, on a filesystem that offers no atomic primitive. Recovery removes an empty entry at a destination only while the journal names a placeholder rename onto it and the path being renamed there still exists; a user's empty file that appeared in the crash window between the journal write and the create is indistinguishable and goes with it. Neither is closed by a design that works on exFAT; both are disclosed here instead.
- **Filesystem support.** ext4, XFS, btrfs, tmpfs, APFS: atomic no-replace rename, hard links, clone where the filesystem has it. NFS and filesystems without the rename flag: link-then-unlink for regular files, a placeholder for a directory. exFAT, FAT, SMB or FUSE without links or the flag: reservation for everything (`TestOnARealFilesystemWithoutHardLinks` in `core/library` and `core/internal/libfs` runs the engine and the primitives on one when `MEDIACORE_TEST_NOLINK_DIR` names a directory on it; it was run on a real exFAT volume). Windows: Transfer, Quarantine and Release are refused with `ErrNotSupported` before anything is journaled, and `libfs.Link`, `RenameNoReplace` and `RenameOver` refuse; a handle-based walk and `MoveFileEx` without `REPLACE_EXISTING` (05-library 5L.3.2) are the follow-up.
- **A transfer's row is deleted only when nothing is owed.** A failure deletes it only if the final name was not published, no replaced file is set aside, no temp or placeholder may remain; otherwise the row stays and the error is `ErrRecoveryPending`. A streamed copy owes no temp until its exclusive create has succeeded. The source of a cross-device Move is removed only while it is still the file that was copied (device, inode, size, mtime, digest), live and in recovery alike. **Residual window:** between that check and the unlink an open-descriptor writer cannot be detected; a file's content cannot be pinned without a lock the library does not take.
- **A FIFO or other special file is never waited on.** Reads open with `O_NONBLOCK` and are refused with `ErrNotSupported` unless the open descriptor is a regular file or directory; a Move refuses a source that is not a file, a directory or a link, and a cross-device Move of a non-regular source is `ErrNotSupported`, not a verification failure.
- **`Hash` is bounded.** It takes one of `runtime.NumCPU()` hash slots, so a request that names many large files cannot start more reads than cores; the byte-rate limit still applies per read.

- **Moving a directory needs oracles that can answer for a subtree.** The static `protected_paths` list answers in both directions (a path under a protected path, and a protected path under the path), by name after symlink resolution and by device and inode. A registered `ProtectionOracle` that is not a `SubtreeOracle` cannot vouch for a directory, so a directory Move or Quarantine is refused while one is registered. **Real cost:** the download adapters' seeding oracles (05-download) must implement `ProtectedUnder` before a directory Move works with them registered. A file Move is unaffected.
- **The AppDir and the Quarantine area belong to core.** No other caller names them as a transfer source or destination, a quarantine source or a release target, and a Move does not carry them inside a directory. A module reaches its own AppDir through `ModuleRoot.AppDir(ctx)`; `Root.AppDir(ctx, name)` is core-only and refuses a name that resolves into or over the Quarantine area (`ErrReservedPath`). The spec's comment on `TransferOptions.Journal` ("false only for temp files inside AppDir") reads as if a module transfers inside its AppDir; under this rule only core does. Owner views can read the areas but not write them; a reader that is not the owner (the download capability) cannot read them, through a view or through `Scope.Hash/Resolve/Abs`. **Taken literally, "files under protected paths are never moved or deleted":** a Replace refuses a protected destination (`ErrSourceProtected`) because it would set the file aside and delete it; a Move **into** a protected subtree is allowed, since protection is of what already lies there.
- **Reserved areas are decided by where a path leads, not by its name, and at the act, not before it.** `localFS.reserved` expands symlinks inside the root (a link to an area is an area; the chain is expanded by the resolution itself, up to `maxLinkHops` (255) links, and a chain that cannot be decided, longer than that or with a link that cannot be read, is refused, not taken as outside. `os.Root`'s own limit is 8 and applies only to the reads it does itself; a mutation is made on the expanded path, so the limit that bounds it is this one), folds case, and compares device and inode, so a second name for an area counts; the identities of the areas are remembered per root, so one renamed away is still recognised. Walk does not follow a link into an area. A symlink target a view is asked to create is checked the same way. Every mutation through a view for anyone but core (and every transfer, quarantine and release a non-core caller makes, via `Root.engineFS`) is then decided from the descriptor of the directory that holds the name: the directory and every one above it up to the root are compared with the areas by identity, the leaf is compared too (by `IdentityAt`), and the act goes through that descriptor (`OpenFileAt`, `MkdirAt`, `RemoveAt`, `SymlinkAt`, link and rename on the two directory descriptors). A directory swapped for a link to an area between the name check and the act is therefore caught where the act happens. Link sources are judged the same way: a sealed view refuses to link from a file reached through an area.
- **A guarded read is decided from descriptors.** `guardedOpen` opens the directory that holds the name through the root, walks that descriptor up with `openat(fd, "..")` to the root's own device and inode, compares every directory with the areas, opens the leaf relative to the descriptor without following a link, and compares the leaf too. A walk that fails anywhere refuses. Nothing re-resolves a name after the open.
- **Refusals are counted wherever the library makes one**: `Transfer`, `Quarantine`, `Release` and `Hash`. `ErrReservedPath` counts as `protected` (5L.8's label set has no other word for it).
- **The picker streams and is bounded twice.** `libraryhttp` reads a directory in chunks of 256, checks the request's context per chunk, filters as entries arrive, and stops once one more than the cap (5000) has been kept **or** 100,000 entries have been examined, so a flat directory of millions of files costs a bounded amount of work. A truncated listing (either cap) is the first directories in the disk's order, sorted, not the alphabetically first. A real `authz.Compile` checker decides the permission cells in the route tests. **Open question (n6):** the route lists every registered root the caller's `core:library.browse` permission reaches; whether a per-caller root allow-list is wanted is a product decision this row did not take.
- **`TransferRecoverTask` cannot run once at boot on `hello` or `coretest` yet.** There is no executor wiring until F2-16/F2-17; the task is tested through its definition, `taskstest.Conformance`, a fake run and the schedule harness.
- **Header date 2026-11-11 and the Sonnet 5.5 trailer** on every commit.
- **`grep -c core.library.schedules.transfer_recover core/kernel/core_sections.go` is 0**: the key is composed from struct tags F2-04 declared, not written out.
- **`core/kernel/core_sections.go` is untouched.** `core.library.roots` and `mappings` are still `[]json.RawMessage` there; typing them is owed to the kernel wiring.

## Seams for later rows

- **F2-16/F7 wiring** registers `TransferRecoverTask(m)` with `Registrar.Tasks`, builds `library.New` with the kernel's keyspace, config handle (via `Bind`), metrics scope and oracles, calls `Reload`, and mounts `libraryhttp` routes. Until then every new function in `internal/libfs` and `internal/libraryhttp` is listed in `scripts/deadcode-baseline.txt`; the wiring row deletes those lines.
- **05-download oracles** implement `SubtreeOracle` (above), or wrap the list a seeding client reports in `library.NewPathSetOracle`.
- **A bound `ExcludePaths`** is a warning and a Walk skip; it is not in the transfer or view reserved set.

## Spec amendment owed

- **5L.3.1: `Scope.Roots` returns `[]*ModuleRoot`.** 05-library lines 156, 186-187, 227 and 537 give `Scope.Roots` as `[]*Root`, `Root.FS(caller)` as callable by anything holding a root and `Root.AppDir(ctx, name)` as taking any name. A module holding a `*Root` could call `FS(CoreOwner)` or name another module's directory, which the spec's own table (line 537, "`Root.FS(caller)` is reachable only by core holders of `Manager`") forbids. The row built the correct shape (`ModuleRoot`, above) and filed the spec change as the `F7-06-5L.3.1` fragment in `todo.d/`; `docs/specs/platform-core/05-library.md` is not edited here. A module that needs a root's `Usage`, `Mounted` or its own directory calls the `ModuleRoot` methods; one that needs a `Root` is not a module.
- **5L.7, `core.library.protected_paths`: "files under them are never moved or deleted"** is read literally (Replace refuses a protected destination); a Move into a protected subtree stays allowed. Both are above.

## Found, not changed

- A hard link outside an area to a file inside one (the same inode under a second name) is readable through any view: the reserved test compares directories, not files, and a file has no path that says it came from an area. Keeping the areas free of files with more than one link is the writer's job (core writes them).
- `Stat` and `Lstat` on a hidden view are name-checked only. They return metadata and never content; a swap between the check and the call can reveal that a name exists in an area. The reads that return content (`Open`, `OpenFile`, `ReadDir`) are descriptor-checked.
- A directory renamed into an area after a guarded read opened it is not noticed: the descriptor still is the directory it was.
- An area renamed away by someone with direct access to the disk is still recognised by the identity the process remembered from an earlier check; one renamed before the process's first check is not. The sentinel lives in the AppDir, so a root whose AppDir was renamed is unmounted and every mutation is refused anyway.
- The transfer engine's early checks (`check`, `recheck`) are name-based, but each mutation a non-core caller makes is judged again from descriptors at the act (above). Core's own driver is unsealed by design.
- `Release` and `Quarantine` of a symlink move the link, not its target.
- Without directory descriptors (Windows) the guarded view refuses every read and Transfer, Quarantine and Release refuse (`ErrNotSupported`): the walk up is the check, and there is no weaker one that does not re-resolve a name or replace a file another writer created. A Windows picker and Windows transfers need a handle-based walk and `MoveFileEx` without `REPLACE_EXISTING`. `go vet ./library/` on Windows fails only on the existing `libroot_test.go` use of `syscall.Umask`.
- Windows has no directory fsync, so `SyncDir` is a no-op there (named in 05-library 5L.5).
