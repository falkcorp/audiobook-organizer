# R1-24 seams and coined names

This file covers what the "checkpoint sweeper and prune" PR added beyond 05-storage §5S.3.12 and §5S.4 step 15, 05-health §5H.3.1, §5H.9 and §5H.10, and 06 §6.4.5 and §6.5.1. It lists:

- names the spec does not have;
- the decisions the row took where the spec or the brief is silent, or wrong;
- the files it touched outside its inventory;
- what it left for later rows, with the fragment that tracks each item;
- the seams later rows build on.

From this row every checkpoint is deleted 7 days after it stops being needed: by the kernel's sweeper after readiness and hourly, or sooner by `storage prune-checkpoints`. The `storage_checkpoint_*` posture tokens travel `GET /api/v1/system/status` only.

## Decisions and deviations

Each took the recommended option. The owner was asleep and the coordinator asked for no gates.

- **D1. R1-25 has not merged, so this row creates `OfflineCommands`.** The brief's dependency check says STOP without `func OfflineCommands`. The coordinator's rule is no owner checkpoints. So this row adds `core/app/offline.go` with `Command` and `OfflineCommands`, copied verbatim from 06 §6.4.5, and `cmd/offline.go`, a generic wrapper that makes one cobra command per entry. The brief says R1-25 owns both files and that `cmd/` needs no edit here. Whichever of R1-24 and R1-25 merges second rebases onto the other. R1-25 should append its commands to the `OfflineCommands` list and reuse `addOfflineCommands`, not write a second wrapper.
  The wrapper does three things:
  - cobra parses none of an offline command's flags, so core's flag set and help are the command's own;
  - the root's persistent flags (`--db`, `--config`, `--db-type` and the rest) are taken out of the arguments, parsed, and then the config is loaded, so prune names the store serve would. The root's `PersistentPreRun` skips these commands, because it would load the config before those flags were parsed;
  - `--help` is answered without loading the config, so help never creates the state directory.
- **D2. The first-boot checkpoint is covered.** `Migrate` always calls `completeCheckpoint` at its end, even when it runs no step, so R1's first-boot checkpoint completes and is deleted 7 days later. `TestCheckpointAutoDeletedAfterSevenDays` checks this against R1's own first-boot checkpoint.
- **D3. The sweep lock, kept and then narrowed to the OS filesystem.**
  - **Kept.** An earlier advisor pass said no lock was needed. It is kept because prune runs while the server serves, so without it the hourly sweep can write `delete_after` into a record prune has just deleted.
  - **Narrowed.** It is now taken only when `vfs.Root(fs) == vfs.Default`, the same rule the chmod and directory-identity helpers follow. The evidence is a deadlock in ABO's crash matrix, at `TestBootCrashMatrix_ABO/checkpoints-to-sweep` (10-minute timeout):
    1. Pebble's cleanup goroutine reached a kill point, and the kit's recorder called `MemFS.CrashClone`, which takes `cloneMu.Lock`.
    2. The sweeper was inside `MemFS.Lock`. That function holds `cloneMu.RLock`, then takes it again inside `Create`.
    3. The second `RLock` queues behind the pending writer, which waits on the first `RLock`.
  - **Cost.** A MemFS is one process's memory, so no other process can prune it. Leaving it unlocked gives up only in-process exclusion in tests. `TestPruneCheckpoints` now checks the busy case on the real filesystem.
- **D4. Prune deletes records only.** Garbage, scratch and modes stay the sweeper's. A store that is booting may be writing a checkpoint whose record does not exist yet, and a prune that removed record-less directories could delete it.
- **D5. The kit freezes at "kernel: start complete".** 06 §6.5.1's writer table has an "After readiness" row, so the first sweep's writes must be inside the range the kit breaks. This moves the kit's freeze for every app. The first sweep runs to completion even when Run's context is already done, which is how the kit stops every boot.
- **D6. `crashmatrix.Row.Retried`.**
  - **Problem.** A sweep that fails is logged, and the server serves anyway; the next period repairs the state. The kit's error runs ended at the first boot that reached readiness, so an injected ENOSPC or EACCES at a sweeper label left a partial or expired checkpoint that I6 then failed.
  - **Change.** For a row marked `Retried`, the kit checks I2 and I3 on the state the failed sweep left, boots once more, and checks I1 to I6 after that boot's sweep. The rule is not weakened: the retry must still repair the state.
  - **Tests.** `TestKitRebootsAfterARetriedWritersError` proves the reboot is what makes the run pass. The same writer without the flag fails I6.
- **D7. `degraded_details`, a sibling field.** 05-storage says `storage_checkpoint_retained` travels "with its `delete_after`", `_open` "with its age" and `_mode` "naming it". R0's `degraded` is a list of strings, and clients read it. Rather than change its shape, the subjects travel a new sibling list, `degraded_details`, of `{token, subject, delete_after, age_seconds}`, on the same authenticated route. It is `[]` when nothing is raised.
- **D8. The split of HEAD's fixed-token source.**
  - `/health` keeps only the tokens `unauthenticatedToken` accepts: `memdb_warming`, `basic_gate_no_password`, and the token of any `startup.Table` step classed `Degraded`.
  - `GET /api/v1/system/status`'s `degraded` carries every token: the fixed source, `auto_update_paused` and the posture tokens.
  - The filter derives the startup tokens from `startup.Table` rather than a literal list, because Table is the review record for a step's class. As a result, `TestHealth_UnauthenticatedTokenSetGolden`'s array and the filter are two sources that must agree. A new Degraded step's token reaches `/health` without a golden edit unless a cell raises it.
  - The R1 cell feeds a posture token through the fixed source too, so a `/health` that stopped filtering fails the test.
- **D9. A failed health read still raises `storage_checkpoint_retained`.** The copy holds plaintext secrets, so a checkpoint directory that cannot be listed is reported, with a fixed subject, rather than left out.
- **D10. No worker pool.** A store has single-digit checkpoints, and the crash-matrix labeller needs the first sweep on one goroutine, so the sweep is a plain loop (CLAUDE.md's concurrency rule targets library-scale loops).
- **D11. Fake clocks, not `synctest`, in `core/storage`.** The storage tests drive the clock through `OpenOptions.Clock` and `PruneOptions.Clock`. The spec marks `TestOpenCheckpointKeptWhileRollback` "(`synctest`)". The kernel's loop test (`TestSweeperRunsAtOnceThenHourly`) does use `synctest`.
- **D12. The brief names `internal/books/module.go` for the wiring.** The provider is installed in `Attach`, which lives in `internal/books/options.go`. `module.go` is unchanged.
- **D13. The crash-matrix kit's checkpoint grammar is a function.** `isCheckpointName` replaces a package-level `regexp`, because core's `TestNoInitOverCore` (03 R5) bans package-level mutable variables.

## Seams later rows build on

- **R1-25:** add `storage restore-offline` and `storage reset` to `OfflineCommands`. `cmd/` wraps them with no further edit. Prune already refuses while `restore/pending.json` or a `restore/<id>/inflight.json` exists. It probes the slot after it takes the sweep lock, so `restore-offline` should hold `.sweep.lock` while it stages and swaps.
- **F2 (health registry):** replace books' `checkpointPosture` and `App.CheckpointHealth` with a core health check over `Kernel.CheckpointHealth`, and audit each deletion.
- **F8 (core endpoints):** the posture tokens move to core's authenticated endpoints. `degraded_details` goes with them or is replaced by the registry's subject field.
- **Any new post-readiness writer:** add a writer table row. Mark it `Retried` only if a later run repairs its failure.
