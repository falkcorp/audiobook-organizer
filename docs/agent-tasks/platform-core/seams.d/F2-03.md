# F2-03 seams and coined names

This file lists what the fresh executor (`core/internal/executor`) and the parity kit (`core/tasks/taskstest/parity`) added beyond 05-tasks, the readings F2-03 took where the spec or the brief says nothing, and the seams later rows build on. Everything not listed here follows the spec as written.

## Names beyond the spec

| Name | What it is |
|---|---|
| `executor.New(Options) (tasks.Executor, error)` | The constructor. Nothing outside core imports the package (the internal path enforces it); the kernel builds it at F5. |
| `executor.Options` | `Config`, `Stores`, `NewBatch`, `Keyspace` (the idempotency records), `Definitions`, `Manifests`, `Catalog`, `Principal`, `Health`, `Lanes`, `ChangeSinks`, `OnTerminal`, `Metrics`, `InstrumentsOff`, `Logger`, `Now`, `Getenv`, `ExtendTimeout`. |
| `executor.Config` | The `core.tasks.*` keys of 5T.10 the executor reads (`Workers`, `SystemWorkers`, `CPUSlots`, `Kinds`, `ShutdownDrain`, `ShutdownExtendMax`, `MinCheckpointInterval`, `MaxYields`, `ZombieCap`, `StandDownLease`, `IdempotencyTTL`, `ModuleMaxConcurrent`), plus four fixed timings tests may set (`DispatchTick`, `WatchdogInterval`, `ProgressInterval`, `MaxAttempts`). F3-01 fills it from core config; the config-file and JSON-env cells of `TestParallelismCap_LowersDeclared` wait for that. |
| `executor.Reconfigure(x, Config)` | Applies the hot keys; the restart keys are ignored. |
| `executor.Manifest{Module, Enabled, TaskLedger, TaskStarts}` | What the executor needs from a module manifest: held runs (5T.3.11) and the system actor's `TaskStarts`. F2-16 passes the kernel's manifests. |
| `executor.Principal` | `func(ctx) (tasks.Actor, rbac.Checker, bool)`: resolves a Client call's caller. F2-05's HTTP layer supplies it. |
| `executor.Attributes()`, `executor.InstrumentNames()` | The attribute keys for the kernel's `Provider.Core("ops", ...)` scope and the 18 instrument names (05-metrics §12's executor cell). |
| `executor.ScheduleMetrics`, `executor.Schedules(x)` | The scheduler's (F2-04) handle on the three schedule instruments. |
| Sentinels `ErrUnknownKind`, `ErrHeld`, `ErrNotPermitted`, `ErrPlanRequired`, `ErrPlanInvalid`, `ErrPlanTooOld`, `ErrApprovalRequired`, `ErrPlanRejected`, `ErrPlanDecided`, `ErrNoApproval`, `ErrReservedCheckpoint`, `ErrRowNotInPlan`, `ErrNotAwaitingDecision`, `ErrHoldLost`, `ErrLaneNotDeclared`, `ErrNoLaneCapacity`, `ErrDirtySource`, `ErrAlreadyRunning`, `ErrShuttingDown` | They live in the executor, not in `core/tasks`. **Seam:** F2-05 maps them to HTTP (404 `tasks.unknown_kind`, 403 `tasks.actor_not_permitted`, 409 `tasks.held`) and F2-16 needs `ErrHeld`; whichever comes first moves the ones it needs into the SDK. |
| `parity.Cases()`, `parity.Excluded()`, `parity.ExerciseInstruments`, `parity.ProbeKind`, `TestParity_ResumeCancelShutdown` | The oracle kit (functions, not package variables: 03 R5). A case asserts that it fired, so an executor that reads nothing in that window fails the case instead of passing it. |
| `tasks.ItemsOptions.PartitionBy` | Added to 05-tasks 5T.3.2 by this PR (spec 1.19.0): a key's items run on one worker in order, each its own item. A Batch's and a Fixer apply's `PartitionBy` use it. |

## Stored formats the executor coined

| Record | Format |
|---|---|
| Checkpoint envelope | `{"core_attempt": <attempt>, "v": <body's JSON>}`. A value without the envelope (one the cutover imported) is read as it is. |
| Reserved checkpoint names | `core.rc` (RC's unnamed checkpoint: the store refuses an empty name), `core.zero` (the attempt from which ResumeFromZero voids earlier checkpoints), `core.approved` (an apply run's approval: `{"plan": <plan run ID>, "rows": [<row IDs>]}`; the apply run applies only while `plan` is its own `PlanRef`, and fails closed with `ErrNoApproval` otherwise). A run body may not write or read any `core.` name (`ErrReservedCheckpoint`), so it cannot forge an approval. |
| Fixer plan rows | Stored as `plan:<Row.ID>` (`ReplaceRows` clears by prefix). Approve, the marks and the apply run use the bare `Row.ID`. **Seam:** F2-05's rows route strips the `plan:` prefix when it lists a plan. |
| Decision events | `RunEvent{Event: "approve"}` or `RunEvent{Event: "reject"}` on the plan run, appended by a move on the plan's record, so a decision and the approval's apply run commit together. The first decision event is the plan's decision: a second approve or a reject after an approve is `ErrPlanDecided`, anything after a reject is `ErrPlanRejected`, and an apply run whose plan carries no approve event applies nothing. |
| Notification failure | When `OnTerminal` fails, the terminal transition commits without it and carries a following `RunEvent{Event: "notify_failed"}` and an `error` log line numbered `attempt<<32 \| 0xFFFFFFFF` (last in the attempt's log page). **Seam:** 05-notify/F2-05 can re-publish from the event. |
| Idempotency records | `idem/<kind>/<key>` in the tasks keyspace, kept `IdempotencyTTL`. |
| Reasons the executor writes | `cancel`, `shutdown`, `quiesce`, `timeout`, `error`, `watchdog`, `unknown_kind`, `resume_drop`, `resume_ask`, `restart_loop`, `yield_without_progress`, `yield_not_continue`, `max_yields`, `decided_drop`, `decided_finish`, `superseded`. |

## Readings taken

- **Approve permission.** Approve and reject need `Perms.Approve` (5T.3.7). There is no fallback to `Perms.Start`, because that fallback is decide's rule and definition validation guarantees `Perms.Approve` whenever `Approval` is set. The apply run is a start, so the approver also needs `Perms.Start`. A call with no caller identity (no `Principal`, or a context it resolves to no one) is refused with `ErrNotPermitted`: a decision is always a person's. The verified-method half (SEC-24) belongs to F2-05's route.
- **A plan is decided once.** Approve and reject record the decision on the plan as a move (above), so concurrent approvals of one plan start exactly one apply run and the others get `ErrPlanDecided`. Approve always starts a new apply run: it never folds into a queued run, and a later start of the kind never folds into a queued apply run (Dedupe skips any run with a `PlanRef`, in both directions). That is why a Fixer may declare `Dedupe`: a fold could otherwise carry one plan's approval into another plan's run.
- **A Fixer's Approval needs `PlanRequired`.** Definition validation refuses a Fixer whose `Approval` leaves it false: every apply run applies an approved plan, and the conformance suite checks it.
- **A plan_ref only through Approve.** `Start`, `StartIn` and `rc.Enqueue` refuse a start that names a plan (`ErrApprovalRequired`). A Live start of a kind whose `Approval.PlanRequired` is set, without a plan, is `ErrPlanRequired`. An apply run with no approval record applies nothing (`ErrNoApproval`). A Live Fixer run that names no plan fails with `ErrPlanRequired` and applies nothing: no start path makes one, and the runner no longer evaluates and applies live when it finds one. A ResumeFromZero resume keeps the approval.
- **Decide permission.** Decide (Resume, Finish, Drop on an `awaiting_decision` run) needs `Perms.Approve`, else `Perms.Start`. As with Approve, a call with no caller identity is refused with `ErrNotPermitted`, after the held check (`ErrHeld` first). Kernel-internal callers that carry the actor use `DecideAs`.
- **Child starts (`rc.Enqueue`).** A child runs as its parent's actor, with trigger `parent` and the parent link. An option may set its mode, params or priority. An option that sets its actor, parent, trigger or idempotency key is refused with `ErrNotPermitted` before anything is staged, and one that names a plan is `ErrApprovalRequired`. The start is bounded by SEC2-15's rule for the module whose body makes it: its own kinds plus its manifest's `TaskStarts`, and its system actor's checker must hold the child's `Perms.Start`. When the parent's actor is itself a module system actor, that actor's rule applies too, so a run another module's system actor started may enqueue only kinds both modules reach. A user's own grants are not consulted. No request principal reaches a body, and a resumed run outlives its request. A child whose `Perms.Start` needs `core:admin` or an `AuthRequired` scope is therefore started directly, never enqueued. With no `Catalog` every child start is refused (`authz.ForSystem` denies all).
- **An overtaken claim ends by its committed stop.** When a hold or Shutdown overtakes a claim after a cancel or watchdog stop committed its move to `stopping` but before the attempt went live, the release ends the run `canceled` (event `cancel`, the stop's reason) and its body never starts. It is not re-queued, which would undo the cancel. The same holds whether or not `stop` had handed the attempt its cause yet. A repeat cancel then gives `tasks.ErrRunNotFound`.
- **Continue in place.** It is honoured only for `ResumeContinue`. Progress counts only past the attempt's starting `Done`. A refused yield names the missing proof.
- **Shutdown of a Continue run** stamps `interrupted`, not HEAD's `interrupted_quiesced`. A `ResumeDrop` run stopped by Shutdown is stamped `interrupted` and dropped by the next boot's sweep.
- **Repeat cancel.** A run that is already terminal gives `tasks.ErrRunNotFound`; one in `stopping` gives nil.
- **Bounded drain.** Shutdown waits at most `min(ShutdownDrain, ctx deadline)`, plus one systemd extension for Uninterruptible runs.
- **Run log pages** are written only through `rc.Note`.
- **`DirtySet` sources fail closed** (`ErrDirtySource`) until the dirty-set store exists.
- **Watchdog** strikes Task-shaped runs only. Batch and Fixer runs are timed by their item loop.
- **Stand-down** quiesces only runs whose kind declares `Yields`.
- **`ref_lock_wait` buckets** are chosen here (milliseconds to ten minutes), since HEAD has no such histogram.
- **`Run` returns after starting its goroutines.** They stop at `Shutdown`.
- **Supersession of stale quiesced runs** (HEAD `supersedeStaleQuiesced`, `resume.go:65-71`; 05-tasks says nothing). Kept, because the parity kit's oracles require it: at boot, per kind, only the newest quiesced run is re-queued, and none when a queued, waiting or running run of the kind exists, unless the kind merges queued params (`Dedupe.Merge`). The rest end `interrupted_dropped` (reason `superseded`). Runs a surviving stand-down marker keeps take no part.
- **A cancel is final.** Cancelling a run that is `stopping` for a quiesce or a shutdown turns the stop into a cancel (the run ends `canceled`, not resumable); one stopping for a cancel, the watchdog or a timeout is answered nil. A cancel that lands after the attempt decided its outcome still ends the run `canceled` unless the body succeeded.
- **Cancel and claim.** The in-process attempt is looked up inside the cancel's CAS, from the read it is staged against, and a claim whose `running` commit landed but whose attempt has not started takes the stop as it goes live: the attempt ends by that stop and its body never starts (HEAD's pickup gate). Starting the body with an ended context would let an uncooperative body do all its work after the cancel. `move` re-reads the run after staging and decides again when the event sequence moved, because Transition's guard covers only state, attempt and fence.
- **Shutdown and a claim not yet live.** Whether Shutdown is under way and whether the attempt goes live are decided together, under the lock Shutdown takes its view of the live attempts under. An attempt is either in that view (canceled, then stamped) or released to the queue without starting (claimed-not-started, 5T.4 step 4). A run stored `running` is therefore not proof that its body runs: tests that need it interrupted wait for the body.
- **Stand-down and a claim in flight.** `startAttempt` checks the stand-down holds in the same critical section as Shutdown's check, so a claim that committed while a hold on its key was taken is released to the queue, and the dispatch gate defers it while the hold lives; it never goes live beside the hold.
- **The writer refuses a stopped run.** `Writer.Do` refuses with `tasks.ErrFenced` once the run's context is done (cancel, timeout, quiesce, watchdog, shutdown), at entry and again after the write-ahead intent, matching HEAD's `opswriter` fence check. A stopped run records no intent and its `fn` never runs, even inside a cancel's grace while the fence is still intact.
- **A superseded attempt writes nothing.** The ledger re-checks the stored attempt and fence on every write, so an attempt that another executor's resume superseded (its own fence intact in memory) has its late checkpoint refused with `ErrFenced`.
- **`storage.GetForUpdate` keeps the first read's precondition** (fixed in `core/storage` by this PR; 05-storage's review history). `move` reads the run row in `Transition` and again when it appends the event; the second read used to replace the precondition with a value committed in between, and two concurrent approvals both committed.
- **`OnTerminal` failure** never leaves a run in limbo: the batch the hook staged into is discarded, the transition commits without it, and the failure is recorded on the run (above) and logged at error. A crash still commits both or neither.
- **A resumed Fixer apply** reports the rows earlier attempts applied (their marks) in `AfterApply` and `Applied`, while their changes still stand: with the module's `ChangeSink`, `Stands` decides; a row whose history was undone is skipped as changed since the plan and not written again.

## Seam for F2-16: a per-module Client

The executor trusts its caller to set who a start is for. `Start`, `StartIn` and `Approve` resolve the caller through `Options.Principal`; with no principal, or a context it resolves to no one, `Start` takes `req.Actor` as given and runs no permission check (`start.go`, `stamp` and `permitStart`). `rc.Enqueue` is the exception: a body's child start is always checked against its module's reach (above). Approve and Decide refuse a call with no identity. The kernel must therefore never hand the raw executor to a module. F2-16 gives each module its own `tasks.Client` wrapper that sets `req.Actor` to that module's system actor (or the verified caller it forwards) and runs the start check before calling the executor. A module that holds the executor itself could start any kind as any actor.

Open for F2-16 or a 5T.3.7 follow-up: an option may state Live for the child of a Preview run, and the executor honours it, because the spec says only that a child with no mode takes its parent's. Whether a Preview parent may start a Live child is a design decision. This PR does not make it.

## Known issue kept for parity

- A parent that awaits a child whose write set overlaps its own waits until it times out: the write-set gate has no parent exemption, as at HEAD (Gate 3b). This PR keeps the behaviour. **For the F5 conversion rows:** a converted definition with that shape needs disjoint write sets or a ref lock.
