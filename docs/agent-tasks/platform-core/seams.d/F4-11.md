# F4-11 seams and coined names

This file covers what the "revocation journal integrity and boot re-apply" PR added beyond 05-backup §5B.3.6 and §5B.9, 06 §6.5.1 P4d steps 2 and 3, and 05-rbac §7.1. It lists:

- names the spec does not have;
- the decisions the row took where the spec or the brief is silent, or offers a choice;
- the files the PR touches beyond the brief's list;
- how the brief's test names map to tests;
- what it leaves for F4-08, F8-01 and later.

Everything here is dark. Nothing in `boot.go`, `kernel.go` or `main.go` calls `reapplyRevocations` or `runRestoreHooks`; F4-08 calls them at P4d. Nothing opens the journal component until F4-08 binds it.

## Decisions where the spec is silent

1. **No unauthenticated journal mode.** `NewComponent` and `OpenFile` need `Keys` and an install ID. A journal without a MAC would be a file anyone with the backup directory could rewrite; the brief's SEC2-9 forbids it.
2. **The MAC covers the exact stored bytes.** `mac` is the last member of every line, and the canonical form is the line up to it. Verification splits the stored line the same way, so no encoder detail (time format, nil against empty slice, member order) can make a verified line differ from what was signed.
3. **Any open failure still yields a broken `File`.** F4-04's rule that `Gap` must work after a failed open is kept: a bad MAC, a retired kid, a header of another install, a read error and a lock refusal all return a `File` whose `Append` fails and whose `Gap` records the interval, along with the error.
4. **Hook lines carry the restore seq.** The kernel wraps the journal handed to the hooks (`stampRestore`), so every line a hook appends carries `RestoreSeq`. That is how a later boot tells an aborted restore's hook lines (never replayed, never evidence) from a committed one's. If the restore line could not be appended (journal broken), the hook lines are unstamped and audit keys its records on the run ID instead of a seq (decision 41); such a boot has `Revocations == nil` and the hooks fail closed anyway.
5. **Broken journal fails closed once, by fingerprint.** A chain that does not verify, a fork, a pruned file, a journal below the anchor or a journal behind the store's head sets `c/backup/journal_broken_closed` to the chain's fingerprint after `Apply.FailClosed` ran. The same broken chain at the next boot is not failed closed again (an operator may have fixed what the fail-closed step undid); a different break is. The fingerprint is `seq|reason|tied|head.Seq|state` (v2), where `tied` is the last mac that verified before the break for a chain that breaks and the mac of the chain's line at the store's head plus its header's base seq for one that does not (decision 32); it no longer includes the length the file *claims* (`ClaimedEnd`). A forged line appended after the break changes only the claim, so under the old key an attacker with write access to the backup directory could mint a new fingerprint at every boot and bump every epoch each time. `state` is `""` for a plain break and `forked` for a forked journal (a line this build cannot apply used to add `unknown:<seq>:<kind>:<mac>`; it no longer stops anything, decision 36). No automatic journal rolling: replacing a broken journal is an operator action, out of scope. `CreateBased` is the primitive for the other-install reset.
6. **A bind failure never skips the verified tail.** If `Bind` fails (file locked, unreadable path), the tail of a journal that did verify is still re-applied; only a chain that is untrusted (broken, forked, pruned, another install's that could not be set aside) is skipped.
7. **An unreadable journal file is a break.** A read error other than not-exist gives a synthetic `Break` (`ClaimedEnd` = max uint64) and fails closed at any head, including 0. A missing file is an empty chain.
8. **An unreadable or undecodable location file with a journaled store reads as replaced.** §5B.3.6 says only that a missing file reads "no marker". A present file that cannot be read cannot be told from a deleted one, and a deleted marker next to a store that has a journal head or a served-boot pair is exactly what a restore from an old copy looks like. The classifier takes the fail-closed reading (`LocUnreadable`); a store with no head and no pair is still the same store.
9. **Another install's journal that cannot be set aside is untrusted.** Its lines are never re-applied. If renaming it fails and the store's head is above 0, the boot fails closed (the store's own journal is gone) and reports broken. At head 0 it only reports: the foreign journal's seqs are not this store's, so "the store is behind the journal's last revocation" is never asked of it, and a store that never journaled has lost nothing to it.
10. **A header written under another keyring is a break.** A journal whose header verifies under no key this keyring holds lands in the `Break` path and fails closed once; it is never silently accepted and never silently discarded.
11. **Evidence (c) excludes aborted restores.** A `restore` line a later `restore_aborted` names, and the hook lines stamped with it, are neither resumed nor counted as proof that this store was replaced, because that restore's boot swapped back.
12. **Replaced-store markers.** When the external restore line of a replaced store was recorded, `served_boot` and the location file are written at the end of step 2. When it could not be recorded (journal broken) they wait until after the hooks, so a crash in between replays the hooks. On a restore boot they always wait (`Deferred`), which is `TestRestoreBootWritesMarkersAfterHooks`.
13. **`restore_hooked` is written by the kernel after the hooks**, in its own batch. Hooks are idempotent, so a crash between the last hook and that write replays them harmlessly.
14. **A restore boot with a broken journal journals `restore_line` with seq 0** (the restoreswap edge records "no line") and still runs the hooks, with nil coverage. It is never failed closed in step 2: the hooks do that themselves.
15. **A restore boot never moves the journal** unless the restore journal says the move is owed, and the location file is trusted for the recorded journal path only when it `Describes` this store.
16. **The tail re-apply is ordered and sequential by design.** Lines are applied in seq order in chunks of 128 (`TailBatch`); each chunk is two batches, auth's and then rbac's with the head, each with `RetryOnConflict` (decision 21). Two workers could apply a role narrowing and a later assignment out of order. This is the case CLAUDE.md's concurrency rule allows for: correctness depends on strict order. The code carries a comment saying so.
17. **Last-admin rule.** An admin a journaled revocation would lock out is kept (the batch skips the whole line and reports `KeptAdmins`) and then restricted by `RestrictLastAdmins` (one call, one batch, for every holder the line kept), so the instance stays reachable and the keep is visible. rbac's hook restricts nobody itself.
18. **Adapter details.** `restoreUsers.ScanUsers` skips `ErrUndecodableRecord` rows instead of failing the boot; `StageRoles` uses the version it scanned; `PutUser` surfaces `ErrConflict` at stage time so the batch retries.
19. **Audit counts shape.** The audit hook's report is `Details{"counts": [{family, n}]}`.

Review round (the independent T4 review of 8ca82e88b):

20. **A journal that does not fully verify still applies what did.** A chain with a `Break`, a journal below the anchor, or a pruned file yields its verified lines after the store's head to the tail re-apply, and then fails closed. The store lacks nothing those lines hold, whatever the rest of the file is; refusing them would leave a revocation unapplied that the journal proves was made. Two chains apply nothing: another install's (its seqs are not this store's) and a forked one (`forkedAt`: the verified line at the store's head has a different mac than the head the store committed, so even the lines before the break are another history). `forkedAt` answers for any chain that verifies at the head's seq, broken later or not; a chain that breaks before the head cannot answer and is reported by its break.
21. **The tail re-apply once lost auth lines, and why.** `StageReapply` of auth and of rbac staged into one batch. A user disabled by an auth line and given a role change by an rbac line had both rows written under one key, and the second stage replaced the first. The tail now commits auth's batch first (`Apply.Auth`, its own retry) and then rbac's batch plus the head (`Apply.RBAC`, its own retry), and `authstore` and `rbacstore` refuse a second stage of the same key in a batch with `ErrDoubleWrite` (read through `GetForUpdate`; a view that differs from the one this batch staged is re-read, and only a committed value equal to the staged one is an error, so a concurrent writer is still `ErrConflict`, not a false double write). The last-admin guard of the rbac batch therefore sees the disables auth's batch committed before it.
22. **The head moves last.** The head below the location file's anchor and the journal lines after the head are the evidence a store was replaced; committing the head erases both. So for a replaced store `writeBookkeeping` writes the external restore line (and any gap line) with `WriteLine` before the first batch moves the head, and the last chunk of the tail commits the `Pending` head the line owes. When that line cannot be written (journal not bound, broken, unwritable) the boot holds the head: no batch stages one, the journal refuses further appends (`Hold`, because the hooks' stamped lines would otherwise stage a head), `reapplyResult.Held` carries the head, and `runRestoreHooks` commits it with `journal.CommitHead` once every hook has run and `restore_hooked` is written, and then lifts the hold (`Resume`), so the journal takes lines again and health stops reporting it unwritable; a hook that fails leaves the hold and the head where they were. A crash anywhere before that reads as a replaced store again. Spec amendment: 05-backup §5B.3.6 puts the tail (3) before the restore line (4); that order commits the head with nothing durable saying why, so a crash between them loses the verdict. The row is amended in `todo.d/2026-11-11-f4-11-spec-reapply-order.md`.
23. **Restore boots keep the spec order.** A restore boot's restore line is written after the tail. Nothing reads a restore boot's head as evidence (R6-4) and its restore journal is the durable verdict. Because a resumed boot recomputes the boundary from the chain, the boundary a retried restore line records can differ from the first attempt's; the line is found by restore ID, so it is never duplicated, and the difference is benign (boundary only ever rises with the head).
24. **The anchor is checked against the journal, not only against the store.** `checkAnchor` compares the location file's committed head (when the file `Describes` this store and its head seq is above 0) with the journal: a chain that ends below the anchor's seq gets a synthetic `Break` (`below_anchor`, `ClaimedEnd` raised to the anchor), a chain whose line at the anchor's seq has another mac gets `forked_anchor`. The head and the file travel together when a store is copied back (the store's head drops, the file's anchor does not) but a truncated or substituted journal next to a current store used to verify. A location file that does not describe this store, or whose anchor is seq 0, leaves the chain alone.
25. *Superseded by decision 36.* A revocation line this build cannot apply used to stop the tail, hold the head below it, refuse later appends (`Component.Refuse`), refuse coverage and fail closed once, with the unknown line's seq, kind and mac in the fingerprint.

26. **The journal path is never followed through a link.** `openJournal`, `ReadFile` and `MoveFile` open with `O_NOFOLLOW` and check the descriptor is a regular file; `MoveFile` also `Lstat`s source and destination, creates the `.moving` temp `O_EXCL|O_NOFOLLOW` after removing any stale one, and `setAside` `Lstat`s before renaming. A symlink in the backup directory otherwise lets whoever can write there point the journal (and the lines appended to it) at a file of their choosing, or make the boot rename an unrelated file. Refusals wrap `ErrNotRegular`.
27. **`Describes` compares cleaned paths and an empty db_path never matches.** It does not resolve symlinks: resolution would make two stores the same store because of where a link points today, and the file's job is to say what this boot recorded. `ReadLocation` errors on a file that decodes to no db_path or no install ID (`{}`, `null`), which the classifier already reads as an unreadable file.

Second review round (the independent re-review of 3620d5919: 0 BLOCKER, 1 MAJOR, 2 MINOR):

28. *Superseded by decision 36.* The known lines after an unknown kind used to be applied in batches of their own with no head (`tailPlan.Later`) because the head stayed below the unknown line. The head now passes it, so there is no `Later`.

29. *Superseded by decision 37.* `File.Hold`, `File.Resume` and `File.Refuse` are deleted; the hold that a replaced store's boot takes lives on `Component` (`Hold`, `Resume`), and nothing refuses for good any more.

30. **A named pipe at the journal path is refused without blocking.** `ReadFile` opens with `O_NONBLOCK` (`openNoBlock`, per OS) so the open of a FIFO returns and the regular-file check refuses it; a plain read-only open waits for a writer and hung the boot. The writer's `O_RDWR` open of a FIFO does not block on the supported systems and is refused by the same check.
31. **A journal file over 256 MiB is `ErrCorrupt`.** The file is read into memory whole, in a boot that has not bound the journal, so the read is capped: by the file's size before any of it is read, and by a `LimitReader` while reading (a file that grew). A line is a few hundred bytes, so the cap is hundreds of thousands of revocations; the boot treats the error like any unreadable chain (breaks, fails closed once, reports broken).
32. **The fingerprint names the state, not the tail.** For a chain that does not break (forked, pruned, a line this build cannot apply) the old `PrevMAC` was the chain's tail, which the boot itself moves by appending its restore line, so a replaced store with an unknown kind failed closed at its first boot and again at its second (one extra epoch bump). It now keys on the line at the store's head and the header's base seq (a line this build cannot apply no longer stops the tail, decision 36, so it needs no tag).
33. **`forkedAt` applies nothing; `forked_anchor` applies the verified lines.** `forkedAt` (the chain's line at the store's own head is not the one the store committed) means the lines are another history, so nothing is applied. `checkAnchor`'s `forked_anchor` and `below_anchor` (the location file's recorded head is contradicted further on) say the journal does hold the store's head: the verified lines after it are applied, then the boot fails closed. The code comments say so on both.
34. *Superseded by decision 36.* The refusal made before the tail was applied, so that the re-apply's own journaled lines could not take the head past an unknown line, is gone with `Refuse`. What keeps the head from passing a line that is not handled is the order of the steps (decisions 36 and 39).

35. **A line is at most 1 MiB, and the bound comes before any buffer is sized from it.** `maxLineBytes` (1 MiB, newline included) is checked by `seal` (before it computes its output's capacity from the object's length; CodeQL flagged that arithmetic as `go/allocation-size-overflow`) and by `unseal`, both returning `ErrLineTooLarge`. A revocation too large to journal fails its `Append` like any append failure (the revoking caller records a gap and the file stays usable); a stored line over the bound reads as a `malformed` break. No revocation is within three orders of magnitude of it.

Follow-up round (the revocation line a build cannot apply, the hold, the audit run key):

36. **A revocation line this build cannot apply is queued, not a wall (replaces 25, 28, 29 and 34).** `KnownKind` is the build's declared set. `IsRevocation` still counts a kind it does not know as a revocation, so a newer build's line is never read as bookkeeping and skipped. `reapplyRevocations` records every such line after the store's head in `c/backup/journal_unapplied/<seq>` (`queueUnapplied`: durable, in batches of `TailBatch`) before `applyTail`'s first batch; `applyTail` steps over the line and the head passes it like any other. An entry is a pointer, not a copy: `{seq, mac, kind, at, closed}`. A build that knows the kind applies the line only if the verified chain holds that seq with that mac (`drainUnapplied`, through `Chain.LineAt`) and deletes the entry in the batch that applies it, so a line is applied and dequeued together or neither. Holding the head below the line, as 25 did, made every later boot re-apply the lines after it (undoing an admin's re-enable or a new password), and refuse the journal for good. Nothing about a queued line is a break: `reapplyResult.Broken` stays nil, the journal takes lines and its health is unchanged. A restore boot queues too, and so writes its restore line under the unknown line; the journal used to be refused for good, so that line could not be written, the restore journal recorded seq 0 and a later `restore_aborted` could not name it.
37. **The hold lives on the component, and nothing refuses for good (replaces 29).** `File.Refuse`, `File.Hold`, `File.Resume` and `Component.Refuse` are deleted. `Component.Hold(err)` makes `Append`, `AppendLine` and `WriteLine` fail with `err` until `Resume()`; it survives `Bind` (a held boot that rebinds stays held), the file's own break is what is reported first, and `Health()` reports `revocation_journal_unwritable` with the hold's detail. Only a replaced store whose restore line could not be written holds the journal (decision 22).
38. **A line this build cannot apply answers once per entry.** A boot that queued a line may have left a revocation the store lacks, and fail-closed (auth's restore fallback: every API key needs_confirmation, every credential epoch bumped, every session deleted) is what answers that. A plain boot runs it once if any entry is not `Closed` (and not at all when this boot already failed closed for a broken chain), then sets `Closed` on the entries it answered (`MarkUnappliedClosed`, a plain batch; a crash between the two repeats the pass at the next boot). An entry is never answered twice. A restore boot does not run the pass: its hooks do their own fallback, and the entries stay open for the next plain boot, as the stopped re-apply they replace did, so a restore onto a journal with an unknown line costs the hooks' pass and one more at the next plain boot. While the queue is not empty every boot logs a Warn and reports the count in `reapplyResult.Unapplied`.
39. **No head completes, and nothing appends, before the tail is handled: a kept last admin is restricted last.** The restriction of a kept last admin (`RestrictLastAdmins`, journaled) is an append, and an append stages its own seq as the head, above every line in the journal. It used to run straight after the chunk that kept the admin, and in the drain before the tail was queued or applied, so a crash right after it left every later line below the head and never to be re-applied: a queued kind of a newer build, or a plain `user.disabled`. The line that kept the admin also passed the head (or deleted its queue entry) in a commit of its own before the restriction, so a crash between the two left an admin the journal proved was demoted with the role, unrestricted, and nothing to replay it. Three fixes were weighed. Queue the tail's unknown lines before the drain only protects those lines: the restriction would still pass a known line not yet applied. Holding the component across the phase turns the restriction's journal line into a gap, so the journal stops carrying a restriction that was made. Deferring the restriction until the queue is written has the first problem and leaves the second window. The fix is the last one generalised: `keptAdmins` records the admins the drain and every tail chunk keep; a batch that kept one stages neither its head nor its queue-entry deletion, and no batch after it stages a head; once the whole tail is applied and queued, `restrictKept` restricts every kept admin in one batch, deletes the waiting entries and commits the withheld head (`Pending.Commit` or `CommitHead`, forward-only like `StageHead`). A crash before that re-applies the withheld chunks at the next boot, which keeps the admin again; a crash after the restriction has every line below the head handled, and a crash between the restriction and the dequeue or the head commit re-applies idempotently. Cost: a tail that keeps an admin in an early chunk resumes from that chunk after a crash, not from the last committed one. The same admin kept twice (a queued removal and the same removal in the tail) is restricted once. The first version of this decision called two different kept admins in one boot unreachable and left it as a limit; it was reachable from ONE line (decision 43), and the restriction is now one batch.
40. **A drain applies a line only from a chain that is whole, and an entry the chain does not hold waits.** "Whole" is what `untrusted` says: a chain that does not verify (`Break`), another install's that could not be set aside, one that verifies but does not hold the line the store committed at its head (forked), or one that starts above the store's head (pruned) drains nothing, even a line its verified prefix holds: the entries were answered when they were queued, the boot already reports the break and fails closed for it, and the entries wait for a journal that verifies. A journal that only ENDS below the store's head (deleted, emptied, truncated) also sets `reapplyResult.Broken`, but `untrusted` does not refuse it: its verified lines drain. An entry whose line the verified chain does not hold with the same mac (a foreign archive's queue, a reset journal, a line retention dropped) is an orphan: counted and Warned at every boot and never applied. It is not failed on again only once it is `Closed`: an orphan still open (queued by a restore boot, or whose pass crashed) costs one fail-closed pass at the next plain boot like any entry, and is inert from then on. An entry that does not decode is different and worse: `ReadUnapplied` returns an error for it (`unapplied.go`), so the drain and the settle fail and EVERY boot fails until it is removed, with no operator tool for that. It is a poison entry (F4-08 clears orphans and poison entries; both are filed). Journal retention must not drop a line while its `journal_unapplied/` entry exists; no prune exists today.
41. **A restore with no restore line keys its audit records on a run ID, not on seq 0 (review MINOR 7).** audit's copy-forward records were keyed on `RestoreSeq`, which is 0 for every restore whose line could not be journaled, so two such restores shared one key and the second wrote nothing. `audit.RestoreDeps.RunKey` carries the run's identity and `restoreTargetID()` is `RunKey` when set, else the decimal `RestoreSeq`, else an error; nothing is keyed on 0. The kernel mints the run ID (`journal.EnsureHookRun`: `c/backup/restore_run`, `run:` and 16 random hex digits, a plain synchronous write) when `RestoreLine == 0`, hands it to the hooks, and clears it (`ClearHookRun`) as the last step before `SetFrozen(false)`, so a re-run after a crash gets the same ID and the next restore a new one. A crash between the hooks' markers and the clear leaves a stale ID, which the next restore's swapped-in store replaces, unless the archive carries one: `c/backup/restore_run` is in the store, so a backup taken while a hook run was in progress (no restore line, hooks not yet cleared) holds the ID, and a restore with no line from that archive reuses it. audit's copy-forward is keyed on it, so that restore finds records already written for the key and writes none: the collision this decision removed, reduced to that one sequence. Two edges are known and left: the stale archived ID (the fix is to mint the ID per boot or clear it on a swap) and the one repeat of the copy-forward when the keyring comes back for a retry, which changes the key from the run ID to the seq (a repeat the idempotent write absorbs).
42. **Consequences and limits of the queue, stated.** `Chain.Cover` still refuses coverage when an unknown revocation follows the boundary (the archive carries the entry, or its head is below the line; the hooks fail closed). A crash between the queue commit and the head move, then a boot of a build that knows the kind, applies the line twice (the drain, then the tail): narrowing and idempotent. An admin's re-enable of a user is overridden by the drain of a queued line that disabled it, whenever it happened between the line being journaled and the first boot of a build that knows the kind: the window is not "between the queue and the drain", it is the whole time before the upgrade and any ordinary upgrade boot. The drain applies what the journal says, in the journal's order, and the journal does not record the re-enable (auth journals revocations only). A re-enable is a revocation's undo and is not journaled; an age rule is the other way out. Both are F4-08's call and filed (`F4-11-F4-08-REENABLE`). No health token reports a non-empty queue: the Warn and `reapplyResult.Unapplied` are all there is, and F4-08 decides. A journal header format version is not needed for line kinds: an unknown kind is queued, costs one fail-closed pass and is applied by the first build that knows it; a format version stays an unbuilt, separate safeguard for a change of the file's layout. A declared-skippable kind rule (a bookkeeping kind a build may pass without the pass) is an optional refinement, not built. The crash tests reach the re-apply's batches (`crashAtBatch`), the queue's and the dequeue's (`QueueBatch`) and either side of the restriction; `MarkUnappliedClosed`, `EnsureHookRun` and `ClearHookRun` take a keyspace and no seam reaches them. Each is safe by construction: a queued line re-staged changes nothing and keeps its `Closed`, a repeated pass is idempotent, and a hook run that lost its ID before any hook ran mints another.
43. **One batch restricts every kept admin (security review M1, replaces the two-admin limit of 39).** rbac's `StageReapply` keeps a line that would leave no active `core:admin` holder by marking EVERY active holder of the role as kept (`for _, id := range had { kept[id] = true }`), so one `role.narrowed` or `role.deleted` line over a role with two holders keeps two. The first version restricted them in a loop of `auth.RestrictLastAdmin` calls, one commit each, and each commit stages the head at the top of the journal: after the first, the head is above the line that kept them, and a crash or error before the second left the second unrestricted with live keys and nothing to replay it from. The reviewer's reproducer (bruce and alfred on a custom `core:admin` role, one `role.narrowed` line, a crash after the first restriction) restricted one and not the other. `auth.RestrictLastAdmins(ctx, d, ids)` restricts the whole list in one `commit`: one load, a restriction per user in the plan, one stage, so every user's change, every journal line and the head they stage land together or not at all. `reapplyApply.RestrictLastAdmins` is one call with `keptAdmins.Users`, and `rbac.PostRestore` makes one call too (its re-run made the loop idempotent, since the owed hooks come from the whole chain and `RestoreUser.Active` ignores `SignInRestricted`, but one mechanism with no mid-list window is the end state). An id with no user is skipped (the review's m1: a kept admin that a later chunk deleted made the restriction fail with `ErrNotFound` after the whole tail had been applied, so the boot failed once and passed on the next, when nothing was kept any more; a deleted user is stricter than restricted). The system user stays an error that commits nothing. Tests: the crash tests of decision 39 run over a scene with two holders (`kaKinds`), the call is asserted to be one call with both ids, a later-deleted admin (alone and next to another) is asserted to finish the boot, auth asserts one `NewBatch` for two users, and rbac asserts one call for two holders and a failed restriction redone for both on the re-run. `auth.RestrictLastAdmin` (one user, strict `ErrNotFound`) is deleted: with `rbac.PostRestore` on the list too, nothing called it.
