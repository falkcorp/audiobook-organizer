# R1-30 seams and coined names

This file lists what the `core/web` PR added beyond 09 §9.4 R1 "Content: UI", 07 §7.3.1-§7.3.3, §7.5.2 and §7.8: names the spec does not have, readings it took where the spec or the brief is silent, files it touched outside the row's inventory, and the seams later rows (R1-06, R2 flips, F9) build on. Everything not listed here follows the spec as written: the workspace layout, the `exports` map, the four-step Docker stage, the clean-tree done-check, `checkBuild`'s signature and the three stale reasons.

old ==> new: none. No package moved. `apiFetch`'s error classes and the stale-build rule moved out of `web/src/utils/apiFetch.ts` into `@mediacore/api-client` and are re-exported from `apiFetch` under their old names, so no importer changed.

## npm lockstep value (12 §12.4.3)

`@mediacore/api-client`'s `version` is `0.1.0`, equal to `core/version`'s `version.Version`. The workspace root `core/web/package.json` is `0.1.0` too. `check_core_version.py` (R1-06) enforces it later; nothing enforces it at this commit.

## Readings and deviations

| Topic | Reading |
|---|---|
| `overrides` placement | The brief and 13 §13.4.1 E1 say the api-client package "carries" `"overrides": {"openapi-typescript": {"typescript": "$typescript"}}`. npm honours `overrides` only in the install root, so it is in `core/web/package.json`, and `$typescript` resolves against that root's own `typescript` alias, so the two-TypeScript layout (`typescript` = TS 6, `@typescript/native` = TS 7) is declared there too. Checked, not assumed: `npm ls typescript` shows `openapi-typescript@7.13.0` on `typescript@npm:@typescript/typescript6@6.0.2 deduped`, and the generator runs. |
| Exact pins | `openapi-typescript` `7.13.0` and `openapi-fetch` `0.17.0`, no range (13 §13.4). Tooling ranges (`vite`, `vitest`, `eslint`, `typescript-eslint`, `globals`, `@types/node`) equal `web/package.json`'s; `jsdom` is the exact `30.0.1` (13 E3). |
| `exports` | `development` (`./src/index.ts`), then `types` (`./dist/index.d.ts`), then `default` (`./dist/index.js`). The `types` condition is not in 07 §7.3.1's two-condition wording: web's type check (TS 7) has no `development` condition and needs a `types` entry before `default`. Source imports are extensionless, so the emitted `.d.ts` has no `.ts` specifiers (TS 7's declaration emit does not rewrite them). |
| `core.json` has no operation yet | Its `paths` is `{}`. The generated `paths` and `operations` are empty and `coreOperations` is `[]`. The coverage test (`npm run test:client-coverage`) asserts "every operation has a row and a declared `operationId`" and "regenerating from the committed document changes nothing", never a count. `generate.test.ts` runs the generator on a Batman-named fixture that has operations, a `public` one and one with no `operationId`. |
| "A generated client function" per operation | openapi-fetch's client is `client.GET(path, init)` over `paths`, so a function per operation does not exist. The brief's check is read as: a table row (method, path, `operationId`, `public`) and a type in `operations` for every operation. |
| Legacy error envelope | Read as ABO reads it (`buildApiError`): `error` is the message. The decoded `Problem` has `title` = `error` (else `message`, else the first 200 characters of a non-JSON body, else the status text), `detail` = `message` when both exist and differ, `code` = `legacy_error`, `request_id` from `X-Request-ID`. The middleware hands a legacy answer on as `application/problem+json`, so the `error` of every call has one shape; a native problem is passed through. |
| One implementation of the transport errors | `ApiTimeoutError`, `ApiAuthRedirectError`, `isAbortError`, `isAuthRedirectError` and the bounce check (`assertNotAuthRedirect`) moved into the api-client verbatim, and `apiFetch` imports and re-exports them, so the legacy and the generated transport cannot drift. The brief asks only that `apiFetch` call `checkBuild`; a copy of the bounce check in two places was the alternative. `apiFetch`'s own suites under `web/src/utils` pass unchanged. |
| `StaleBuildBanner` imports from the runtime | The banner imports `getStaleReasons` and `onStaleBuild` from `@mediacore/api-client`, not from `utils/apiFetch` (R1-19's seams note allowed either). `apiFetch` still re-exports them. |
| `StaleReason` | Widened to the spec's three: `legacy-spa` joins `header-mismatch` and `pre-r1-server`. `checkModules` exists and nothing in ABO calls it (case 2 is the shell's). `checkBuild`'s `shell` is required and not read: cases 1 and 3 hold for both bundles. |
| `web/src/api/core.ts` not created | 07 §7.5.2 says ABO's one `createCoreClient({ buildId: readPageBuildId(), shell: false })` is created "in release R1". It is outside the inventory and nothing could call it (`core.json` has no operation), so it would be dead code. Filed: `todo.d/2026-11-08-web-api-core-client.md`. |
| Docker frontend stage | The four steps of 07 §7.3.2 with steps 1-3 in one `RUN` of the entry point: `core/web/` (manifests and sources; `.dockerignore` already keeps `node_modules` and `dist/` out) and `web/package*.json` are copied, then `build_web.sh deps` runs `npm ci` in `core/web`, builds `@mediacore/api-client` and runs `npm ci` in `web/`. Then `ARG BUILD_ID=`, `COPY web/`, `npm run build`. The alternative, one `RUN` per step, would run `npm` in the Dockerfile and not through the one entry point. The cost: a change under `core/web/` reruns the web `npm ci` too, which a change under `web/src` never does. The same edit is in `Dockerfile.build-cgo`. `ARG BUILD_ID` is the R1-19 todo (`todo.d/2026-11-08-docker-build-id-arg.md`), which this PR deletes; `TODO.md` had no entry for it. |
| Docker not built locally | The Docker daemon was not running here. I ran the frontend stage's steps by hand in a clean directory shaped like `/build` (no `.git`, no `node_modules`, no `dist`, `BUILD_ID` empty): `build_web.sh deps`, then `npm run build`, which stamped a timestamp ID. The full `docker build` and the `Dockerfile.build-cgo` build are the PR's `docker-image` job. |
| `web-deps` stamp | Its `find` over `core/web/packages` skipped nothing, so it listed 20 `src/` files inside `node_modules` (packages ship `src/`) and would have tracked them. It now excludes `node_modules`. |
| `minimatch` override | Dependency Review failed #4491 on GHSA-g3hv-75wg-m249 (`minimatch` >= 7.0.0, < 11.0.1): `eslint` and `typescript-eslint` pull `minimatch@10.2.6`. `core/web/package.json` overrides `minimatch` to `^11.0.1` under `eslint` and `typescript-eslint` only (lock: 11.0.5, the version `web/` already runs). Scoped, not global as in `web/`, because `openapi-typescript`'s `@redocly/openapi-core` takes `minimatch@5.1.9` (outside the range) and a global override would move the generator onto a major it was not built for. `npm audit` in `core/web`: 0 vulnerabilities. |
| `core/web` `web-test` | `npm ci`, then `npm test --workspaces --if-present -- --run` (vitest in every workspace). `web-lint` and `web-test` both depend on `web-install`, so one `make -C core ci` runs `npm ci` once. |

## Risks

| Risk | Cost of the fix |
|---|---|
| `web/`'s vitest and `tsc` resolve `@mediacore/api-client` through `dist/` (no `development` condition in ABO's configs), so after a bare `npm ci` in `web/` they need it built. The reusable frontend job behind `frontend-ci.yml` runs exactly that (`npm ci`, `lint`, `build`, `test` in `web/`, no input to change it), and its `build` failed on #4491 for this reason. `web/`'s `build`, `typecheck`, `typecheck:ts6`, `test`, `test:coverage`, `test:ui` and `test:all` scripts now run `scripts/ci/ensure_core_web.sh` first, which builds the package only when `dist/` is missing or older than its sources. Other ways to run `vitest`, `tsc` or `vite` directly (`npx vitest`) skip that guard and still need `make web-deps` once. | Adding `resolve.conditions` to `web/vitest.config.ts` would read `src` under vitest, but 07 §7.3.1 gives that to the shell preset and leaves the pre-shell app on `dist/`; `tsc` and `vite build` would still need `dist/`. |
| The generator is TypeScript run by Node's type stripping. It needs Node 22.18 or later, and CI and the image use 26. | None today. |

## Seams for later rows

- **R1-06 (`check_core_version.py`):** asserts `core/web/packages/*/package.json` `version` equals `version.Version` (`0.1.0`); the root `core/web/package.json` carries the same value.
- **R2 flips (07 §7.19 step 3):** create `web/src/api/core.ts`; each flip regenerates `core.json` with `make -C core openapi-regen` and the client with `make -C core generate-api-client` in the same PR. `make -C core openapi-check` and `web-lint` fail when either is stale.
- **F9 / shell adoption:** `ui-kit` and `shell` join `workspaces` (`"packages/*"` already matches them) and `build_web.sh`'s explicit order list; `createShell` calls `createCoreClient({ buildId: readPageBuildId(), shell: true, onUnauthorized })`; the shell's `/modules` fetch calls `checkModules`; the shell banner replaces `StaleBuildBanner`; `../examples/hello/web` joins `workspaces`.

## Deployability

Deployable on its own. Rollback is a revert: `web/` returns to R1-19's local stale-build rule, `core/web` disappears, and the Docker stages return to installing `web/` alone.
