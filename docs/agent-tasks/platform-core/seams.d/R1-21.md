# R1-21 seams and coined names

This file covers what the "journaled swap and boot crash matrix" PR added beyond 05-backup §5B.3.4, 05-storage §5S.3.15 and §5S.3.16, and 06 §6.4.8 and §6.5.1. It lists:

- names the spec does not have;
- readings it took where the spec or the brief is silent;
- the decisions D1–D15 of the row's plan as built, and the spec lines they changed;
- one R1-20 defect the crash matrix found (F2), which keeps `TestBootCrashMatrix` red until R1-20 fixes it;
- the seams later rows build on: R1-23, R1-24, R1-25, F3-04, F8 and health.

ABO is unchanged. Nothing in ABO stages or swaps through core yet.

## Names beyond the spec

| Name | What it is |
|---|---|
| `core/internal/bootseam`: `Seams{FS, BuildID, Clock, Labels}`, `Labeler`, `With`, `From`, `FS`, `Region`, `RegionOf`, `Labelled` | The per-boot seam, carried in the `context.Context` that `app.New` receives. It holds the boot's filesystem, binary ID, clock and crash-point labeller. A boot with no seams uses `vfs.Default`, `buildid.Binary` and `time.Now`, and its regions do nothing. It is L0 (`archtest_layers_test.go`), so storage (L1) reads it. 05-storage §5S.3.16 names a `core/internal/statefs` seam for the labelled state-directory FS; this build has one filesystem for Pebble and the state files, and the labels are regions on it. |
| `core/internal/bootseam/bootseamtest.Recorder`, `Options{Clones, Fail, Stores}`, `Event{Label, Ordinal, Kind, Path, Engine}`, `Clone`, `LabelPebble`, `LabelNone`, `(*Recorder).Freeze` | The kit's filesystem: Pebble's `errorfs` over a crashable `MemFS`. It records each durable operation (create, link, remove, rename, reuse for write, mkdir, write, sync) with its region's label and takes a crash clone before each one. `Fail` returns an error from one operation. An operation is the engine's (`Engine`, label `pebble.engine`) when it touches a Pebble file name, or is a mkdir or sync of a store directory named in `Stores`, or is a sync of an ancestor of one outside any region. `Freeze` ends the window at readiness. Ordinals count non-engine operations only, so an error run finds its operation again although Pebble's own file numbers differ. |
| `core/internal/restoreswap`: `Swapper`, `New(Options)`, `Options{FS, StateDir, BuildID, Clock, Owners, Recheck, Probe, Logger, Actor}`, `(*Swapper).Stage`, `RunP0a`, `Opened`, `RestoreApplied`, `CheckpointFailed`, `ResetApplied`, `ResetDone`, `SwapBack`, `Journal`, `BootKind` (`BootPlain`, `BootRestore`, `BootReset`, `BootResetApplied`), `Outcome{Boot, ID, Intent, Last, Degraded, Reason}`, `InFlight`, `InFlightJournal`, the `Step*` constants | The one journaled swap. The kernel holds the `Swapper`, runs `RunP0a` at P0a, and reports each later step through the named methods. |

A staged `KindRewrite` (M8) halts the boot with `ErrRewriteNotInThisBuild` until F3-04 lands. `ErrSlotConflict` means `pending.json` and an in-flight file name two different swaps. |

| `kernel.ReaderCheck(stateDir, ReaderCheckAllow{FailedCheckpointEscape})` | 05-storage §5S.3.7's reader check for every opener but the kernel's own boot (decision D9): `ErrSwapInFlight` while an in-flight file exists. The one exception is the `failed` `KindCheckpoint` escape. |
| `restorejournal.CreateIntentFS(fs, stateDir, in)` | `CreateIntent` over a `vfs.FS`. `CreateIntent` is now its wrapper over `vfs.Default` (decision D15). |
| `restorejournal.SetAsideDest`, `FailedDest`, `StagingDir`, `AsideRoots`, `SetAsides`, `CoreSidecarSuffixes`, `LevelsSuffix`, `CheckpointSuffix` | The one set-aside rule of §5S.3.15 "Stage", step x's `failed/` destination under the same rule (decision D3), the staging directory a restore's stager extracts into, the private directories a swap may create, and step c's set-asides derived from an intent (decision D1). |

| `storage.RewriteSidecars(ctx, fs, dbPath, owners)` | Rewrites the level sidecar and the projection sidecars beside a **closed** store from its own stamps. The swap calls it at step e and at step x, before any `storage.Open`. |

The crash-point labels are the writer table's, listed in `crashmatrix.Rows()`:

- `swap.*`: the swap, the rejection, step x, and the kernel's journal steps;
- `storage.*`: the sweep, the checkpoint, the fresh batch, the marker, the ratchet, the migration list, the completion, `ready_at`, and `storage.close`;
- `pebble.engine`: Pebble's own files.

## Spec readings

| Topic | Reading |
|---|---|
| P0a's position (decision D14) | P0a runs after P1 (the catalog, which does no I/O) and the logger, and before P2. Step e needs the app's owners (the projection sidecars) and the swap needs a logger. Nothing durable happens before P0a, so the order a crash can observe is unchanged. 06 §6.5.1's P0a row now says so. |
| Step x's `failed/` (decision D3) | DB-side items that step x moves out of the live paths go to `<db parent>/.mediacore-restore/<id>/failed/`, by the same rule as `previous/`. 05-backup step x said `restore/<id>/failed/`, which is under the state directory, and a rename there fails with `EXDEV` when `core.storage.path` is on another filesystem. 05-backup step x now names the rule. |
| The swap-back's durable marks (decision D5, refined) | Machine 1 has no "swapping back" state, so step x records its progress as two files beside the journal. `restore/<id>/swapback.started` is written before x's first operation, and a boot that finds it continues the swap-back instead of resuming forward, which would journal `applied` over the original store. `swapback.moved` is written once every item that is not the original is in `failed/`; from then on a live path that exists can only be an original that was moved back. There is no new journal step. The plan's mark, `<D>/failed/` existing, could not tell "x started" from "x moved everything". |
| A reset boot's completion | `applied` is journaled after P4a's fresh install (R1 has no keyring, so at the point where `secrets.Open` would rewrite its header, the start of P4b). The delete entries, `hook_done` and the deletion of `inflight.json` come after P4b, which is P4d step 1 (R1 has no P4c or P4d phase). A P4b failure on a reset boot leaves the journal at `applied` with the in-flight file, and the next boot finishes it after its own P4b (`TestResetHookDoneAfterMigrationList`). |
| The restore boot's checkpoints at step x (decision D6) | They stay in `.mediacore-checkpoints/`. Moving them into `failed/`, or marking them `restore_left`, needs checkpoint-record writes, which are storage's private format. This is safe: they carry the restored store's `install_id`, epoch and directory identity, so the original store never reuses them, and R1-24's sweeper ages them out. 05-backup step x still says to move them. A storage export such as `ReleaseCheckpointsSince` belongs to R1-24. |
| Step b's recheck at R1 (decision D4) | `Options.Recheck` is a hook. The default checks that every placement's `From` exists and re-runs `Validate`. F8 installs the archive manifest's re-hash. |
| The install ID (decision D8) | The stager writes the live install ID into `Intent.InstallID`. P0a copies it into `set_aside_started`, and P2 gives it to a marker-less restored store. |
| The reader check (decision D9) | The kernel opens a store with an in-flight file only for the journal its own P0a took over. Every other opener calls `ReaderCheck`. |
| Degraded tokens before health exists | P0a's `restore_rejected`, `restore_failed` and `factory_reset_failed` are logged at ERROR with the reason and the journal ID. Health's degraded reasons arrive with health's checks. |
| A failure after P2 on a restore boot | `swapPhase` wraps P2, P4a and P4b. A failure closes the store, runs step x and exits with `ErrSwappedBack`. The restart boots the original store. A `KindCheckpoint` restore that fails in P4b instead journals `failed` with this binary's ID, keeps the in-flight file and refuses this binary (DATA7-12). A reset boot's failure halts the boot, and the next boot resumes the journal. |
| Journal encoding (decision D2) | JSON Lines: each record is appended as one line and fsynced. A last line with no newline, or one that does not decode, is a torn append that was never acknowledged. The next append overwrites it. A torn line before the last one is corruption and halts the boot. 05-storage's `Record` doc now says so. |
| The kill model (decision D11) | The kit boots each fixture once, fault-free (the census). Before every durable operation it takes `CrashClone` with no unsynced data. Each clone is a kill point: the kit boots the current build on it, up to three boots in all, and checks the invariants. A write therefore collapses into the next sync of its file. |
| The error mode's reach (decision D12, narrowed one step) | `ENOSPC`, then `EACCES`, is returned from each labelled operation that is not Pebble's own, and the boot goes on. Pebble's own files, including the WAL write and sync of a labelled `Sync` batch, are kill points only. Pebble treats a failed WAL or MANIFEST operation as fatal, and that panic is unrecoverable when it happens on a background goroutine. 05-storage §5S.3.16 and 06 now say so. |
| A boot that panics | The kit treats a recovered panic as the process dying at that operation. The restart sees a crash clone, and the dead boot's open store is abandoned. Pebble's `atomicfs.Marker.Move` panics on a failed directory sync. |
| I5 and a failed `KindCheckpoint` restore | I5 says the current build reaches readiness after every kill. A `KindCheckpoint` restore whose migrations fail refuses the binary that failed them (DATA7-12), so for that fixture a kill or error in P4b legally ends in the refusal. `Fixture.Refusal` declares it, and I5 accepts it. |
| I1 and I4 at R1 | Both are vacuous: R1 has no cutover step and no level step above `PrevLevels`. `Scenario.PrevLevels` exists (decision D10), and F3-04 adds the checks with the steps. |
| I2's "exactly one store" | The kit compares the DB path's module rows (the `m/` digest) with those of the legal outcomes. For a fixture with a staged swap there are two: the fault-free run's, and the untouched store, which is what the boot leaves when the swap is removed. |
| I6's checkpoint bound | A crash loop may leave at most as many checkpoints as the legal runs leave between them (at least one). A swapped-back restore's checkpoint stays (D6), and the original store's boot may take its own. Every checkpoint must open, and must hold the fixture's rows, no module row, or a legal checkpoint's rows. A kill between the fresh-install batch and its seed step makes the next boot an upgrade boot, which takes a checkpoint of the empty store. |
| The kit's window | From P0a until the kernel logs `kernel: ready` (start step 8). The shutdown's close is outside the table. A boot that fails after P2 closes its store inside the window, so `storage.close` is a row. `MarkServed` (Run 0) is inside the window. |
| Kit fixtures | `crashmatrix.Boot` boots in memory and saves the result to disk, so a fixture's directory identity is the one an in-memory boot sees. `MemFS` has no device or inode numbers, so the store generation never bumps in the kit. `TestStoreGenerationBumpsOnSwap` (`core/kernel`) covers the real-disk case, as do generation and the rename pre-check. |

## R1-20 defect found by the matrix (F2): an unopenable checkpoint with a complete record

This is BLOCKED on R1-20. Ten to twelve kill points of `TestBootCrashMatrix` fail on it in each run, and `make -C core ci` stays red until it is fixed.

- **The state.** Pebble v2.1.7's `Open` is killed after it moves the new MANIFEST's marker and before it creates the new WAL (`000007.log`). Kill points: "create 000007.log" and "sync main.pebble", and in some runs "remove 000002.log". The set of Pebble-internal kill points varies with Pebble's background timing (its obsolete-WAL removal). The error mode is unaffected, because ordinals skip the engine's operations.
- **The next boot.**
  - Its `Open` writes no version edit, because the WAL it creates equals `minUnflushedLogNum`. So the version set's `manifest.Size()` is 0.
  - `storage.takeCheckpoint` calls `DB.Checkpoint`, which copies `manifest.Size()` bytes (Pebble `checkpoint.go:196-197`). The checkpoint's MANIFEST is therefore empty, and opening it fails with "pebble: malformed manifest file" (`version_set.go:309`).
  - Storage then writes the record and the pointer. The rollback copy is unusable, and nothing reports it.
- **Fixtures that hit it:** `markerless`, `upgrade-pending-step`, `checkpoint-garbage`, `level-step` and `restore-checkpoint-dag-fails`. Each has two kill points, or three when the WAL removal falls inside the window.
- **Suggested fix in `storage/checkpoint.go` (`takeCheckpoint`).** After `Checkpoint` returns and before `writeRecord`, open the copy read-only and fail closed. The record-less directory is swept next boot, and the restart's open has a WAL to advance past, so it heals itself. Another option is to force a version edit (a flush) before `Checkpoint`.
- **The kit's check.** I6's "every checkpoint opens" (`invariants.go`) is the check. It was not relaxed.

## Other observations

- **A `KindCheckpoint` restore and P4b I/O errors.** Any P4b error (an `ENOSPC` on a sidecar write, say) journals `failed`, and the binary is refused until a fixed build or the previous binary's escape. 05-backup's "DAG fails" covers a failing migration. Whether a transient I/O error in P4b should count is a spec question. The kit follows the spec as written: `refused(restore-checkpoint)`.
- **`storage.levelstep.rollback` is unreachable by filesystem faults.** It runs only when a level step's commit returns an error, and Pebble fails a WAL commit fatally instead. The P4b row counts as covered through its other labels (`Uncovered`'s one-label rule).
- **`kernel.markServed` uses `time.Now()`, not the boot clock** (`supervisor.go`, R1-20's file). It is harmless to the kit: `ready_at` is not compared, and an operation's ordinal does not depend on the time.

## Seams for later rows

- **R1-23 (ABO's crash-matrix instance):**
  - `crashmatrix.Run` with ABO's `Build`, its fixtures, and `Scenario.Rows` for books' writers. A writer without a row fails the run.
  - Books' non-Pebble boot writes must go through `bootseam.FS(ctx)` inside a `bootseam.Region`. A write through `os` shows up in the after-fixture tree diff.
- **R1-24 (checkpoint sweeper):**
  - D6: the restore boot's checkpoints are left in place at step x.
  - The sweeper also owes `<db parent>/.mediacore-restore/<id>/failed/` and `previous/`, which no one deletes yet.
- **R1-25 (offline restore and reset):**
  - `StageReset` resolves the targets and calls `Swapper.Stage`, which runs `Validate` and `CreateIntentFS`.
  - The P0a reset apply is `restoreswap/resetapply.go` (D7).
  - `TestInflightPrecedesFirstRename` is the canonical in-flight test (D13). R1-25 adds an ABO-stager case to it.
  - The offline commands call `kernel.ReaderCheck`.
- **F3-04:** `KindRewrite` halts the boot (`ErrRewriteNotInThisBuild`). I1 and I4 arrive with the cutover and level steps.
- **F8:** `Options.Recheck` gets the manifest re-hash. Step c's and step x's `backup.location.json` copy is copy-if-exists, and absent at R1.
- **Health:** the degraded tokens are logged until health's checks exist.

## Scope notes

R1-21 touched these R1-20 and app files, with labels and wiring only. No R1-20 behaviour changed.

- **`core/storage/{boot,checkpoint,db,levels,migrate}.go`:** each durable step is wrapped in `db.labelled(<label>, …)`.
  - `Open`'s error path and `DB.Close` carry `storage.close`.
  - `Open` adopts the boot seams, and `OpenOptions.Clock` is passed through.
- **`core/storage/swap.go`** (new): the labels, `ErrRenameRefused` and `RewriteSidecars`.
- **`core/kernel/boot.go`:** the P0a call after `buildLogging`, and `swapPhase` around P2, P4a and P4b.
- **`core/kernel/storage.go`:**
  - `binaryID` is computed once per process (`buildid.Binary` hashes the executable);
  - `swapBeforeOpen`;
  - the boot clock.
- **`core/kernel/kernel.go`:** `Config.StateDir`, and the kernel's `swap` and `build` fields.
- **`core/app/app.go`:** `StateDir` is resolved whenever `StoragePath` is set.
- **`core/internal/archtest_layers_test.go`:** `internal/bootseam` is at layer 0.
- **`core/storage/restorejournal/restorejournal.go`:** `CreateIntent` delegates to `CreateIntentFS`.
