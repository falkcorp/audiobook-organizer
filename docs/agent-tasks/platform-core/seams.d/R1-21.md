# R1-21 seams and coined names

This file covers what the "journaled swap and boot crash matrix" PR added beyond 05-backup §5B.3.4, 05-storage §5S.3.15 and §5S.3.16, and 06 §6.4.8 and §6.5.1. It lists:

- names the spec does not have;
- readings it took where the spec or the brief is silent;
- the decisions D1–D15 of the row's plan as built, the review's deviation judgements (a)–(f), and the spec lines they changed;
- what the row's independent review (T4) found and how each item was closed;
- the defects the crash matrix found, in R1-20 (F2, fixed there) and in this row's own swap (four, found by the nested kills);
- what the matrix costs;
- the seams later rows build on: R1-23, R1-24, R1-25, F3-04, F8, health and §5S.4.

ABO is unchanged. Nothing in ABO stages or swaps through core yet.

| `storage.RewriteSidecars(ctx, fs, dbPath, owners)` | Rewrites the level sidecar and the projection sidecars beside a **closed** store from its own stamps. The swap calls it at step e and at step x, before any `storage.Open`. At step x a failure no longer fails x (review M2, below). |
| `storage.OpenOptions.Clock` | The boot clock for the store's timestamps and checkpoint names. The kernel passes the boot seam's clock, so a crash-matrix boot names its checkpoints the same way on every run. |
| `coretest/crashmatrix`: `Fixture.Refusal`, `Fixture.Mutate`, `KillAt`, `Scenario.Rows`, `Row{Phase, Writer, Labels}`, `Rows()`, `Unobserved`, `Observed`, `Boot`, `Stage`, `StageWith`, `BuildID`, `Now` | The kit's names beyond 05-storage §5S.3.16. `Refusal` is a legal end besides readiness, only where the fault-free boot refuses too. `Mutate` changes a fixture's in-memory copy before each boot, for starting states staging cannot make, and `KillAt(tb, f, build, label, nth)` is one: the crash clone a boot of `f` leaves before the `nth` operation labelled `label`. `Rows` is core's part of the writer table, and `Scenario.Rows` is an app's. `Observed` runs only the fault-free boots and returns the labels seen; `Unobserved(rows, observed, allow)` returns every row label no fault-free boot reached and no allowlist entry excuses, and every stale allowlist entry. `Boot` writes a fixture by booting in memory and saving the result to disk. `Stage` stages an intent under the kit's binary ID and clock; `StageWith` takes the rename pre-check's probe. |

The crash-point labels are the writer table's, listed in `crashmatrix.Rows()`:

- `swap.*`: the slot (`swap.slot.inflight`, `.rejected`, `.invalid`, `.cleanup`, `.remove`), the journal steps (`swap.journal.*`, `swap.journal.resync` among them), step c and the reset set-aside, the placement, the location copy, step x (`swap.back.*`) and the kernel's `delete` removals (`swap.delete.remove`);
- `storage.*`: the sweep, the checkpoint (its reuse and a stranded attempt among them), the fresh batch, the marker, the ratchet, the step batch, a level step's sidecars and rollback, the completion, `ready_at`, and `storage.close`;
- `pebble.engine`: Pebble's own files.

## Spec readings

| Topic | Reading |
|---|---|
| P0a's position (decision D14) | P0a runs after P1 (the catalog, which does no I/O) and the logger, and before P2. Step e needs the app's owners (the projection sidecars) and the swap needs a logger. Nothing durable happens before P0a, so the order a crash can observe is unchanged. 06 §6.5.1's P0a row now says so. |
| Step x's `failed/` (decision D3) | DB-side items that step x moves out of the live paths go to `<db parent>/.mediacore-restore/<id>/failed/`, by the same rule as `previous/`. 05-backup step x said `restore/<id>/failed/`, which is under the state directory, and a rename there fails with `EXDEV` when `core.storage.path` is on another filesystem. 05-backup step x now names the rule. |
| The swap-back's durable marks (decision D5, **superseded** by (a)) | Machine 1 has no "swapping back" state, so step x records its progress as two files beside the journal. `restore/<id>/swapback.started` is written before x's first operation, and a boot that finds it continues the swap-back instead of resuming forward, which would journal `applied` over the original store. `swapback.moved` is written once every item that is not the original is in `failed/`; from then on a live path that exists can only be an original that was moved back. There is no new journal step. D5's mark, `<D>/failed/` existing, could not tell "x started" from "x moved everything", and with step c not done no `failed/` is ever created, so it would never exist on that path. The review accepted the two marks as (a). |
| A reset boot's completion (deviation (e)) | `applied` is journaled after P4a's fresh install (R1 has no keyring, so at the point where `secrets.Open` would rewrite its header, the start of P4b). The `delete` removals, `hook_done` and the deletion of `inflight.json` come after P4b, which is P4d step 1 (R1 has no P4c or P4d phase), as 06's writer-table row "P4d 1" says. A P4b failure on a reset boot leaves the journal at `applied` with the in-flight file, and the next boot finishes it after its own P4b (`TestResetHookDoneAfterMigrationList`). The review accepted it; 06's P0a prose and 05-storage §5S.3.15's "Completion" row and P4d step 11(a) said "right after `applied`", and now place it after P4b. |
| The restore boot's checkpoints at step x (decision D6, deviation (c)) | They stay in `.mediacore-checkpoints/`. Moving them into `failed/`, or marking them `restore_left`, needs checkpoint-record writes, which are storage's private format. On unix this is safe: a record matches a store on `install_id`, epoch and DB directory identity (`dir_fsid`, `dir_ino`), the restored store's directory is not the original's, so the original never reuses them, and R1-24's sweeper ages them out. **Off unix it is not**, which the review graded MINOR: R1-20's directory identity reads 0/0 there (`fsid_other.go`), so matching falls back to the epoch, and when the archive's epoch equals the original's, a restore boot's leftover checkpoint matches the original store after the swap-back. Only `MarkServed` at the next ready boot defuses it; a binary upgrade before any ready boot could take it as the rollback copy and bring back the archive's data. Recorded for R1-24 below, and filed beside R1-20's Windows directory-identity todo. 05-backup step x still says to move them. |
| Step b's recheck at R1 (decision D4) | `Options.Recheck` is a hook. The default checks that every placement's `From` exists and re-runs `Validate`. F8 installs the archive manifest's re-hash. |
| The install ID (decision D8) | The stager writes the live install ID into `Intent.InstallID`. P0a copies it into `set_aside_started`, and P2 gives it to a marker-less restored store. |
| The reader check (decision D9, narrowed) | The kernel opens a store with an in-flight file only for the journal its own P0a took over: an in-flight file P0a did not take over refuses the open with `kernel.ErrSwapInFlight`. D9 also exported `kernel.ReaderCheck` for every other opener. No opener without P0a exists in R1-21 (the offline commands are R1-25's, the updater's rollback F8-02's), so it had no caller, and `make lint-deadcode-ratchet` refused it as a new unreachable function. It is removed; 05-storage's `CheckReader` (tokens `restore_pending`, `restore_inflight`, the failed-checkpoint escape) is the spec'd check those openers get, built with its first caller. `restoreswap.InFlightJournal` reports what it needs: the in-flight swap's id, kind and last step. |
| Degraded tokens before health exists | P0a's `restore_rejected`, `restore_failed` and `factory_reset_failed` are logged at ERROR with the reason and the journal ID. Health's degraded reasons arrive with health's checks. |
| A failure after P2 on a restore boot (deviation (f)) | `swapPhase` wraps P2, P4a and P4b. A failure closes the store, runs step x and exits with `ErrSwappedBack`. The restart boots the original store. A `KindCheckpoint` restore that fails in P4b journals `failed` with this binary's ID, keeps the in-flight file and refuses this binary (DATA7-12) **only when a migration step itself failed** (`storage.StepError`). A P4b bookkeeping error (an `ENOSPC` on a sidecar, the checkpoint's record or pointer) journals nothing: the journal stays at `opened` with its in-flight file, and the next boot of the same binary resumes the restore boot. A persistent fault becomes a restart loop, as on any plain boot. The coordinator adopted the review's (f); 05-backup's error row, 06's P4b row and 05-storage's error block now say so. A reset boot's failure halts the boot, and the next boot resumes the journal. |
| Journal encoding (decision D2) | JSON Lines: each record is appended as one line and fsynced. A last line with no newline, or one that does not decode, is a torn append that was never acknowledged; a reader drops it, and the next append **rewrites** the journal without it (temp, fsync, rename, directory fsync; review m6), since `vfs.File` has no truncate and stale bytes past a shorter line could otherwise later read as a corrupt middle line. A torn line before the last one is corruption and halts the boot. |
| A step found done is not known durable (review M6) | A boot whose fsync failed may leave a rename, a removal or a directory visible but not durable, and the next boot then finds the step done. So: `MkdirAllSynced` syncs the chain it finds; `mv` and the slot's moves sync both directories again when they find the rename done; a removal found done syncs its directory; P0a rewrites the journal before acting on it (`swap.journal.resync`; a re-fsync after a failed writeback may report success without writing it); and a rename whose destination directory fails to sync is renamed back, so what a boot sees is what a crash keeps. |
| Twin proofs (review M3) | When a swap rename finds both its source and its destination, the crash model's answer (a kill between a rename's two directory fsyncs leaves both names) holds only in memory. On the real filesystem `rename(2)` is atomic, so both names mean a foreign write: the two are twins only when `os.SameFile` says so over `Lstat` (never for a directory), and otherwise the boot halts with `ErrSwapAmbiguous` and deletes nothing. In memory the caller's proof still decides (`memGhost`, `existsProof`). |
| Step x over an unopenable original (review M2) | x4 moves the original's own sidecars back with it, so when x5's `RewriteSidecars` fails (an empty directory, a truncated MANIFEST) they stand: the error is logged at ERROR and added to `swapped_back`'s note, and x6 finishes. The next boot meets the original as it was: an empty directory becomes a fresh install, and a corrupt store fails P2 on its own with the slot free. |
| A reset's `delete` entries (review M1) | `ResetDone` skips every kept path (rule (4)) and records it in `hook_done`'s `kept`; a relative entry is refused and recorded as failed; and it runs only once the journal reads `applied` or `hook_done`. `Stage` refuses a `delete` entry that is relative, kept, or on the DB's filesystem (the stager sets those aside, which can be undone). |
| The kill model (decision D11) | The kit boots each fixture once, fault-free (the census). Before every kill point it takes `CrashClone` with no unsynced data, and boots the current build on each clone, up to three boots in all, checking the invariants. A write therefore collapses into the next sync of its file. |
| Nested kills (review M6) | The boots after a break run recovery writers no fault-free boot reaches: step x after a failed P0a, a reset's move-back, a rejected reset, the slot cleanup, and every step that finds its work done. So the first reboot after each kill, and the rest of the boot after each injected error with its first reboot, are killed again before each of their kill points that carries a `swap.*` label, one level deep, and each nested kill is booted and checked like any other. Most nested kills of a fixture leave a state another already left, and a kit boot is a function of its filesystem (the clock and binary ID are fixed), so the kit boots one nested clone per distinct content (`stateKey`: directories and file bytes, not hard-link identity, on which no boot writer depends). Which kill point a report names then depends on the order the runs finish. |
| The error mode's reach (decision D12, deviation (b)) | `ENOSPC`, then `EACCES`, is returned from each labelled operation that is not Pebble's own, and the boot goes on. Pebble's own files, including the WAL write and sync of a labelled `Sync` batch, are kill points only. Pebble treats a failed WAL or MANIFEST operation as fatal (v2.1.7 `db.go:885` `Fatalf`, `db.go:955` panics), and that panic is unrecoverable when it happens on a background goroutine. The review accepted it; 05-storage §5S.3.16 and 06 say so. |
| A boot that panics | The kit treats a recovered panic as the process dying at that operation. The restart sees a crash clone, and the dead boot's open store is abandoned. Pebble's `atomicfs.Marker.Move` panics on a failed directory sync. |
| I5 and a failed `KindCheckpoint` restore (deviation (d)) | I5 says the current build reaches readiness after every kill. A `KindCheckpoint` restore whose migration step fails refuses the binary that failed it (DATA7-12). `Fixture.Refusal` declares that end, and the kit accepts it only where the fault-free boot refuses too, so it cannot hide a wrong end elsewhere. After (f) the plain `restore-checkpoint` fixture declares none: its error runs end ready. `restore-checkpoint-dag-fails` keeps it. |
| I1 and I4 at R1 | Both are vacuous: R1 has no cutover step and no level step above `PrevLevels`. `Scenario.PrevLevels` exists (decision D10), and F3-04 adds the checks with the steps. |
| I2's "exactly one store" (review M5) | Each outcome has an end class from its journals: none; applied (`applied`, `hook_done`); back (`swapped_back`, `rejected`); failed (a `KindCheckpoint` journal at `failed`); or open and mixed, which match nothing. A run is legal only when its class, its store and its module rows (the `m/` digest) together match a legal run's: the fault-free run, or the untouched store, which counts as "back". An applied end must also leave the original store opening in `previous/`, and a restore that ended back must leave the staged store opening in `failed/` or staging. The fault-free run is held to the same rules first, so a wrong census cannot make itself the yardstick. |
| I6's checkpoint bound | A crash loop may leave at most as many checkpoints as the legal runs leave between them (at least one). A swapped-back restore's checkpoint stays (D6), and the original store's boot may take its own. Every checkpoint must open, and must hold the fixture's rows, no module row, or a legal checkpoint's rows. A kill between the fresh-install batch and its seed step makes the next boot an upgrade boot, which takes a checkpoint of the empty store. |
| Coverage (review M4) | Only the operations of a fixture's fault-free boot are broken, so a label no fault-free boot reaches is a writer the matrix never faults. `TestBootCrashMatrixCoversEveryWriter` requires every label of every row to be observed, or allowlisted with a reason. hello allowlists one: `storage.levelstep.rollback`, which runs only after a level step's sidecar write fails; the `level-step` fixture's error runs at `storage.levelstep.sidecars` run it. Two limits stay, in the kit's doc: a writer added inside an existing region takes that region's label, and the Recorder's label is per boot, not per goroutine (m9). |
| The kit's window | From P0a until the kernel logs `kernel: ready` (start step 8). The shutdown's close is outside the table. A boot that fails after P2 closes its store inside the window, so `storage.close` is a row. `MarkServed` (Run 0) is inside the window. |
| Kit fixtures | `crashmatrix.Boot` boots in memory and saves the result to disk, so a fixture's directory identity is the one an in-memory boot sees. `MemFS` has no filesystem ID or inode numbers, so the store generation never bumps in the kit. `TestStoreGenerationBumpsOnSwap` (`core/kernel`) covers the real-disk case, as do generation and the rename pre-check. |
| `kernel.Config.StorageFS` and P0a | R1-20's `StorageFS` is the filesystem P2 opens the store on; P0a runs on the boot seam's filesystem (`vfs.Default` outside the kit), which is not it. A `coretest` harness boot sets `StorageFS = storage.MemFS()` and a real temp `StateDir`, so its P0a reads the real state directory while its store is in memory. With nothing staged that is a plain boot. Staging a swap under the harness is not supported: the swap would move real paths while the store lives in memory. A test that stages goes through `crashmatrix` (`Stage`, `StageWith`), whose boots have one filesystem for both. |

## The spec lines this PR changed

- **06 §6.4.8:** `Scenario` gains `PrevLevels` (D10), and `Run`'s doc gains the error mode's reach (D12).
- **06 §6.5.1:**
  - the P0a row's position (D14), and its prose places the kernel's own `hook_done` at P4d step 1, after P4b ((e));
  - the write rule's "error from each" (D12);
  - the writer-table rows the kit labels that the table did not have: P2 `opened`, P4b `failed` (journaled only for a migration step's own error, (f)), step x after P2 and P4, and `storage.close`.
- **05-storage §5S.3.5:** the runner's error block gains `StepError` ((f)).
- **05-storage §5S.3.15:**
  - `storage.ErrRenameRefused` is the leaf's re-export;
  - the `Record` doc has the JSON Lines rule (D2), with the torn tail dropped by a rewrite (m6), and `Record` gains `Kept` (M1);
  - the "Completion" row and P4d step 11(a) place the kernel's own `hook_done` after P4b ((e)).
- **05-storage §5S.3.16:** `Run`'s doc and the scenario paragraph state the error mode's reach (D12).
- **05-backup §5B.3.4:** step x's `failed/` destination rule (D3), and the error row "migration DAG fails" counts only a migration step's own error ((f)).

## Defects the crash matrix found

### R1-20 (F2): an unopenable checkpoint with a complete record

Fixed in R1-20 (`checkpointInto`, `TestCheckpointAfterOpenKilledBeforeWAL`, `TestUnopenableCheckpointCopyRefused`). Pebble v2.1.7's `Open`, killed after it moves the new MANIFEST's marker and before it creates the new WAL, leaves a store whose next `Open` writes no version edit, so `DB.Checkpoint` copied a 0-byte MANIFEST and storage wrote a complete record for a copy that could not open. I6's "every checkpoint opens" found it at ten to twelve kill points per run in five fixtures; the check was never relaxed. R1-20 now flushes before the copy and opens the copy read-only before writing its record. Both operations carry R1-21's checkpoint labels.

### This row's swap: four defects found by the nested kills

1. **A reset resume that skipped a journaled target** (introduced by n1's first fix). A move-back killed before its `rejected` record puts items back under their `moved` records, so skipping the rename of a journaled target left the original store live under `applied`, or the undo gone. Every target's rename now runs on every resume; only its record is skipped. `TestResetResumeMovesAJournaledTargetAgain`.
2. **Step x's `failed/` chain was never made durable** after a boot whose parent fsync failed, so a crash lost the restored store moved into it. `MkdirAllSynced` with a durable root syncs the chain it finds. `TestSwapBackSyncsTheFailedChainItFinds`.
3. **P0a trusted an unsynced journal record**: a `rejected` record a failed fsync left visible, which a crash then dropped. P0a rewrites the journal before acting on it (`swap.journal.resync`), and repairs a `rejected.json` found without its record. `TestP0aMakesTheJournalDurableBeforeActing`, `TestP0aRepairsARejectionWithoutItsRecord`.
4. **A half-durable rename, made by the first fix for found-done steps.** Syncing a found-done rename's source directory committed the store's removal from its live path while its destination directory was still unsynced, so a crash kept it nowhere. `renameSynced` renames back when the destination's sync fails. `TestRenameUndoneWhenItsDestinationSyncFails`, `TestFoundDoneOperationsAreMadeDurable`.

## What the matrix costs

Measured on hello, `go test -count=1 ./examples/hello`, on a laptop under load:

| Run | Without nested kills | Nested, every clone booted | Nested, one per distinct state |
|---|---|---|---|
| No race detector, wall / user CPU | about 3.5 s / 14 s | 28 s / 138 s | 6.4 s / 29 s |
| `-race` (as `make -C core ci` runs it), package time / user CPU | 22 s / 78 s | 196 s / 991 s | 39 s / 195 s |
| Nested kill points booted | 0 | 51,171 | 3,540 |
| Boots, all fixtures | 4,460 | over 55,000 | about 8,100 |

Only fixtures whose swap runs grow, by 1.8x (`restore-bad-level`) to 3.7x (`reset-factory`); the three whose intent P0a rejects gain a few boots, and the eight without a staged swap none. About one nested kill point in fifteen leaves a state no earlier one left (`restore-archive`: 249 of 5,048). Boot counts vary by a few dozen between runs with Pebble's background timing. If 39 s under `-race` is still too much for `make -C core ci`, the options are a `testing.Short()` gate on the nested kills (CI's `-short` run keeps the single-level matrix, a nightly or `make -C core test` runs both), or nested kills on the restore and reset fixtures only.
