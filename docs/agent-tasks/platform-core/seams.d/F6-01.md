# F6-01 seams and coined names

What F6-01 added beyond 05-events §5E.4 to §5E.13, the readings it took where the brief or the spec is silent, and what F6-03, F6-04 and F6-05 must know. The PR is dark: no boot builds an `outbox.Outbox`, ABO declares no durable topic and no consumer, and nothing in `boot.go` or `kernel.go` mentions the package.

## What F6-03 must do

1. Append `outboxOwnerSpec()` to `storageOwners` (the first boot after it writes one claim-ledger row) and call the `kernelOutbox` steps in the order its comment gives: build after the metrics provider, the health registry and the frozen bus catalog exist; `DeclareConsumers` for every manifest, enabled or not, before `Register`; `Freeze` after the last `Register`.
2. Pass `ko.ob.RelayDefinition()` to the executor's definition list (it is a `tasklint:constructor`, allowlisted until then; no kernel wrapper exists on purpose, because tasklint reads a wrapper nobody calls as an orphan kind) and call `BindRuns(executor)` once it exists.
3. **A kind started by an outbox consumer must carry `DedupePolicy.Key` and be idempotent.** `Tx.StartRun` ignores nothing now (a folded start is counted and logged), but it cannot make a fold safe. The default dedupe rule folds a start into a queued OR RUNNING run with byte-identical params, so a message that arrives while its twin runs is acked and its work is never done by a run of its own; `DedupePolicy.Key` folds only into a QUEUED run with an equal key, which a run that has begun cannot be. `books.deluge.path-update` (F6-03's first consumer, `books.book.relocated.v1`) has this shape: give it a `Key` over the book id and have the run read the book's current path rather than the path in the message.
4. Add `Manifest.OutboxConsumers`, `Registrar.OutboxHandler` and `Deps.Outbox` to `core/module/`. `module.ProblemOutboxConsumerUndeclared` and `ProblemTopicUndeclared` already exist; the outbox's registration refusals each wrap one sentinel so the kernel can map them.
5. Extend `archtest.OutboxModuleConsumersAreTasks` to the root module's packages (it checks `examples/...` only: the root module cannot be loaded from core's test).
6. A disabled module's consumers: the kernel passes their names to `DeclareConsumers` and registers no handler. The relay keeps their backlog and never delivers; `PurgeBacklog` is the only thing that discards it. Raw-consumer handling for a disabled module is F6-03's.

## Readings taken where the spec is silent

- **`Perms.Start` of the relay is `core:tasks.manage`**, not `core:system.manage`: the executor strips AuthRequired scopes from core's system actor, so a `system.manage` start requirement makes the relay unstartable by its own nudge and by its `Every(1m)` schedule.
- **`seq/`, `cur/` and `dead/` are all Serialized.** The spec and the brief name `seq/` only. A pair's state is guarded through its cursor (every writer reads it with `GetForUpdate` and rewrites it), which covers `try/`, but a dead letter must be guarded by its own key: a pair with no cursor row (an operator acting on an orphaned consumer) has nothing else to conflict on, and two operators, or replay against discard, could both commit. `StageDead` and `LoadDead` use `GetForUpdate` on the dead key; `StageDeleteDead` without a prior `LoadDead` is a blind write and fails at commit.
- **Retry of a dead letter** deletes the dead row and re-stages the message in the same batch, addressed `To:<consumer>`, under a new intake id (the original `IdempotencyKey` is kept). Every other consumer of the topic acks it without running it. It is delivered at the end of the stream, not at its old position.
- **A row that cannot be read stops, never skips.** An unknown codec version, or any other decode failure (a corrupt row), on a message, cursor or try row stops that pair; on an intake or seq row it stops the topic. Either reports `core.outbox` Degraded (`delivery_stopped`, the detail names the pair or topic and the cause token: `unknown_version` or `corrupt_row`) and logs one Error line. The stop is looked at again every 30 s and lifts when the row reads. Neither the log nor the health detail quotes the decoder's text (it repeats the value it rejected, which is a payload): they carry the cause token, the Go type of the error and which row (`intake row`, `message row`, ...).
- **A changed partition count stops the topic.** A topic's messages are spread by `hash(key) mod partitions` and `seq/<topic>` stamps the count they were spread over. When the declared count differs from the stamp, the relay stops the whole topic at every place that would work on it: intake, delivery, creation of a new consumer's cursors, the retention sweep, and `PurgeBacklog` (which refuses with `ErrPartitionsChanged`). Health reports `delivery_stopped` with `partitions_changed` and one Error line says which counts; `Status.Stopped` lists the topic. No message is lost and none is delivered. **The stop is not repaired by editing the stamp**: that would route the messages of the partitions the smaller count does not have to nowhere. There are two ways out. Restore the declaration to the stamped count (revert the topic's `Partitions` in the build), and the stop lifts by itself and every message is delivered; or run a migration that re-sequences the messages over the new count, which this PR does not provide. While the topic is stopped the relay costs a read of `seq/<topic>` per loop and no write: the stamp is checked before cursor creation enters the run's writer, which records an intent row whatever it returns.
- **Failures are tokens.** A dead letter stores `permanent`, `schema`, `mode_unset`, `nested_write`, `panic`, `timeout` or `error`, the attempt count and the message; never an error text or a panic value.
- **Logs carry no payload.** A handler's error or panic can embed the payload (a schema validator quotes the instance it rejected). The relay logs the token, consumer, topic, seq, attempt and the Go type of the error (`err_type`), and for a panic the Go type of the value and the function names of its stack (`panic_type`, `frames`). `ErrSchema` is wrapped opaque (topic only), for a raw consumer's schema check and for a typed decode. `TestOutbox_FailureLogsCarryNoPayload` fails if a sentinel payload value reaches the log.
- **Shutdown cancellation is not a failed attempt**: a handler that returns because its context ended is redelivered, not retried or dead-lettered. Handlers must honor `ctx`.
- **Unordered** is available on `Consume` and `ConsumeRaw` only. A round of messages settles in one guarded batch; a crash before it redelivers the round (at-least-once). The pair's retry list is bounded at 64 entries: past it the pair takes no new messages until some settle.
- **Retention** deletes a message when every holder's floor (its cursor, or one before its earliest retry) has passed it, re-reading each cursor inside the deleting batch. A topic nobody holds keeps its messages for `orphan_retention`. An orphan consumer's grace period (a cursor of a name registered and declared nowhere) runs from the first sweep that saw the name missing, persisted in `Cursor.Absent` and cleared by the first sweep that sees it back; it is not measured from the cursor's last touch, which for an idle consumer on a quiet topic is long ago, so a rollback or a manifest typo cannot delete a fresh message the idle consumer still needs. While the grace runs the orphan holds everything like a live holder; after it the cursors and the messages only it held are dropped and counted. A build that dies before its first sweep leaves a returned consumer's old mark in place (the first sweep of every relay clears it).
- **A retry entry whose message is gone** (removed out of band) is dropped by the next round of its pair and logged once, instead of holding a slot of the bounded retry list for good.
- **A run start that folds** into an existing run is acked like any delivery, counted in `mediacore_outbox_folded_total{topic,consumer}` (an eleventh family beside §5E.10's ten; the table in 05-events carries the row) and logged at Info with the run id. A purge that lands between a task-starting delivery's staging and its commit makes the commit conflict, and the retry sees the cursor past the message: no run starts.
- **Relay rotation** is clamped to `tasks.MaxTimeout`. Health `stop` and `clear` report at once, not on the next status tick.
- **A consumer whose cursors cannot be created is left alone for 5 s** (`cursorRetryEvery`): cursor creation is a write of the run, so a failure retried on every loop would write on every loop. The failure is logged once a minute per consumer.
- **Relay failure logs** carry the class of the failure under the key `fault` (not `kind`: the run's own logger already stamps `kind=core.outbox.relay` on every line) and the Go type under `err_type`; the closed tokens are `unknown_version`, `corrupt_row`, `partitions_changed`, `conflict`, `fenced`, `canceled`, `timeout`, `no_space`, `io`, `permission`, `closed`, `read_only`, `too_large` and `error`. `RefreshStatus`'s warning draws on the same once-a-minute allowance as the relay's own.
- `ErrPartitionsChanged` is not re-exported from `outbox` (the `NoInit` rule flags a package var that is not `errors.New`); the relay uses the `outboxstore` sentinel.

## Known gaps, not done here

- `ScanIntake` reads the whole `in/<topic>` prefix when many `NotBefore`-delayed rows exist: O(n) per scan, memory bounded. A delayed-row index would fix it; nothing needs it before a producer uses `NotBefore` at scale.
- The operator reads (`ListDead`, `OldestMessages`, the intake prefetch) page by count, not by bytes; `FindDead`, `DeadCounts` and `knownConsumer` scan; the status diff in `changed()` is quadratic in consumers. All are bounded by the dead-letter and consumer counts an operator can realistically reach; a byte cap and indexes are the fix.
- A dead letter retried through `RetryDead` is delivered at the end of its stream, not in its old order, and `RetryDead`, `DiscardDead` and `PurgeBacklog` carry no caller identity: F6-04's routes own authorization and the audit row.
