### Which names carry the `t6g4` prefix

The prefix is carried by the group's shared machinery and its helpers: `t6g4Base`, `t6g4Store`, `t6g4Writer`, `t6g4Deps`, `t6g4View`, `t6g4Res`, `t6g4ResProvenance`, `t6g4IntroTranscribeWrites`, `t6g4StatsSink`, `t6g4Kinds`, `t6g4KindsUnchecked`, `t6g4NativeBase`, `t6g4Par`, `t6g4RunEach`, `t6g4RefuseModeKeys`, `t6g4RequireLive`, `t6g4StartRequirement`, `t6g4ClearFileIntros`, `t6g4RunUnknownRowsBackfill`, `t6g4UnknownRowsPool`, `t6g4ApplyFSRepairPlan`, `t6g4DeferAggregatesWriter` and the test-side `t6g4*` fixtures. ## Readings the brief did not settle

- **`dry_run` is refused by the native shell** for every kind whose HEAD params carry `dry_run`/`dryRun`/`apply`: the mode comes from the start request (R2 item 3). The marker fields exist only so the run can refuse them with a named error.
- **Live-only writers** (ai-dedup-batch, extract-wav-clips) error with "preview not supported; start with mode live" when the mode is not live (R7).
- **Effects use only `pkg/ops` constants** (coordinator ruling). `t6g4Res` takes `ops.Resource`, but a bare string converts to one, so the vocabulary is closed by a test, not by the compiler: `TestT6G4Kinds_EveryDeclaredResourceIsAPkgOpsConstant` reads the constants of `pkg/ops/effects.go` with `go/ast` and requires every name in every kind's declared Effects (writes, reads, deletes), in the spy map and in the expected table to be one of them. Stores with no constant are mapped to the nearest one or left undeclared, and each is a review decision: ai-dedup-batch's `ai_jobs` row is declared `review_items` (`operations` is the undo journal only); the file-provenance ledger is declared `book_files` through `t6g4ResProvenance` (the export also declares `files` for its JSONL); a dedup candidate row lives in the embedding store, so dedup-exact-triage declares `embeddings`. Left undeclared: the whisper result journal (`stats:transcribe` and `stats:transcribe-files` are below). Only transcribe-book-intros calls `OpenWhisperJournal` (`intro_transcribe.go`); transcribe-file-intros keeps its result on the book file and does not use the journal. Whether ai-dedup-batch's `ai_jobs` row belongs under `ai_journal` instead is the coordinator's call.
- **`files` rule (N14).** `files` ("bytes on disk") is declared wherever the op writes bytes to disk, and recorded in the parity table as `unrecorded` (no writer call can record it). Verified against the code: file-provenance-export (the JSONL it appends to), extract-wav-clips (the clips and the content-stable hardlinks under the library root), dedupe-book-file-rows (the per-book and per-row decisions TSVs under the library root) and transcribe-book-intros (the clips cut into the clip cache; `extractClip`). No other kind of the group writes a file: filepath-collision-report returns its report as the result, and the capture kind only reads and hashes.
- **Stats keys (N6).** `stats:transcribe` and `stats:transcribe-files` have no `pkg/ops` constant, so a gated write could not declare them, and a gated write that is not declared would be refused once F5-18 wires the real writer over `rc.Writer()`: the counters would silently stop being written (both accumulators log a failed flush and carry on). They are therefore written OUTSIDE the gated writer, through `t6g4Deps.Stats` (`t6g4StatsSink`), straight to the store, as a monitoring aggregate that no run reads back to decide anything. `TestT6G4Kinds_TranscribeStatsBypassTheGatedWriter` pins it: the writer interface and the spy map name no stats method, the counters reach the sink, and no stats call is recorded on the spy. **F5-18 must set `t6g4Deps.Stats`** (the store's `TranscribeStatsStore` and `FileIntroStatsStore` capabilities); left nil, the native kinds persist no counters.
- **Swaps at stacking (coordinator).** Sibling F5-06 adds `ops.ResFileProvenance` (`file_provenance`) and `ops.ResAIJournal` (`ai_journal`); the row's own branch could not reference them and kept `book_files` for the provenance ledger until stacking. Each swap is one line in production and one in the spy map: (1) DONE in the integration stack (2026-11-15): `t6g4ResProvenance` in `kinds_t6_g4.go` is `ops.ResFileProvenance` (the capture and export Effects follow it), and the six test lines that spell the same resource independently (the expected table, the spy map's `AppendFileEvent` and `SetFileProvExportCursor` entries, the two parity `want` rows) name `ops.ResFileProvenance` directly, not through the production constant, so a wrong production constant fails a test instead of agreeing with itself; (2) DONE in the integration stack (2026-11-15): `ops.ResAIJournal` is in `t6g4IntroTranscribeWrites` (production, `kinds_t6_g4.go:93`; the Effects, the expected table at `kinds_t6_g4_test.go:649` and the parity case at `:638` follow the variable) and the spy map's `OpenWhisperJournal` entry, once `""`, is `ops.ResAIJournal` (test, `kinds_t6_g4_test.go:1050`). `ops.ResSyncIdentity`: no change. `embeddings` (dedup candidates) and `review_items` (ai_jobs) stay as they are. The baseline file `scripts/deadcode-baseline.txt` will conflict with siblings: take the union, sorted; this row's 23 dark lines stay until F5-18.
- **HEAD fields dropped per kind**: schedules (below); `CheckpointFn` on intro-transcribe; HEAD's `DependsOn` becomes `NotWhile` (R5; only dedupe-book-file-rows has one, and a `library.scan` dependency adds the scan-full companion).
- **Write sets were widened where HEAD left them undeclared** (R7 "Writes found"). file-intro-transcribe: HEAD's comment says declaring books/book_files would queue acoustid.backfill behind the whole multi-day run; the native kind declares `book_files` and `books` because the body writes them (intro results onto the file rows, and the book transcript through `ModifyBook`; it does not re-aggregate the parent book), and F5-14/F5-18 must decide the queueing consequence. A ref lock cannot narrow an Effects hold ("a ref lock grants no write"), so only a different declaration changes it; this is the owner decision recorded in the PR body and in `todo.d`. intro-transcribe declares `books` (HEAD) plus `book_files` (timeout strikes). ident-index declares `books` (HEAD) plus `indexes` (the ident: rows). That matches the F5-07 ruling (`seams.d/F5-07.md` item 8: `indexes` is for index families with their own writers, `ident:` among them; row-family secondary indexes such as `book_atpath:`, `book_hash:` and `book_file_acoustid:` are `books` / `book_files`): `RebuildIdentIndex` (`internal/books/store/ident_state.go`) writes only `ident:state/by/dirty/reason/meta` rows, through its own writers (`identTxn`, `writeIdentForBook`) under the book metadata-cache stripes, so the spy map's `"RebuildIdentIndex": ops.ResIndexes` stays. dedupe-book-file-rows adds `books`, `fingerprint_index` and `operations`; fs-regroup-xml adds `external_ids` and `operations`; duration-backfill adds `books`.
- **file-intro-transcribe Timeout** is clamped from HEAD's 30 days to `tasks.MaxTimeout` (24h). HEAD never checkpoints this op, so its restart is a run from zero. The native kind is `ResumeContinue` because it yields (below), not because HEAD checkpoints: that is a deliberate deviation, and the conformance table records it as `yieldsNatively`.
- **file-intro-transcribe yields before its deadline** (review M4, N1). No core hook was added: the native shell reads the run context's deadline, and once `time.Until(deadline) < fileIntroYieldMargin` (exactly the margin left is "not yet within") it stops starting batches, checkpoints a cursor (run id, batches done, the last group of the completed prefix, the run's counters), resets the bar to the exact prefix and returns `tasks.ErrContinueInPlace`. The margins are derived, not a constant: the call margin is `transcribe.PoolPaceMax()` + `fileIntroCheckpointBudget` (2 minutes) + 1 minute, and the yield margin is the call margin + 1 minute, so a batch started just outside the yield margin still has room for the longest the whisper pool can pace one call plus the checkpoint write (`TestFileIntroMargins_TheCallMarginCoversThePoolPaceAndTheCheckpoint`). The next attempt reuses the cursor's run id (whatever its own op id is) and counters, reports from the batches already done, and (only for a forced `only_missing=false` run) skips the completed prefix by key; the cursor comment states the hazard of that skip.
- **The native waits are deadline-aware (N1) and the whisper call has its own earlier deadline (N16).** The scan-busy pause (before the whisper call and at the write gate) and the whisper outage retry sleep stop waiting once the run is inside the yield margin: the batch is skipped like one never started (not failed, not completed, `afterBatch` not called), the cursor is checkpointed and the run returns `tasks.ErrContinueInPlace`. The whisper call itself runs under a context cut at `deadline - callMargin` (`boundCall`): a call still in flight then is cancelled with the cause `errFileIntroYieldNow` and its batch settles nothing, and a call that would start already inside the call margin returns the same error before any request is made (`TestFileIntroCallBound_*`). A cut call does not go through `shouldYield`, which is why the item still sets `l.yielding` itself. HEAD's shell sets neither `giveUp` nor a call margin, so its waits are exactly main's (an unbounded pause, a 10-minute retry budget). **Two documented exceptions remain, and a native run can end `timed_out` in them.** (1) Nothing is bounded until this attempt's batch 0 is done, because a yield with no completed batch fails the executor's progress proof (`yieldNext` requires `done > rec.Done` and a checkpoint); a scan or an outage that outlasts the whole attempt before batch 0 completes ends the attempt `timed_out`. (2) A scan that outlasts a whole 24 h attempt, found by a RESUMED attempt (below). Tests: `file_intro_yieldwait_test.go`, `file_intro_round4_test.go`. The shell's own hand-over of both margins is pinned by `TestFileIntroNativeShell_PassesTheCallMarginSoABlockedWhisperCallYields` (it drives the kind's `Run` to a blocked whisper call with the margin variables narrowed to a seconds-long deadline; dropping `CallMargin` from the shell fails it, N32), and the outage-sleep give-up reaches `runBatch`'s yield branch in `TestFileIntroYieldWait_AnOutageSleepThatGivesUpWritesNothingForTheBatch` (N19).
- **A resumed attempt waits for a scan instead of refusing (N17).** HEAD refuses to start while a library scan is running (`fileIntroRefuseIfBusy`). A continued attempt is the same run, so refusing would turn a routine yield into a failed run: the native shell's resumed attempt (a cursor exists) calls `waitWhileScanBusy` instead and announces `paused — ...` through `env.Progress`. A fresh start keeps HEAD's refusal. This differs from HEAD, which has no resumed attempt. It deliberately cannot yield again while it waits, for the reason in exception (1): the executor's `yieldNext` needs progress past the attempt's starting point, which a wait does not make. A scan that outlasts a whole attempt therefore ends `timed_out` (`TestFileIntroResume_AResumedAttemptWaitsForAScanWhereAFreshStartRefuses`). **Residual (N31).** A resumed attempt that waits on continuous scan activity for a whole attempt (about 24 h) ends `timed_out`, which is terminal. A normal nightly or 6-hourly scan cannot reach it (a full scan of the production library takes about 5 h); it needs a zombie queue row, back-to-back chained scans, or a weekly sweep that runs across restarts. HEAD in the same situation (a restart while a scan is queued) re-enters `fileIntroRefuseIfBusy` and fails at once, so the native run is better than HEAD there; what it loses against HEAD is only how much continuous busy time one run tolerates (HEAD's mid-run wait runs to its 30-day timeout). Nothing inside the kind can fix it: only the executor's done counter proves progress, and reporting a false `base+1` would ratchet `rec.Done`. The fix is an F5-18 dispatch-time hold, which burns no attempt clock (a waiting run holds no worker, key or clock): either a `Ready` signal from the v2 queue (a component that is Down while one of the busy defs is queued or running), or, once the busy ops are native kinds that declare `book_files`, the write-set conflict or `NotWhile`. That would also make the in-run v2 gate dead code, which is tied to the owner's write-set decision. Filed as a `todo.d` fragment. **The wait stays after the selection read (N36).** Moving it before `GetAllBookFilesCore` would put the selection after a possibly hours-long wait, which is the better order, but it is not a small change: the slot, preflight and writes-available checks and the preview return currently sit between the selection and the wait, and they decide HEAD's error precedence, the order of the progress lines and what `res` carries on an error. Hoisting them for every run, or duplicating them for the resumed case, changes HEAD's log output, which this row must not do. The cost of the current order is paid work only: a stale selection is caught per row (`stale`), and the wait reports `base+1` as its total.
- **The cursor is saved after every completed batch (N22).** Besides the yield, the batch loop calls `onAdvance(prefix)` under its mutex each time the contiguous completed prefix grows, and the shell saves the cursor then (`saveCursor`, shared with the yield path). A crash or a restart after batch K therefore resumes from K, not from the last yield, up to the executor's checkpoint throttle: it flushes a staged checkpoint at most every 30 s (core/internal/executor/attempt.go), so a cursor staged just before a long park at a gate reaches storage with the next checkpoint or ledger write or at the attempt's end, and a crash in between resumes up to 30 s of batches earlier. A default run repeats nothing in that window (files with a result drop out); a forced run repeats at most those batches. Cost: one small JSON checkpoint write per completed batch, and a batch is eight files of whisper work, so the write rate is bounded by the transcription rate. A failed mid-run save is logged at Warn and the run goes on; the yield's own save still fails the attempt (`TestFileIntroCheckpoint_ACrashAfterBatchKLeavesACursorAtK`).
- **duration-backfill book pool** is a seam (review MINOR 12, N3): HEAD runs `Workers` goroutines (unchanged), the native shell runs each book as one item of a loop declared `Fixed(workers)` with a 30-minute per-book timeout (`durationBookTimeout`). Because the items are books, the operator's `parallelism_cap`, a pause and the per-item timeout apply mid-run, and the progress counts books (the denominator is the library's book count). The item re-reads the book by id and skips it if it is gone. A book that panics ends the run with an error naming it (the error wraps a `tasks.PanicError` with the stack) instead of hanging it. A failed re-read of a book ends the run naming it; a nil book is "gone". A book whose probe outlasts the per-book bound (a real-clock `context.WithTimeout`, so the test shortens `durationBookTimeout` rather than using a fake clock) is reported once as a read error for that book, strikes nothing and writes nothing (N18; `TestDurationBackfillNative_ABookThatOutlastsItsBoundIsReportedOnceAndStrikesNothing`). The unknown-rows grain runs on `Each`.
- **duration-backfill unknownRows recompute (stack review M3).** The row-grain run used to recompute its measured books in a final sweep that was meant to outlive a cancel. HEAD's store is ungated, so on HEAD it does; natively `RecomputeBookAggregates` is a gated write and the writer refuses it with `tasks.ErrFenced` once the run is canceled, timed out or abandoned, which left a book with every row measured and a stale `Duration` that no rerun finds (a measured row is no longer a candidate) and that a book-grain run skips for 90 days. Now every row of either pass settles once, in the item that decided it, right after its own write (`settleNoWrite`/`writeRow`), and the book's CLOSER (the row that begins last; it waits for the book's other writes to return) recomputes the book inside that item. Nothing is owed to a point after the loop and there is no write outside the fence (no detached context). The final sweep still runs, as a net for a book whose item failed with the run alive and, on HEAD, for the books of a cancelled run; natively a book it cannot reach is logged by name (as having a stale aggregate), never counted as done, and a row write refused with `ErrFenced` is a cut row, not a settled one.

**The recompute is owed by the book's state, not by the run's writes (delta r2, M-r2-1).** The first version recomputed only a book this run had written a measured row for. A book with rows in both passes that was cut mid pass 2 keeps its pass-1 rows unreflected, and a rerun whose leftover rows all end unwritten (file absent, row changed) or failed (probe failure) writes no measured row for it, so nothing recomputed it, ever; HEAD's ungated sweep does. Now the plan marks every candidate book that already has a measured row (read from the whole-library rows before anything changes) and the book is recomputed when its last row settles, whatever that row's outcome. How a cut book is found again: the kind is `ResumeDrop` and keeps no cursor for this grain; a rerun re-plans from the store and a row is a candidate while it is unknown.

**The last row and its recompute are one write (delta r2, m-r2-1).** The row that closes its book and measures is written with `ModifyBookFile`, which recomputes the book inside the one gated write, so a cancel cannot land between the row and the recompute (that fell between two adjacent gated writes and left every row measured, which no rerun reaches because no candidate is left). The unknownRows writer interface (`unknownRowsWriter`), the typed writer (`t6g4DurationWrites`, `headT6G4Writer.ModifyBookFile`), the spy and the fakes carry it; the table row is `ModifyBookFile` (`book_files` plus the book write), already inside duration-backfill's declared set, so its Effects did not change. What remains: the store's recompute inside `ModifyBookFile` is best effort and only logs a failure (`notifyBookFileChange`), so a recompute that fails there is not counted in `books_recomputed` or as a failed recompute; and a book whose last row ends WITHOUT a write (left alone, or a failure record) is recomputed by a second write after it, which a cancel can still cut, but such a book still has an unmeasured row, so a rerun reaches it and recomputes it by the state rule above. HEAD's pin (`TestUnknownRows_CancelledRunStillRecomputesWrittenBooks`) still holds on HEAD's runner; the native counterparts are `TestDurationBackfillNative_UnknownRowsCancelledRunLeavesTheRestToARerun` (an ordinary cut and rerun; it cannot fail on the pre-fix code, the test says why), `..._AGroupCutAfterOneRowStillRecomputesThatBook`, `..._APassOneBookIsRecomputedInItsOwnItem` and `..._AMixedBookCutInPassTwoIsRecomputedByARerunThatWritesNothingForIt` (`kinds_t6_g4_unknown_rows_test.go`), which run the native kind behind a writer that fences like the gated one; `requireNoBookIsLeftStale` takes a `rerunDone` flag so that after a completed rerun it no longer skips books that still have an unknown row.

## Progress labels (stack review C1)

`tasks.ItemsOptions.Label` is pure (the item only, `core/tasks/items.go`) and the kernel renders it before the item runs, so a label that reads running counters would show pre-item tallies and could step backwards under a parallel pool. HEAD's `registry.RunItems` re-renders after the item under `progressMu`, which the kernel does not. One rule across groups 3, 4, 5 and 6 (F5-11 recorded it first, `seams.d/F5-11.md`): the native loop carries only the index-only labels (`t6g4EachOpts.PureLabel`, handed to the item-only kernel label, the item being the index) and DROPS the counter labels (`t6g4EachOpts.Label`); HEAD's shells keep both, so a HEAD run still shows the counters. Dropped natively: the unknown-rows probe (`duration_backfill_unknown_rows.go`), the intro clear (`file_intro_clear.go`), the intro transcribe pages and file-intro batches (`intro_transcribe.go`, `file_intro_transcribe.go`), the WAV extract (`extract_wav_clips.go`), and both fs-regroup loops (`fs_regroup_xml.go`). Carried: the duration backfill pool (`book <id>`), the filepath-collision shards, the dedupe-book-file-rows books and the single-file intro migrate pages. The native label total is the absolute `ProgressTotal` when the loop sets one, as HEAD renders it. A seam, not a regression of the HEAD shells. If the counter text matters, the larger fix is a core `ItemRC.Note(...)` hook called after the item, which would also bring F5-11's heal and recover labels back; not done here.

**Stamping (F5-18 obligation, `todo.d/2026-11-15-f5-18-multi-resource-writer-stamping.md`).** A gated write carries ONE resource (`core/tasks/writer.go`, `tasks.Write.Resource` is one `entity.Ref`). Admission does not read it: the executor's dispatch gate compares the kinds' DECLARED write sets (`core/internal/executor/dispatch.go`, `overlapsSet(a.writes, ws)`), so a kind that declares every resource of its rows is excluded against every kind that declares one of them whatever a write is tagged. What one tag per write loses is runtime detection of an under-declared Effects: the writer checks only the tag against the kind's Effects (`core/internal/executor/writer.go`), so a file-row write tagged `books` that also touches `book_files` passes even if the kind never declared `book_files`. The declaration tests are the only guard until the writer API carries every resource of a call. Not refused and not worked around here. F5-18 should extend the writer API so a write names its resources; see `F5-10.md` for why one `Do` per resource is not recommended.

## Known wall-clock tests (stack review C2, C3)

Three tests still depend on real elapsed time. Each can fail only a correct implementation on a badly overloaded runner (a false red), never let a broken one pass, and each has a reason the technique used on its siblings (a test-driven deadline, or a gate instead of a window) does not apply:

- `TestFileIntroNativeShell_PassesTheCallMarginSoABlockedWhisperCallYields` (`file_intro_round4_test.go`): the native shell reads the run context's deadline itself, with a 5 s deadline, a 1.5 s yield margin and a 1.2 s call margin, and asserts the run yields before `deadline - 500 ms`. The context belongs to the shell under test (host-owned), so the test cannot hand it the armed deadline context that `TestFileIntroCallBound_ABlockedWhisperCallYieldsWithTheCursorAndNoStrike` uses (the C2 fix).
- `TestFileIntroYieldWait_AnOutageSleepThatGivesUpWritesNothingForTheBatch` (`file_intro_round4_test.go`): a 4 s context and a 300 ms margin, asserting the outage retry sleep is cut at the margin (elapsed at least 3 s, about 3.7 s by design). The sleep (`fileIntroOutageInterval` is an hour, so only the give-up ends it) is a real timer that waits for the real clock to reach `deadline - margin`; the test cannot move that point without a clock the production wait reads, so it spends the real time and asserts a lower bound only.
- `TestDurationBackfillNative_ABookThatOutlastsItsBoundIsReportedOnceAndStrikesNothing` (`duration_backfill_pool_test.go`): `durationBookTimeout` is 2 s (it was 100 ms; C3). The kernel starts the item clock in `loop.one` before the item runs and core has no clock to inject, so the window is widened, not removed: a probe that begins within 2 s of dispatch sees a live item context.

If one of them flakes on CI, widen the margins in the test rather than skipping it; a clock hook in `core/tasks` would remove all three and is not part of this stack.
