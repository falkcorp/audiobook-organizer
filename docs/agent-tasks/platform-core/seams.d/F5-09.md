### Which names carry the `t6g4` prefix

The prefix is carried by the group's shared machinery and its helpers: `t6g4Base`, `t6g4Store`, `t6g4Writer`, `t6g4Deps`, `t6g4View`, `t6g4Res`, `t6g4ResProvenance`, `t6g4IntroTranscribeWrites`, `t6g4StatsSink`, `t6g4Kinds`, `t6g4KindsUnchecked`, `t6g4NativeBase`, `t6g4Par`, `t6g4RunEach`, `t6g4RefuseModeKeys`, `t6g4RequireLive`, `t6g4StartRequirement`, `t6g4ClearFileIntros`, `t6g4RunUnknownRowsBackfill`, `t6g4UnknownRowsPool`, `t6g4ApplyFSRepairPlan`, `t6g4DeferAggregatesWriter` and the test-side `t6g4*` fixtures. HEAD's adapters are `headT6G4*`. It is NOT carried by the unprefixed names the native code added next to HEAD's own: `fileIntroBatchLoop`, `fileIntroCursor`, `fileIntroKey`, `fileIntroKeyOf`, `fileIntroSkipThrough`, `fileIntroYieldMargin`, `fileIntroCallMargin`, `fileIntroCheckpointBudget`, `durationProbe`, `durationPoolHEAD`, `durationPoolOn`, `durationPoolReason`, `introTranscribeHelpBody`, `introTranscribeNativeHelp`, `fileProvenanceExportHeadEnv`, and the per-kind `<id>NativeParams`, `<id>Result`, `<id>Env`, `run<Id>Core`, `<id>Kind`. They were not renamed: they sit in their kind's own file and read with it.

## Readings the brief did not settle

- **`dry_run` is refused by the native shell** for every kind whose HEAD params carry `dry_run`/`dryRun`/`apply`: the mode comes from the start request (R2 item 3). The marker fields exist only so the run can refuse them with a named error.
- **Live-only writers** (ai-dedup-batch, extract-wav-clips) error with "preview not supported; start with mode live" when the mode is not live (R7).
- **Effects use only `pkg/ops` constants** (coordinator ruling). `t6g4Res` takes `ops.Resource`, but a bare string converts to one, so the vocabulary is closed by a test, not by the compiler: `TestT6G4Kinds_EveryDeclaredResourceIsAPkgOpsConstant` reads the constants of `pkg/ops/effects.go` with `go/ast` and requires every name in every kind's declared Effects (writes, reads, deletes), in the spy map and in the expected table to be one of them. Stores with no constant are mapped to the nearest one or left undeclared, and each is a review decision: ai-dedup-batch's `ai_jobs` row is declared `review_items` (`operations` is the undo journal only); the file-provenance ledger is declared `book_files` through `t6g4ResProvenance` (the export also declares `files` for its JSONL); a dedup candidate row lives in the embedding store, so dedup-exact-triage declares `embeddings`. Left undeclared: the whisper result journal (`stats:transcribe` and `stats:transcribe-files` are below). Only transcribe-book-intros calls `OpenWhisperJournal` (`intro_transcribe.go`); transcribe-file-intros keeps its result on the book file and does not use the journal. Whether ai-dedup-batch's `ai_jobs` row belongs under `ai_journal` instead is the coordinator's call.
- **`files` rule (N14).** `files` ("bytes on disk") is declared wherever the op writes bytes to disk, and recorded in the parity table as `unrecorded` (no writer call can record it). Verified against the code: file-provenance-export (the JSONL it appends to), extract-wav-clips (the clips and the content-stable hardlinks under the library root), dedupe-book-file-rows (the per-book and per-row decisions TSVs under the library root) and transcribe-book-intros (the clips cut into the clip cache; `extractClip`). No other kind of the group writes a file: filepath-collision-report returns its report as the result, and the capture kind only reads and hashes.
- **Stats keys (N6).** `stats:transcribe` and `stats:transcribe-files` have no `pkg/ops` constant, so a gated write could not declare them, and a gated write that is not declared would be refused once F5-18 wires the real writer over `rc.Writer()`: the counters would silently stop being written (both accumulators log a failed flush and carry on). They are therefore written OUTSIDE the gated writer, through `t6g4Deps.Stats` (`t6g4StatsSink`), straight to the store, as a monitoring aggregate that no run reads back to decide anything. `TestT6G4Kinds_TranscribeStatsBypassTheGatedWriter` pins it: the writer interface and the spy map name no stats method, the counters reach the sink, and no stats call is recorded on the spy. **F5-18 must set `t6g4Deps.Stats`** (the store's `TranscribeStatsStore` and `FileIntroStatsStore` capabilities); left nil, the native kinds persist no counters.
- **Swaps at stacking (coordinator).** Sibling F5-06 adds `ops.ResFileProvenance` (`file_provenance`) and `ops.ResAIJournal` (`ai_journal`); this branch cannot reference them, and keeps `book_files` for the provenance ledger. Each swap is one line in production and one in the spy map: (1) change `t6g4ResProvenance` in `kinds_t6_g4.go` to `ops.ResFileProvenance` (the capture and export Effects follow it) and change the two test lines that spell the same resource independently (N21: the spy map and the expected table name `ops.ResBookFiles` on purpose, so a wrong production constant fails a test instead of agreeing with itself; three lines in all); (2) add `ops.ResAIJournal` to `t6g4IntroTranscribeWrites` (production, one line; the Effects, the expected table and the parity case follow) and change the spy map's `OpenWhisperJournal` entry from `""` to `ops.ResAIJournal` (test, one line). `ops.ResSyncIdentity`: no change. `embeddings` (dedup candidates) and `review_items` (ai_jobs) stay as they are. The baseline file `scripts/deadcode-baseline.txt` will conflict with siblings: take the union, sorted; this row's 22 dark lines stay until F5-18.
- **HEAD fields dropped per kind**: schedules (below); `CheckpointFn` on intro-transcribe; HEAD's `DependsOn` becomes `NotWhile` (R5; only dedupe-book-file-rows has one, and a `library.scan` dependency adds the scan-full companion).
- **Write sets were widened where HEAD left them undeclared** (R7 "Writes found"). file-intro-transcribe: HEAD's comment says declaring books/book_files would queue acoustid.backfill behind the whole multi-day run; the native kind declares `book_files` and `books` because the body writes them (intro results onto the file rows, and the book transcript through `ModifyBook`; it does not re-aggregate the parent book), and F5-14/F5-18 must decide the queueing consequence. A ref lock cannot narrow an Effects hold ("a ref lock grants no write"), so only a different declaration changes it; this is the owner decision recorded in the PR body and in `todo.d`. intro-transcribe declares `books` (HEAD) plus `book_files` (timeout strikes). ident-index declares `books` (HEAD) plus `indexes` (the ident: rows). That matches the F5-07 ruling (`seams.d/F5-07.md` item 8: `indexes` is for index families with their own writers, `ident:` among them; row-family secondary indexes such as `book_atpath:`, `book_hash:` and `book_file_acoustid:` are `books` / `book_files`): `RebuildIdentIndex` (`internal/books/store/ident_state.go`) writes only `ident:state/by/dirty/reason/meta` rows, through its own writers (`identTxn`, `writeIdentForBook`) under the book metadata-cache stripes, so the spy map's `"RebuildIdentIndex": ops.ResIndexes` stays. dedupe-book-file-rows adds `books`, `fingerprint_index` and `operations`; fs-regroup-xml adds `external_ids` and `operations`; duration-backfill adds `books`.
- **file-intro-transcribe Timeout** is clamped from HEAD's 30 days to `tasks.MaxTimeout` (24h). HEAD never checkpoints this op, so its restart is a run from zero. The native kind is `ResumeContinue` because it yields (below), not because HEAD checkpoints: that is a deliberate deviation, and the conformance table records it as `yieldsNatively`.
- **file-intro-transcribe yields before its deadline** (review M4, N1). No core hook was added: the native shell reads the run context's deadline, and once `time.Until(deadline) < fileIntroYieldMargin` (exactly the margin left is "not yet within") it stops starting batches, checkpoints a cursor (run id, batches done, the last group of the completed prefix, the run's counters), resets the bar to the exact prefix and returns `tasks.ErrContinueInPlace`. The margins are derived, not a constant: the call margin is `transcribe.PoolPaceMax()` + `fileIntroCheckpointBudget` (2 minutes) + 1 minute, and the yield margin is the call margin + 1 minute, so a batch started just outside the yield margin still has room for the longest the whisper pool can pace one call plus the checkpoint write (`TestFileIntroMargins_TheCallMarginCoversThePoolPaceAndTheCheckpoint`). The next attempt reuses the cursor's run id (whatever its own op id is) and counters, reports from the batches already done, and (only for a forced `only_missing=false` run) skips the completed prefix by key; the cursor comment states the hazard of that skip.
- **The native waits are deadline-aware (N1) and the whisper call has its own earlier deadline (N16).** The scan-busy pause (before the whisper call and at the write gate) and the whisper outage retry sleep stop waiting once the run is inside the yield margin: the batch is skipped like one never started (not failed, not completed, `afterBatch` not called), the cursor is checkpointed and the run returns `tasks.ErrContinueInPlace`. The whisper call itself runs under a context cut at `deadline - callMargin` (`boundCall`): a call still in flight then is cancelled with the cause `errFileIntroYieldNow` and its batch settles nothing, and a call that would start already inside the call margin returns the same error before any request is made (`TestFileIntroCallBound_*`). A cut call does not go through `shouldYield`, which is why the item still sets `l.yielding` itself. HEAD's shell sets neither `giveUp` nor a call margin, so its waits are exactly main's (an unbounded pause, a 10-minute retry budget). **Two documented exceptions remain, and a native run can end `timed_out` in them.** (1) Nothing is bounded until this attempt's batch 0 is done, because a yield with no completed batch fails the executor's progress proof (`yieldNext` requires `done > rec.Done` and a checkpoint); a scan or an outage that outlasts the whole attempt before batch 0 completes ends the attempt `timed_out`. (2) A scan that outlasts a whole 24 h attempt, found by a RESUMED attempt (below). Tests: `file_intro_yieldwait_test.go`, `file_intro_round4_test.go`.
- **A resumed attempt waits for a scan instead of refusing (N17).** HEAD refuses to start while a library scan is running (`fileIntroRefuseIfBusy`). A continued attempt is the same run, so refusing would turn a routine yield into a failed run: the native shell's resumed attempt (a cursor exists) calls `waitWhileScanBusy` instead and announces `paused — ...` through `env.Progress`. A fresh start keeps HEAD's refusal. This differs from HEAD, which has no resumed attempt. It deliberately cannot yield again while it waits, for the reason in exception (1): the executor's `yieldNext` needs progress past the attempt's starting point, which a wait does not make. A scan that outlasts a whole attempt therefore ends `timed_out` (`TestFileIntroResume_AResumedAttemptWaitsForAScanWhereAFreshStartRefuses`).
- **The cursor is saved after every completed batch (N22).** Besides the yield, the batch loop calls `onAdvance(prefix)` under its mutex each time the contiguous completed prefix grows, and the shell saves the cursor then (`saveCursor`, shared with the yield path). A crash or a restart after batch K therefore resumes from K, not from the last yield. Cost: one small JSON checkpoint write per completed batch, and a batch is eight files of whisper work, so the write rate is bounded by the transcription rate. A failed mid-run save is logged at Warn and the run goes on; the yield's own save still fails the attempt (`TestFileIntroCheckpoint_ACrashAfterBatchKLeavesACursorAtK`).
- **duration-backfill book pool** is a seam (review MINOR 12, N3): HEAD runs `Workers` goroutines (unchanged), the native shell runs each book as one item of a loop declared `Fixed(workers)` with a 30-minute per-book timeout (`durationBookTimeout`). Because the items are books, the operator's `parallelism_cap`, a pause and the per-item timeout apply mid-run, and the progress counts books (the denominator is the library's book count). The item re-reads the book by id and skips it if it is gone. A book that panics ends the run with an error naming it (the error wraps a `tasks.PanicError` with the stack) instead of hanging it. A failed re-read of a book ends the run naming it; a nil book is "gone". A book whose probe outlasts the per-book bound (a real-clock `context.WithTimeout`, so the test shortens `durationBookTimeout` rather than using a fake clock) is reported once as a read error for that book, strikes nothing and writes nothing (N18; `TestDurationBackfillNative_ABookThatOutlastsItsBoundIsReportedOnceAndStrikesNothing`). The unknown-rows grain runs on `Each`.
- **capture and export Timeout** are 120 minutes, stated explicitly (review MINOR 13); HEAD declares none.
- **Help text** of most kinds is reworded beyond the mode-key sentence the brief required, where HEAD's Description names a param the native shell refuses; the conformance test derives which kinds from HEAD's text.
- **intro-transcribe** drops HEAD's `CheckpointFn` (never called at page concurrency 6). `LastBookID` stays a start param.
- **fs-regroup-xml** needs `fsRepairStore` and `merge.BookWriter`; `t6g4FSRegroupView` satisfies them with four stubs that refuse (`UpdateBook`, `DeleteBook`, `MoveBookFilesToBook`, `ReassignExternalIDs`) because the body reaches none of them live.
- **dedup-exact-triage** reaches its service through the store/writer seam (`DedupTriagePreview`, `DedupTriageApply`).
- **Mode-key refusal and live-only writers**: every native writing shell refuses `dry_run`, `dryRun` and `apply` (case-insensitive) by name, and fs-regroup refuses a live apply when `deps.Scan` is nil. A native shell with its own checkpoint (ai-dedup-batch, file-intro-transcribe) restores HEAD-shaped bytes where HEAD wrote any.
- **Removed F5-18 exemptions**: two `tasklint_exempt` lines that this row no longer needs were removed with the owner's approval (commit 4ff960801).
- **Regressions caught inside this PR.** Two defects were introduced by this PR's own round-2 commits (46e28d918, 822b19c53). Both were pushed (46e28d918 went red in CI) and both were caught by new tests: the producer of the duration pool selected on the wrong context, so a panicking worker left it blocked and hung the run; and the file-intro checkpoint was restored after the first progress call, so a resumed attempt reported 0/1. Main never had either; both are fixed here and pinned by tests.
- **Dropped schedules**: ai-dedup-batch (`0 0 * * *`) and integrity-check (02:30) keep their schedule only on the v2 definition; the native kind takes `Schedule` from the hook (R9), owned by F5-14.
- **Commit trailer**: the session reminder names Claude Sonnet 5.5; the builder rules say Opus 5.5. The session reminder was followed.

## Not provable without the real tools

Nothing here runs the real ffmpeg, a real whisper worker or taglib: the parity cases use a stand-in ffmpeg and a stubbed batch transcriber. The parity table runs HEAD's `def.Run` and the native kind against real in-memory Pebble stores and compares the end state (books, file rows, the undo journal, aggregate sizes, parsed transcript fields, the stats keys); the other tests use recording fakes, which prove which methods a core calls and through which seam, not what the real F5-18 writer does with them.
