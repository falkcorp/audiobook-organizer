# F4-08 dark slice A4: revocation-journal follow-ups (Q6a token, Q6c, Q6d)

Dark: nothing binds the journal component at boot until F4-08's flip. Q6b (journal `user.enabled` re-enables) is not built: it can switch an account on at boot, which widens access, and waits for the owner's ruling. The offline `storage journal-queue list|clear` command is not built either (`core/app` and `core/kernel/offline.go` are F3-07's files).

## Names beyond the spec

| Name | What it is |
|---|---|
| `journal.ErrOtherApp` | `OpenFile` (and so `Component.Bind`) refuses a journal whose header's `app` differs from `FileOptions.App`. Checked in the same switch as the install, before any write, so the file stays byte-identical (no header, no cut of a torn tail). |
| `FileOptions.App`, `ComponentOptions.App` required | An empty app is a caller's mistake (nil File / nil Component), not a skipped comparison. |
| `(*Component).App()` | The one source of the expected app. The kernel's `setAside` reads it for the `CreateBased` header; `reapplyInput.App` is deleted, so the journal a boot starts and the one it binds next cannot disagree. |
| `journal.HealthQueued` = `revocation_journal_queued` | Info. Raised while `c/backup/journal_unapplied/` holds entries at the end of P4d step 2; the Detail is the count only (an entry's kind is a newer build's string). Pinned in `core/health`'s `TestPostureTokensGolden`, so it is generalised on every public surface and never on `/health`. |
| `(*Component).NoteUnapplied(n)` | `settleUnapplied` calls it with `reapplyResult.Unapplied` (not `Queued`), before the restore-boot return, so a later boot of the same build that queues nothing new still reports the waiting entries, and a drained queue clears it. |

## Decisions

1. **Another app's journal is broken, not set aside.** The install matches and every line verifies under this store's keyring, so the lines are this store's revocations. The boot re-applies the verified tail (narrowing), does not fail closed for it (the store lacks nothing the journal holds), refuses appends (the revoking callers record gaps), and reports `revocation_journal_broken` until an operator resolves the file. `TestReapply_AnotherAppsJournalIsReportedBrokenAndItsLinesStillApply` pins it.
2. **Two installs sharing one `db_path` stay a documented limit.** They share an install ID, so neither the install nor the app check tells them apart; `storage.Admin.StoreIdentity()` is the check if the owner wants one.
3. **Health Details are fixed sentences or counts (Q6c).** `Health()` never formats an error: open and write errors name the journal file. The cause is logged where the condition is recorded: Bind's failure by the kernel (`restore_reapply.go`, "not usable for appends", with the path), every `res.Broken` the classifier's `untrusted` step records (new Error log with the path), the move failure (existing). `Health()` itself logs nothing, since it runs on every health request.
