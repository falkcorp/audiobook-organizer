# R1-19 seams and coined names

This file lists what the build-identity PR added beyond 09 §9.4 R1 "Content: endpoints and build identity", 06 §6.4.5, 07 §7.5.2 and §7.6.3: names the spec does not have, readings it took where the spec or the brief is silent, files it touched outside the row's inventory, and the seams later rows (R1-23, R1-30, F9, R3) build on. Everything not listed here follows the spec as written: the five `--version-json` fields, `app.BinaryID`, the one build-ID rule, the meta tag as its one source, goreleaser's two deleted flags and the `--version-json` post-check.

old ==> new: none. No package moved.

## Names beyond the spec

| Name | What it is |
|---|---|
| `books.AppID` | `internal/books`'s `appID` constant, exported. `main`'s `--version-json` prints it as `app`, and `Options.AppID` reads the same constant, so the two cannot drift. It is a new exported name outside the brief's code contract. The alternative was a second `"abo"` literal in `main`. |
| `server.BuildIDFromFS(fsys fs.FS) string` | Reads `web/dist/index.html` from an embedded filesystem and returns its `mediacore-build` content, `""` when there is no bundle or no tag. It calls `buildIDFromIndex`, the parse stage 5's `X-App-Build` uses, so `--version-json`'s `ui_build_id` and the header come from one reader. `main` maps `""` to `dev`. New exported name, for the same reason as `books.AppID`. |
| `main.fastExit`, `versionInfo` | `--version-json` and `--print-upgrade-floor`, beside `app.FastExit`'s `--print-capabilities`. They stay in `main` because the first needs ABO's `WebFS` and `books.AppID`, which core cannot import. |
| `web/build-id.ts` (`resolveBuildId`, `stampBuildId`, `mediacoreBuildPlugin`, `BUILD_ID_PATTERN`) | The ID rule and the Vite plugin that writes it, split out of `vite.config.ts` so the rule's tests need not load the React and babel plugins. It is in `web/tsconfig.node.json`'s `include`. |
| `apiFetch`'s `checkBuild`, `readPageBuildId`, `onStaleBuild`, `getStaleReasons`, `StaleReason` | The names of 07 §7.5.2's `@mediacore/api-client` contract, implemented in ABO's `apiFetch` with `checkBuild(response, { buildId })` (no `shell` option: ABO's pre-shell bundle is always `shell: false`). R1-30 replaces the bodies with the api-client's and keeps the banner's subscription. |

## Readings and deviations

| Topic | Reading |
|---|---|
| `--print-upgrade-floor` | Prints zero bytes and exits 0. The brief says "empty until R3" and the acceptance accepts 0 or 1 bytes; 05-storage's "empty requirement" is read as "nothing", so a recipe's `[ -z "$(...)" ]` and a `wc -c` both read it as no floor. R3 replaces it with the `{release, owners, requires}` object. |
| `--version-json` commit in a build from a dirty tree | `buildid.Commit()` is Go's `vcs.revision` plus `+dirty`, so a developer build of this worktree prints `<sha>+dirty`. A `go test` binary and a Docker build have no VCS data and print `""`, present. `+dirty` itself is pinned by `core/buildid`'s `commitFrom` table test, which `TestVersionJSONFields` cites instead of injecting build settings. |
| The two halves of `TestBinaryIDDistinguishesBuilds` | `core/app/binaryid_test.go` proves `BinaryID(opts) == buildid.Binary(opts.Version)` and that the version changes it. The second half, two executables with different code, is not proved across two real binaries (`todo.d/2026-11-08-binaryid-cross-binary-proof.md`). |
| `TestBuildID_HeaderEqualsEmbeddedMeta` | Lives in `internal/server` (`build_id_test.go`), because it needs `setSPAInlineScripts` and the perimeter harness. It feeds a fixture bundle through the same path an embedded build takes and asserts `X-App-Build` on the SPA page, a routed call and an unrouted path, then `dev` without a bundle. The real-image check is `image_probe.sh` with `PROBE_BUILD_ID=1`, now on. A hand run of a `-tags embed_frontend` build confirmed that the header, the served page's meta and `--version-json`'s `ui_build_id` are one value. |
| Stale-build rule: cases 1 and 3 only | 07 §7.5.2 lists three cases. `apiFetch` implements the two that read headers: a differing `X-App-Build` (case 1) and an app answer with `Reporting-Endpoints: csp=...` but no `X-App-Build` on a status below 500 (case 3, a tab after a rollback to R0). Case 2 (`checkModules`, shell only) belongs to the shell. An empty or `dev` page ID, or an empty or `dev` header, never triggers. |
| The banner | A fixed-position MUI `Snackbar` with an `Alert` and a Reload button, not dismissable, `App`'s one mount. `App`'s root is a flex box with `height: 100vh`, so an in-flow banner would sit beside the content, not above it. The invite page returns before the banner mounts (`todo.d/2026-11-08-stale-build-banner-invite-page.md`). |
| The Vite build and a dirty tree | A tree with any tracked modification, including a lockfile change from `npm install`, takes rule 3. `make build` runs `npm ci`, which does not change it. |
| `vite serve` | Evaluates no ID and runs no git. The placeholder's `dev` stands. |

## Risks

| Risk | Cost of the fix |
|---|---|
| The Docker image build has no `.git`, so its UI ID is a build timestamp plus random hex. Two builds of one commit differ, so a tab on the earlier image is offered a reload after a rebuild of the same code. That is rule 3's intended reading (a tab on an earlier build is offered a reload before its lazy chunks are gone). | None; a release that wants a stable ID passes `BUILD_ID` (`todo.d/2026-11-08-docker-build-id-arg.md` adds the `ARG`). |
| A response double with no `headers` is never stale. | None; several suites stub `fetch` that way. |

## Seams for later rows

- **R1-23 (storage levels):** adds `--print-storage-levels` beside `fastExit` in `main.go`, sets `PROBE_STORAGE_LEVELS=1` in `docker-image.yml`, and adds its words to the changelog line ("`--version-json`, `--print-storage-levels` and `--print-upgrade-floor` print machine-readable build and store facts"). `test_check_embed_context.py` asserts the level probe off; flip that assertion with the workflow.
- **R1-30 (api-client):** `@mediacore/api-client`'s `checkBuild` and `onStaleBuild` replace `apiFetch`'s. `StaleBuildBanner` imports `getStaleReasons` and `onStaleBuild` from `utils/apiFetch`; re-export them from there, or point the banner at the runtime's. Both transports must reach the one banner (07 §7.5.2).
- **F9 / shell adoption:** the shell's banner replaces `StaleBuildBanner`, and the Vite preset (`@mediacore/shell/vite`) replaces `web/build-id.ts` with the same rule.
- **R3 (upgrade floor):** `--print-upgrade-floor` prints the declared floor; the `deploy` template and the updater compare it.

## Deployability

Deployable on its own. Rollback is a revert: the meta tag and `X-App-Build` carry `dev` again, the banner never shows, the two flags answer "unknown flag" as a pre-R1-19 binary does, and the deploy post-check goes back to its dead route.
