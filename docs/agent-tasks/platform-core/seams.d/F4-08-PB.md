# F4-08 pre-PR P-B seams and coined names

This file covers the labelled-filesystem seam for `core/backup/journal`: what it added beyond 05-backup §5B.3.6 and 06 §6.5.1 P4d step 2, the decisions it took, and what it leaves for F4-08.

Everything here is dark. Production keeps plain `os` with byte-identical behaviour: the same modes, the same fsync points, the same rename atomicity. Nothing opens the journal component at boot until F4-08 binds it.

## Names beyond the spec

| Name | What it is |
|---|---|
| `journal.FS`, `journal.FSFile`, `journal.OSFS()` | A stdlib-only filesystem interface for the journal's file writes, and its `os` implementation. `TestJournalImportsOnlyAllowed` limits the journal to `entity`, `storage`, `storage/restorejournal` and the standard library, so the interface cannot name `vfs.FS`; the bridge lives outside the package. |
| `journal.WithFS(fs)`, `journal.FSOption` | A variadic option on the free functions `ReadFile`, `CreateBased`, `ReadLocation`, `WriteLocation`, `MoveFile`, `RemoveMoved`. Every existing call site compiles unchanged and gets `OSFS()`. |
| `FileOptions.FS`, `ComponentOptions.FS` | The filesystem of the stateful types. Nil means `OSFS()`. `FileOptions.wrap` (the line-file failure seam the unit tests use) is unchanged and still works. |
| `journal.RemoveMoved(path, opts...)` | The labelled `os.Remove` of the old journal once `backup.location.json` points at the moved one. The kernel's raw call becomes this (F4-08). |
| `journal.Label*`, `journal.FSLabels()` | The 19 stable writer labels, under the prefix `journal.`. `FSLabels` lists them for the writer table. |
| `journalfs.From(ctx)` (`core/internal/journalfs`) | The bridge. No seam, a seam without a filesystem, or `vfs.Default` returns `journal.OSFS()` itself; an in-memory filesystem (plain, errorfs-wrapped or crashable) returns a memory-backed `journal.FS` whose writes go through the seam and carry the open region's label; any other filesystem is refused, so a write can never go past the recorder unseen. |
| `crashmatrix.Row.Unbound`, `LabelKernelJournalAside`, `LabelKernelJournalAsideSync` | `Unbound` is why no boot reaches a row's writer yet. `Unobserved` never reports an Unbound row's label as missing, and reports one a fixture does reach as stale, so the mark cannot outlive the wiring. The two kernel labels are reserved for the set-aside's two raw calls. |

## Decisions

1. The in-memory adapter models what Pebble's `vfs.File` lacks: an append is a `WriteAt` at the end, the flock is a per-boot path set (so a second open of a locked journal is `ErrLocked` and the path is free again after `Close`), and a truncate is an atomic replace (temporary copy, fsync, rename, directory fsync, reopen). The two outcomes of a crash inside it equal `ftruncate`'s.
2. A label is a region around the operation, closure-scoped and never exited twice (the labeller's exit is not guaranteed idempotent). Cleanup that follows a failed step runs after the failed step's region closes, under its own label (`journal.location.cleanup`, `journal.move.cleanup`, `journal.base.create`'s remove), so the matrix can fail a cleanup on its own.
3. `journal.move.clear` is reached only when a temporary copy an earlier attempt left exists; the site test plants one.
4. The writer-table rows sit after the "P4d 1" row, in the new phase "P4d 2", every one Unbound with a reason that names F4-08.

## F4-08 wiring obligations: kernel journal-file write sites

`core/kernel` is untouched by this PR. These are the raw `os` calls and unlabelled journal calls F4-08 must route through the seam. Each has an Unbound row in `crashmatrix.Rows()` that names F4-08.

| Site | What F4-08 does |
|---|---|
| `core/kernel/restore_reapply.go:281` `journal.ReadLocation(in.StateDir)` | Pass `journal.WithFS(journalfs.From(ctx))`. |
| `core/kernel/restore_reapply.go:439` `journal.MoveFile(recorded, in.JournalPath, in.Keys)` | Pass the same option. |
| `core/kernel/restore_reapply.go:454` `journal.ReadFile(path, in.Keys)` | Pass the same option. |
| `core/kernel/restore_reapply.go:479` and `:486` `os.Lstat` (regular-file check, aside-name probe) | Read-only. Route through the filesystem so a memory-backed boot sees the same files; no label. |
| `core/kernel/restore_reapply.go:491` `os.Rename(path, aside)` | A labelled rename under `crashmatrix.LabelKernelJournalAside`. |
| `core/kernel/restore_reapply.go:494`, `:504-510` `syncDirOf` | A labelled directory fsync under `crashmatrix.LabelKernelJournalAsideSync`. |
| `core/kernel/restore_reapply.go:498` `journal.CreateBased(path, in.Keys, hdr, head)` | Pass the same option. |
| `core/kernel/restore_reapply.go:1270` `comp.WriteLocation(ctx, desc, pair)` | Set `ComponentOptions.FS` where the component is built. |
| `core/kernel/restore_reapply.go:1274` `os.Remove(moved)` | Replace with `journal.RemoveMoved(moved, journal.WithFS(...))`. |
| `core/kernel/restore_hooks.go:364` `journal.ReadFile(path, keys)` in `restoreAborted` | Pass the same option. |
| `OpenFile` of the journal component | Set `ComponentOptions.FS` (and `FileOptions.FS` where `OpenFile` is called directly). |

The filesystem each time is `journalfs.From(ctx)`, the ctx being the boot's.

## Follow-up

Once F3-07 merges, `core/internal/journalfs` and `statefs` (F3-07's labelled state filesystem) should share one labelled-FS helper: both adapt the boot's seam filesystem to a package-local interface and both model the same missing `vfs.File` operations. This PR mirrors `statefs`'s shape on purpose so the merge is mechanical.

## Verification notes

`make lint-deadcode-ratchet` needed no baseline lines: no `main` imports `core/internal/journalfs` yet, so deadcode does not load it. F4-08's import is what brings it into the ratchet, and the identifiers it uses are then reachable.
