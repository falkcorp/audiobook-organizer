# F8-01 seams and coined names

This file covers what the "core backup, dark" PR added beyond 05-backup §5B.3 and §5B.10: names the spec does not have, the readings it took where the spec or the brief is silent, the security-review fix made in the PR, how the brief's test names map to tests, and what it left for later rows. Everything is dark: ABO's backup, its routes and its R1 extractor are unchanged (I8), `internal/backup` is not imported, and no kernel boot path builds a `backup.Svc`. The only live change is `storage restore-offline --archive` (below).

## The restore-option gate (coordinator security finding)

`core.backup.stage-restore` has `Perms.Start` of `core:backup.restore` only. A task body that passed `Foreign`, `ReplaceConfig`, `AcceptUnreadableSecrets` or `AllowWeakVerify` to `StageRestore` would have bypassed the route's interactive-owner (and, for `Foreign`, `core:admin`) guard. The gate is in `StageRestore` and `RevertLastRestore` themselves, not in their callers:

- `authorizeOptions(ctx, opts)` runs first, before the backup resource is taken (the metric records "rejected"). Any of those four options needs `RestoreProof{Owner: true}` on the context; `Foreign` also needs `Admin: true`.
- The route (`backuphttp`) is the only code that sets the proof, after its own authorise step: `Owner: true` (its guard already required the interactive owner) and `Admin` from `holds(core:admin)`. The task body never sets it, so the task path refuses the privileged options (`TestStageTaskRefusesPrivilegedOptions`).
- A plain restore and `Restart` need no proof from the package: who may stage one is the caller's gate (the route's `core:backup.restore` plus its owner guard, the task's `Perms.Start`).

A caller added later cannot forget the check, because the check is not the caller's. Tests: `TestRestoreOptionsGate`, `TestPlainRestoreNeedsNoProofFromThePackage`, `TestRevertGate`, `TestStageTaskRefusesPrivilegedOptions`, and the route tests assert the proof the route passes.

**Residual, for the owner.** A plain restore reached through the task path is gated only by `core:backup.restore` (Sensitive, AuthRequired) per the spec's task row, with no owner assurance, where the route also has the owner guard. Making the task path owner-gated would mean only the route may enqueue it. `Restart` is left ungated on purpose: it only asks for the restart the staged restore already needs.

## Verification reasons and host text (second security finding)

A verification's error text (`VerifyResult.Detail`) quotes host paths (`OpenRegular` names the archive path), entry names and the errors of the files and the store the check touched. The first draft returned it in the API's `verified` member and in a list's entries, so any `core:system.view` holder could read it. Now:

- `verifyDTO` has no `detail` member. It carries `reason`, one of `checksum_mismatch`, `no_checksum`, `manifest_mismatch` (a missing, invalid or disagreeing manifest, including an entry that changed, was added or is absent), `unsafe_content`, `malformed_archive`, `limit_exceeded`, `needs_newer_build`, `store_unopenable`, `failed`. The set is a wire contract: codes are never renamed or reused, and a new cause gets a new code. `TestVerifyDTOHasNoFreeTextMember` pins the DTO's member set, so a field that could carry text is a deliberate edit of a test.
- `reasonOf` sorts the error; the more specific cause wins (`verifyLegacy` joins a scan's error with `ErrManifest`), an open-level failure is the store's whatever its error wraps, and anything unclassified is `failed`, never a pass.
- The text still goes to the operator: `Verify` logs it at Warn with the archive, level and code, and the sidecar keeps `detail`.
- The sidecar sits in a directory an operator or a share can write, so `reason` is read as untrusted (`VerifyReason.Normalize`): a code this build does not know, or none on a failure, reads as `failed`; a code on a pass reads as none. `verifyOf` normalizes again at the API boundary, whatever the `Catalogue` returned.
- The same class, fixed with it: the restart-failure warning, the rename pre-check's refusal and the config copy's location were `PendingRestore.Warnings`, which `pendingDTO` returns, and carried the error text or the host path. They are fixed phrases now (the config pointer reads `<state_dir>/restore/<id>/config.restored`); the text and the full path go to the log. `TestStageWarningsCarryNoHostText`.
- **Not changed, owner's call.** (1) was resolved in the third review round: the secrets-coverage refusal and warning no longer name key IDs (see below). (2) A failed verification that is none of the route's mapped errors (a limit, an unsafe entry, an unopenable store) answers 500 with the cause logged, where a verdict could be a 409 `archive_verification_failed` with the `reason` code; making it one is a few lines in the route and a status change a client would see. (3) A module name in the `module %s ... is not in this build` warning comes from the archive's manifest, not from the host. (4) A task run's error text (`core.backup.verify` joins its per-archive errors) reaches the task API through the task framework, which is outside this row.

## Third review round (CodeQL, free space, hardening)

The independent review of 5734c4f49 held the PR for one blocker (four open CodeQL alerts) and one major (no free-space guard, caps that do not hold against sparse or compressed content), with minors. What changed, and the readings it took:

**Blocker: nothing the caller sent, and no key ID, reaches a log.**

- `checkSecrets` returns `*UnreadableSecretsError{Count}` (matches `ErrUnreadableSecrets` with `errors.Is`), whose text is the sentinel plus the number of distinct missing keys. The warning an accepted unreadable-secrets restore carries is the same count ("secrets sealed under N key(s) this install does not hold are unreadable and must be re-entered"). No key ID exists as text in an error, a warning, a log line or an API body; `archiveDTO`'s "key IDs stay out" comment is now true. An operator who needs the IDs reads them from the archive's manifest offline. `TestUnreadableSecretsRefused` pins this with a captured logger. This resolves the owner's call (1) of the second finding.
- `Verify` logs the catalogue's own ID of the archive it found, not the text of the request path. `StageRestore` already did.
- `Import` ignores its `name` argument (kept in the signature because the `Catalogue` interface has it) and always stores under a service-chosen name, so a caller's text is never a path under the backup directory nor a string in a log line. The route still validates the name it is given; it is only a suggestion. `TestImportRefusals` asserts that not even a conformant, free name names the stored file.
- `httpapi.writeError` logs the handler error and the request path with CR and LF removed (alert 2246 is open on main too, and this PR adds flows into it: an import's refusal quotes an entry name from the upload). The body is unchanged (fixed text, no cause).

**Major: nothing is extracted without room for it, and nothing is extracted past what was admitted.**

- `requireSpace` (`core/backup/space.go`) is the one place every extraction asks "will this fit", before the first byte is written: the staged restore (the manifest's entries plus the manifest, on the staging directory's filesystem; a legacy archive's scanned bytes), the open-level verification (the `db/` entries, on the scratch directory's filesystem), `Rewrap` (the entries on the staging root and again on the backup directory, summed when they share a device) and the offline extractor (`db/` only). Claims on one device add up and are checked against it once; each device keeps the margin. A device or free-space query that fails fails the check. The margin is `Settings.SpaceMargin`, 2 GiB when unset (HEAD's `backupSpaceMargin`); the offline restore has no settings and keeps none (margin 0: nothing else is running to starve). The error is `ErrInsufficientSpace` (507 at the API) and names no path.
- A refused verification is not a verdict on the archive, so `Verify` returns the error without writing a sidecar (as for a cancellation).
- `Extractor.SetBudget` bounds what an extraction writes to the bytes it admitted: `WriteFile` reads one byte past the remaining budget (or the manifest's declared size, whichever is smaller) and refuses with `ErrLimit` (`ErrEntryMismatch` when it is the declared size that was exceeded), and a refused file is neither kept nor charged. Every extraction sets it from the figure it checked the space against. Removing the `SetBudget` call from the staged extraction is not observable in a test: the tar header size and the manifest's size already bound each write, so the budget is defence in depth, and its own behaviour is unit-tested in `backuparchive`.
- A sparse file is refused: `GNU.sparse.*` PAX records on a header (archive/tar serves such an entry as a regular file of its logical size, so a few kilobytes of archive can declare terabytes) and the GNU sparse type. The fixture is built by hand (archive/tar's writer drops those records), and a test proves the standard reader admits it, so the refusal is not passing on a malformed tar.
- Default limits are 4 TiB for the archive file and for the sum of entries, 256 GiB for one entry and 262144 entries (were 16 TiB for the archive file and in total, 1 TiB per entry, 1048576 entries). They are far above any real store (a 40 GiB library's checkpoint is some hundreds of files of a few GiB) and are not what holds an extraction to the size it declared: the free-space check and the budget do. An operator with a larger store sets `Options.Limits`.
- **Closed in the fourth round (below).** An import's upload was bounded by `MaxArchiveBytes` but not checked against free space (its length is not known before it is read); the fourth round's `spaceWriter` checks it as it is written.

**Minors and nits.**

- `New` requires `Options.Markers` (a nil `Markers` used to skip the journal touch points silently).
- `ParseManifest` requires a ULID `ArchiveID` (the `legacy-` form is the catalogue's name for a manifest-less archive and no manifest carries it), bounds every free string and map key (256 bytes, valid UTF-8, no control character, at most 4096 names per map) and the entry paths and sums. The catalogue lists one file per archive ID (the name that sorts first; a legacy `.tar` and `.tar.gz` of one stem count as one) and names each dropped file once in the log.
- Floor 1 of retention counts Own archives only. An archive from before provenance takes it only while no verified Own archive exists. A Foreign archive never does (its verification record is a file anyone who can write the directory can write). The scheduled verification opens (open level) only an Own archive, so a Foreign or legacy archive is never handed to `storage.Open` by the task.
- A stale `.backup-verify/v-*` directory (untouched 24 h), and a `.partial` or `.tmp` file with the app's prefix (untouched 6 h) are removed; a younger one belongs to a running pass. `writeFileAtomic` writes to `<name>.<random>.tmp` (O_EXCL, 0600), so a stale temp file never fails the next write.
- The `runs` counter's `reason` label is `schedule`, `manual` or `other`, never the caller's text. `VerifyResult.Detail` is cut at a rune boundary.
- The operator's keyring copy in a restore is created 0600 before its first byte (it was chmod-ed afterwards, and a process that opened it in between kept a readable handle). `WithRestoreProof` is documented as the trust boundary it is: a context that carries one is trusted to have been through the owner guard.

**Follow-ups, not in this PR.** F8-04 must close the task path's plain restore before it registers `StageRestoreTask` (a plain restore reaches `StageRestore` with no owner assurance; see the residual in the restore-option gate); the legacy archive's rehash and SHA-256 binding (review m6); and the reviewer's nits n2, n5, n6 and n7.

## Fourth review round (the reason on write, publication without a window, free space during an upload)

The re-review of the re-cut PR held it for one major and two minors. What changed, and the readings it took:

**Major: a manifest is checked on the way out with the test it meets on the way in.**

- A reason was bounded by `ParseManifest` (256 bytes, valid UTF-8, no control character) and by nothing that wrote one: the route allowed 128 *runes* (up to 512 bytes), `Create` signed whatever it was given, and a 100-character CJK reason produced an archive that was written, reported made (with `VerifyAfterCreate` off) and then listed by nothing. `backup.ValidReason` (and `backup.MaxReasonBytes`) is now the one rule; `ErrInvalidReason` is its sentinel.
- `Create` applies it first, before the backup resource is taken, before a directory is made and before the store is touched. A refusal records no `runs` sample (a refused request is not a run); a configuration error found later inside `create` (an unknown codec) still records `error`. The route's `cleanReason` calls the same function, so its bound is in bytes and cannot drift from the reader's. The route's refusal and the mapping of the service's `ErrInvalidReason` (which reaches the route from the task path) are one answer, `invalidReason()`: a 422 `validation_failed` on `/body/reason` with a fixed body (the fourth round first wrote the second as a 400 `invalid_reason`; the fifth made them one).
- `New` judges `AppID`, `AppVersion`, `CoreVersion` and every `Modules` name and version with the same text test, so a build whose own identity the reader would refuse never starts. The error names the option and quotes no value. Empty versions stay legal.
- **The class, not only the field.** The reason is one of several members of a manifest that come from somewhere other than the caller of `Create`: the install ID (the store), the served-boot nonce (the journal), the level and keyspace names (the inspector), the key ID (the keyring), and the manifest's total size (the 16 MiB read cap). `Create` and `Rewrap` now run `ParseManifest` over the marshalled manifest before the archive is streamed (`checkReadsBack`), so no archive is written that its own catalogue could not read. It runs after the checkpoint and the content-marker advance (the manifest does not exist before), so a failure there is a failed run with nothing in the backup directory. Cost: one decode of the manifest per create or rewrap.

**Minor: an archive is published by a link, never by a replacing rename.**

- The name was chosen by a lookup (`freshName`) and taken by `os.Rename`. Two imports in the same second, or an import and a create, both found it free; the second rename replaced an archive that had already been reported made, and the first writer's sidecars then described the second's bytes. `Svc.publish` replaces both: it takes the name by `os.Link(partial, final)`, which fails with `fs.ErrExist` when anything is at the name, tries the next second on that, and removes the partial name once linked. It also skips a name that has a sidecar and no archive (a crashed run's, or another writer between its two steps), since the sidecars written next would overwrite those. `Create`, `Rewrap` and `Import` all use it (the review named the first two sites; `Rewrap` is the same code).
- The temporary names no longer depend on the final name: `<prefix>create-<id>.partial` and `<prefix>rewrap-<id>.partial` (the run's own ID), and `<prefix>import-upload.<random>.tmp` for an import (it was `import-<unix nanos>.partial`, so two imports on a coarse clock could not both start). The stale-file sweep keys on the suffix and is unchanged; `removeArchive` no longer lists a `.partial` that nothing makes.
- **Filesystems without hard links** (FAT, exFAT, some network and container mounts) answer `os.Link` with an error that is not `fs.ErrExist`. `Disk.publish` then claims the name by creating it exclusively (0600) and renames the finished file over its own claim, which replaces nothing. The claim is visible, empty, for the instant between the two calls, where a link never is; refusing every backup to such a volume would have been the other choice, and a backup directory on an exFAT drive is a common one. `Disk.Link` is the seam (core forbids a package-level function variable for it); the zero value is `os.Link`. On Windows, Go's errno mapping reports an existing name (`ERROR_ALREADY_EXISTS`, `ERROR_FILE_EXISTS`) as `fs.ErrExist` as well, so one branch should serve both; that is Go's documented mapping, and this was type-checked for Windows but not run there.

**Minor: an upload cannot starve the volume.**

- `Import` asks `requireSpace` for the next `uploadCheckBytes` (32 MiB) plus the margin before it makes a file, and a `spaceWriter` asks again each time that much has been written (and for a single write larger than the window). The claim is the interval, not the upload's length (unknown until it ends), which bounds how far an upload can go past the margin to about one interval of writes **where the filesystem's free-space figure keeps up with the writes**. A filesystem that reports free space late (ZFS counts a write when its transaction group commits; a network mount, when its cache is flushed) can take more than an interval before the figure falls: there the margin is the cushion and the interval only says how often the figure is read. A refusal is `ErrInsufficientSpace` (507), the temporary file is removed, and a refused write does not reach the file.

**Closed in the fifth round (next section).** Two concurrent imports of the *same* archive both passed the duplicate-ID check (it ran before either published) and both were stored under different names; `Import` now checks again under a lock that publishes.

## Fifth review round (the concurrent import, and the minor items)

The re-review approved the fourth round with no blocker and no major. Its one minor, and what the nits asked for:

**Minor: two imports of one archive at once are stored once.** The reviewer reproduced it with a barrier at the link: both imports returned an archive, the directory held two files with one ID, the catalogue listed the one whose name sorts first (`dropDuplicateIDs`), and `Delete(ID)` removed that file and brought the other back under the same ID.

- `Import` now ends in `Svc.install`. It takes `Svc.importMu`, looks at the catalogue again (`scan`, `idTaken`) immediately before publishing, then publishes and writes the sidecars, and releases the lock. The check at the top of `Import` stays as the fast refusal: a duplicate is turned away on its manifest before the upload is read through, which is the cost an upload of hours should not pay. Both refuse with the same error (`errDuplicateID`, `ErrManifest`, "already in the catalogue"), which is also what the second of two simultaneous imports now returns.
- The lock is held through publish and the sidecar writes, so a second import's check finds the first's archive whole, or (when the first's sidecars failed and it removed the archive) not at all. It is not held while the upload is read or verified (an upload can last hours and would queue every import behind one), and it is not the backup resource, which `Import` never takes.
- A legacy archive skips the check: its ID is its file's name, and `publish` never gives one name twice. An archive copied into the directory by hand is still the case `dropDuplicateIDs` exists for.
- Limits, stated: waiting for the lock is not cancelled by the request's context (what waits behind it is a scan, a link and two small files); the lock is per service value, so two services over one directory (not a supported shape) are not covered; and no test can tell "held through the sidecar writes" from "released right after publish", since a second import that reaches its check in that gap sees the archive either way, unless the first's sidecars fail; pinning that would need a hook between the link and the sidecar write in production code.
- `TestConcurrentImportsOfOneArchiveStoreItOnce` forces the interleaving: the first import is held at its link (it holds the lock), the second runs until its first duplicate check has passed (the test counts the catalogue scan through the `Store`'s install-ID calls, one per archive described), is then given a second (`settle`) to reach a link of its own, which it can do only if nothing makes it wait, and only then is the first let go. The settle is a window for a bug to show itself in, not a measurement: on correct code the second import waits as long as the first is held, so a slow machine can miss a bug but cannot report one that is not there. Without it a mutant that removes the lock and keeps the second check survives, because the second import then usually reaches its check after the first has finished. The first must win, the second must be refused as a duplicate, the directory must hold the seed and one import, and deleting the import must leave the seed alone. It also pins that the second import's upload and first check do not wait on the first's lock. `TestImportRefusesADuplicateBeforeReadingItThrough` imports a truncated copy of a listed archive and requires the duplicate refusal (reading it through would fail some other way). The reviewer's own test held both imports at the link, which this change makes impossible by design (the second waits at the lock), so the test holds one and observes the other.

**Nits.**

- **`Ensure` judges its reason first.** It returns a recent verified archive without touching the reason, so a caller whose reason `Create` would refuse learned it only on the day none existed. `ValidReason` is now its first statement (an empty reason is legal; `Create` defaults it). `TestEnsureRefusesAReasonTheCatalogueCouldNotRead` has a recent archive in the directory and requires the refusal anyway, and that three legal reasons (one of the longest length, one empty) still return the archive.
- **One status for an invalid reason.** The route said 422 and `mapError` said 400 `invalid_reason`. Both are `invalidReason()` now: a 422 `validation_failed` on `/body/reason`, the status of every other invalid body field of this API. The code `invalid_reason` no longer exists. The test makes the route refuse a reason and the service's sentinel reach the route and compares the two problems.
- **The read-back test pins the order.** `TestCreateRefusesAManifestItsOwnCatalogueCannotRead` now requires exactly one marker advance before the refusal: the manifest carries the new marker, so the read-back cannot come earlier, and a run that fails there leaves the marker moved once and no archive.
- **The fallback says so, once.** When `Disk.publish` leaves the link for the claim-and-rename path it returns the error that made it, and `Svc.publish` logs one Warn per service (a `sync.Once`, so once per process in practice) that a hard link could not be made (usually a filesystem without them), that archives are published by claim and rename, and what that shows (an empty file at the name for an instant). The cause is logged without the two paths an `*os.LinkError` carries. It is not logged when links work. `TestPublishSaysOnceThatTheVolumeCannotLink`.
- **Free-space wording.** `uploadCheckBytes`, `spaceWriter`, `Import`'s comment, this note and the changelog fragment say what the check bounds (what is asked, and the overshoot where the figure keeps up with the writes) and name the filesystems whose figure lags (ZFS, a network mount).

**Residue, noted and left (the zero-byte claim).** The no-hard-link fallback claims a name by creating an empty file there and then renames the finished archive over it. A crash between the two leaves the empty file. Measured on this tree with an empty archive-named file and no sidecars: the catalogue lists it as a 0-byte `legacy-abo/0` archive with `pre_provenance` and no verification; `Verify` refuses it (`no_checksum`); the stale-file sweep leaves it (it removes only `.partial` and `.tmp` files); `Delete` removes it; `publish` skips its name; and retention counts and ages it like any archive (it is unverified, so no floor protects it), so it leaves with the count, age or byte bound. It exists only on a volume without hard links, after a crash in that instant. A sweep for it would remove an archive-named file that is empty, has no sidecar and is older than `stalePartialAge`: about fifteen lines and a test; it is not built because the review asked for a note.

## Readings the spec leaves open

| Topic | Reading |
|---|---|
| Strict manifest | `ParseManifest` uses `DisallowUnknownFields`: a newer additive field (for example `encrypted`) must refuse, never be read as plaintext. The MAC is over the canonical re-marshal with the MAC field cleared, compared with `hmac.Equal`. |
| Catalogue source of truth | The archive's own first-entry manifest, not the `.manifest.json` sidecar (a sidecar can be swapped under another archive's ID or provenance). Verify compares the sidecar with the archive and fails on a difference. |
| Legacy first entry | HEAD's archives begin with the store directory's own entry, so a first entry of another type is classified `ErrManifest` ("not a mediacore-backup/1 archive") and the caller tries the legacy scan. |
| Tar entries | Only regular files (and directories in a legacy archive); symlinks, hard links, devices, FIFOs, sparse files (the GNU sparse type and a PAX header carrying `GNU.sparse.*` records, which archive/tar serves as a regular file of its logical size), absolute names, `..`, doubled separators, backslashes and NULs are refused. Header sizes are checked against `Limits` before any buffer is sized. Files are created `O_EXCL` 0600 and directories 0700 from the start. |
| Retention and the floors | The count bound includes the floor-protected archives, so the newest verified archive can outlive a newer unverified one (floor 1 of §5B.3.5). Retention runs before the space check. |
| Config on restore | A config file archived redacted (`ConfigFileHasSecrets()`) is never swapped in: it is staged to `config.restored` for the operator. `ReplaceConfig` swaps only an unredacted copy. |
| `Requires` data-migration floors | Not provable from the manifest. The Inspector's `storage.Open` of the staged store applies them; its `ErrKeyspaceTooNew` is mapped to `ErrBackupTooNew` after extraction, not before. `ErrUpgradeFloor` is raised from the manifest before extraction. |
| Derived items | `DerivedGeneration` is a seam. `StorageInspector` does not fill `StoreInfo.Generations` until F7-07's generation API exists; `TestDerivedItemsGenerationChecked` drives the check through a wrapping Inspector. |
| Intent IDs and TTL | `<yyyymmddThhmmssZ>-<8 hex>`; the default TTL is 24 h (`core.storage.swap.intent_ttl` at F8-04). |
| Platforms | Core builds for Windows (`GOOS=windows go build ./...` is clean) and the backup package keeps it so. Free space comes from `library.Stats` (Bavail, with its Windows implementation). The same-device proof (`Stat_t.Dev`) exists on unix only (`disk_unix.go`); on any other platform `osDevice` returns an error, so create and staging refuse rather than assume one device. `backuparchive.OpenRegular` has the same split (`open_unix.go`/`open_other.go`). |
| `Rewrap` | Re-MACs under the active key with a new ID and deletes the original only when no retention floor protects it. Only an `Own` archive is re-signed (`ErrForeignArchive` otherwise). |

## Offline restore (`storage restore-offline --archive`)

- `backup.ExtractStore(ctx, archive, storeDir)` has `kernel.Config.ArchiveExtract`'s signature. A mediacore-backup/1 archive is read through its manifest (the manifest sidecar must equal the archive's, every entry must be listed and match its size and SHA-256 as it streams) and **only `db/` is written**, so an `--into` copy never receives the config or boot-record entries. A legacy-abo/0 archive is scanned end to end, then extracted with its top-level directory stripped. A `.sha256` sidecar, when present, must match (unreadable or malformed refuses too); an archive named by hand with no sidecar extracts, as HEAD's did, and the kernel opens the extracted store read-only with this build's guard before it stages anything.
- **Provenance is not checked offline.** The command is the state directory's owner at a terminal with the service stopped and `--accept-loss` (the kernel refuses anything else), which is the authority to replace the store by hand. The spec's `[--foreign]` flag and an offline MAC check would need the kernel seam to carry provenance and the keyring-derived key; they are not in the brief's flag list (`--archive`, `--keyring`, `--gap-fill`, `--accept-loss`) and are not built. The staged restore is the provenance gate.
- `--keyring <file>` and `--gap-fill <file>` (archive only; a checkpoint holds its own copies) are staged under the state-file labels `keyring` and `gap_fill` and replace the live file of that label at the path the app declared in `StorageStateFiles`, else `<state dir>/secrets.keyring` and `<db parent>/config.yaml`. The replaced files are set aside in `previous/` like every replaced state file; a source with no such file never removes or replaces the live one (DATA-11). The keyring must be a regular, non-empty, mode-0600 file of at most 1 MiB, never a symbolic link. With `--into` both are copied to `<into>.state/<label>`.
- A legacy archive restored without `--gap-fill` warns what then migrates empty and that its encrypted rows are read with the host's `.encryption_key`. The warning does not list HEAD's setting keys: the managed set is HEAD's to change, and a list here would go stale.
- `app`: an app that sets no `R1ArchiveExtract` now extracts through `backup.ExtractStore` (was: `--archive` refused). ABO sets its own until its R2 flip, so ABO's behaviour is unchanged (I8).
