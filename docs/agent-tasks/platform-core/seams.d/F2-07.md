# F2-07 seams and coined names

What the audit-store PR (`core/audit`, `core/kernel/audit.go`) added beyond 05-rbac §3.5, §7, §10 and §11, the readings it took where the brief or spec is silent, and the decisions the F2-16 wiring row and F4 must know. Everything not listed here is 05-rbac as written. The PR is dark: no route, no registered task, no stored-row change, and `boot.go`, `kernel.go`, `storage.go` and `swap.go` are untouched.

## F2-16 must know (the brief's base-state grep found no kernel pattern)

The brief says to register the `c/audit/` core keyspace "the same way the kernel registers `c/storage/`" and gives a grep for it. The grep (`c/storage/` in `core/kernel/*.go`) finds one comment in `swap_test.go` and no registration code: `core/storage` is implicit inside `storage.register` (`core/storage/db.go`), and every other owner reaches storage through `OpenOptions.Owners`, which the kernel fills in `storageOwners()` (`core/kernel/swap.go`, a file this PR may not edit). So there is no kernel pattern to copy; the choice made is the owner route.

| Name | What F2-16 does with it |

## Readings where the spec is silent

- **RequestID and TraceID are not filled from the context.** §3.5's comment says "filled from ctx when empty", but the request-ID context key lives in `httpmw` (L6), which audit (L4) cannot import. The field is stored as the caller gives it; httpapi sets `Event.RequestID` (F4). The Event field comment is §3.5's text verbatim.
- **Stored JSON uses Go field names** (§3.5's structs carry no json tags): `Seq`, `ID`, `Time`, `Action`, `Actor`, `Target` and so on, `Coalesced` always present. F4's route and the export must use the same names or add tags with a codec version bump.
- **Key layout** as `keys.Join` segments (05-storage §5S.3.3): `rec/<seq 8B>`, `idx/actor/<userID>/<seq>`, `idx/action/<action>/<seq>`, `idx/target/<module>/<kind>/<id>/<seq>`; the `actor` index only for a record with an actor user, the `target` index only when some Ref field is set. Records use `codec.JSON[Record](1)`. The sequence is named `seq` in the keyspace.
- **Counting.** `audit_records_total` counts a `RecordIn` record when it is staged: the store cannot see the caller's commit, so a batch that is then discarded is counted too. `audit_pruned_total` is 0 until the tasks flip registers `core.audit.prune`. Both `audit_write_errors_total` paths (`sync`, `async`) are always exported.
- **Redaction** (§7.7): key match by the §7.7 regexp at any depth, case-insensitive; a string value is redacted when it, or any word of it, starts with `mcs_`, `mck_`, `mcb_`, `mci_`, `mct_`, `abk_` or `abbs_` (a note reading "Bearer mck_..." is as much a leak as the bare token). Details over `DetailsMaxBytes` lose whole keys in key order and gain `_truncated` (the drop count); Details that JSON cannot encode become `_unserializable: true`. The caller's map is never changed.
- **`New` writes nothing**: the first record takes the first sequence lease, so the crash matrix of storage is unchanged.

## Denial coalescing decisions (security review of the first push)

1. **The fold key is the spec's.** §7.3 says "identical denials (same actor, route, permission, outcome)". The key is those four, the actor as user, credential and address (so anonymous callers differ), plus the action. It does **not** include `Target` or `Reason`. A review asked for them; §7.3 does not name them and the instruction was to follow the spec, so denials of one route that differ only by target are one record, carrying the first denial's target and reason. `TestAudit_FoldKeyIsTheSpecs` pins this. This leaves a real gap: a caller who walks many targets through one route inside the window shows the first target only. Closing it is a spec change to §7.3 (add Target to the key, which also raises fold cardinality), left to the owner.
2. **Open folds are bounded.** The writer held one fold per distinct key with no cap, so many addresses, credentials or routes grew memory without bound. Open folds are now capped at `AsyncBuffer` (`core.audit.async_buffer`): at the cap the oldest fold ends early and is written as it stands (it joins the ready list, flushed at `BatchMax` or on the batch timer). No record is lost and none is counted dropped by this path; the cost is that a key flood folds less. Memory is bounded by queue (`AsyncBuffer`) + open folds (`AsyncBuffer`) + one batch (`BatchMax`). `TestAudit_OpenFoldsAreBounded` drives more distinct keys than the cap and checks the early writes, the drop count and that every denial is accounted for.
