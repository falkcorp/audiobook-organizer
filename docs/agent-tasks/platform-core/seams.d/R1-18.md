# R1-18 seams and coined names

This file lists what logging stages 1 and 2 added beyond 05-logging §3, §4, §8, §9 and §11 items 1, 4, 5 and 6: names the spec does not have, readings it took where the spec or brief is silent, deviations from the brief, and the seams later rows (R1-16, R1-34, F3) build on. It is stacked on R1-15 and replaces R1-15's `logTee`.

## Names beyond the spec

| Name | What it is |
|---|---|
| `app.Options.R1Log *log.Settings` | The whole `core.log` section, release R1 only. R1 has no config layer to read `core.log.*` from (04 §8.1), so books builds it (`logSettings`) and the kernel validates it exactly as it would a loaded one (level, levels, format, output). F3 deletes it with the config layer. nil keeps `log.DefaultSettings()`. |
| `kernel.Config.Log`, `kernel.Config.StateDir` | What `R1Log` and the state directory become in the kernel. `StateDir` is where `core.log.file.path` resolves in file mode; file mode with no `StateDir` fails boot. R1 only: F3 derives it from the resolved paths. `app.New` fills it from `ResolveStateDir(opts)` when file output is on and no logger was injected. |
| `App.Logging()`, `Kernel.Logging()` | The pipeline, for the composition root: books registers its activity tap on it in `Attach`. nil when the caller injected its own `*slog.Logger` (`Options.Logger`). |
| `kernel.registerLogMetrics` (`core/kernel/logmetrics.go`) | The `mediacore_log_*` bridge (05-logging §9): three observable counters over `Logging.Counters()`, one callback. Series golden `core/kernel/testdata/log/series.golden`. Label values: `level` is slog's name at debug and above, `TRACE` and `TRACE+n` below. |
| `activity.Writer.Feed(p []byte)` | `Write` without the stdout copy. `Write` is `stdout.Write` then `Feed`, so its behaviour is unchanged. The tap feeds through `Feed`: the pipeline's own stream already prints the line, and `Write` would print every record twice. |
| `books.logSettings`, `logStream`, `tapActivity`, `activityLine` (`internal/books/logging.go`) | `logSettings` is ABO's `core.log` for R1: defaults, level from `log_level`, file output at `logs/abo.log` under the state dir when serve passes one, else stdout. `activityLine` renders a record as the line HEAD's `slog.NewTextHandler` over the activity writer wrote, so Activity rows are unchanged. `tapActivity` registers it at info with a 4096-record queue. |
| `books.ServeInputs.StateDir`, `ServeInputs.LogOut` | serve passes the state directory it resolved (`EnsureSecureStateDir`) and, in tests, the stream the pipeline prints to (nil is stdout, where HEAD's lines went). `logTee` and `booksModule.logOut` are gone. |
| `kernel.Config.ProcessLogging func(root *slog.Logger, stdlib slog.Handler) error` | Boot hook, run in P5 right after `BeforeTelemetry` and before any module's Register (never by Describe). `app.New` sets it when `Options.ProcessDefaults` is true, to `installSlogDefault`. It exists because a module's Register captures `slog.Default()` (the operations registry, built in NewServer, does) so the pipeline has to be the default before that, not at `InstallProcessDefaults`. |
| `installSlogDefault` (`core/app/defaults.go`) | The slog half of the process installs: `slog.SetDefault(root)`, the stdlib `log` output and flags, with one restore. `app.New` calls it early through `ProcessLogging`; `InstallProcessDefaults` adopts that install (same pattern as the OTel pair) and calls it itself only when `New` did not. Restored by `New` if boot fails after it. `noglobals_test.go` lists it in its exemption map. |
| `server.NewServerWithLogger(store, log)` | `NewServer` over a logger for the operations registry (and so every op reporter's `Logger()`) and the flight recorder. nil is `slog.Default()` (what `NewServer` passes). books passes its module logger (`Registrar.Deps().Log`), whose records are not `Process`: the registry's per-run info lines (enqueued, dispatched, started, finished, 5 or more per run) reach the journal, `abo.log` and the per-op log store, but are not Activity rows. Neither base nor pre-R1-15 HEAD made them rows (the registry captured the file logger, which wrote to stdout and the file only). The op's own structured rows come from the registry's activity mirror, unchanged. |
| `kernel.Kernel.StdlibLogHandler()` | The one place the stdlib `log` bridge's handler is chosen (the pipeline's non-process `Handler()`, or an adopted logger's). Boot's `ProcessLogging` call and `app.InstallProcessDefaults` both take it from here. |
| `logger.InstallStdoutDefault(level, warnTo)`, `logger.ParseLevelOrInfo(level)` (`internal/logger/stdout_default.go`) | A text handler on stdout at `log_level` as `slog.Default`, with a restore. scan and organize use it for their whole run and print an unknown-level warning to stderr; serve installs it at the top of its run (nil `warnTo`: `books.Options` already reports an unknown level once) so lines before `app.New` (config, store open, migrations, key guard) go to stdout, not slog's stock stderr default (they are in the log file no longer: it opens with the App's pipeline, after them; the changelog says so). `app.InstallProcessDefaults` stacks on it and its restore puts it back. `ParseLevelOrInfo` uses core's parser (so `trace` is a level) and is the one place the unknown-level warning is worded; `books.logSettings` uses it too. The level is the one `initConfig` loaded, before the database overlay, so the earliest serve lines may use a level the database later changes. |
| `log.Logging.ProcessHandler()`, `Handler()` | `Root()` and `ProcessHandler()` mark their records `Process`; `Handler()` does not. `Handler()` is the one adapters take (the stdlib `log` bridge, gin, logr): a line from one must not become an Activity row. |
| `logger.FromSlog(*slog.Logger) *StandardLogger` | The books shim (stage 2). It returns the concrete type, which is assignable to `Logger`: the spec's signature returns `Logger`, but `New` and `NewWithActivityLog` are built on it, and `make lint-deadcode-ratchet` fails on a `FromSlog` nothing in a main reaches. `StandardLogger` is now the same type over slog: `With` builds the dotted subsystem name and the record carries it as the `subsystem` attribute. `New`/`NewWithActivityLog` resolve `slog.Default()` at call time, because loggers are package variables built before the App's pipeline is the default. The derived logger is cached per default pointer. |

## Spec readings

| Reading | Why |
|---|---|
| core's handler moves a logger's scope when `WithAttrs` receives a non-empty string `subsystem` attribute outside a group. | 05-logging §3 levels per `module.subsystem`, and §11 item 4 says the shim passes the subsystem as an attribute so per-subsystem levels work. Without this, `slog.Logger.With("subsystem", x)` is only an attribute and `core.log.levels` cannot reach it. The attribute is consumed (it becomes the record's Subsystem, which the text and JSON output print as `subsystem=`). `TestWithAttrs_SubsystemMovesTheScope`. |
| Legacy per-subsystem level keys are `core.<subsystem>`. | `slog.Default()` is core's root logger (module `core`), so a books subsystem scopes under `core`. A module-owned logger would use its module ID. |
| The tap renders `"<Subsystem>: msg"` and omits the module. | HEAD's shim baked the prefix into the message, and `internal/activity`'s parser derives the summary and tags from it. Module is not a structural key of the line parser; it would land in every row's summary. |
| `log.Record.Process`: the activity tap feeds only records from the process default logger (`Root`, `ProcessHandler` and loggers derived from them; not `Handler()` and so not the stdlib bridge). | R1-15's review found core's own lines (`kernel: listening`, `metrics: ...`) becoming Activity rows once the App's logger is the default. HEAD's feed saw only what went through `slog.Default`, so core's own loggers (`Scope("core", ...)`) and a module's (`Module(id)`) make no row, and the activity line never carries `module=`. `TestRecord_ProcessMarksTheProcessDefault` (core), `TestActivityTap_CoreOwnRecordsMakeNoEntries` and `TestActivityTap_EntriesMatchHEADAndCarryNoModule` (books). Re-check after R1-15's own fix (a default logger with no module attr) lands: if the default stops being `Root`, the flag must follow it. |
| Third-party libraries' `log.Print` lines no longer make Activity rows. | The stdlib bridge writes through `Handler()`, which is not `Process` (m3). HEAD's `log.SetOutput` pointed the standard logger at the activity writer, so a library's `log.Print` became a system row; now it reaches the journal and file only. This is a deliberate parity change: a library line is not a system event, and one in a hot path would flood the page. `TestNoSecondDefaultLogger` pins that the line still reaches the pipeline. |
| The tap floor is info. | HEAD's second default logger was `slog.LevelInfo`. |

## Deviations from the brief

| Deviation | Reason |
|---|---|
| The metrics bridge is registered in `kernel.services`, not `app.New`. | The Provider and the pipeline both exist there; `app.New` would need the kernel to expose both. |
| `FromSlog` returns `*StandardLogger`, not `Logger`. | The deadcode ratchet; see the names table. |
| `core/log/handler.go` changed (the subsystem re-scope above). | Needed for per-subsystem levels; the brief says "nothing in core/log" for the shim. |
| An unknown `log_level` falls back to info with a warning on stderr; it does not fail boot. | A stored typo must not stop serve before core's config validation exists. |
| A log file that cannot be opened fails boot (spec §6). HEAD warned and continued. | The spec's rule; the changelog fragment says so. |
| `scan` and `organize` lose their debug-level file logger; they log text to standard output at `log_level` (info unless set) through `logger.InstallStdoutDefault`. | `setupFileLogging` is deleted for all three commands (§11 item 1). They never had an App, so they get a plain text handler on stdout, where their other output goes, instead of slog's stock default (stderr). `TestScanAndOrganizeLogToStdoutAtLogLevel`. |
| The old cwd-relative `logs/audiobook-organizer-<date>.log` is not reproduced. | The file is under the state dir now, rotated by core. |
| `Counters` has no journal families, so the bridge exports three families. | That is what the pipeline counts today. |

## Follow-ups from R1-15 done here

- `logger.Sanitizing` and its handler are deleted; the flight recorder logs through the module logger books passes to `NewServerWithLogger`. `Sanitizing` did control-character escaping only (a CR or LF in a path forging a log line); it never redacted secrets. Both guarantees now come from the pipeline, and only because it is the process default before any module's Register (`kernel.Config.ProcessLogging`): the output handler (slog's text or JSON handler) quotes the message and values, and `core/log`'s `Redactor` runs in the pipeline's `Handle` on the message and every attribute. A logger that bypasses the pipeline has neither. `TestOpLogger_CapturedDuringRegisterKeepsLevelAndOpID` pins the Register-time capture.
- The `InfoCtx`/`WarnCtx`/`ErrorCtx`/`DebugCtx` helpers no longer append `corelog.AttrsFrom(ctx)`; the pipeline does, after the record's own attributes. The helpers keep the sanitizing barrier for the message and the call's own values. `TestCtxHelpers_AppendAttrsFrom` runs over a real pipeline and counts each attribute once.
