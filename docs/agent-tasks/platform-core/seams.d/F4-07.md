## Readings taken

- **The oracle is in `internal/books/cutover`, not `internal/books`.** The brief names `internal/books/reach_oracle_test.go`. The M3 rig (`newIDRig`, `idAtoms`, `idSnap`) is a test fixture of package `cutover`; a test in `internal/books` cannot reach it. The command line of the brief is `go test ./internal/books/cutover -run TestIdentityCutover_ReachOracle`.
- **The R0 side is recorded on a GitHub-hosted ubuntu runner with the pinned `Linux_x86_64` v0.223.0 asset.** The Darwin arm64 asset is not used. A temporary push-triggered workflow did the recording and is deleted in this PR; `scripts/r2corpus/record_r0_reach.py` is the reproducible entry point, and `--check` reruns it. The committed data is GitHub Actions run 43685703236, attempt 1, at recorder commit f04f53afc (a throwaway branch commit that carries this PR's `scripts/r2corpus/record_r0_reach.py` and its test as of 5d849d318 and a workflow file; the branch is deleted). The evidence that the recording is stable is three recordings of the same store and binary agreeing cell for cell: the first recording (run 43412869288, recorder commit b4e945a3, the one the oracle was first written against), run 43672477887 (attempt 2, the config-digest recorder) and run 43685703236 (the committed one). Compared with the first: 0 of 572 routes differ in letters over 37 principals, and the task starts, approvals, canary, uniform-404 set and overlay digest are identical. Only recorded statuses differ, on the routes whose authorized probe answered a different 5xx or 4xx: the two config PUTs (200 then, 400 now: the probe body is now one the handler refuses, see Probes) and `POST /api/v1/update/apply` and `POST /api/v1/audiobooks/bulk-write-back` (a listed `OK_5XX` that depends on timing). The earlier comparison in the F4-07 review (run 43401808073, 565 of 572 agreeing, the 7 that differ being routes whose flags were turned on after it) is superseded. `verdicts.json` also holds `overlay_sha256`, the digest of the overlay store it copied. The re-run procedure (a Linux host, or the workflow template `r0config/r0reach-record.workflow.yml.txt` on a throwaway branch) is in the recorder's docstring.
- **The route dump is generated from the v0.223.0 tag's source** (`dump_r0_routes.py`), not from a running binary. 572 routes, the number 05-rbac names.
- **`ENABLE_AUTH` and `ENABLE_RATE_LIMIT` do not reach a store that has a `config_blob`.** R0 reads the stored config after the environment. The recorder therefore spreads its probes over loopback source addresses (one per request, so the limiter stays on as shipped) and edits the stored keys (`edit_config`): `enable_auth=true>false` for the auth-off boot only, and two flags for both boots.
- **Two flags are turned on in both boots.** `fingerprint_remote_workers_enabled` (R0's `flagGuard` answers 404 ahead of authentication on `/api/v1/fingerprint/worker/*` while it is off, so no principal's reach there was observable) and `deluge_discovery_enabled` (the two discover handlers answer 403 from inside the handler while it is off, which a probe reads as a denial for everyone, the admin's session included).
- **A probe is a request that fails after authorization when authorized.** A 401 or 403 is a denial and any other status below 500 is an allow. A 429, a 5xx and a connection error are recorder failures, never verdicts, except the routes listed in `OK_5XX` with R0's own message (the handler's outbound call fails after the authorization decision). A listed route must also show a denial for some principal, so a 5xx cannot hide a decision that never ran. `POST /audiobooks/bulk-write-back` is timing-dependent (202 or 500 by whether an earlier probe's run holds the op's concurrency key) and is listed for that reason. Since round 5 the recorder also names the cause of every 5xx it lets through: `OK_5XX_REASONS` gives each listed route a closed-vocabulary reason token (for example `deluge-unreachable`, `no-fingerprint-backend`, `recovered-panic`), the response body must carry the route's message (or be empty for `enqueue-failed`), and `verdicts.json` (`DATA_VERSION` 1.2.0) records a per-route `reason` list, one entry per principal, `""` for every cell that is not 5xx; the body is never recorded. `TestReachBaseline_EveryServerErrorCellCarriesItsListedReason` holds the committed recording to a Go-side copy of the same table (`reachServerErrorReasons`), so a 5xx whose cause changed, or a refusal that now looks like a failure, fails by name. In the recording that regenerated it (GitHub Actions run 43703785630) 21 of the 23 listed routes answered 5xx to at least one principal; the other two (`POST /audiobooks/bulk-write-back`, which is timing-dependent, and `POST /update/check`) were answered below 500 and carry no reason.
- **Census.** Users, books and task definitions are counted before and after the pass, and a canary request per principal follows; a changed census or a dead server fails the run. The census counts the corpus's seven books through `GET /api/v1/audiobooks/count`; R0 wraps bodies in `{"data":...}`, so the first version of the census read no count at all and the run did not fail (fixed, with a test that a non-integer count fails the run).
- **Probes do start work on the throwaway copy.** The recorder's task starts send an empty parameter list that fails validation after authorization, so no task start begins a run, and the one awaiting run (`repairs.plan`) is created once and approved by none. The route probes are another matter: about 20 of them answer 202 and start a background operation on the throwaway copy (`dedup/scan`, `maintenance-window/run`, `openlibrary/download` and others), and `PUT /api/v1/config` and `PUT /api/v1/maintenance-window/config` are written with an empty body. The census checks users, books and task definitions; it does not cover operations or the stored config. The census does hold a digest of `GET /api/v1/config` (`config_sha256`), restored in round 3: a first version of it failed the first real run (GitHub Actions run 43636904080, "the store drifted while probing (config)") because the two config PUTs were probed with an empty body and R0 wrote the config back. The probe body of both is now a single unknown key, which `UpdateConfig` refuses with a 400 before it writes, and two real runs (43672477887 and 43685703236) passed with the digest, so the config is unchanged by the pass. The 400 is the probe's answer for every authorized principal, the same letter as the old 200.
- **The test-local evaluator replica (SEC-26).** Core's `authz` is importable only by `auth`, the executor and the kernel (`archtest.NoSystemPrincipalOutsideKernel`), and nothing outside core builds an `rbac.Service` before F4-08 wires one. `reach_eval_test.go` is a test-local copy of `Compile`, `AuthDisabled`, `Has` and `Satisfies`, written from `core/internal/authz/authz.go` (the replica is checked against it by reading, not by import). A fault in the copy shows as a cell that differs from R0 and is on no row, so it cannot hide; what the copy cannot show is a fault core and the copy share. F4-08 replaces it with the registered path.
- **The seed roles and catalog are written in `reach_spec_test.go`.** Books declares no catalog and no `DefaultGrants`, so the spec's tables (05-rbac 4.8 for the roles, 6.1 for the scopes, their implications and flags) are the source. The rig's `idSeedRoles` and `idCatalog` (F4-06) differ from the spec: the editor lacks `books:delete` and `books:request.approve` and holds `books:collections.manage`, and `books:admin.debug` lacks `AuthRequired` and `Sensitive`. `TestReachSpec_*` pin the oracle's copy to the spec. F4-06's rig is not changed here.
- **`Guards.Owner`.** Core ships no `OwnerVerifier`, so by 05-authn 4.8 an owner-guarded route falls back to `Interactive` plus `core:admin`. The replica models exactly that (`TestReachGate_OwnerGuardFallsBackToInteractiveAdmin`).
- **Task starts and approvals.** A start is `scan.trigger`'s route floor then each of the definition's own permissions resolved through the atom table, as R0's handler does; an approval is the route's `library.view`, the definition's approver permission, and a verified method (the auth-disabled principal has no user). The recorder does not start tasks as the auth-disabled principal, so those cells have 36 letters, not 37. An approval's R0 letter is A once it reaches the approver check (R0 answers 400 to the probe's invalid decision); N means the run was not readable by the caller and carries no reach information.
- **The random native roles half (05-http-api 8.1) is not recordable.** R0 has no role CRUD route, so no R0 baseline exists for a random native role; the half belongs to a core test over core's own routes. It is an obligation on F4-08 below and a `todo.d` fragment, so it is not lost.
- **ABS-delegated routes (`OwnAuth`) are excluded and counted.** Their authorization is the ABS handler's own token check, outside the router's decision.
- **In-handler checks behind 404 lookups.** A probe with a dummy path id that a handler turns into a 404 before its own permission check cannot show that check. The recorder's `uniform_not_found` list names every route whose 404 was identical for all principals; none of them is a decision.
- **Rows are asserted on both letters** and fail if they match nothing (`TestReachClassify_*`). Two kinds are kept apart: `reachExpected` (clauses of 05-rbac) and `reachRecorderLimits` (a refusal that is the handler's answer to the probe, not the router's reach).
- **Pinned one-sided routes.** R0 only: `GET /` (the SPA handler, outside the manifest) and the two HEAD reset routes (`POST /system/factory-reset`, `POST /system/reset`, deleted at F4, 05-rbac 6.2). R2 only: `POST /admin/guest-service-tokens/:userId/reissue`, newer than the R0 tag (no baseline). `TestReachOracle_RoutesOnOneSideAreExactlyThesePinned` fails on any other.
- **`playlists.create` is unenforced.** Books' table gives it a zero route requirement, so no route reads it; `TestAtomTable_Golden` and `TestIdentityFixture_MatchesTheAtomGolden` pin the row. `requests.create` and `requests.approve` are likewise named by no manifest route.

## Ruled

The oracle reported three differences between R0 and R2 that were on no expected row of 05-rbac section 12 (STOP 2). The spec's owner ruled on each on 2026-11-13: the oracle was right on all three, and none is an R2 security bug. The spec and the oracle were changed together, so the oracle is green with 217 differing cells, all claimed by a row, and no row unused.

**F-1. An `fp-worker` user's keys scoped outside the worker scope lose every authenticated-only route (96 cells: 3 principals on 32 routes). Ruled: listed, spec amended.** `key:fp-worker:view`, `key:fp-worker:settings` and `key:fp-worker:users` reach the `AnyAuthenticated` routes at R0 because `workerOnly` reads an empty effective set as not worker-only (`internal/server/middleware/auth.go:271-274` @v0.223.0), although the guard confines a user holding only the fp-worker role. After M3 the key's checker is empty (the `fp-worker` role holds no ambient scope) and it reaches no route; R2 closes that gap on purpose. 05-rbac 6.3 (keys and ambient bullets), 6.1 (`playlists.create` notes), 12 (the oracle row and `TestWorkerKey_Confined`) and 09 9.2.6 (recorded changes) now say so. The expected row is "05-rbac 6.3" over `reachAuthenticatedRoutes()` (the manifest's `KindAuthenticated` routes). The playlist-writes test now covers viewer sessions and keys whose compiled checker holds a non-`Confining` scope, so it requires a non-empty set.

**F-2. A role holding every atom, and an admin-owned `["settings.manage"]` key (`key:admin:settings`), gained `GET /cache/stats/keys` (4 cells: `session:custom-all`, `key:admin:settings`, `key:custom-all:every`, `key:custom-all:empty`). Ruled: a fix, in this PR.** The route needs `books:admin.view` (`internal/server/legacy_manifest.go`, was `core:system.view`), which matches R0's `adminRole` reach exactly. 05-rbac 6.2 and 6.1 are corrected (`core:system.view` is status detail and sysinfo; `books:admin.view` is the debug reads and ABO's cache key listing), and the "reviewed gain" row is gone from 12 and from `reachExpected`.

**F-3. An admin's every-atom or empty-list key loses the three debug edit routes (6 cells). ## Obligations on F4-08

**How an obligation is cleared (round 5).** Six obligations block the flip to `LegacyAuthCore`: `reachObligations` in `internal/books/cutover/reach_flip_obligations_test.go` has one row for each, with the discharge test's name and directory and a bar. Nobody keeps a list of the open ones: a row is open until a test with its name exists in its directory (found with go/ast: no receiver, a `*testing.T`, it asserts and never skips) and the coverage that test declares meets the bar the guard computes from the recording, the diff and the route table (never from a hand-edited list and never from a function's name). A test in the cutover package declares its coverage by registering a `Covers` function in `reachDischarges` (an `init` in its own file); a test in another directory declares it by the string literals of its file (the bar's items must occur in it). The ABS replay is exact; the others must contain the bar. `reachFlipProblems` fails at the flip once per open row. The rows and their test names are held to this section in both directions: a row without a statement here fails, and a statement here without a row fails, so a row is not dropped without this text changing too. **What this does not prove:** declared coverage is a claim and nothing here runs the test, so a test can declare the whole bar and assert nothing about it; review of the change that registers a discharge stays the barrier. What it removes are the cheap closes the round-4 review ran: renaming the row function that held the evidence (C1: the bar now reads the diff, so the cells stay while the name changes), swapping the owner predicate at one of two call sites (C2: the owner-set comparison and the owner bar read one function, `reachOwnerAssured`), and evidence that no discharge could ever change.

- **The core-route half.** This oracle compares books' manifest routes. The brief's second half, "plus every core route of F4-05", and spec step 5 (the auth-disabled principal against **every core route**, 09 section 9.2.6) need core's registered router; they are not here. The expected-difference clauses that live on core routes (§4.11 (b), (c) and (d) for core's own credential-metadata and backup routes, §6.2's tightened `settings.manage` system routes, the `core:system.status` readiness reach of `editor` and `viewer`, dominance and `CanAssign` on `core:users.manage`, the deleted reset routes' successor) are asserted when that half exists; a row with no cell to match fails, so none can be written early.
- **Reconcile the route count.** R0's router dump has 572 routes; the books manifest has 495 and core's routes 574 in the F4-05 count. The books half compared 505 R0 routes (572 recorded, less 3 only R0 has and 64 delegated; the count is derived by the oracle, `res.routesCompared`, and pinned), and counted and left out 68 delegated manifest routes: 64 of R0's plus 4 newer than R0. The first version of this note said 501, which subtracted all 68 from R0's 572 although 4 of them are not R0 routes.
- **Discharge the 11 pinned cells (`reachHandlerAdmin`).** The pin hides `footprint` and `merges` for `session:custom-all`, `key:admin:users`, `key:custom-all:every`, `key:custom-all:empty` and `authoff` (10 cells) and `PUT /users/:id/email` for `session:custom-all` (1 cell). The F4-08 brief names only the core half of `TestUserMerge_ScopedAdminKeyRefused`, which covers the merge handler and the scoped-admin-key column. F4-08, or the handler migration (04) before it, must add tests that run the migrated handlers on the registered path and refuse each of the 11 cells: the core half of `TestUserMerge_ScopedAdminKeyRefused`; a `SetUserEmail` equivalent (a role holding every atom without `core:admin` is refused, an admin is not); and columns for a custom role holding every atom and for the auth-disabled principal on `footprint`, `merges` and `email`. When those pass, F4-08 deletes `reachHandlerAdmin`, `reachHandlerAdminFuncs`, `reach_pin_test.go` and `reach_pin_source_test.go`'s handler half; until then `TestReachHandlerAdminPin_GoesWhenTheHandlersMigrate` fails the day the role-name checks leave the named handler functions, and `TestReachFlip_FailsWhileThePinOrTheOwnerlessModelStands` fails the day `module.go` mounts with `LegacyAuthCore` before the pin is gone.
- **The custom-role half over random native roles (`F4-07-RANDOM-ROLES`, 05-http-api 8.1, SEC4-2).** For random native roles, stage 13 admits a legacy route only if the route's successor admits it. R0 cannot record it (no role CRUD), so it is a test over core's own routes on the registered path, written by F4-08 in `core/httpapi` (the directory of the stage-13 decision, `legacy.go`) as `TestLegacyStage13_RandomRolesAdmitOnlyWhatTheSuccessorAdmits`, and it blocks the flip: stage 13 is the decision the books mount hands to core, and a custom native role created after the cutover that reaches a route its successor does not admit is exactly what the books oracle cannot see. The bar is every legacy atom the manifest's routes require (`reachBarRandomRoles`), each of which the test file must name as a string literal (the mapping from the legacy atom to its successor is where a role gains or loses a route). ## What the manifest mutation check proves (round-2 NIT-1)

`reachRouteMutants` changes each manifest route four ways (widened, narrowed to `core:admin`, AllOf to AnyOf, a guard dropped) and requires the oracle to fail on every mutant that is not equivalent. From a run (round 5, the same counts as round 4): 979 mutants generated, 952 killed, 27 equivalent and 0 escape. The 952 are 949 whose R2 reach moves and fail the oracle, plus 3 whose reach does not move and which `reachChecks` fails all the same: the Owner guard dropped on the three guest-token routes, whose requirement (`core:admin`) gives the admin session the letter the no-owner fallback gave it, but which the recorded owner-set refusal (`owner_set`, read through R2) does not. Those 3 are killed by the owner-set comparison alone; an earlier version of this note and of the changelog called them equivalent "under the no-owner model", which was wrong once the owner model reads R2. A route whose requirement already is `core:admin` is not narrowed to it (that is no mutant), which is why the denominator is 979 and not 986. The 27 equivalent mutants (by kind: 8 Interactive guard dropped, 8 narrowed to `core:admin`, 11 widened to AnyAuthenticated; none an Owner guard dropped) are routes an Owner guard or the handler-admin pin dominates, or whose requirement no principal of the table tells from its replacement: the principal table holds no owner-assured principal, so the no-owner fallback and the owner-set model refuse everyone the route's own requirement would. They are equivalent because of the table, not because the requirement does not matter: a principal that is the Access-verified owner would distinguish them, and that allow side is the unrecorded `F4-07-OWNER-ALLOW` obligation. 19 of the 27 are also failed by the masked-route pin, which the mutation loop does not run. The owner-set recording (committed, with the boot's canaries and each route's admin refusal) and the flip guard (which fails if `verdicts.json` ever loses it) hold the owner side open.
