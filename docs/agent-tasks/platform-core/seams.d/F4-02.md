# F4-02 seams and coined names

What the core auth PRs added beyond 05-authn v1 §3 to §11 and 05-rbac §4.6, §4.7 and §9, the readings they took where the brief or the spec says nothing, and what F4-02b, F4-05, F4-08 and F4-11 must know. F4-02 lands in two PRs: **F4-02a** (store, password, throttle, ceilings, keys, sessions, `PrincipalFor`, stage-12 middleware, `Login`, the user methods) and **F4-02b** (bootstrap and setup, invites, temp-login and reset links, `PostRestore`/`BootWrites`, `Compat`, auth-off, the metrics golden). This file covers F4-02a; F4-02b appends its own section. Everything not listed here is the spec as written. Both PRs are dark: nothing in ABO or the kernel calls `auth.Service`.

## Deviations from the brief

1. **The invite limiter is renamed, not moved.** `internal/server/invite_rate_limit.go` becomes `internal/server/invite_gate.go` with its test, rename plus doc comment only. Its `IPRateLimiter` layers are perimeter code keyed on the request, and core admits invite attempts through the one `Throttle` instance (§4.9), so nothing of it belongs in `core/auth`. F4-08 deletes it with the legacy invite routes.
2. **Three ABO gate files hold the request keying of what moved.** `login_gate.go` (was `login_ceiling.go`'s gin half), `bootstrap_gate.go` (was `bootstrap_rate_limit.go`'s keying) and `invite_gate.go` are gin residue that call `coreauth.LoginCeiling`, `coreauth.BootstrapLimiter` and the throttle. They exist until F4-08's identity flip removes the legacy routes.
3. **`internal/config/invite_config.go` is renamed `env_only_settings.go`** and also holds `ResolveBootstrapKeyTTL`; `bootstrap_key_ttl.go` is deleted. The saturated-login bounds are `coreauth.Min/Max/DefaultSaturated*`.
4. **`lru.go` left `absauth`.** The login tables moved to core with their own unexported copy (`core/auth/throttle.go`), which left the CSP reporter the table's only user, and four methods unreachable (deadcode ratchet). It is now `internal/server/csp_lru.go`, unexported, without the pinned tier the CSP table never used.
5. **`TestNoDirectBcrypt` runs from `core/auth/password/password_archtest_test.go` (package `password_test`)**: in package it closed the cycle password → archtest → httpapi → auth → password (F4-01 item 5's rule).

## Coined names

| Name | What it is |
|---|---|
| `Store` = `UserStore` + `SessionStore` + `APIKeyStore` + `OneTimeStore` + `IdentityStore` + `StageMerge` | The spec's 25-method `Store`, split so no interface declares more than eight entries (interface-width). The method set is the spec's plus `DeleteUser`, `GuardUser`, `ScanIdentities`, `ScanOneTime`, `DeleteOneTime`. |
| `UserStore.GuardUser(b, u)` | Stages an Expect that `u` is stored at `u.Version`. The last-admin rule guards the other holder with it. |
| `Deps.NewBatch`, `Deps.Settings func() Settings`, `Deps.Extensions`, `Deps.Client`, `Deps.Hasher` | The service stages on the identity store's own batch, reads settings through a function (auth never imports config), receives `app.Options.Authenticators`, reads httpapi's resolved client (auth L4 cannot import httpapi L6), and takes a hasher (nil builds the production one). |
| `Settings{SessionTTL, RememberTTL, KeyDefaultTTL, KeyMaxTTL, SessionCookie, NoHostPrefix, MinPasswordLength, Login ThrottleLimits, SaturatedRate, SaturatedBurst}` | The `core.auth.*` values of §8. Zero takes the default. `Login` is reloadable (`Throttle.SetLimits` on every sign-in); the saturated pair is read once by `New`, which refuses values outside `SaturatedLimitsValid` (`ErrBadInput`), as HEAD refuses to start. `SessionCookie` defaults to `mediacore_session`; the kernel passes `<AppID>_session`. |
| `ClientInfo{Addr, Peer, UserAgent, Forwarded, TrustedProxy, HTTPS, OnLink}`, `Local()` | `HTTPS` follows the perimeter's trust rule (TLS, or `X-Forwarded-Proto: https` from a configured trusted proxy), never any peer's header. `OnLink` marks a global IPv6 inside an on-link prefix of this host: a throttle source of its own, not one member of its /64. Only httpapi's resolver can know it; the default client leaves it false. |
| `(*Service).SessionCookie(c ClientInfo, token string, expires time.Time) *http.Cookie` | The session cookie for this request: its name follows `c.HTTPS` (§4.3's Secure rule and `NoHostPrefix`), HttpOnly, SameSite Strict; an empty token clears it. |
| `ThrottledError{RetryAfter}` | Every throttle or ceiling refusal from `Login`; `errors.Is(err, ErrThrottled)` holds. `RetryAfter` is the route's Retry-After, at least 1. `LoginRetryAfter` (60) when no ceiling computed one. |
| `Throttle`, `ThrottleLimits`, `NewThrottle`, `SetLimits`, `SaturationPolicy`, `SetSleep`, `SetClock` | HEAD's `absauth.Throttle` as instance state. `SaturationPolicy` is a method now and reads the configured soft threshold. `SetSleep`/`SetClock` are test seams. |
| `LoginCeiling`, `LoginAdmission`, `CeilingDecision`, `Admit`/`Done`, `SetSaturatedBound`, `SaturatedLimitsValid`, the `Login*`/`MaxSaturated*` constants | HEAD's `loginCeiling` as instance state. `Admit` returns an admission whose `Done(outcome, account)` releases the slot on every return, a panic included. No Cloudflare Access exemption in core: that is an ABO extension concern. |
| `BootstrapLimiter`, `BootstrapLimits`, `LimiterAggregate`, `NewBootstrapLimiter`, the `Bootstrap*` constants | HEAD's bootstrap attempt limiter as instance state. ABO's `bootstrap_gate.go` keeps the request keying. |
| `password.Hasher`, `password.New(Options{Permits, Time, MemoryKiB, Compute})`, `HashWithin`, `VerifyWithin`, `VerifyLoginWithin`, `SpendVerification`, `HasCredential`, `AlgoOf`, `Derivations`, `ErrBusy`, `ErrEmpty` | HEAD's absauth password functions on one instance. Permits default to GOMAXPROCS. The dummy hash is built in `New` (HEAD built it lazily, which could deadlock under a full semaphore). `Time`, `MemoryKiB` and `Compute` panic outside a test binary, and `archtest.NoLoweredHashCost` refuses them in non-test files. |
| `MintCredential`, `ParseCredential`, `HashCredential`, `HashHex`, `CredentialKind` | §4.1's formats: a prefix, 32 random bytes in base64url and a base62 CRC32, 54 characters. A value without the kind's prefix is `ErrNoCredential` (the next authenticator may try); one with the prefix and a bad length, alphabet or checksum is `ErrInvalidCredentials` and never falls through. |
| `NormalizeEmail`, `SameEmail`, `FoldUsername` | Moved from `internal/util`; `FoldUsername` is `strings.ToLower`. |
| `ErrDenied`, `ErrKeyRevoked`, `ErrBadInput`, `ErrBusy`, `ErrUserExists`, `ErrNotFound`, `ErrSetupClosed`, `ErrInviteInvalid` | Refusals §3.2's methods need that §3.3's block does not name. F4-05 maps them to §6's responses (`ErrKeyRevoked` is 409 `key_revoked`, `ErrBusy` 503 `busy`). |
| `DefaultBootstrapKeyTTL` (8h), `MaxBootstrapKeyTTL` (24h), `DefaultMinPasswordLength` (8) | Moved from ABO config; HEAD's values. |

## Readings where the spec is silent

- **Login order is HEAD's**: the ceilings admit first; then validation, the source block, the saturated policy, the user read (a store failure charges nothing), one derivation for every outcome, failures charged and delayed, and only then status and reset/restriction (not charged). A bcrypt hash is re-stored as argon2id after the session is issued, best effort, without an epoch bump.
- **Login audit** (05-rbac §8): success `core.auth.login` in the session's batch; refusals on the async path with reasons `throttled`, `invalid_credentials`, `inactive`, `reset_required`, `busy`. The target is the account only when the submitted name resolved to one. The submitted name is never recorded, since a password typed into the name field would land in the log. A malformed request and a store failure record nothing. Login emits no metrics in F4-02a; the counters and the golden are F4-02b's.
- **Account writes** need `core:users.manage` through an interactive method, and dominance over the target's current roles, the actor's own account included (a session always dominates itself). A dominance refusal is returned as `ErrDominance` and not audited here: §8's `core.permission.deny` for a 403 `dominance_required` is recorded where the 403 is written (F4-05).
- **`SetRoles`** calls `CanAssign` once over added ∪ removed. Every removed role is a current role, so dominance already covers it; the call names it as rule 2 does.
- **Last admin**: a holder is a user with status `active` and a role whose permissions `rbac.GrantsAdmin` (an unknown role grants nothing; an undecodable user holds nothing; `SignInRestricted` does not matter). When a write would end the target's holding, the first other holder found is guarded in the same batch. One guard is enough: of the writes that would together leave no holder, the one committing last guarded a holder another of them changed after it read it. `TestLastAdmin_ConcurrentDemotions` fails with the guard removed.
- **Known gap, not closed here**: the role definitions are read, not guarded. `rbac.Store` is frozen SDK and has no way to stage an Expect on a role record into auth's batch, so an rbac edit that takes `core:admin` from the other holder's role and commits between auth's read and auth's commit is not seen. rbac's rule reads holders through its batch, so the reverse order is caught there. Closing it needs an optional role-guard interface on the role store (F4-01's `ImportSealer` pattern) and an `rbac.Service` method auth calls inside its batch: about 100 lines across `rbac`, `rbacstore` and tests. Also open: nothing implements `rbac.Deps.Holders` yet, so until F4-08 wires it every rbac write that takes `core:admin` from a role is refused.
- **E-mail uniqueness** is HEAD's rule: an address another account holds **verified** refuses a creation (`ErrUserExists`); an unverified holder does not. The store indexes usernames only (§3.4's table), so the check and the commit run under a service mutex (`emailMu`, HEAD's `inviteMu`). F4-02b's invite accept and any later e-mail setter must take it too.
- **Password length** is counted in bytes, HEAD's rule, so pre-cutover accounts meet the same bound.
- **`ChangeOwnPassword`** refuses an API key, verifies the current password within the 2 s hashing wait without charging the throttle (HEAD), refuses an account without a password (`ErrInvalidCredentials`), and lands only if the epoch is still the verified one (`ErrStaleEpoch`; a rehash keeps the epoch and does not refuse it). It does not clear `PasswordResetRequired` or `SignInRestricted`. Audited `core.user.reset_password` with `self: true`, since §8 names no self-change action.
- **`SetStatus`** sets only `active` and `disabled`, refuses `_system` and a pending invitee, and writes nothing for the current status. Enable journals only `credential_epoch.bumped` (there is no `user.enabled` kind). API keys are refused while the owner is disabled and work again after.
- **`DeleteUser`** deletes the user's sessions, keys, identities and every invite or temp-login it is the target or creator of, in one batch, and journals one `user.deleted`. F4-02b's `PostRestore` must cascade the same records when it re-applies that line. A record the store cannot decode is left (logged); auth refuses it anyway.
- **Invalidation events** (`core.principal.invalidated.v1`, §4.12) are not published: `Deps.Events` is not wired in F4-02a.
- **Audit action names** follow 05-rbac §8: `core.user.{create,disable,enable,delete,reset_password,set_roles}`, `core.apikey.set_status` (was `core.apikey.status` before this PR), and `core.apikey.revoke` for a change to `revoked`. `core.auth.authenticate` (a stage-12 refusal) is not in §8's table and is coined.

## F4-08 must know

Build one `auth.Service` per process and hand stage 12 its middleware. Wire `Deps.Client` to httpapi's resolver (`HTTPS`, `OnLink`), `Deps.Settings` to the config snapshot, and implement `rbac.Holders` over the identity store, reading each user it reports through the batch (F4-01's seam). The ABO gate files above go with the legacy routes.
