# F4-02 seams and coined names

What the core auth PRs added beyond 05-authn v1 §3 to §11 and 05-rbac §4.6, §4.7 and §9, the readings they took where the brief or the spec says nothing, and what F4-02b, F4-05, F4-08 and F4-11 must know. F4-02 lands in two PRs: **F4-02a** (store, password, throttle, ceilings, keys, sessions, `PrincipalFor`, stage-12 middleware, `Login`, the user methods) and **F4-02b** (bootstrap and setup, invites, temp-login and reset links, `PostRestore`/`BootWrites`, `Compat`, auth-off, the metrics golden). The first sections cover F4-02a; the F4-02b section at the end is the second half. Everything not listed here is the spec as written. Both PRs are dark: nothing in ABO or the kernel calls `auth.Service`.

## Deviations from the brief

1. **The invite limiter is renamed, not moved.** `internal/server/invite_rate_limit.go` becomes `internal/server/invite_gate.go` with its test, rename plus doc comment only. Its `IPRateLimiter` layers are perimeter code keyed on the request, and core admits invite attempts through the one `Throttle` instance (§4.9), so nothing of it belongs in `core/auth`. F4-08 deletes it with the legacy invite routes.
2. **Three ABO gate files hold the request keying of what moved.** `login_gate.go` (was `login_ceiling.go`'s gin half), `bootstrap_gate.go` (was `bootstrap_rate_limit.go`'s keying) and `invite_gate.go` are gin residue that call `coreauth.LoginCeiling`, `coreauth.BootstrapLimiter` and the throttle. They exist until F4-08's identity flip removes the legacy routes.
3. **`internal/config/invite_config.go` is renamed `env_only_settings.go`** and also holds `ResolveBootstrapKeyTTL`; `bootstrap_key_ttl.go` is deleted. The saturated-login bounds are `coreauth.Min/Max/DefaultSaturated*`.
4. **`lru.go` left `absauth`.** The login tables moved to core with their own unexported copy (`core/auth/throttle.go`), which left the CSP reporter the table's only user, and four methods unreachable (deadcode ratchet). It is now `internal/server/csp_lru.go`, unexported, without the pinned tier the CSP table never used.
5. **`TestNoDirectBcrypt` runs from `core/auth/password/password_archtest_test.go` (package `password_test`)**: in package it closed the cycle password → archtest → httpapi → auth → password (F4-01 item 5's rule).
6. **`IssueKey`, not §3.2's `IssueAPIKey`, and the key prefix is `KindKey`; bearer tokens are `auth.Token`.** CodeQL's `go/weak-sensitive-data-hashing` (HIGH) flagged the SHA-256 of a minted key as password hashing. It is a false positive: the query's password-name heuristic matches `api.?(key|tok)`, so any identifier containing `APIKey` that flows into `sha256.Sum256` reads as a password, while the input is a prefix and 32 `crypto/rand` bytes and §4.1 mandates SHA-256 (a slow hash buys nothing over 256 bits of entropy and would cost every request). The rename (the earlier F4-02a heads called them `IssueAPIKey` and `KindAPIKey`) keeps the key-path identifiers consistent with `IssueSession`, `IssueOneTime` and the other `Kind*` prefixes; `Token` makes the hashed value a type of its own: `MintCredential` returns one, `HashCredential` and `HashHex` take only one, and the store's `Issue*`, `*ByToken`, `TakeOneTime` and `LookupOneTime` methods speak it, so a password string cannot reach the SHA-256 without an explicit conversion. Behaviour is unchanged. 05-authn §3.2 still names `IssueAPIKey`; amend it when the spec next moves.

## Readings where the spec is silent

- **Login order is HEAD's**: the ceilings admit first; then validation, the source block, the saturated policy, the user read (a store failure charges nothing), one derivation for every outcome, failures charged and delayed, and only then status and reset/restriction (not charged). A bcrypt hash is re-stored as argon2id after the session is issued, best effort, without an epoch bump.
- **Login audit** (05-rbac §8): success `core.auth.login` in the session's batch; refusals on the async path with reasons `throttled`, `invalid_credentials`, `inactive`, `reset_required`, `busy`. The target is the account only when the submitted name resolved to one. The submitted name is never recorded, since a password typed into the name field would land in the log. A malformed request and a store failure record nothing. Login emits no metrics in F4-02a; the counters and the golden are F4-02b's.
- **Account writes** need `core:users.manage` through an interactive method, and dominance over the target's current roles, the actor's own account included (a session always dominates itself). A dominance refusal is returned as `ErrDominance` and not audited here: §8's `core.permission.deny` for a 403 `dominance_required` is recorded where the 403 is written (F4-05).
- **`SetRoles`** calls `CanAssign` once over added ∪ removed. Every removed role is a current role, so dominance already covers it; the call names it as rule 2 does.
- **Last admin**: a holder is a user with status `active` and a role whose permissions `rbac.GrantsAdmin` (an unknown role grants nothing; an undecodable user holds nothing; `SignInRestricted` does not matter). When a write would end the target's holding, the first other holder found is guarded in the same batch. One guard is enough: of the writes that would together leave no holder, the one committing last guarded a holder another of them changed after it read it. `TestLastAdmin_ConcurrentDemotions` fails with the guard removed.
- **Known gap, not closed here**: the role definitions are read, not guarded. `rbac.Store` is frozen SDK and has no way to stage an Expect on a role record into auth's batch, so an rbac edit that takes `core:admin` from the other holder's role and commits between auth's read and auth's commit is not seen. rbac's rule reads holders through its batch, so the reverse order is caught there. Closing it needs an optional role-guard interface on the role store (F4-01's `ImportSealer` pattern) and an `rbac.Service` method auth calls inside its batch: about 100 lines across `rbac`, `rbacstore` and tests. Also open: nothing implements `rbac.Deps.Holders` yet, so until F4-08 wires it every rbac write that takes `core:admin` from a role is refused.
- **E-mail uniqueness** is HEAD's rule: an address another account holds **verified** refuses a creation (`ErrUserExists`); an unverified holder does not. The store indexes usernames only (§3.4's table), so the check and the commit run under a service mutex (`emailMu`, HEAD's `inviteMu`). F4-02b's invite accept and any later e-mail setter must take it too.
- **Password length** is counted in bytes, HEAD's rule, so pre-cutover accounts meet the same bound.
- **`ChangeOwnPassword`** refuses an API key, verifies the current password within the 2 s hashing wait without charging the throttle (HEAD), refuses an account without a password (`ErrInvalidCredentials`), and lands only if the epoch is still the verified one (`ErrStaleEpoch`; a rehash keeps the epoch and does not refuse it). It does not clear `PasswordResetRequired` or `SignInRestricted`. Audited `core.user.reset_password` with `self: true`, since §8 names no self-change action.
- **`SetStatus`** sets only `active` and `disabled`, refuses `_system` and a pending invitee, and writes nothing for the current status. Enable journals only `credential_epoch.bumped` (there is no `user.enabled` kind). API keys are refused while the owner is disabled and work again after.
- **`DeleteUser`** deletes the user's sessions, keys, identities and every invite or temp-login it is the target or creator of, in one batch, and journals one `user.deleted`. F4-02b's `PostRestore` must cascade the same records when it re-applies that line. A record the store cannot decode is left (logged); auth refuses it anyway.
- **Key status writes** (§4.4, §4.13's key rows). The owner, or another user through `core:users.manage`, an interactive method and dominance. Two rules more: a key actor manages only keys it may create (every scope of the target held by its effective set as stored now and by the checker it presented, the `CreateAPIKey` test; `ErrScopeEscalation`), for every change; and every change into `active` (re-enabling a disabled key, a manager's disable included, or confirming a restored one) needs an interactive method (`ErrDenied`), as HEAD's credential guard on `PATCH /api-keys/:id` did. A session disables or revokes its user's keys without more (a restriction widens nothing), as HEAD's `DELETE` did. A key whose owner was demoted below its scopes therefore cannot revoke itself; the owner's sign-in can.
- **Extension order**: an extension's `Order` is above `OrderAPIKey` (a presented key wins, §4.2 item 2) and is not `OrderSession`; `New` refuses anything else (`ErrMethodSpec`).
- **Imported key prefixes**: `New` refuses an empty prefix and one that overlaps a native prefix (either a prefix of the other, `ErrBadInput`), so the key authenticator never claims a session or one-time token.
- **Store errors never carry a key's bytes**: `authstore` describes a key as family and length (`session/h key len=N`), as `storage.keyRef` does, because session, key and one-time keys embed the credential's SHA-256 and the stage-12 touch logs its errors.
- **Invalidation events** (`core.principal.invalidated.v1`, §4.12) are not published: `Deps.Events` is not wired in F4-02a.
- **Audit action names** follow 05-rbac §8: `core.user.{create,disable,enable,delete,reset_password,set_roles}`, `core.apikey.set_status` (was `core.apikey.status` before this PR), and `core.apikey.revoke` for a change to `revoked`. A stage-12 refusal is recorded for stage 13 and not audited: §7.1's table (`audit.CoreActions`) names no action for it, and §9's `mediacore_auth_attempts_total` (F4-02b) counts the outcomes. Auditing it would take a new row in 05-rbac §7.1 and `CoreActions`.

## F4-08 must know

Build one `auth.Service` per process and hand stage 12 its middleware. Wire `Deps.Client` to httpapi's resolver (`HTTPS`, `OnLink`), `Deps.Settings` to the config snapshot, and implement `rbac.Holders` over the identity store, reading each user it reports through the batch (F4-01's seam). The ABO gate files above go with the legacy routes.

Two hard prerequisites:

1. **The role-definition last-admin guard lands before, or in the same PR as, any `rbac.Holders` implementation.** Today every rbac write that takes `core:admin` from a role is refused because nothing implements `Holders`; that refusal is what keeps the gap in "Last admin" above (role definitions read, not guarded) from being reachable. Implementing `Holders` alone opens it: an rbac role edit and an auth user write committing in the wrong order can leave no active admin. Tracked in `todo.d/2026-11-11-f4-02-role-definition-last-admin-guard.md`.
2. **Stage 12 is not wired before F4-02b's `mediacore_auth_attempts_total`.** Stage 12 records a refusal for stage 13 and audits nothing (above); until the counter exists, a wired stage 12 leaves failed credential attempts with no audit record and no metric.

And one behaviour for F4-08 and extension authors: **a Bearer value with no recognised prefix stays anonymous.** Neither core authenticator claims a Bearer that is not `mcs_`, `mck_` or an imported prefix, so with no extension claiming it the request proceeds anonymous: a Public route serves it, and any other route answers 401 `authentication_required`, not `invalid_credential`. An extension that accepts Bearer tokens of its own must claim its prefix and return an error for a malformed one, not `ErrNoCredential`, or a typo in its token is silently anonymous.

## F4-02b

What the second PR added beyond 05-authn §3.2, §4.6, §4.9 to §4.14, §5, §9, the readings it took, and what F4-08, F4-11 and the kernel must wire.

### Coined names

- `auth.Deps.Reach func() Reach` (`Reach{NonLoopbackListener, TrustedProxy}`; nil means unknown, which counts as remote), `auth.Settings.Mode` (`ModeRequired` | `ModeDisabled`), `Settings.DisabledAllowRemote *bool`, `Service.Posture() Posture{Disabled, DisabledRemote}`, `ErrAuthDisabledRemote`. The mode is read once in `New`; the auth-off principal binds `authz.AuthDisabled(catalog)` inside auth and nothing exports a wrapper around it.
- `auth.Settings.BootstrapEnabled *bool` (default true), `ReadOnlyKey bool`, `ReadOnlyKeyScopes []rbac.Permission` (default `core:system.view`; `core:admin` and unparseable scopes are `ErrBadInput`).
- `auth.RestoreDeps{Store, Previous, Revocations, StateFiles, Clock, NewBatch, Settings, RoleGrantsAdmin, Log}` is the argument of `PostRestore(ctx, d, rc)` and `BootWrites(ctx, d)`. `NewBatch`, `Settings`, `RoleGrantsAdmin` (reads a role through rbac, because `auth` cannot call the kernel) and `Log` are coined. `RestoreCounts` is a map keyed by the `Count*` constants (`api_keys_revoked`, `api_keys_disabled`, `api_keys_unconfirmed`, `users_disabled`, `users_deleted`, `passwords_blanked`, `identities_unlinked`, `sessions_revoked`, `sign_ins_deleted`, `epochs_bumped`, `users_restricted`).
- `auth.RestrictLastAdmin(ctx, d, id) (RestoreCounts, error)`: the §4.14 restricted-last-admin treatment as an exported seam. rbac's restore hook cannot import auth, so the kernel adapter calls this when rbac keeps the last admin's role.
- `auth.SystemUserID` (`_system`), `ReadOnlyKeyName`, `ReadOnlyKeyTTL` (24 h), `ReadOnlyKeyFile` (`readonly-key`), `ReadOnlyKeyLabel` (`auth.readonly_key`).
- `OneTimeToken.CreatorEpoch` (temp-login: the creator's credential epoch at mint; an invite keeps its creator's in `CredentialEpoch`). `errLinkCreator` (unexported) marks a link refused at consume for its creator; the audit reason is `creator_changed`, the outcome `denied`. `stageDeleteCreatedLinks` (beside `stageDeleteCredentials`, one helper for four call sites), `Service.holdsUsersManage`, `reasonBootstrapDisabled` (`bootstrap_disabled`), `Service.bootstrapEnabled`, and the test-only `Service.ClientOf`.
- `Principal.keyRef()` (unexported): the key a principal rests on, for `MethodAPIKey` (an empty `CredentialID` fails closed) and for a compat principal that remembers its key. Every key gate (`Revalidate`, the effective scope set, `CreateAPIKey`, `SetAPIKeyStatus`, `CheckCredentialFor`) goes through it.
- `Compat` handles: `VerifyPassword`, `AuthenticateKey`, `PrincipalFor` and `CheckCredentialFor` per method; compat `VerifyPassword` shares the login ceilings and the per-source throttle, and only an invalid key (not a revoked, expired or restricted one) is charged.

### Readings where the spec is silent

- A reset link sets the password at consume time (the link carries no password); an invite carries its creator's credential epoch and dies when the creator changes it, is disabled, or loses `core:users.manage`; an accepted invite has an unverified e-mail and no SSO allow-list entry. A `todo.d` fragment asks for §3.2 and §4.13 to say so.
- **Creator parity for temp-login and reset links** (review of #4599; the temp-login twin of an invite's SEC3-2 re-check). Consuming a link is refused, the token spent and an audit record written (outcome `denied`, reason `creator_changed`), unless its creator still exists, is active, is at the epoch the link recorded, is not `SignInRestricted`, still holds `core:users.manage` (compiled interactive) and still dominates the target's current roles. A token with no recorded creator names no stored user and is refused the same way. A link that lifts `SignInRestricted` was minted by an actor carrying `AssuranceOwner`, a per-request attribute the store cannot replay; the re-check holds it to the owner gate instead: it is refused once `core.auth.owner.required` (or an owner-set verifier extension) no longer applies. Disabling a user, signing it out everywhere, merging it away and removing `core:users.manage` from it also delete the links it created in the same batch, so a re-enable does not revive them. The mint reads and guards the creator row (`Store.GuardUser`); a creator that is the target uses the post-bump epoch. A `todo.d` fragment asks for §3.2 and §4.12 to say so.
- **`core.auth.bootstrap.enabled=false` stops redemption.** `RedeemBootstrap` refuses (`ErrBootstrapInvalid`, nothing charged) and a token-bearing `Setup` refuses (`ErrSetupClosed`), read live; `BootWrites` deletes the stored bootstrap tokens (with no state filesystem too) and the token file. A tokenless loopback `Setup` is governed by `setup_requires_token` alone.
- `Revalidate` of the auth-off principal returns nil while auth is off (it has no user, credential or epoch to go stale). Without `Deps.Client` the default client resolver marks a request `Forwarded` when any forwarding header is present (`Forwarded`, `X-Forwarded-For/Host/Proto`, `X-Real-IP`, `CF-Connecting-IP`, `True-Client-IP`). `StageUserMerge` refuses a target that is not active. `Setup` looks the token up before hashing the password. The invite accept batch guards the creator row.
- `Revalidate` reads the store on every call until `Deps.Events` is wired (the invalidation events of §4.12 are not published).
- Sign-out-everywhere needs an interactive actor even for oneself; the bootstrap and `BootWrites` admin pick skips a `SignInRestricted` holder, and bootstrap may then create a new admin.
- `BootstrapLimiter` stays ABO gate residue until F4-08.
- `Setup` returns the user and opens no session.
- A compat key principal is refused (`ErrDenied`) when minting or managing keys, stricter than the scope-escalation gate alone.
- Stage 12 outcome labels: `CodeResetRequired` counts as `inactive`; the closed label sets are exported from zero; the two live-count gauges rescan the store at most every 30 s.

### PostRestore notes

- Lines the hook derives itself (pre-swap restrictions, the nil-coverage unconfirm, `RestrictLastAdmin`) are journaled through `RestoreDeps.Revocations`; a failed `Append` records a `Gap`. A re-applied journal line is not journaled again. The lines carry no `RestoreSeq`: `rc` has no restore-line sequence, so the kernel may wrap `RevocationJournal` to stamp one.
- `identity.unlinked` carries `Detail = [provider]` or `[provider, subject]` (a superset of the spec's `[provider]`). The step-2 epoch bumps are not journaled. Restricted flags have no journal kind.
- Beyond the spec's step 3, a user present in both stores takes the higher credential epoch and the OR of `SignInRestricted` and `PasswordResetRequired`, so credentials killed after the archive stay killed.
- `BootWrites` runs after `PostRestore` in P4d step 4; a state file that cannot be written is logged, not fatal; nothing logs a credential.

### Deferred, and owned elsewhere

- **N3, `DeleteInvite` audit.** Deleting an invite writes no audit record; left as it is, with `DeleteUser`'s cascade the only other deleter. A later change adding `core.invite.delete` needs a row in 05-rbac §7.1 and `audit.CoreActions`.
- **`TestReplacedStore_RunsPostRestoreHook` and `TestReplacedStore_TruncatedJournalKeysNeedConfirmation`** need the kernel's P4d detection of a file-copied-back store (content marker, head below the anchor) and the step 2 re-apply; that is F4-11 (its `TestReplacedStoreRunsHooks`). F4-02b covers the hook body they end in: `TestPostRestore_NoJournalKeysNeedConfirmation` and `TestRestoreNilCoverageKeepsRevokedTerminal` call `PostRestore` with a nil-coverage `RestoreContext`, the exact input a replaced store produces.

### F4-08 and F4-11 must know

Not recorded in the `mediacore.auth` scope, and absent from `testdata/series.golden`: `mediacore_auth_password_hash_seconds` and `_password_queue_wait_seconds` (they need an observer on the `auth/password` hasher, which has none), and `mediacore_auth_extension_errors_total` (stage 12 treats every extension error as a refusal; §8's "internal error opens to the next method" rule needs a sentinel the `Authenticator` interface does not have). The prerequisite in "F4-08 must know" above, that stage 12 is not wired before `mediacore_auth_attempts_total`, is met by this PR. F4-11's P4d runner calls `PostRestore` (hook body only) and `BootWrites`; F4-08 registers the hook and gives the kernel adapter `RestrictLastAdmin`.
