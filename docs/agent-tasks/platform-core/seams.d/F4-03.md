# F4-03 seams and coined names

What F4-03 added beyond 05-authn §4.7, §3.3 and §6, the readings it took where the brief or the spec says nothing, and what F4-05 and F4-08 must know. The PR is dark: no route serves `core/auth/oidc`, nothing registers `cfaccess.Extension`, and ABO's sign-in behaves as at HEAD.

## Coined names

| Name | What it is |
|---|---|
| `auth.ErrExtensionUnavailable` | What an `Authenticator` returns when it could not decide (its IdP's keys, its backend). Stage 12 opens to the next method, warns with the extension name only, and counts `mediacore_auth_extension_errors_total{extension}`. Any other extension error is a refusal; `ErrStoreUnavailable` is still 503. This closes the gap F4-02.md's last metrics paragraph records, so that paragraph is superseded: **F4-08's `mediacore.auth` scope must declare the label key `extension`** (the family is open-labelled and not seeded, so `testdata/series.golden` is unchanged). |
| `(*auth.Service).LockEmails() (unlock func())`, `NoteUserCreated()` | The account-write seam `oidc` shares with `CreateUser`: the e-mail mutex every creator holds around "no other account holds this address verified", and the first-run flag. Nothing else of `Service` is exposed. `oidc.AccountLock` is the interface over them. |
| `oidc.Flow`, `New(ctx, Deps)`, `Start(StartRequest) (*Started, error)`, `Callback(CallbackRequest) (*Completed, error)`, `Reload`, `Providers` | The sign-in. F4-05's routes call `Start` and `Callback`: `Started.Binding` goes in a short-lived HttpOnly SameSite=Lax cookie for `MaxAge` seconds and comes back as `CallbackRequest.Binding`; the route clears it whatever the outcome. `Completed` is a session (`Session`, `Return`) or, for an app hand-off, a `Location` with no session. Errors are `oidc.Err*` sentinels (match with `errors.Is`; `ErrBadRedirect` is answered inline with 400, never by redirecting to the URI) plus `auth.ErrEmailInUse`, `ErrInactiveUser`, `ErrResetRequired`, `ErrStoreUnavailable`, `ErrBadInput`. |
| `oidc.Deps{Settings, Keys, Resolver, Sessions, Handoff, HasUsers, CallbackBase, Audit, HTTPClient, Log, Clock}` | `Settings func() Settings` is read per request (`redirect_base_url` changes at once; a provider-set change at the next `Reload`). `Keys` is a `KeyDeriver` (`*secrets.Store`); the state key is `DeriveKey("mediacore/auth/oidc-state/v1")`. `Handoff` is `MethodSpec.AppHandoff` of the module's compat method. `CallbackBase` is `auth.Options.OIDCCallbackBase`, default `/api/core/v1/auth/oidc`. |
| `oidc.ProviderConfig`, `Policy`, `Settings`, `Resolver`, `ResolverDeps`, `NewResolver`, `Resolver.Resolve(ctx, Policy, Claims)` | Config with its client secret already resolved (`core.auth.oidc.<id>.client_secret`, bound by the F3 sibling work), redacted in every rendering. `Resolve` is the one admission and linking gate; an extension with its own identity source (Cloudflare Access) calls it with a `Policy` of its own. |
| `oidc.StateCodec`, `Payload`, `StateTTL`, `StateKeyInfo`, `CodeChallengeS256` | The signed state: `ID, State, Verifier, Nonce, Provider, Return, IssuedAt, AppRedirectURI, AppChallenge, AppState`. |
| `cfaccess.Extension(ExtensionConfig) (auth.Extension, error)`, `AssertionVerifier`, `VerifiedAssertion`, `(*CFAccessVerifier).VerifyIssued`, `AccountResolver`, `OrderCFAccess` (150), `ErrKeysUnavailable` | F4-08 registers the result in `app.Options.Authenticators` with `ExtensionConfig{Verifier, Resolver: *oidc.Resolver, Policy{Provider: "cfaccess", ...}, OwnerEmail}`. |
| `cfaccess.Hooks{KeyPresented, BindUser, Permissions}`, `middleware.CFAccessHooks` | What the gin binder takes from the gin chain so `internal/cfaccess` never imports `internal/server/middleware`. Deleted with the binder at F4-08. |

## Readings where the spec is silent

- **The OIDC move is a new package, not a rename.** `core/auth/oidc` is written against `auth.Store` and `*slog.Logger`; HEAD's `resolve.go`, `state.go`, `providers.go` and `oauth.go` (which depend on `internal/database` and `internal/logger`) remain, behaviour unchanged, as `internal/legacyoauth` for the gin chain until F4-08 deletes them (the brief's STOP 3: no change to ABO sign-in before F4-08). The old tests moved with them.
- **Layer values.** §8.2 places `internal/cfaccess` at layer 5, but `internal/httputil` is a layer-0 leaf at BASE and the layering test computes 3, so `layerOf` carries 3 for `internal/cfaccess` and `internal/legacyoauth` until httputil moves.
- **Link rule.** Only a holder whose address we verified blocks or takes a link; an unverified holder blocks nothing (the verified provider identity wins the address, and displacement is audited). "Prove the password in the same flow", the other reading of "never takes a password account", is F4-05's to add if wanted; core's rule is the stricter refusal (`email_in_use`, sign in and link from the profile).
- **Trust.** `link_existing_by_email` governs both linking and displacement: an untrusted provider never takes or un-mails an account.
- **PKCE and nonce are new** (HEAD's GitHub flow had no PKCE; HEAD sent no nonce). They exist only in core's providers; the legacy chain is unchanged.
- **Linked sign-ins take no e-mail lock.** \`Resolver.Resolve\` decides a sign-in of an already linked subject, whose account needs no write, without \`LockEmails\` (\`linkedFast\`); only an unseen subject, or a linked account that needs its address marked verified, takes the lock. Once F4-08 registers the Cloudflare Access extension, every browser request it authenticates runs \`Resolve\`, and it must not queue behind account creation. Its cost is two store reads per request (identity, user) plus admission (a domain or address match, or one \`InviteAllowed\` read when the allowlist misses); if that is too much for stage 12, F4-08 can put a short TTL cache in front of the extension.
- **Shared files touched.** \`core/archtest/thirdparty_allow.txt\` gains \`github.com/coreos/go-oidc/v3\`, \`github.com/go-jose/go-jose/v4\` (the fake providers' signer, tests only) and \`golang.org/x/oauth2\`; \`scripts/deadcode-baseline.txt\` gains the three \`internal/cfaccess\` identifiers of the dark extension (F4-08 registers it); \`internal/arch/layering_test.go\` swaps \`internal/oauth\` for \`internal/legacyoauth\` and \`internal/cfaccess\`. core's \`go-jose\` is v4.1.6 and the root's \`go-jose\` moved from indirect to direct: \`internal/cfaccess/keys.go\` (the key cache) parses and verifies the Access JWT signature with it, and the extension's tests sign with it. Nothing in \`core/secrets\`, \`core/kernel\`, \`core/config\` or core/auth's \`templogin.go\`, \`bootwrites.go\`, \`users.go\`, \`sessions.go\` was edited.
- **Single use is per process** (an in-memory, bounded set of spent state ids). A replay after a restart still fails at the provider, whose code is single use.
- **Login audit** is the async `core.auth.login` Emit for success and (see "Failed sign-ins are audited") failure; a refused link audits `core.identity.link` as denied with reason `email_in_use`, once per refusal-cache TTL.
- **Cloudflare Access: header 401, cookie falls through.** A bad `Cf-Access-Jwt-Assertion` header is a 401 from stage 12, per §3.3 (Cloudflare injects it at the edge, so a bad one is a forgery). A bad `CF_Authorization` cookie is `ErrNoCredential`: the cookie is the browser's, Access cookies outlive sessions, and one planted from a sibling subdomain must not lock out a browser whose valid session cookie rides with it, so the session authenticator runs and nothing is granted for the cookie. Every `CF_Authorization` cookie is tried (at most five), the first that verifies wins, and a key outage while only cookies are presented is `ErrExtensionUnavailable`. A valid token for an identity the app does not admit still falls through, as the binder did. (The first revision of this PR refused a request carrying an expired cookie; that is no longer true.)
- **Cloudflare key cache.** `internal/cfaccess/keys.go` replaces go-oidc's remote key set (which refetched on every unknown kid, so a caller-chosen kid was a fetch per request, and never expired a key). Keys are cached for `keysTTL` (1 hour; past it the next request refetches and a failed refetch is "unavailable", never a stale yes, and a withdrawn key stops verifying). An unknown kid fetches at most once per `keysMissWindow` (30 seconds, measured from the last attempt) and concurrent callers share the in-flight fetch. Inside the window an unknown kid is "invalid" if the last attempt succeeded and "unavailable" if it failed. A token under a cached kid is judged by that key alone, so a forgery under a known kid is a 401 even during an outage, and only an unknown kid in an outage is `ErrExtensionUnavailable`. Cost to know: after Cloudflare rotates in a new key, tokens under it are refused for up to 30 seconds (a cookie in that state falls through; a header is a 401). Any status other than 200, including a 3xx, is an outage and a redirect is never followed. The legacy gin binder uses the same cache.
- **Refusal cache.** A refusal that depends on stored state (`ErrEmailNotAllowed`, `auth.ErrEmailInUse`) is remembered per (provider, subject, address) for `oidc.RefusalTTL` (1 minute, 4096 entries, expired then soonest-expiring evicted) and answered again with no e-mail lock, no user scan and no audit event; the denied `core.identity.link` audit is raised once per TTL, not once per request. Only refusals are cached, never an admission, so a stale entry can delay a sign-in that has become possible (the holder lost its admin role or password; the address was invited) by at most a minute and can never let one through. Store failures, inactive and reset-required results are not cached.
- **F4-08 gate (owner sign-in).** An owner who is an admin with a password is refused `email_in_use` by the link rule, and the Cloudflare Access identity (cfaccess, sub) is a new subject for them. **F4-08 must not register `cfaccess.Extension` until an owner-link path exists**: either the import migrates the (cfaccess, sub) identity rows of HEAD's `internal/oauth` links, or F4-05 adds the prove-password link (05-authn 4.7, the second reading in "Link rule" above). Until then registering the extension would lock the owner out of the Access path (it would fall through to the next method on every request, now cheaply thanks to the refusal cache, but never sign in).
- **Plain ASCII addresses only.** `NormalizeEmail` folds compatibility characters onto ASCII (the Kelvin sign, the long s, fullwidth letters), so a claim that is not printable ASCII equal to its normalised form up to case is refused (`oidc.ErrEmailNotPlain`) before it can link, displace or be admitted, the rule `IsOwnerEmail` already applies. Consequence: a provider account whose address has a non-ASCII character cannot sign in through `oidc` or the Cloudflare extension. Internationalised addresses are not supported; relaxing this needs a decision on which fold is safe.
- **Binding size.** The signed binding cookie is bounded: `AppState` at most `oidc.MaxAppState` (512 bytes), the app `redirect_uri` at most 512, and `Start` refuses a binding over 3500 bytes (`ErrAppStateTooLong`), so the cookie stays under the browsers' 4 KB limit. Native apps that send a longer state must keep it on the device.
- **Token checks.** An id_token with several audiences, or any `azp`, must carry `azp` equal to the client id (OIDC core 3.1.3.7). This is not applied to Cloudflare Access tokens, which carry no `azp` and whose `aud` is the application tag. `email_verified` is accepted as boolean true or the string "true" only (Microsoft-style string booleans), anything else is unverified. The discovery document's authorization, token and JWKS endpoints must be https; there is no loopback exception, the tests' fake providers are TLS servers.
- **Failed sign-ins are audited.** 05-rbac 7.1 names `core.auth.login` for both outcomes of one action, so each refusal after the code exchange emits it async with `failure` (or `error` for a store failure) and a reason class (`exchange_failed`, `email_not_verified`, `email_not_plain`, `email_not_allowed`, `email_in_use`, `inactive`, `reset_required`, `app_handoff_failed`, `refused`), the provider's origin and nothing else: no address, token, code or target. State, missing-code and provider-declined errors precede identity and are not logins.
- **Log rate limits.** Stage 12 warns about an unavailable extension at most once a minute per extension with a `suppressed` count (`mediacore_auth_extension_errors_total` stays exact); `cfaccess` warns about a bad token or an unadmitted identity at most once per 30 seconds with the same count.
- **Known residue, for F4-05.** A squatter who registers an unverified account with a victim's address keeps that address when the holder is an admin or has a password (the displacement guard); the verified provider identity is then refused `email_in_use`. The remedy is the prove-password link (F4-05), not this PR.
- **`internal/auth/owner.go` did not move** (STOP 2); see the `todo.d` fragment `F4-03-OWNER` for the cost.
- **No end-to-end ABO to `auth.Service` test**: `core/internal/authstore` is not importable from ABO. The extension is tested through `Authenticate` with a real verifier over a fake team domain; stage 12's handling is tested in `core/auth` (`TestStage12_ExtensionUnavailableOpensToNextMethod`).

## F4-05 and F4-08 must know

- F4-05 serves `oidc.Flow`; `TestOIDC_AppHandoffMintsABSCode` is F4-08's (needs the routes and the ABS redemption).
- F4-08 registers `cfaccess.Extension` only after the owner-link gate above is met (needs a `*oidc.Resolver` built with `ResolverDeps{Store, NewBatch, Audit, Roles: rbac, Accounts: *auth.Service}`), declares the `extension` label key, and deletes `internal/legacyoauth` and the gin binder.
