# F7-08 seams and coined names

Names this task added that later rows may rely on (implementation plan §(n) rule 5), and the rulings it records.

| Name | Where | What it is |
|---|---|---|
| `m6.Plan(ctx, legacy, cfg) (*Report, error)` | `internal/books/cutover/m6/plan.go` | The step's dry run (05-metadata M1.10): reads books' legacy range through `legacy`, runs the step's own `Step` over every source row against importers that accept everything and a writer that keeps nothing, and returns the Report the real run would produce. It never goes through the runner, so it leaves no plan, level stamp, cursor or state record, and a real boot after it steps every row. F7-09 wires it to the storage CLI's dry run, called between `Prepare` and `Migrate`. It cannot see core's importers' answers: an instance, job, root list or rule core already holds a different row for is reported imported here and quarantined by the real run; on the empty native side every cutover store has, the two reports are equal (`TestPlan_IsTheRealRunsReport`). The runner's own scratch-copy rehearsal (05-storage 5S.3.6) is the one that exercises the importers. There is no `Config.DryRun`: a dry run through the runner records a plan and a running state, and a failed record only re-verifies, so the next boot never stepped a row. |
| `m6.Config.Effective` | `internal/books/cutover/m6/step.go` | `func(ctx, integrations.Ref) (map[string]string, error)`: the operator overlay in effect at cutover for an instance, URL field to URL as supplied (empty is none). Required by `New` and `Plan`; a caller with no overlay passes a function returning nil. F7-09 builds it from the same sources the operator layer will read: for `download/deluge`, `url` is HEAD's environment variable or config-file Deluge web URL (`internal/config` `applyEnvAuthoritativeConfig`, `config.go` 2243-2256, 2316-2322, 2556-2561, `head_bind.go` 57-61); production's is env-locked. An error fails the boot: it is never read as "no overlay". |
| `cutover.PlanBlobResidual`, `cutover.BlobResidual` | `internal/books/cutover/config_plan_residual.go` | M2's own planner over one `setting:config_blob` row: the residual row it leaves for M6, the secrets it writes (with the names it gives them) and what it quarantines. The m6 rig seeds its secrets store from it, so the credential names M6's tests read are the names M2 writes and the secrets double validates them with `secrets.Name.Validate`. A permanent test seam, not dark code waiting for a caller: no production code calls it, and its `scripts/deadcode-baseline.txt` line stays after F7-09 registers M6. |

## Rulings

- **Origins are signed from the effective destinations, not from the stored ones.** 05-metadata M1.10's "Trust carried over" says to sign `Local`, `SecretsOrigin` and `OperatorSecretOrigin` from the instance's stored origins. `seams.d/F7-01` rows 17 and 22 say the signature core compares at the first boot is over the effective view (the stored layer with the operator overlay applied) and that F7-08 computes migrated rows "the same way, with the operator overlay in effect at the time". The two disagree wherever an operator overlay moves a destination, and a row signed from the stored origin is withheld at the first boot (`integration_secret_withheld_destination_moved`, `Local` void), which is the failure M1.10 exists to prevent. **F7-01 rows 17 and 22 win.** `pending.finish` signs from stored destinations with `Config.Effective` applied field by field; an overlay that is no absolute URL removes that field's destination from the signature (it has no origin to trust). The stored value is kept as the instance's setting; only the signature and, for `download/deluge`, the instance URL come from the overlay. The M1.10 text should be amended to say "effective".
- **Deluge's URL is the operator's when there is one.** HEAD reads the Deluge web URL from the environment or config file ahead of the stored blob, including over a stored empty value, so an install that pins it that way has a blank or stale `deluge_web_url` in the blob. M6 builds `download/deluge` from the overlay's `url` when set, else the blob's; with neither it creates no instance and reports that (a "note" entry, no URL in it). When both are set and differ, the report says the stored one is superseded and carries neither.
- **No URL, credential or userinfo is printed in a report, log or quarantine detail.** A trust entry names the origin it signs (scheme, host, port), never a path; an overlay is reported as "the effective <field> is the operator's".
- **Registration needs more claims than books' spec declares today (F7-09).** The `rootscan:` family (M6's own write, a books family with no claim) and the nested retired claims `counter:import_path` and `idx:sidx:dirty:` (nested inside books' whole-family `counter:` and `idx:` claims) exist only in the m6 test rig; F7-09 must declare them in books' spec before registering the step.
- **Path aliases stay per root; an ancestor alias is carried (departs from 05-library §5L.10, which this task amended).** HEAD renders a path through the first alias, in list order, whose `Root` contains it (`web/src/utils/pathAliases.ts` `matchAlias`; its doc asks callers to order the list most specific first, but PathLinks passes `cfg.path_aliases` as stored and `config.SeedPathAliases` keeps the mappings' order, so nothing does), while core's `library.Alias` has no root of its own and renders its root's path. So for each root M6 takes the first alias in list order whose `Root` is the root's path or an ancestor of it: at the root's path it is attached as is, and at an ancestor it is carried to the root with the relative path appended, in each form as HEAD renders it (`derivedAlias`: Windows and UNC trim a trailing separator run and join with `\`, the SMB URL joins with `/` and percent-encodes each segment as `encodeURIComponent` does, an empty form stays empty). The root then renders exactly as HEAD rendered it. An alias no root takes is quarantined raw with a reason that says its display rendering is not carried: one inside a root (HEAD seeds those from an iTunes mapping's `To` below a root, `config.SeedPathAliases`), one over roots that each matched an alias listed before it (including a second alias at the same root), and one near no root.
- **F3-07's `UnfoldRoots` must match the alias carry (open obligation; the function is on the unmerged `agent/platform-core-f3-07-e2u` branch, not on main).** It returns every alias of every migrated root with that root's path as its `Root`, so after the carry a nested root returns the derived alias beside the ancestor's original: rendering-equivalent at HEAD (the more specific alias produces the same string), but one more `path_aliases` row than the blob held. Either `UnfoldRoots` drops an alias on root R that equals `derivedAlias` of an ancestor root's alias, or its round-trip test accepts the extra row as rendering-equivalent. - **Unknown capability ticks and undeclared features are dropped, not carried.** HEAD kept a tick it did not register and ignored it in selection, and stored features as free strings. core's `ai.Router.ValidateEndpoint` refuses an endpoint with an unknown or wildcard tick (an import has no stored row to grandfather it) or a feature outside `json_schema`, `json_mode`, `vision`, `batch_api`, `tools`, `timestamps` and `shared_fs:<root>`, which would quarantine the whole endpoint. M6 keeps the ticks in `headCapabilities` (aidispatch's 13, pinned both ways against `aidispatch.Registry()`) and the features core declares, and reports each dropped value as `dropped: ...` on the instance. A `capability_models` entry for a capability outside `headCapabilities` is dropped and reported the same way: HEAD validated those keys with the same `capabilityIDProblem` as ticks and read them only by exact capability ID (`internal/aidispatch/dispatch.go`, `ep.CapabilityModels[spec.Capability.id]`), so such an entry never chose a model. core accepts any key there, and its router also reads only `CapabilityModels[spec.ID]`, so carrying the entry would change nothing but list its model in the per-model metrics. `TestAIInstances_PassCoresEndpointValidator` runs core's real validator over what M6 writes. The census is the dry run: `m6.Plan`'s report lists every dropped tick.
- **The exact HEAD ID wins an instance ID, whatever the order.** When a renamed entry (`batcave_db` becomes `batcave-db`) lands on an ID another entry of the same list already has as its HEAD ID, the exact entry keeps it, listed before or after, and the renamed one is quarantined as the duplicate (`groupRun.exactIDs`, over `metadata_sources` and `ai_endpoints`). The renamed entries that land on an exact ID are decided after the list (`groupRun.settleDeferred`): when the exact entry was not written (it did not decode, or core refused it or holds another instance under the ID), nothing holds the ID, so the first renamed entry takes it and the report says why.
- **A renamed instance takes only its own credentials.** It never takes `refsFor` under its new ID: a name there belongs to the exact-ID sibling or to no source. Its credentials are carried from the HEAD-ID names. A secret already under the new name with no owner in this pass is not carried over and not bound; the report says both names stay unbound. The old-name secret stays in the store, unreferenced, and the report says so.
- **A row renamed to `openai` keeps HEAD's OpenAI key when its `auth_ref` named it.** HEAD sent the OpenAI key to any row whose `auth_ref` is `openai_api_key`, whatever its ID (`internal/ai/pool_routing.go` `poolSecret`). A hand-typed `OpenAI` row is renamed to `openai` and takes no ref under its new name, but that name, `integrations.ai.openai.api_key`, is the key HEAD sent it, so M6 binds it and reports the binding. Without that `auth_ref` nothing is bound. The renamed row still suppresses the synthesised `ai/openai`, which stays decided by the new ID (a second `ai/openai` would be a duplicate). A stored OpenAI key no migrated endpoint refers to is reported.
- **The synthesised `ai/openai` stays when `ai_endpoints` is present (round-1 n4 not taken), is ticked, and follows `enable_ai_parsing` (F7-09 D1, r2 m-a).** HEAD's `migrateAIEndpointsBlob` synthesised its row only while `ai_endpoints` was absent, but whatever `ai_endpoints_routing` said, the sites the pool never routed read the key from the scalars and ran only while `enable_ai_parsing` was on: `internal/server/ai_ops.go:60` (author review and discovery), `internal/plugins/maintenance/dedup_ops.go:155` (the author dedup batch) and `internal/server/diagnostics_ai_ops.go:68` (the diagnostics batch). So the synthesised row is what carries that use past the flip, and it is ticked with exactly those capabilities (`legacyKeyCapabilities`: `books.author_review`, `books.author_discovery`, `books.author_dedup_batch`, `books.diagnostics`) and enabled exactly when `enable_ai_parsing` is on. Off, it is written disabled with its ticks kept (it serves nothing and is never probed; enabling it restores HEAD's behaviour), and the report says which. It is not ticked for `llm.filename_parse`, `embed.text` or `llm.cover_art_vision`: the pool routes those, so a tick would send OpenAI scan, embedding and vision calls HEAD sent only where a row was ticked. **F7-09 wiring obligation:** `m6.Config.EnableAIParsing` (required) must answer HEAD's effective `enable_ai_parsing` (M2 moved it to `modules.books.ai.enable_ai_parsing`, and the residual blob no longer holds it); it is read only when the row is synthesised, and a read error stops the step. Key-reading sites outside this set (`internal/server/handlers/ai.go` ParseFilename and ParseAudiobook, the cover analysis in `internal/server/entities_ops.go`, the `llmparser` service behind metadata rerank and dedup review, gated by `llm_mode`) are not carried by this row; see the F7-09 D1 PR.
- **A local process endpoint is written with no `url` (F7-09 D1).** HEAD's `local_process` url is the marker `config.LocalUVEndpointURL` (`local:uv-openai-whisper`), which names no address and which HEAD's launcher never dials; HEAD's validator accepts any string there. `books.whisper_local` declares no `url` setting and core refuses a destination-named setting that is no URL with a host, so a record carrying it was refused at Put. M6 writes none; a value other than the marker is reported (never printed) and quarantined under `setting:config_blob#ai_endpoints.<n>.url`.
- **The exact `openai` row binds HEAD's key only when its `auth_ref` is `openai_api_key` (F7-09 D1, r2 m-f; a narrowing).** HEAD sent the dummy local key to a row with no `auth_ref`, and `poolSecret` answers no secret for any other name, which made the row uncallable. M6 had bound the stored key (and paired the operator's) to the exact row whatever its `auth_ref`, serving a credential HEAD withheld. It now binds and pairs only for `auth_ref: openai_api_key`; otherwise the key stays in the store and the report says no endpoint refers to it.
- **A renamed source never pairs with an operator key.** HEAD's metadata provider switch was exact and case-sensitive (`internal/metafetch/service_search.go`), so a source M6 renames to `google-books` or `hardcover` was an inert unknown source at HEAD. It gets no `OperatorSecretOrigin`, and the operator key is never served beside a `base_url` HEAD never sent it to. A row renamed to `openai` pairs only when its `auth_ref` named HEAD's key.
- **A dropped `capability_models` model is quarantined.** The entry is left out of the instance and its model value is quarantined under `setting:config_blob#ai_endpoints.<n>.capability_models.<key>`, so the owner can recover it.
- **`rate_limit.max_concurrent` carrier: RESOLVED in core by F7-09 D4 as `integrations.Limits.MaxConcurrent`, enforced by the metadata `Chain`; the m6 mapping and the books adapters' default of 2 are still fold-time work.** (Original text, round-1 m4:) HEAD bounded searches in flight per provider with it (`internal/metafetch/source_chain_walk.go` `NewProviderSemaphore`). After the flip the bound falls to `DefaultPerProviderFetchCap` (2) until a carrier exists. A books-owned settings key does not fit this slice: no `books.<id>` metadata adapter exists yet to read it, and once #4804's `validateImport` runs on imports, an undeclared settings key could get the whole instance refused. Carrying it needs either that adapter's settings schema or a `Limits` field in core.
- **An unreadable credential of a renamed source is carried as unreadable.** The instance refs the new name, and M6 stages `secrets.Importer.ImportUnreadable` there with reason `corrupt`, so it reports `integration_secret_unreadable` ("re-enter it") exactly as a source that kept its ID does. The reason cannot be the source's: `Config.SecretValue` answers found false, not why. `corrupt` is the remedy that holds, since the carried record has no bytes any key could open. Nothing is staged, and "carried" is not reported, until the instance import succeeds.
- **An unproven operator Deluge URL is reported, not quarantined.** It is not a row M6 owns: no instance is built and the report says to supply the URL without userinfo. The blob's `deluge_web_url` is quarantined only when it is that same URL. A blob value that is not a string is quarantined as undecodable, and the operator's URL still builds the instance.
- **Unread plugin settings are kept.** `leftovers` treats `plugins` as read, so the webhook converter quarantines every other plugin entry (`plugins.<name>`) and every `plugins.webhook.settings` key other than `urls`, `events` and `secret` (M2's), each with its raw value and a report line.
- **`import_path:` is not a sensitive family.** It holds a path, a name and scan counters, so its quarantine records are not sealed and a listing without the keyring can read them. `Sensitive` is `KeyBlob` alone.
- **`rate_limit.max_concurrent` is reported as dropped.** HEAD's per-source bound on searches in flight has no field in core's `Limits`. The recursive frozen-decoder pin (`TestFrozenDecoders_CoverHEADFields` now walks nested structs) found it missing from the decoder.
