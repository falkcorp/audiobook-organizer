# F7-08 seams and coined names

Names this task added that later rows may rely on (implementation plan §(n) rule 5), and the rulings it records.

| Name | Where | What it is |
|---|---|---|
| `m6.Plan(ctx, legacy, cfg) (*Report, error)` | `internal/books/cutover/m6/plan.go` | The step's dry run (05-metadata M1.10): reads books' legacy range through `legacy`, runs the step's own `Step` over every source row against importers that accept everything and a writer that keeps nothing, and returns the Report the real run would produce. It never goes through the runner, so it leaves no plan, level stamp, cursor or state record, and a real boot after it steps every row. F7-09 wires it to the storage CLI's dry run, called between `Prepare` and `Migrate`. It cannot see core's importers' answers: an instance, job, root list or rule core already holds a different row for is reported imported here and quarantined by the real run; on the empty native side every cutover store has, the two reports are equal (`TestPlan_IsTheRealRunsReport`). The runner's own scratch-copy rehearsal (05-storage 5S.3.6) is the one that exercises the importers. There is no `Config.DryRun`: a dry run through the runner records a plan and a running state, and a failed record only re-verifies, so the next boot never stepped a row. |
| `m6.Config.Effective` | `internal/books/cutover/m6/step.go` | `func(ctx, integrations.Ref) (map[string]string, error)`: the operator overlay in effect at cutover for an instance, URL field to URL as supplied (empty is none). Required by `New` and `Plan`; a caller with no overlay passes a function returning nil. F7-09 builds it from the same sources the operator layer will read: for `download/deluge`, `url` is HEAD's environment variable or config-file Deluge web URL (`internal/config` `applyEnvAuthoritativeConfig`, `config.go` 2243-2256, 2316-2322, 2556-2561, `head_bind.go` 57-61); production's is env-locked. An error fails the boot: it is never read as "no overlay". |
| `cutover.PlanBlobResidual`, `cutover.BlobResidual` | `internal/books/cutover/config_plan_residual.go` | M2's own planner over one `setting:config_blob` row: the residual row it leaves for M6, the secrets it writes (with the names it gives them) and what it quarantines. The m6 rig seeds its secrets store from it, so the credential names M6's tests read are the names M2 writes and the secrets double validates them with `secrets.Name.Validate`. A permanent test seam, not dark code waiting for a caller: no production code calls it, and its `scripts/deadcode-baseline.txt` line stays after F7-09 registers M6. |

## Rulings

- **Origins are signed from the effective destinations, not from the stored ones.** 05-metadata M1.10's "Trust carried over" says to sign `Local`, `SecretsOrigin` and `OperatorSecretOrigin` from the instance's stored origins. `seams.d/F7-01` rows 17 and 22 say the signature core compares at the first boot is over the effective view (the stored layer with the operator overlay applied) and that F7-08 computes migrated rows "the same way, with the operator overlay in effect at the time". The two disagree wherever an operator overlay moves a destination, and a row signed from the stored origin is withheld at the first boot (`integration_secret_withheld_destination_moved`, `Local` void), which is the failure M1.10 exists to prevent. **F7-01 rows 17 and 22 win.** `pending.finish` signs from stored destinations with `Config.Effective` applied field by field; an overlay that is no absolute URL removes that field's destination from the signature (it has no origin to trust). The stored value is kept as the instance's setting; only the signature and, for `download/deluge`, the instance URL come from the overlay. The M1.10 text should be amended to say "effective".
- **Deluge's URL is the operator's when there is one.** HEAD reads the Deluge web URL from the environment or config file ahead of the stored blob, including over a stored empty value, so an install that pins it that way has a blank or stale `deluge_web_url` in the blob. M6 builds `download/deluge` from the overlay's `url` when set, else the blob's; with neither it creates no instance and reports that (a "note" entry, no URL in it). When both are set and differ, the report says the stored one is superseded and carries neither.
- **No URL, credential or userinfo is printed in a report, log or quarantine detail.** A trust entry names the origin it signs (scheme, host, port), never a path; an overlay is reported as "the effective <field> is the operator's".
- **Registration needs more claims than books' spec declares today (F7-09).** The `rootscan:` family (M6's own write, a books family with no claim) and the nested retired claims `counter:import_path` and `idx:sidx:dirty:` (nested inside books' whole-family `counter:` and `idx:` claims) exist only in the m6 test rig; F7-09 must declare them in books' spec before registering the step.
- **Path aliases stay per root; an ancestor alias is carried (departs from 05-library §5L.10, which this task amended).** HEAD's `PathAlias.Root` is matched as a path prefix, most specific first (`web/src/utils/pathAliases.ts`), while core's `library.Alias` has no root of its own and renders its root's path. So for each root M6 takes the alias whose `Root` is the root's path; with none, the alias with the longest `Root` that is an ancestor of the root's path is carried to it with the relative path appended, in each form as HEAD renders it (`derivedAlias`: Windows and UNC trim a trailing separator run and join with `\`, the SMB URL joins with `/` and percent-encodes each segment as `encodeURIComponent` does, an empty form stays empty). The root then renders exactly as HEAD rendered it. An alias no root takes is quarantined raw with a reason that says its display rendering is not carried: one inside a root (HEAD seeds those from an iTunes mapping's `To` below a root, `config.SeedPathAliases`), one over roots that all have a more specific alias, and one near no root.
- **F3-07's `UnfoldRoots` must match the alias carry (open obligation; the function is on the unmerged `agent/platform-core-f3-07-e2u` branch, not on main).** It returns every alias of every migrated root with that root's path as its `Root`, so after the carry a nested root returns the derived alias beside the ancestor's original: rendering-equivalent at HEAD (the more specific alias produces the same string), but one more `path_aliases` row than the blob held. Either `UnfoldRoots` drops an alias on root R that equals `derivedAlias` of an ancestor root's alias, or its round-trip test accepts the extra row as rendering-equivalent. - **Unknown capability ticks and undeclared features are dropped, not carried.** HEAD kept a tick it did not register and ignored it in selection, and stored features as free strings. core's `ai.Router.ValidateEndpoint` refuses an endpoint with an unknown or wildcard tick (an import has no stored row to grandfather it) or a feature outside `json_schema`, `json_mode`, `vision`, `batch_api`, `tools`, `timestamps` and `shared_fs:<root>`, which would quarantine the whole endpoint. M6 keeps the ticks in `headCapabilities` (aidispatch's 13, pinned both ways against `aidispatch.Registry()`) and the features core declares, and reports each dropped value as `dropped: ...` on the instance. `TestAIInstances_PassCoresEndpointValidator` runs core's real validator over what M6 writes. The census is the dry run: `m6.Plan`'s report lists every dropped tick.
- **The exact HEAD ID wins an instance ID, whatever the order.** When a renamed entry (`batcave_db` becomes `batcave-db`) lands on an ID another entry of the same list already has as its HEAD ID, the exact entry keeps it, listed before or after, and the renamed one is quarantined as the duplicate (`groupRun.exactIDs`, over `metadata_sources` and `ai_endpoints`).
- **A renamed instance takes only its own credentials.** It never takes `refsFor` under its new ID: a name there belongs to the exact-ID sibling or to no source. Its credentials are carried from the HEAD-ID names. A secret already under the new name with no owner in this pass is not carried over and not bound; the report says both names stay unbound. The old-name secret stays in the store, unreferenced, and the report says so.
- **An unreadable credential of a renamed source is carried as unreadable.** The instance refs the new name, and M6 stages `secrets.Importer.ImportUnreadable` there with reason `corrupt`, so it reports `integration_secret_unreadable` ("re-enter it") exactly as a source that kept its ID does. The reason cannot be the source's: `Config.SecretValue` answers found false, not why. `corrupt` is the remedy that holds, since the carried record has no bytes any key could open. Nothing is staged, and "carried" is not reported, until the instance import succeeds.
- **An unproven operator Deluge URL is reported, not quarantined.** It is not a row M6 owns: no instance is built and the report says to supply the URL without userinfo. The blob's `deluge_web_url` is quarantined only when it is that same URL. A blob value that is not a string is quarantined as undecodable, and the operator's URL still builds the instance.
- **Unread plugin settings are kept.** `leftovers` treats `plugins` as read, so the webhook converter quarantines every other plugin entry (`plugins.<name>`) and every `plugins.webhook.settings` key other than `urls`, `events` and `secret` (M2's), each with its raw value and a report line.
- **`import_path:` is not a sensitive family.** It holds a path, a name and scan counters, so its quarantine records are not sealed and a listing without the keyring can read them. `Sensitive` is `KeyBlob` alone.
- **`rate_limit.max_concurrent` is reported as dropped.** HEAD's per-source bound on searches in flight has no field in core's `Limits`. The recursive frozen-decoder pin (`TestFrozenDecoders_CoverHEADFields` now walks nested structs) found it missing from the decoder.
