# F3-06 seams and coined names

This file lists what the books config cutover PR (`internal/books/cutover`) added beyond 05-config §1.12 and the F3-06 brief: names the spec does not have, readings it took where the spec or the brief is silent, the spec discrepancies it found, and what F3-07 and later rows must do with it. Everything not listed follows the brief.

Nothing here runs on `main`: `books.Module()` registers none of it (`grep -rn 'cutover\.' internal/books/module.go | wc -l` prints 0, `ls internal/books/cutover/steps.go` finds nothing). F3-07 registers M2 and the books level step.

## What is here

| File | What it is |
|---|---|
| `rename_data.go`, `rename_table.go`, `rename_convert.go` | The generated rename table (`Table()`, `RetiredConfigNames()`, `CanonicalEnvNames()`), its golden `testdata/rename_table.golden` (330 rows), and the converters (`Convert`). |
| `head_*.go` | Frozen copies of HEAD's `Config` types, blob decoder, effective-value rules, AES-GCM decrypt, gap-fill reader, managed-key list, removed keys and env binding list. Each carries the "FROZEN COPY" header and is deleted in R3 with the other HEAD-format readers. |
| `config_plan.go`, `config_step.go` | M2a: `ConfigStep(cfg, sec, ConfigStepOptions)`, a `datamigrate.DataMigration` over the four encrypted rows and the blob. One chunk's batch holds the secrets, the staged keys, the quarantine records, the row deletes and the blob rewrite, so a crash leaves HEAD's rows or the finished result. Its Preflight refuses the upgrade (nothing written, a Fix on each blocker) for an undecodable blob, an encrypted row with no key, an unreadable `config.yaml`, and the two no-source shapes below (the second includes the viper-read `config.yaml` keys). |
| `config_strip.go`, `config_strip_owner_*.go` | M2b: `StripGapFill(ctx, FileOps, path, GapFillHolder)` (fourteen of the fifteen managed keys, case-insensitive, and `database_path` is always kept and listed in `Kept`; writes like HEAD's `writeFileAtomic`: follows a symlink, keeps mode and owner, falls back to an in-place write when the directory is not writable) and `ConfigCutoverDone`. `NewGapFillHolder` builds the holder over core's stores. F3-07 calls the strip after `ConfigCutoverDone` is true. |
| `head_legacy_keys.go` | The 127 setting names HEAD's `applySetting` maps onto a Config field: the only per-key rows HEAD's legacy path reads when there is no blob. |
| `stepids.go`, `levelsteps.go`, `cutoverlist.go` | The step IDs (the only place a literal lives), books' level step (`BooksLevelStep`, `BooksLevelStepRef`), M8 (`RewriteStep`, which returns `storage.RewriteStep`, F3-04's type) and `ValidateCutoverList`. |

## Names beyond the spec

| Name | What it is |
|---|---|
| `cutover.ConfigStepOptions` | `LevelStepVersion`, `StateDir`, `DatabasePath`, `ConfigFile`, `Legacy`, `AllowKeyRegen`, `Files`, `Logger`. `Legacy` is an accessor for books' legacy range: the runner hands a Step one source pair only, and M2 needs the other rows and the blob. `DatabasePath` is HEAD's database path, and is required: `ConfigStep` panics without it (as it does without `LevelStepVersion`), because an empty path silently drops the second key directory and a pre-state-directory install would be refused an upgrade HEAD itself boots. Its directory is the second place the key is searched. |
| `cutover.KeyGuardError`, `ConfigFileError`, `ErrNotStaged`, `ErrConvertInput`, `ErrInvalidCutoverList` | Errors callers match with `errors.Is` / `errors.As`. `ConfigFileError` is a `config.yaml` that exists and cannot be read. |

The tests inject a failure at each operation. |
| `books.config-cutover`, `books.level-1`, `books.rewrite` | M2a's, the level step's and M8's IDs. The level step is `books`'s step 69: LegacyCap (66) plus three. |

## Spec readings and rulings (each is a recommendation to write into 05-config §1.12.2 / §1.12.3; filed in todo.d)

| Topic | Reading |
|---|---|
| Undecryptable row against gap-fill | 05-config §1.12.2 is not silent here: it says a row that does not decrypt is quarantined and the secret marked unreadable. HEAD does otherwise (`LoadConfigFromDatabase` logs "will try config file fallback" and the file's value applies), and M2 keeps HEAD's behaviour (decision 1, parity wins over the text): the file's value is imported (the three file-named secrets), the ciphertext is quarantined sealed, and no unreadable marker is written. A row with no other source is quarantined sealed and its secret marked unreadable with `"key"` (no key to try) or `"corrupt"`, the two reasons `secrets` accepts. What M2 adds is visibility: the count `recovered-from-config-yaml` and the log line "secret <name> recovered from config.yaml after an undecryptable row", apart from an ordinary gap-fill. The spec text needs amending to match (todo.d). The overlay corpus gives exactly two quarantine records, matching F2-13's overlay report. |
| Gap-fill values are applied once | A value only `config.yaml` held is a candidate a replan cannot reconstruct: once the first run commits and the row is gone, the file's value looks fresh beside the value the row gave. A name that already holds content therefore means the value was applied (core's secrets are dark before the cutover), and the file's value is skipped with the count `gap-fill-already-present`, never quarantined. A crash between the chunk's commit and the done record would otherwise quarantine the file's value as a conflict (found by the crash matrix). Row-sourced and blob-sourced values still quarantine on a conflict. |
| Key guard | An encrypted row and no key file (or a key that is not 32 bytes) is a Preflight blocker: `storage.ErrCutoverBlocked`, exit 78, nothing written, naming `.encryption_key`, the directories searched and `ABO_CORE_SECRETS_ALLOW_KEY_REGEN`. With the override the rows become unreadable. An undecodable blob is a blocker too (HEAD refuses to run on it). |
| Key search order | HEAD searches `[StateDir, Dir(DatabasePath)]` (`bootSettings`'s `legacyKeyDir`, `guardAgainstKeyRegeneration`, `FindEncryptionKey`), and the first directory holding a key file wins, readable or not. M2 searches the same two in the same order and then `<root_dir>/.appdata/` as an extra fallback. The brief and the spec name only `<root_dir>/.appdata`; an install that predates the state directory keeps its key beside the database, and the first cut missed it. `ConfigStepOptions.DatabasePath` carries it and is required; F3-07 must pass HEAD's database path (the effective one: `DATABASE_PATH`, else `config.yaml`, else the stored value). |
| An upgrade with no source row | The runner steps M2 once per source key present (the blob and the four rows). With none present it never runs, and M2b would then strip `config.yaml` of values nothing imported. Preflight cannot make the runner run M2, and it is read-only, so it blocks, with the Fix "save settings once on the pre-freeze release, which writes the blob and the secret rows", in three cases. (1) No blob and `config.yaml` holds a usable `root_dir`, or one of the three file-named secrets while none of the four rows exists. (2) No blob and `config.yaml` holds a viper-read key (below). (3) No blob and a per-key `setting:` row whose name HEAD's legacy path maps onto a Config field (`head_legacy_keys.go`). **The viper-read keys.** HEAD points viper at `config.yaml` (`cmd/root.go`: `SetConfigFile`, `ReadInConfig`; `docs/configuration.md` documents `--config` at the file beside the database) and `configFromViper` reads ten of the managed keys from it: `playlist_dir`, `setup_complete`, `organization_strategy`, `scan_on_startup`, `auto_organize`, `folder_naming_pattern`, `file_naming_pattern`, `enable_ai_parsing`, `concurrent_scans`, `log_level` (`headViperFileKeys`, matched case-insensitively as viper does, a null being an unset key). With no blob they are HEAD's effective settings and M2 has nothing to receive them, so one whose value differs from HEAD's default blocks (`headIsDefault`, the same comparison the blob path uses); a value equal to the default loses nothing. Hence `enable_ai_parsing: true` (HEAD's default) is a no-op and `enable_ai_parsing: false` blocks. With a blob the blob shadows the file for all ten, as at HEAD, so nothing blocks. The refusal names keys, never values. **`database_path` is deliberately not in the set**: M2 never stores it, blob or no blob (rename table: convert `never-stored`, target `core.storage.path`, operator-layer), and the store being cut over is already at that path, so a file's `database_path` loses nothing at M2 (and M2b keeps the line, row below). A test pins a file holding only `database_path` as not blocked. The census does not block on every `setting:` row that is not the blob, a secret row, a marker or the embedding-index flag, as a literal census would: HEAD keeps at least ten other state rows under `setting:` on any real install (`purge_legacy_fp_done`, the remux and transcode flags, the pause gate, the scan stand-down, the repairs last-run keys, the retention flags), so that census would refuse every upgrade. With a blob the per-key rows are stale and HEAD ignores them too. **Preflight only.** The census runs in Preflight, and `core/kernel/cutover.go` (`cutoverBlockers`) skips Preflight once a cutover step has started; after that the planner (`buildPlan`'s `noBlobError`, which reads the same `fileBlobBound` set) refuses the blob-bound part again, but the three-secret-with-no-row and per-key-row shapes are Preflight-only. F3-07 must not rely on Preflight for a resumed cutover. |
| M2b verifies before it deletes | The ten managed keys HEAD wrote are always stripped: HEAD's viper does read them from `config.yaml`, but for nine of them every install M2 runs on has a blob that shadows the file, and Preflight refuses the no-blob case that would not (the row above), so the file's copy is dead by the time M2b runs. `database_path` is the exception: no blob can shadow it (the database must be open before the blob is readable) and M2 never stores it, so no destination can be shown to hold it and the strip always keeps it (`headNeverStrippedKeys`), listing it in `StripReport.Kept` whenever the file holds a value for it in any key case (a null or empty line says nothing and goes). A file whose only managed key is `database_path` is therefore never deleted, and a second strip reports `clean` with it still kept. Ruled in review round 3 (option B); see F3-07 item 6 for when it may be dropped. The five gap-fill keys (the three secrets, `root_dir`, `enable_ai_parsing`) are stripped only when their destination already holds the value, per `GapFillHolder`: a secret's name is set and readable (an unreadable marker, or a record whose ciphertext fails to decrypt, is `Meta.Set` true with `Meta.Err` set and holds no value, so a key an operator adds to the file afterwards is kept and listed), `root_dir` is in the blob or `core.library.roots` lists a root, `enable_ai_parsing` is effectively true (the effective value, not "a row exists": the importer skips a value equal to its default, and `true` is HEAD's default). Otherwise the line stays and `StripReport.Kept` names the key. A nil holder keeps all five. M2b does not import or quarantine: a quarantine exists only inside a runner chunk, so M2b keeps what it cannot verify and M2a's Preflight is what guarantees the import ran. A `config.yaml` that is a dangling symlink reads as absent; the "target cannot be resolved" branch of the strip is reachable only on a race between the stat and the resolve. |
| Strip failures | Not fatal to boot: `StripGapFill` returns an error and leaves the file as it was (or already stripped after the rename), and F3-07 raises a health warning, not an exit. Symlinked `config.yaml`: the target is stripped, never replaced by a regular file. A file that would end empty through a symlink is rewritten `{}`. A multi-document file is refused (HEAD reads only the first and a rewrite would drop the rest). Temp files an interrupted strip left (`.<name>.strip-*`) are removed on the next run. |
| `config.yaml` read errors | A file that exists and cannot be read is a Preflight blocker (Fix: make it readable by the service user, or move it aside) and a step error, never "no file": read as empty, M2 would skip its gap-fill imports and M2b would strip the file on a later boot. |
| URL userinfo | A credential in a URL must not land in a staged config row. Every URL-typed string leaf of a staged value is checked: the key itself when its HEAD name is `url`, `endpoint` or ends `_url` or `_endpoint` (derived by the generator, not listed), and the fields so named inside list and object elements (`whisper_endpoints[].url`). A well-formed userinfo moves to `<key>.userinfo` (`<key>.item-<n>.<field>.userinfo` inside a list) and the staged URL keeps no credential. A string with no `@` has no userinfo. With an `@`, M2 splits only what `net/url` reports; a URL that does not parse, or whose userinfo `net/url` does not report (a schemeless `user:pw@host:port` is an opaque URL), is quarantined sealed with the reason "the URL may carry a credential that could not be split out" and nothing is staged. A list is all-or-nothing: one element that cannot be proven quarantines the whole value, original included. F7-08 owns the class-i members' URLs, which stay in the blob for M6: `deluge_web_url`, `openai_base_url`, `metadata_sources[].base_url`, `path_aliases[].smb_url` and `ai_endpoints[].url`. A test pins that set, so a new class-i URL field fails it. |
| OAuth leftovers | `oauth_default_role` (when not HEAD's default `viewer`) and `oauth_allowed_emails` ride on the provider entries; with none built (sign-in off, or no client id) each is quarantined sealed, reason "oauth sign-in is disabled" or "oauth settings had no provider entry to attach to". A disabled provider's client id is quarantined as `{"client_id": ..., "client_secret_name": ...}`: its client secret still moved, to `core.auth.oidc.<id>.client_secret`, a name nothing references while sign-in is off, and the record pairs the two so the operator sees they belong together. |
| `FailClosed` keys | `core.auth.mode` and `core.http.basic_gate.enabled` are staged whenever the blob has their HEAD field, at the default too: the registry skips default-equal values except these, so a stored stricter value defends against a weaker operator value. HEAD always writes both fields (no `omitempty`). A blob with neither field stages nothing (ruling d). |
| Disabled OAuth | `oauth_enabled` false creates no provider entry (an entry would turn SSO on); the client ids are quarantined sealed with the reason "oauth sign-in is disabled". The client secrets still move (see "OAuth leftovers"). |
| Quarantine reasons | `QuarantineRecord.Reason` is one of fourteen fixed sentences (`reason*` in `config_plan.go`); it never carries a setting name's value, a secret or an `err.Error()`. A conflicting secret is quarantined under the legacy key it came from: the setting row's key, or `setting:config_blob#<member>`. A quarantined source key is deleted by the quarantine itself, so M2 does not delete it again (a chunk may write a key once). |
| (d) Fields absent from the blob | Stage nothing. R2's default drift against R0 is F3-07's oracle; M2 never stages HEAD's defaults, which would overwrite on a rerun. |
| Metadata credentials | A credential key is snake-cased (`apiKey` becomes `api_key`) into `integrations.metadata.<id>.credentials.<key>`; one that is no name segment afterwards is quarantined. |
| Not M2's | The per-endpoint `integrations.ai.<row id>.api_key` copies (05-metadata) belong to M6; the days-to-duration and updater-check zero semantics belong to 05-tasks and 05-updater; the instance rows (`metadata_sources`, `download_client`, `plugins`, `ai_endpoints`) have no canonical key until M6/F7-08, so their retired names only warn. |

## Spec discrepancies found

| Where | What |
|---|---|
| §1.12.2, undecryptable rows | The text says a row that does not decrypt is quarantined and its secret marked unreadable; HEAD gap-fills it from `config.yaml`. M2 follows HEAD (see the ruling above); the text is the one to amend. |
| Key search | The brief and §1.12.2 put the key under `<root_dir>/.appdata`; HEAD searches the state directory and the database's directory. See "Key search order". |
| §1.12.3 counts | The table body lists 18 `o` and 9 `s` rows, its header says 11 `s` and 16 `o`. `abs_jwt_secret` and `cf_policy_api_token` are classed `s` in the golden (env or file, never stored) though the body's rows say `o`; the golden keeps `s` and the spec body is the text to amend. The golden header counts: top-level 173 (k 134, s 11, i 9, o 16, x 3), two two-target rows, 129 sub-key rows, 3 virtual, 23 removed-key rows, 2 process rows, 330 in all. HEAD's `BindEnv` count is 155, not 142. |
| §1.12.4 | The example says `LOGIN_SATURATED_RATE` warns. `core.auth.login.saturated_rate` is `protect:"admin"` (`core/kernel/core_sections.go:457`), so its retired name is refused. The golden follows core. |
| Core registry at this base | It lacks the coined keys, and `config` refuses a retired name whose canonical path is not registered. `TestRenameTable_RetiredNamesAreValidForConfig` checks the shape; the schema-faithful half is F3-07's `TestRenameTable_EveryKeyRegistered`. |
| `OTEL_*`, `OPENAI_API_KEY`, `OPENAI_BASE_URL` | Ecosystem bindings: classed "kept" and left out of `RetiredConfigNames`. |
| Reads outside config | `BASIC_AUTH_PASSWORD`, `OPENAI_BASE_URL` and `ABK_ALLOW_ENCRYPTION_KEY_REGEN` are also read with `os.Getenv` outside viper at HEAD; F3-07 deletes those readers. |

## The test rig and what it does not cover

The rig opens the R2 corpus (`internal/books/testdata/r2corpus/{stage1,overlay}`) through the real `storage.Open` and the real kernel data-migration runner, with real `secrets.Open` and `config.Store` for the two `FailClosed` keys. Every other key goes to a table-backed double that accepts exactly the table's key, entry and fold targets and skips default-equal values with HEAD's defaults. Keys outside the two registered ones, and the entry-list targets (`core.library.roots`, `core.auth.oidc.providers`, `core.library.mappings`), are not schema-checked here. F3-07's real-registry run is the other half.

The golden's retired-name verdict (`refuse` or `warn`) is generated from the rows' `Admin` flag and the two registered `FailClosed` keys' tags. It is not asserted against core's real verdict for the keys the registry has, because `coreSections()` is unexported in `core/kernel` and this PR leaves `core/` untouched. F3-07's `TestRenameTable_EveryKeyRegistered` should also assert, for every key the real registry has, that the golden's `refuse` equals `config`'s verdict for that path.

`TestConfigCutover_RestoreDrill` is the binary-free half: the pre-migration checkpoint restores a store the pre-cutover build opens, byte-identical in books' legacy range, with nothing under core's keyspaces, and the frozen codec still decrypts the four rows. The pre-freeze binary half is F2-15's `TestRollbackRestoreBootsPreviousBuild`, which runs M2 once books registers it.

## For F3-07

1. Register `ConfigStep` (and read `ConfigCutoverDone` before calling `StripGapFill(ctx, nil, configFile, NewGapFillHolder(secretsStore, booksLegacyRange, effective))`, where `effective` reads a key's stored override or else its default from core's config store; log the returned `StripReport` (`Kept`, `InPlace`, `TempsRemoved`) and raise a health warning when it returns an error or `Kept` names a key other than `database_path`: a `Kept` of `database_path` alone is the expected state of an install whose file states its database path, item 6), pass `ConfigStepOptions.DatabasePath` HEAD's database path (required, a missing one panics), `BooksLevelStep`, and `RewriteStep` in books' cutover list in the order `ValidateCutoverList` enforces; convert the four rows' `store.BooksClaims()` entries to `ClaimRetired` (the tests do it themselves through `BooksSpec`).
2. Pass the settings key file and `config.yaml` as `storage.StateFile`s to the pre-migration checkpoint, so a restore brings the key back and the file M2b strips. The rig keeps the state directory on the real filesystem and the store on a memory filesystem, so it cannot show this.
3. Add the rows for the env names OWNER-04's P4 left unmapped (five at the time of the brief) when the owner records them; the golden changes with them.
4. Delete the `os.Getenv` readers named above, and the frozen `head_*.go` copies in R3.
5. Run `TestRenameTable_EveryKeyRegistered` (with the verdict assertion above) and a real-registry oracle run once the coined keys exist.
6. M2b always keeps `database_path` in `config.yaml` and lists it in `StripReport.Kept` (`headNeverStrippedKeys`): M2 never stores it (convert `never-stored`) and no blob shadows it, so the strip cannot show the value to be anywhere else, and the strip does not delete what it has not shown to be stored. The census leaves it out for the same reason. Once F3-07 has wired `core.storage.path` from the same source (the operator layer reading that file line, or whatever replaces it), it may drop `database_path` from `headNeverStrippedKeys`, which makes the strip remove the line like the other managed keys; the tests to change then are the `database_path` rows of `TestStripGapFill_VerifiesTheDestinationBeforeDeleting`, the `Kept` and file assertions of `TestStripGapFill` and `TestStripGapFill_HolderOverRealStores`, and `TestStripGapFill_WritesLikeHEAD`'s key counts. Until then F3-07's health warning must not fire for a `Kept` of `database_path` alone (item 1).
7. Surface M2's Preflight blockers to the operator as `storage cutover-blockers` rows: each carries its Fix.
