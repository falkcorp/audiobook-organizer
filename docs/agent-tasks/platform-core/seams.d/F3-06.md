# F3-06 seams and coined names

This file lists what the books config cutover PR (`internal/books/cutover`) added beyond 05-config §1.12 and the F3-06 brief: names the spec does not have, readings it took where the spec or the brief is silent, the spec discrepancies it found, and what F3-07 and later rows must do with it. Everything not listed follows the brief.

Nothing here runs on `main`: `books.Module()` registers none of it (`grep -rn 'cutover\.' internal/books/module.go | wc -l` prints 0, `ls internal/books/cutover/steps.go` finds nothing). F3-07 registers M2 and the books level step.

## What is here

| File | What it is |
|---|---|
| `rename_data.go`, `rename_table.go`, `rename_convert.go` | The generated rename table (`Table()`, `RetiredConfigNames()`, `CanonicalEnvNames()`), its golden `testdata/rename_table.golden` (330 rows), and the converters (`Convert`). |
| `head_*.go` | Frozen copies of HEAD's `Config` types, blob decoder, effective-value rules, AES-GCM decrypt, gap-fill reader, managed-key list, removed keys and env binding list. Each carries the "FROZEN COPY" header and is deleted in R3 with the other HEAD-format readers. |
| `config_plan.go`, `config_step.go` | M2a: `ConfigStep(cfg, sec, ConfigStepOptions)`, a `datamigrate.DataMigration` over the four encrypted rows and the blob. One chunk's batch holds the secrets, the staged keys, the quarantine records, the row deletes and the blob rewrite, so a crash leaves HEAD's rows or the finished result. |
| `config_strip.go` | M2b: `StripGapFill(FileOps, path)` (the fifteen managed keys, case-insensitive, 0600, atomic) and `ConfigCutoverDone`. F3-07 calls the strip after `ConfigCutoverDone` is true. |
| `stepids.go`, `levelsteps.go`, `cutoverlist.go` | The step IDs (the only place a literal lives), books' level step (`BooksLevelStep`, `BooksLevelStepRef`), M8 (`RewriteStep`, which returns `storage.RewriteStep`, F3-04's type) and `ValidateCutoverList`. |

## Spec readings and rulings (each is a recommendation to write into 05-config §1.12.2 / §1.12.3; filed in todo.d)

| Topic | Reading |
|---|---|
| Undecryptable row against gap-fill (TODO.md, "Rule whether an undecryptable secret row counts as empty") | HEAD's behaviour: a row that does not decrypt reads as empty, so `config.yaml`'s value (the three file-named secrets) is imported; the corrupt ciphertext is quarantined sealed; no unreadable marker. A row with no other source is quarantined sealed and its secret is marked unreadable with `"key"` (no key to try) or `"corrupt"`, the two reasons `secrets` accepts. The overlay corpus gives exactly two quarantine records, matching F2-13's overlay report. |
| Gap-fill values are applied once | A value only `config.yaml` held is a candidate a replan cannot reconstruct: once the first run commits and the row is gone, the file's value looks fresh beside the value the row gave. A name that already holds content therefore means the value was applied (core's secrets are dark before the cutover), and the file's value is skipped with the count `gap-fill-already-present`, never quarantined. A crash between the chunk's commit and the done record would otherwise quarantine the file's value as a conflict (found by the crash matrix). Row-sourced and blob-sourced values still quarantine on a conflict. |
| Key guard | An encrypted row and no key file (or a key that is not 32 bytes) is a Preflight blocker: `storage.ErrCutoverBlocked`, exit 78, nothing written, naming `.encryption_key`, the directories searched and `ABO_CORE_SECRETS_ALLOW_KEY_REGEN`. With the override the rows become unreadable. An undecodable blob is a blocker too (HEAD refuses to run on it). |
| `FailClosed` keys | `core.auth.mode` and `core.http.basic_gate.enabled` are staged whenever the blob has their HEAD field, at the default too: the registry skips default-equal values except these, so a stored stricter value defends against a weaker operator value. HEAD always writes both fields (no `omitempty`). A blob with neither field stages nothing (ruling d). |
| Disabled OAuth | `oauth_enabled` false creates no provider entry (an entry would turn SSO on); the client ids are quarantined sealed with the reason "oauth sign-in is disabled". The client secrets still move. |
| Quarantine reasons | `QuarantineRecord.Reason` is one of twelve fixed sentences (`reason*` in `config_plan.go`); it never carries a setting name's value, a secret or an `err.Error()`. A conflicting secret is quarantined under the legacy key it came from: the setting row's key, or `setting:config_blob#<member>`. A quarantined source key is deleted by the quarantine itself, so M2 does not delete it again (a chunk may write a key once). |
| (d) Fields absent from the blob | Stage nothing. R2's default drift against R0 is F3-07's oracle; M2 never stages HEAD's defaults, which would overwrite on a rerun. |
| Metadata credentials | A credential key is snake-cased (`apiKey` becomes `api_key`) into `integrations.metadata.<id>.credentials.<key>`; one that is no name segment afterwards is quarantined. |
| Not M2's | The per-endpoint `integrations.ai.<row id>.api_key` copies (05-metadata) belong to M6; the days-to-duration and updater-check zero semantics belong to 05-tasks and 05-updater; the instance rows (`metadata_sources`, `download_client`, `plugins`, `ai_endpoints`) have no canonical key until M6/F7-08, so their retired names only warn. |

## Spec discrepancies found

| Where | What |
|---|---|
| §1.12.3 counts | The table body lists 18 `o` and 9 `s` rows, its header says 11 `s` and 16 `o`. `abs_jwt_secret` and `cf_policy_api_token` are classed `s` (env or file, never stored). The golden header counts: top-level 173 (k 134, s 11, i 9, o 16, x 3), two two-target rows, 129 sub-key rows, 3 virtual, 23 removed-key rows, 2 process rows, 330 in all. HEAD's `BindEnv` count is 155, not 142. |
| §1.12.4 | The example says `LOGIN_SATURATED_RATE` warns. `core.auth.login.saturated_rate` is `protect:"admin"` (`core/kernel/core_sections.go:457`), so its retired name is refused. The golden follows core. |
| Core registry at this base | It lacks the coined keys, and `config` refuses a retired name whose canonical path is not registered. `TestRenameTable_RetiredNamesAreValidForConfig` checks the shape; the schema-faithful half is F3-07's `TestRenameTable_EveryKeyRegistered`. |
| `OTEL_*`, `OPENAI_API_KEY`, `OPENAI_BASE_URL` | Ecosystem bindings: classed "kept" and left out of `RetiredConfigNames`. |
| Reads outside config | `BASIC_AUTH_PASSWORD`, `OPENAI_BASE_URL` and `ABK_ALLOW_ENCRYPTION_KEY_REGEN` are also read with `os.Getenv` outside viper at HEAD; F3-07 deletes those readers. |

## The test rig and what it does not cover

The rig opens the R2 corpus (`internal/books/testdata/r2corpus/{stage1,overlay}`) through the real `storage.Open` and the real kernel data-migration runner, with real `secrets.Open` and `config.Store` for the two `FailClosed` keys. Every other key goes to a table-backed double that accepts exactly the table's key, entry and fold targets and skips default-equal values with HEAD's defaults. Keys outside the two registered ones, and the entry-list targets (`core.library.roots`, `core.auth.oidc.providers`, `core.library.mappings`), are not schema-checked here. F3-07's real-registry run is the other half.

`TestConfigCutover_RestoreDrill` is the binary-free half: the pre-migration checkpoint restores a store the pre-cutover build opens, byte-identical in books' legacy range, with nothing under core's keyspaces, and the frozen codec still decrypts the four rows. The pre-freeze binary half is F2-15's `TestRollbackRestoreBootsPreviousBuild`, which runs M2 once books registers it.
