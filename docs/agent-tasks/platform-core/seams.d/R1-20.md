# R1-20 seams and coined names

This file covers what the "core storage, dark" PR added beyond 05-storage §5S.3.1–§5S.3.7, §5S.3.12, §5S.3.15 (the `restorejournal` declarations) and 06 §6.5.1 P2/P4. It lists:

- names the spec does not have;
- readings it took where the spec or the brief is silent;
- where it drifts from the brief;
- the boot writers R1-21's crash matrix must label;
- the seams later rows build on: R1-21, R1-23, R1-24, R1-25, R1-15 and R2.

ABO is unchanged. ABO still opens its own store, and nothing in ABO opens a store through core.

## Names beyond the spec

The table leaves out the names that moved from `internal/compactprogress` with their meaning unchanged: `Step.Frame`, `Step.Interval`, `Result.Elapsed`, `Result.HasStats`, `LogReporter`, `FormatTick`, `FormatDone`, `HumanBytes`, and the `CompactionStats` fields. `storage.Stats` is an alias of `CompactionStats`.

| Name | What it is |
|---|---|
| `storage.OpenOptions` | What the kernel passes to `Open`: the resolved path, every owner of the build (enabled or not; `core/storage` is implicit), the binary ID, and the `core.storage.*` values of §5S.7. Zero values take the documented defaults. Unexported fields carry the vfs, free-space, same-device and chmod seams that in-package tests inject. |
| `storage.OwnerSpec{Owner, Spec, Enabled}` | One owner of the build. A disabled owner's claims are validated and recorded in the claim ledger, and its keyspace stays reserved. It gets no handle and runs no migration. |
| `storage.Opened`, `Open`, `(*Opened).Fresh`, `(*Opened).Prepare`, `(*Opened).Close` | The two-phase boot. `Open` is §5S.4 steps 1–5 (06 P2): open, guard, validate, and write nothing. `Prepare` is steps 6–7 (P4a): the fresh-install batch, or the checkpoint followed by the install marker, then the format ratchet. |
| `(*DB).Migrate` | §5S.4 steps 8–9 (P4b): every runnable step in DAG order, then `finish` (claim ledgers, store generation, books marker, sidecars, checkpoint completion). |
| `(*DB).Serves`, `(*DB).AppliedVersion`, `(*DB).CheckpointName`, `(*DB).Levels` | Boot results the kernel reads after P4b: the serving barrier, an owner's applied version, the checkpoint this boot took or reused, and the store-side and supported level vectors that `<ns>_storage_level` reports. |
| `(*Admin).CheckpointBytes() (open, completed uint64, err error)` | The two states of `<ns>_storage_checkpoint_bytes` (§5S.8). |
| `storage.VersionSource` | §5S.3.5's per-owner version-source adapter ("Bookkeeping") as an interface with two methods, `Applied` and `Stage`, both over the owner's own `LegacyRange`. It is the one member this row adds to the spec's `Spec` block. |
| `storage.AppliedStep` | One applied record. `HasCompat` is false for a record written before compat existed (a HEAD books record), which counts as Breaking. |
| `storage.StateFile{Label, Path}` | One file the pre-migration checkpoint copies (05-config §2.4's table). A missing file is skipped. One that exists but cannot be read halts boot before any write. |
| `storage.CensusEntry` | One partition of the census: a keyspace, one owner's claim interval, or the unowned keys. |
| `storage.SpecError`, `ClaimConflictError`, `ForeignKeysError` | Typed errors. Each lists every problem it found, and each matches its sentinel with `errors.Is`. |
| `ClaimMode.String`, `MigrationCompat.String`, `StepRef.String` | Log forms. |
| `internal/pebble.Guard`, `Guard.Decide`, `Decision{Store, Source, TooNew, Disagree}` | The one guard type of §5S.3.7 "One implementation", used twice: once with `MinReader` (the level vector) and once with `LegacyExact` (books' projection). `Store` is `max(stamp, sidecar)`. |
| `internal/pebble.WriteFileAtomic`, `SyncDir`, `ReadFile`, `ReadInt`, `WriteInt`, `ReadLevels`, `WriteLevels`, `FormatLevels`, `LevelsSuffix`, `CheckpointSuffix` | The sidecar and file helpers. Every durable file core storage writes goes through `WriteFileAtomic` (temp file, fsync, rename, directory fsync). |
| `Engine.NeedsRatchet`, `Engine.Ratchet`, `Engine.FormatMajorVersion` | The format pin's ratchet (§5S.4 step 7). It runs only after the checkpoint or on a fresh store. |
| `module.Manifest.Storage storage.Spec`, `module.Deps.Storage module.StorageHandles{Keyspace, Legacy}` | 06 §6.4.4's members at R1. `Indexes`, `Aux` and `Derived` arrive with their subsystems. |
| `kernel.Config.StoragePath` | `core.storage.path`, resolved by `app`. When it is empty the kernel opens no store. |
| `ModuleState.Disabled == "storage"` | The reason given for an enabled module that storage does not serve after P4b. |
| `coretest.Store`, `NewStore`, `DB`, `Path`, `Keyspace`, `Reboot` | The store fixture (04 §8.5 R1). It boots exactly as P2, P4a and P4b do, so a fresh fixture runs its Seed steps. `Reboot` is the next boot of a build, with a checkpoint when a step is pending. |
| `archtest.NoBatchByValue` | The vet-style check that `storage.Batch` is never copied by value. |

## Spec readings

| Topic | Reading |
|---|---|
| When the store opens | The kernel opens it whenever `Config.StoragePath` is set: `core/storage` is always an owner, and 05-metrics expects the storage families on such a boot. `app` resolves the path only when some module declares storage (the brief's "for apps whose modules declare storage"). An enabled module that declares storage on a boot with no path refuses the boot and names `core.storage.path`. `Describe` never opens the store (COR2-13). |
| `core.storage.path` | An absolute `<EnvPrefix>_CORE_STORAGE_PATH` wins, and a relative one is refused (§5S.4 step 1). Otherwise it is `<state_dir>/storage/main.pebble`, made absolute. |
| Serving barrier | After P4b, an enabled module that `DB.Serves` rejects is held. It is not registered, `ModuleState` reports it disabled with reason `storage`, and a WARN line "module not started" names its pending steps (§5S.3.5 "Barrier and serving"). |
| Handles of a module without storage | `Deps.Storage` holds zero values, and every method on them fails with `ErrInvalidKeyspace`. A module with a keyspace but no claims gets a `Legacy` that refuses every write. |
| Storage metrics | The gauges are recorded once, right after P5, because the Provider exists only from P5. `checkpoint_bytes` counts a record with `completed_at` set as `completed`, and every other record as `open`. |
| Fresh install | As 06 §6.5.1 P4a says: every step below an owner's lowest Seed step is recorded as applied without running, and so is every step of an owner with no Seed step. Only Seed steps and the steps after them run, in P4b. Tests that need a step to run on an empty store mark it `Seed`. |
| Range delete under claims | A legacy `DeleteRange` over `[lo, hi)` is allowed only when every byte of the range lies in intervals the owner holds. Shadow mode does not relax this. D-S2 (§5S.0) defines shadow only for single-key reads and writes and says nothing about range deletes, so the code refuses. See "Security fix folded in". |
| Late Stops versus storage close | `stopInBackground` keeps its goroutine's done channel on the kernel (`Kernel.lateStops`) instead of returning it. Its two callers, `stopHooks` and `awaitLateStart`, return before `closeCore` runs, so a returned channel would have to be threaded through both of their signatures. With a store open, `closeCore` waits for the channels within its one floor (`awaitLateStops`), then closes the store whether or not they finished, and logs any Stop still running at ERROR. With no store it does not wait, so R1-13's stop timings are unchanged. |
| State files | The kernel passes no `StateFiles` until config's state-file table is wired (R1-23 and F3). The checkpoint's copy mechanism, with its hashes and modes, is complete and tested. |
| Install ID of a marker-less store | It comes from the restore hand-over, else from an open record of the same store generation, else a new one (§5S.3.12 "How"). When the checkpoint records cannot be read, the boot fails before any write. Choosing a new ID instead would orphan the open record and take a new full checkpoint on every boot. |
| Scan errors | Keyspace and snapshot scans share one loop (`yieldScan`). It yields the iteration's error, or else the close's, once, as the last pair. Pebble reports a failed read through `Iterator.Close` too. After the consumer stops, the error is logged at WARN instead, since nothing is listening. |

## Drift from the brief

1. **P4b is wired, not only P2 and P4a.** `Migrate` runs the fresh install's Seed steps and `finish`. Without it a fresh store would never reach the shape 06 §6.5.1 states, and hello's seed would never run. R1-13's seams file also hands P2–P4 to this row.
2. **`internal/database/dbtest/newstore.go` is not rewired onto `coretest.Store`.** Doing so would make ABO's test stores open through core, which is the brief's first STOP condition. It belongs with R1-23, when ABO's store moves onto core.
3. **ABO's compaction-stats producers return `database.CompactionStats`.** `metafetch`, the maintenance deps and the server deps now return it, and `plugins/maintenance/db.go` converts it with `storage.Stats(...)`. The struct conversion is exact because the fields are identical. The db-optimize step passes a slog handler over its StandardLogger, so its output keeps the `db-optimize: <line>` format.
4. **The series golden covers two scopes**, the kernel and storage. A local `assertSeries` gathers both scopes, because `metricstest.AssertSeries` takes one.
5. **`core/kernel/supervisor.go` is edited.** It is an R1-13 file and not on this row's inventory, but R1-13's seams file gives this row the late-Stop wait.
6. **The `TestSpecGoBlocksCompile` pin is fixed in its own commit**, 85553aa28. The six commits from 8db968ef4 to 62b406408 build, but they fail that one pinned assertion. Folding the fix into 8db968ef4 would rewrite pushed commits, which the brief forbids. The coordinator can choose to fold it.
7. **testify is a core test dependency.** The moved compactprogress test uses it, so it is allowlisted in `core/archtest/thirdparty_allow.txt` for tests only.
8. **`core/scripts/ci/check-errcheck-ratchet.sh` is edited.** `storage.LogReporter.Log` joins core's exempt progress reporters. It is the root `.golangci.yml`'s `compactprogress.LogReporter` exemption, moved with the package. Every other errcheck finding this PR's code raised is handled, and core's count is back at its baseline of 1.

## R1-13 problem found

R1-13 built logging inside P5 (`services`), which comes after the point where P2 must open the store. 05-logging §4 steps 1–2 build logging first, and the store's open and guard lines need a logger. This row moves `buildLogging` to just after P1, ahead of P2. R1-13's `k.lifecycle.log = k.log` moves with it, still before any module code runs.

## Security fix folded in

The coordinator's review found that legacy `DeleteRange`'s coverage walk went through the shadow dial. A range that ran past the owner's claims could therefore delete foreign and reserved rows under `core.storage.claims.mode=shadow`. Commit bb9e88abe makes the walk refuse the whole range, staging nothing and returning `ErrOutsideKeyspace`, when any byte falls outside the owner's own intervals. That includes a gap, another owner's interval, or any overlap with `c/` or `m/`. D-S2 is silent on range deletes, so the code always refuses. If the spec later gives range deletes shadow semantics, that is a spec change and a code change together.

## Other findings

- **Pebble's MemFS under `-race`.** With invariants on, which `-race` turns on, Pebble's `vfs.MemFS` inverts every byte of the buffer passed to `Write` (XOR 0xff) after copying it. A state file hashed after the write therefore recorded a wrong SHA-256, but only in race builds. The checkpoint now hashes each chunk before writing it, through `io.MultiWriter(hash, file)`. Any later code that reuses a buffer after a vfs `Write` has the same hazard.

## Boot writers for 06 §6.5.1's writer table (for R1-21)

These are every durable write the boot makes at this row, in order. R1-21's crash matrix kills the boot and injects errors at each one.

| Phase | Writer | Durable operations, in order | A kill at each step leaves |
|---|---|---|---|
| P2 | `storage.Open` | None: it opens Pebble, runs the guard, and validates. | Nothing changed. |
| P4a, empty store | `freshInstall` | 1. One `Sync` batch: install marker, store generation (epoch 1), every level owner's stamp at the supported level, applied records below each owner's lowest Seed step (through `VersionSource` when set), dm `done` for each floor `Requires`, and the claim ledgers. 2. `.storage-levels` (atomic). 3. Each `LegacyGuard` projection sidecar (atomic). 4. The format ratchet. | Before 1: an empty store, which boots as fresh again. After 1, before 2–3: missing sidecars, which the guard reads as 0 and step 9 rewrites from the stamps. |
| P4a, non-empty store with work | `takeCheckpoint`: garbage sweep | Remove records without a directory, `RemoveAll` directories without a record and `<name>.tmp` directories, then fsync the directory. The scratch area is excepted. | Partial sweep: the next boot finishes it. |
| P4a | `takeCheckpoint`: reuse | When an open record has the same `install_id` and epoch, and its vector is an ancestor of the current one: rewrite `.migration-checkpoint` (atomic). | Old pointer: reused again next boot. |
| P4a | `takeCheckpoint`: new | Headroom and device checks, which write nothing. Then: `MkdirAll` of the checkpoint directory (0700), mkdir `<name>.tmp`, a Pebble `Checkpoint` `WithFlushedWAL` into `<name>.tmp/db`, the state files into `<name>.tmp/state` (each hashed and fsynced), chmod of the tree to 0700/0600, rename `<name>.tmp` to `<name>`, fsync the directory, the record `<name>.json` (atomic), then `.migration-checkpoint` (atomic). | Before the rename: a `.tmp` directory, swept next boot. After the rename, before the record: a directory without a record, swept. After the record: the attempt reuses it. |
| P4a | `writeMarker` | One `Sync` `Set` of `c/storage/install` on a marker-less non-empty store. It is the first store write after the checkpoint. | Before it: the next boot reuses the checkpoint, since the record carries the `install_id` the marker will get. |
| P4a | `Engine.Ratchet` | Pebble's format-version ratchet (Pebble's own manifest and marker writes). It runs only after the checkpoint or the fresh batch. | A store at the old or the new format, both readable by this build. |
| P4b | `runStep`, per versioned step | One `Sync` batch: `Up`'s writes, the version and applied record (or `VersionSource.Stage`), and for a level step the stamp. | Atomic per step. |
| P4b | `commitWithRaise`, a step that raises a level | The sidecars with the new level (atomic) **before** the batch commit. If the commit fails, the sidecars are rewritten from the committed stamps. | Between the sidecar and the commit: a sidecar ahead of its stamp. An older build refuses (`max`), and this build re-runs the step. The test hook `hooks.beforeStampCommit` marks the gap. |
| P4b | `runLegacy`, books legacy steps (none at R1) | The step's own writes, which are not atomic, then its bookkeeping in its own batch through `VersionSource`. | The step re-runs, so legacy steps must be idempotent (§5S.3.5 "Atomicity"). |
| P4b | `finish` (§5S.4 step 9) | 1. One `Sync` batch: claim ledgers (when changed), store generation (when new), and books' marker cleared when no Breaking step is pending. 2. Sidecars from the stamps (atomic). 3. `completeCheckpoint`: the record rewritten with `completed_at` and `delete_after` (atomic), then `.migration-checkpoint` with state `completed` (atomic). | After 1: the checkpoint is still open, and the next boot has nothing to run but completes it. After the record, before the pointer: the pointer still says open, while the record decides. |

## Seams for later rows

- **R1-21 (swap and crash matrix):**
  - The vfs is an unexported field of `OpenOptions`. The injector needs an exported or internal way to pass a fault-injecting vfs through `kernel.Config` into `storage.Open`. Prefer an internal package to widening `OpenOptions`.
  - `WriteFileAtomic` is the single place state-directory file writes happen, so it is the place to label them.
  - Pebble's own writes go through the same vfs.
  - `restorejournal` holds only types: the intent, the record and the swap journal's kinds.
- **R1-23 (ABO on core storage):**
  - Rewire `dbtest/newstore.go` onto `coretest.Store`.
  - Pass the state-file table as `OpenOptions.StateFiles`.
  - Give books its `VersionSource` over HEAD's migration-version rows and its `LegacyGuardProjection` over `<db>.storage-format`.
  - Strict claims for books.
- **R1-24 (checkpoint sweeper):**
  - The dated sweeper and `storage prune-checkpoints` read the records `takeCheckpoint` writes.
  - `delete_after` is written only by `completeCheckpoint` at this row. The open-checkpoint clock and the health tokens are R1-24's.
  - The garbage sweep in P4a stays as it is.
- **R1-25 (offline restore and reset):** `Admin` has no staging or swap method (04 §8.1 R1).
- **R1-15 (`coretest.MetricsProvider`):** the storage families are recorded by the kernel on its own Provider after P5. A Provider built by the fixture for a module test has no storage scope unless the test boots a kernel with a store.
- **R2:** `Spec.Derived`, `ReadAdapters`, `DataMigrations` and the cutover importers have no fields yet, so no declaration can set one and have it ignored.
