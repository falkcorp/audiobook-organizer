# R1-20 seams and coined names

This file covers what the "core storage, dark" PR added beyond 05-storage §5S.3.1–§5S.3.7, §5S.3.12, §5S.3.15 (the `restorejournal` declarations) and 06 §6.5.1 P2/P4. It lists:

- names the spec does not have;
- readings it took where the spec or the brief is silent;
- where it drifts from the brief;
- the boot writers R1-21's crash matrix must label;
- the seams later rows build on: R1-21, R1-23, R1-24, R1-25, R1-15 and R2.

ABO is unchanged. ABO still opens its own store, and nothing in ABO opens a store through core.

## Names beyond the spec

The table leaves out the names that moved from `internal/compactprogress` with their meaning unchanged: `Step.Frame`, `Step.Interval`, `Result.Elapsed`, `Result.HasStats`, `LogReporter`, `FormatTick`, `FormatDone`, `HumanBytes`, and the `CompactionStats` fields. `storage.Stats` is an alias of `CompactionStats`.

## Spec readings

| Topic | Reading |
|---|---|
| When the store opens | The kernel opens it whenever `Config.StoragePath` is set: `core/storage` is always an owner, and 05-metrics expects the storage families on such a boot. `app` resolves the path only when some module declares storage (the brief's "for apps whose modules declare storage"). An enabled module that declares storage on a boot with no path refuses the boot and names `core.storage.path`. `Describe` never opens the store (COR2-13). |
| `core.storage.path` | An absolute `<EnvPrefix>_CORE_STORAGE_PATH` wins, and a relative one is refused (§5S.4 step 1). Otherwise it is `<state_dir>/storage/main.pebble`, made absolute. |
| Serving barrier | After P4b, an enabled module that `DB.Serves` rejects is held. It is not registered, `ModuleState` reports it disabled with reason `storage`, and a WARN line "module not started" names its pending steps (§5S.3.5 "Barrier and serving"). |
| Handles of a module without storage | `Deps.Storage` holds zero values, and every method on them fails with `ErrInvalidKeyspace`. A module with a keyspace but no claims gets a `Legacy` that refuses every write. |
| Storage metrics | The gauges are recorded once, right after P5, because the Provider exists only from P5. `checkpoint_bytes` counts a record with `completed_at` set as `completed`, and every other record as `open`. |
| Fresh install | As 06 §6.5.1 P4a says: every step below an owner's lowest Seed step is recorded as applied without running, and so is every step of an owner with no Seed step. Only Seed steps and the steps after them run, in P4b. Tests that need a step to run on an empty store mark it `Seed`. |
| Range delete under claims | A legacy `DeleteRange` over `[lo, hi)` is allowed only when every byte of the range lies in intervals the owner holds. Shadow mode does not relax this. D-S2 (§5S.0) defines shadow only for single-key reads and writes and says nothing about range deletes, so the code refuses. See "Security fix folded in". |
| Late Stops versus storage close | `stopInBackground` keeps its goroutine's done channel on the kernel (`Kernel.lateStops`) instead of returning it. Its two callers, `stopHooks` and `awaitLateStart`, return before `closeCore` runs, so a returned channel would have to be threaded through both of their signatures. With a store open, `closeCore` waits for the channels within its one floor (`awaitLateStops`), then closes the store whether or not they finished, and logs any Stop still running at ERROR. With no store it does not wait, so R1-13's stop timings are unchanged. |
| State files | The kernel passes no `StateFiles` until config's state-file table is wired (R1-23 and F3). The checkpoint's copy mechanism, with its hashes and modes, is complete and tested. |
| Install ID of a marker-less store | An **empty** store takes the restore hand-over, else a new ID, never an open record's: a record beside an empty store belongs to a store set aside (review BLOCKER-3; 05-storage §5S.4 step 5 now says so). A **non-empty** marker-less store takes the hand-over, else the install ID of an open record of the same store, else a new one (§5S.3.12 "How"). "The same store" is `ofStore`: the record's `epoch`, `dir_dev` and `dir_ino` all equal the live store's. The record carries the DB directory identity its epoch was read against, so a different HEAD store swapped in at the same path between a crash (after the checkpoint, before the marker) and the retry, which lands on the same epoch number, adopts no record and reuses no checkpoint (coordinator, after the review; `TestSwappedStoreDoesNotInheritOpenRecord`). The reuse rule and `MarkServed` match the same way. Two limits remain: off unix the identity reads 0/0, so there the match is the epoch alone (the coordinator deferred `fsid_windows.go`; `todo.d/2026-11-08-core-storage-windows-dir-identity.md` gives the cost and the risk); and a store copied file by file into the same directory keeps the directory's identity, which the epoch design already accepts (§5S.3.7 store generation). When a record cannot be read, the boot fails before any write; one that reads but does not parse is logged and skipped (records are written atomically, so that is a hand edit or corruption; handed to R1-24). |
| DB directory identity | `dir_dev` holds `statfs`'s `f_fsid` (both words packed), not `st_dev`, which ZFS, btrfs, overlayfs and LVM can renumber across a reboot; `dir_ino` is the inode (verification review MINOR; 05-storage §5S.3.7). An all-zero `f_fsid`, and the unix platforms whose `f_fsid` core does not read (netbsd, solaris, illumos, aix, hurd), fall back to `st_dev`; on darwin `f_fsid`'s first word is the device number. The key keeps the name `dir_dev`: renaming it to `dir_fsid` would touch 05-backup's `backup.location.json` schema and the F4-11 brief, which other rows own, so it is left to the coordinator. The same-device check keeps `st_dev`. |
| `core.storage.checkpoint_dir` | The **parent**: the code always appends `.mediacore-checkpoints`, so `<db parent>` is the default and a setting naming it is harmless (review BLOCKER-4). `Open` refuses a relative value and an overlap with the store before it creates anything. The garbage sweep and the record reader touch only names of the checkpoint grammar `<YYYYMMDDTHHMMSSZ>-<8 hex>(.tmp|.json)`. 05-storage's "Where", "Scratch copies" and config rows say so. |
| Served write | `ready_at` is written at the start of `Run`, before start step (1), so before any module code that can write runs (coordinator, after the review). The review placed it after readiness and the first fix put it at start step 8, just before READY=1; that left a window in which a start hook or worker could write and the boot then die before step 8, leaving the record open, so the next upgrade reused a checkpoint older than those writes. 05-storage §5S.4 step 14 and 06 §6.5.2 step (0) say so, and 06's boot-writer table has the row. The brief said "in core/kernel/boot.go"; `Run` lives in `supervisor.go`. The pointer is left `open`: `served` is a record state only (§5S.3.7 table). Accepted cost: a previous-build boot that dies in a start hook before writing anything still marks the record, so the retry takes a fresh checkpoint instead of reusing one, and restoring the old one asks for `--accept-loss`. Two readings: "before any module code that can write" rests on 05-storage §5S.4 step 12 ("a module constructor writes nothing"), which no code enforces, since `Register` gets live storage handles in `Deps` (the enforcement, handles that refuse writes until the start of `Run`, goes to R1-23: `todo.d/2026-11-08-core-storage-register-writes-nothing.md`); and core's every-boot writers at P4d and P7 (seed roles, default grants, task definition snapshots, and from R2 `auth.BootWrites` and post-restore hooks) still run before the mark. They rewrite the same rows each boot, and the post-restore hooks run only on a restore boot, whose store is a new generation that no open record matches. |
| Stranded attempt | `Open` still writes nothing: `readBoot` only reads `c/storage/attempt`. `Prepare` completes the record before the checkpoint decision, writing checkpoint files only, and deletes the key after the checkpoint, so the checkpoint still holds every row as it was. It completes a record that is open or served (`pending()`), rewrites the pointer only while the pointer still names that checkpoint and says open, and only clears a key whose record is completed or gone. |
| Step handles | Inside a migration step, a batch (plain, indexed, of a `Sub`, of the `LegacyRange`), a `Bind` of a step handle into another batch, and a `Sequence` are refused with `errTxKeyspaceWrite`; a `Snapshot` with `errTxSnapshot`, since it would read the engine and miss the step's writes (review MAJOR-1). |
| Claim prefixes | A prefix must end in `:`, `/`, `_` or `.`, and one of only 0xff bytes is refused. 05-storage's comment named a `BareAllow` exception list that nothing defines; no ABO family needs one (`narrator_counter` and `sync_alias_use_seed_cutoff` are single keys, claimed with `Key`), so the comment now states the rule without it. |
| Legacy projection sidecar | An unreadable or unparsable `.storage-format` refuses the boot, because it is the projection guard's only input. The level sidecar `.storage-levels` keeps its log-and-continue: the store's stamps are read too, so the level guard still decides. |
| Scan errors | Keyspace and snapshot scans share one loop (`yieldScan`). It yields the iteration's error, or else the close's, once, as the last pair. Pebble reports a failed read through `Iterator.Close` too. A failed value read yields its error in place of the pair, never the key with a nil value. After the consumer stops, the error is logged at WARN instead, since nothing is listening. |

## Drift from the brief

1. **P4b is wired, not only P2 and P4a.** `Migrate` runs the fresh install's Seed steps and `finish`. Without it a fresh store would never reach the shape 06 §6.5.1 states, and hello's seed would never run. R1-13's seams file also hands P2–P4 to this row.
2. **`internal/database/dbtest/newstore.go` is not rewired onto `coretest.Store`.** Doing so would make ABO's test stores open through core, which is the brief's first STOP condition. It belongs with R1-23, when ABO's store moves onto core.
3. **ABO's compaction-stats producers return `database.CompactionStats`.** `metafetch`, the maintenance deps and the server deps now return it, and `plugins/maintenance/db.go` converts it with `storage.Stats(...)`. The struct conversion is exact because the fields are identical. The db-optimize step passes a slog handler over its StandardLogger, so its output keeps the `db-optimize: <line>` format.
4. **The series golden covers two scopes**, the kernel and storage. A local `assertSeries` gathers both scopes, because `metricstest.AssertSeries` takes one.
5. **`core/kernel/supervisor.go` is edited.** It is an R1-13 file and not on this row's inventory, but R1-13's seams file gives this row the late-Stop wait. It also hosts the served write (`markServed` at the start of `Run`, before start step (1)), because `Run` lives there and not in `boot.go`, where the review placed it.
6. **The `TestSpecGoBlocksCompile` pin is fixed in its own commit**, 0cbe9a30e. The six commits from 5a2a32808 to 250c9298a build, but they fail that one pinned assertion. Folding the fix into 5a2a32808 would rewrite pushed commits, which the brief forbids. The coordinator can choose to fold it.
7. **testify is a core test dependency.** The moved compactprogress test uses it, so it is allowlisted in `core/archtest/thirdparty_allow.txt` for tests only.
8. **`core/scripts/ci/check-errcheck-ratchet.sh` is edited.** `storage.LogReporter.Log` joins core's exempt progress reporters. It is the root `.golangci.yml`'s `compactprogress.LogReporter` exemption, moved with the package. Every other errcheck finding this PR's code raised is handled, and core's count is back at its baseline of 1.
9. **05-storage.md is edited** (version 1.14.1) with the code it describes: `checkpoint_dir` as the parent, the fresh store's install ID, `ready_at` and `MarkServed` (at the start of `Run`), the record's DB directory identity, `c/storage/attempt`, step handles, the claim-prefix rule, the projection sidecar and its refusal's remedy, the restore journal's JSON tags, the checkpoint copy rule (F2), the directory identity from `f_fsid`, and the new test rows.
10. **Files edited after the rebase onto R1-37, outside the inventory.** `docs/specs/platform-core/06-app-sdk.md` (main's 1.14.1 to 1.14.2): §6.5.2 start step (0), the served write, its row in §6.5.1's boot-writer table, and `App.Close` in §6.4.5. R1-37's `core/coretest/harness.go` and `harness_test.go` (each 1.0.1 to 1.0.2): the harness registers `App.Close` with `t.Cleanup`, and `TestHarness_NoProcessGlobals` boots each harness in a subtest. `core/app/app.go` gains `App.Close`, and `core/kernel/supervisor.go` gains `Kernel.Close`. `core/app/options.go` (1.0.0 to 1.0.1) gains `StorageFS`, and `core/kernel/kernel.go` gains `Config.StorageFS`. See "R1-37 interaction". The commit SHAs cited in this file are the rebased ones.

## R1-37 interaction

R1-37's harness (`core/coretest/harness.go`) merged while this row was in review. Its doc said the App had no storage at R1 and that "the row that gives the App a close path ... registers the cleanup". With this row, hello declares a keyspace, so every harness boot opened a Pebble store that nothing closed: `TestHarness_NoProcessGlobals` counted 2 goroutines rising to 262 over 20 boots, and `TestHarness_InSynctestBubble` panicked with a synctest deadlock on Pebble's goroutines. This row adds `App.Close` (over `Kernel.Close`), and the harness registers it with `t.Cleanup` as 06 §6.4.8 says; `TestHarness_NoProcessGlobals` boots each harness in a subtest so its cleanup runs before the count. Both tests passed 20 runs in a row, and 5 under `-race`. Then, as the coordinator decided, the harness store moved to in-memory Pebble as 06 §6.4.8 says: `app.Options.StorageFS` and `kernel.Config.StorageFS` carry a `storage.FS`, and the harness passes `storage.MemFS()` (`TestHarness_StorageInMemory`, `TestStorageFSKeepsTheStoreOffDisk`). The coordinator ratified `App.Close`; 06 §6.4.5 states that it closes what New built for an App that never Ran, does nothing once Run has started, and that Run after Close returns `errRunTwice`. R1-37's seams line that said the App has no close path now points here.

## R1-13 problem found

R1-13 built logging inside P5 (`services`), which comes after the point where P2 must open the store. 05-logging §4 steps 1–2 build logging first, and the store's open and guard lines need a logger. This row moves `buildLogging` to just after P1, ahead of P2. R1-13's `k.lifecycle.log = k.log` moves with it, still before any module code runs.

## Security fix folded in

The coordinator's review found that legacy `DeleteRange`'s coverage walk went through the shadow dial. A range that ran past the owner's claims could therefore delete foreign and reserved rows under `core.storage.claims.mode=shadow`. Commit 42d408784 makes the walk refuse the whole range, staging nothing and returning `ErrOutsideKeyspace`, when any byte falls outside the owner's own intervals. That includes a gap, another owner's interval, or any overlap with `c/` or `m/`. D-S2 is silent on range deletes, so the code always refuses. If the spec later gives range deletes shadow semantics, that is a spec change and a code change together.

## Other findings

- **Pebble's MemFS under `-race`.** With invariants on, which `-race` turns on, Pebble's `vfs.MemFS` inverts every byte of the buffer passed to `Write` (XOR 0xff) after copying it. A state file hashed after the write therefore recorded a wrong SHA-256, but only in race builds. The checkpoint now hashes each chunk before writing it, through `io.MultiWriter(hash, file)`. Any later code that reuses a buffer after a vfs `Write` has the same hazard.
