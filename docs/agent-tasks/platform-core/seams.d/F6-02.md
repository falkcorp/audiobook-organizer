# F6-02 seams and coined names

What F6-02 added beyond 05-realtime, the readings it took where the brief or the spec says nothing, where it differs from the spec's text, and what F6-03 (the kernel wiring) and the follow-up rows must know. The PR is dark: nothing imports `core/realtime`, `core/internal/sse` or `core/internal/eventhttp` before F6-03.

## Shape

- `core/internal/sse` is the engine: `Broker` (ring, caps, `Publish`, `Subscribe`, `End`, `WakeAll`, `Close`, `Wait`), `Subscriber.Serve` (the frame writer and heartbeat loop) and the `Judge` interface the hub implements per stream. It knows nothing of permissions or topics. `core/realtime` is the hub: catalog expansion, the per-event judge (`stream`), revalidation, metrics and the handler. `core/internal/eventhttp` only mounts the route. The three are the same layer (L6, `internal/sse` is listed in `archtest_layers_test.go`).
- Query parsing, refusals and the handler live in `realtime`, not `eventhttp`, because the refusals need `httpapi.WriteError` and the same checks must hold when the handler is mounted bare. `eventhttp.Register(g, Deps{Hub})` returns `ErrNoHub` for a nil hub.
- `tasks.RunViewRedactor()` is the `Redact` F6-03 and the task owner put on `core.task.run-changed.v1`: it decodes the payload as a `RunView`, applies `RedactRunView` and re-encodes; undecodable payloads become `{}`.

## Differences from the spec text

- **`NewHub` returns `(*Hub, error)`** and refuses a nil `Deps.Auth` or `Deps.Catalog` (a hub that cannot revalidate would keep a revoked credential streaming). `Deps.Auth` is the one-method `realtime.Revalidator` interface, satisfied by `*auth.Service`, so the hub is testable without an auth store.
- **`Deps.Bus` is gone; the hub exposes `Subscriptions()`.** The bus refuses `Subscribe` after `Freeze`, so spec section 5 step 3 (the hub subscribes itself when built) is impossible after P5. F6-03 builds the hub, calls `Hub.Subscriptions()` once (it returns an error the second time) and registers the result with `Bus.Subscribe("core", subs...)` before `Freeze`. It returns one raw subscription per Realtime topic, named `core.realtime.<slug>`, with `events.Coalesce(window)` where the topic declares one, plus `core.principal.invalidated.v1` and `core.rbac.changed.v1` when the catalog declares them.
- **The control topics are required.** `Subscriptions()` returns an error naming the topic when the catalog does not declare `core.principal.invalidated.v1` or `core.rbac.changed.v1`, unless `Options.AllowNoControlTopics` is set (a deliberately smaller catalog: a test, an App with no auth). F4-08 must declare `core.principal.invalidated.v1 {user_id, credential_id?, reason}` and `core.rbac.changed.v1 {generation}` without Realtime meta and publish them from `auth` and `rbac`. **F4-08 should also publish `core.principal.invalidated.v1` from `auth.SetRoles`** (today it bumps neither the credential epoch nor the rbac generation and publishes nothing): the hub does not need it to be correct (the per-heartbeat refresh below notices a role change within one heartbeat), but the event cuts the stream off at once.
- **`Deps.Refresh` is REQUIRED (`NewHub` refuses nil) and runs on every heartbeat.** `auth` has no re-resolve call (a key principal's scopes and a method's interactivity are the kernel's to rebuild), so the kernel supplies `Refresh(ctx, *Principal) (*Principal, error)`; it also runs once when a `core.rbac.changed.v1` arrives. A role assignment change moves neither the epoch nor the generation, so a stream's rights could otherwise stay stale for its whole life; there is no "no Refresh" mode. Topics the principal no longer holds are dropped from the stream's set and from its broker interest (so they stop filling its queue); losing one the client named exactly ends the stream `permission_revoked`; another user, a nil principal or one failing AnyAuthenticated ends it `permission_revoked`; a definite error ends it `credential_revoked`; a panic ends it `permission_revoked` (a panic in `Revalidate` too). A store failure is retried on each heartbeat and ends the stream on the third in a row. **While a refresh is failing the stream stays open and delivers nothing** (`events_filtered{reason=stale}`): what it may see is unknown, so it fails closed. The withheld events are not replayed, so on the first successful refresh the stream is sent `core.stream.reset.v1{gap}` and the client refetches. A widening is not picked up until reconnect: the topic set is fixed at subscribe and only ever shrinks, so a dropped topic that is later regranted stays dropped on that stream (`TestHub_RegrantAfterDropStaysDroppedUntilReconnect`). **Cost for F6-03:** one `Refresh` per open stream per heartbeat (default 15 s); the kernel's closure should read the user from a cache or the store cheaply (one keyed read) and must be safe for concurrent calls.
- **Revalidation runs on the heartbeat and on invalidation events**, not on every event. `Heartbeat` and `WriteTimeout` are at most one minute each (the heartbeat bounds how long a revoked credential or a role change can go unnoticed, and the write timeout how long a client that stopped reading can hold a stream's goroutine).
- **Coalescing is the bus's.** `events.Coalesce` (latest wins per key per window) is used as is. Not done: a "deleted supersedes updated" merge for `books.book.changed.v1` (needs a `core/events` hook; for the row that declares that topic) and `core.realtime.max_coalesce_keys` (the bus coalescer has no key bound), so that config key is unconsumed.
- **Bounds beyond the spec**: `MaxPayload` (default 256 KiB, ceiling 4 MiB): an oversize event is dropped and counted, never truncated; query at most 8 KiB, 32 topic and 32 exclude patterns of at most 128 bytes, one key of at most 256 bytes, `last_event_id` at most 128 bytes (the header wins). A resume id longer than a real one, malformed, or past the ring head is a `gap` reset; another process's nonce is `restart`.
- **Per-subscriber queue and replay.** The queue holds pointers to shared ring entries. A resume's replay is a separate snapshot bounded by `RingSize` (not `ClientBuffer`). An overflow drops the queue and any undelivered replay, owes one `reset{overflow}` frame, and the new event starts a fresh queue; the dropped count is the `events_dropped{reason=overflow}` counter.
- **Frames.** Control frames (`opened`, `reset`, `closed`) carry no `id:` line, so they never move the resume point; their order is `retry`, `opened`, then `reset`. Frames omit `actor`, `run_id` and `trace_id`. A payload with a newline is compacted onto one `data:` line, or withheld if it is not JSON, so no payload can inject a field or frame. `Visible` and `Redact` receive copies of the payload because the ring's bytes are shared; a `Redact` that returns invalid JSON withholds the event (`events_dropped{reason=redact}`) and a panic in either is contained (`filter_panic`). `Key` is not redacted: owners must not put user-identifying text in an event key.
- **Buckets.** The per-user cap is keyed by user and credential class: `apikey`, `session`, or `method:<m>` (a module compat method, an extension). The auth-disabled principal has no bucket and only `MaxClients` bounds it. A principal with neither a user nor `auth_disabled` opens nothing.
- **`*` with zero Realtime topics is an empty stream**, not a 400; `module.*` matching nothing is a 400 `unknown_topic`.
- **A shutdown or a revocation interrupts a write in flight.** `end()` (and so `Close`, `Run` and every revocation) moves the stream's write deadline to now through its `http.ResponseController`, so a client that stopped reading cannot hold the stream for a whole `WriteTimeout`; the stream then returns the end reason, not `write_timeout`. **F6-03 must assert that `SetWriteDeadline` and `Flush` are supported on the real chain** (every wrapper in `httpmw` and the router must implement `Unwrap() http.ResponseWriter`, as the compression and access-log writers do); a chain that hides them silently restores the `WriteTimeout` bound and drops the per-write deadline entirely (the stream tolerates `ErrNotSupported` so tests run on recorders).
- **The hub copies each event's payload at ingest** (`bytes.Clone`): the ring outlives the bus call and the bus's bytes are shared with every other subscriber of the topic.
- Extra errors `ErrNotPermitted`, `ErrNotReady` and `ErrClosed`; `Hub.Subscribers()`; two extra dropped reasons (`oversize`, `redact`).

## Tests and what they do not yet cover

- The cells run over a real `auth.Service` and rbac compile (sessions, keys, revoke, `SetStatus`), over a bare hub in a `synctest` bubble (deadlines, coalescing windows, strikes, shutdown budget; the bubble itself fails on a leaked goroutine), and over the sse engine directly. Cross-topic order is not preserved by the bus (a goroutine per topic), so tests compare sorted topics.
- `TestCatalog_RedactAppliedOnEverySurface` runs the real `taskhttp` `GET /runs/{id}` with a fake `tasks.Client` over a fixture topic. `core.task.run-changed.v1` is not a live topic yet: **F6-03 reruns the run-redaction and `TestHub_TaskTopicVisibleWithoutTasksView`-shaped cells over the real topics.**

## Review round 1 (T3 review of #4620)

- **M1 fixed in this PR**: a role assignment change reached no open stream (probe `TestProbe_SetRolesNotNoticed`). Now `Deps.Refresh` is required and runs every heartbeat (`TestHub_RoleChangeReachesAnOpenStream`), a nil `Refresh` is a `NewHub` error, and an undeclared control topic is a `Subscriptions` error unless `AllowNoControlTopics`.
- m1: dropping the `allowed`-set check in `Deliver` is NOT equivalent: after a drop and a regrant it would resurrect the topic. `TestHub_RegrantAfterDropStaysDroppedUntilReconnect` pins the shrink-only rule. m2: fail closed while Refresh fails (above). m3: ingest copy. m4: `TestHub_ConfinedAndEmptyPrincipalsNeverStream` now includes a query over 8 KiB, so the handler guard is what answers a refused caller (403 before 400).
- n1: ceilings on `Heartbeat` and `WriteTimeout`. n2: `Subscriber.SetInterest` narrows the broker interest when rights narrow. n3: interrupt a write in flight on end (above). n4: `Check` is panic-contained and fails closed.
- **Hand-off: `core.task.log-appended.v1` needs a declared `Redact` from its owner (F2-xx, the tasks module).** A task log line can carry text a non-manager must not read; the hub applies whatever `Redact` the topic's catalog entry declares and nothing else, so an undeclared one streams the raw line to every holder of the topic's permission. Fixture topic `core.task.log-appended.v1` in the tests has none.
