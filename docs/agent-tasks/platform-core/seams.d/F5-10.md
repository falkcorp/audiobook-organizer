# F5-10 seams and coined names

What the dark conversion of maintenance file group 5 (14 definitions in `itunes_clone_into_library.go`, `itunes_playlist_import.go`, `itunes_regroup.go`, `library_state_repair.go`, `mark_missing_files.go`, `merge_same_path_dupes.go`, `metadata.go`, `metadata_cache_reap.go`, `missing_file_audit.go`, `missing_file_repair.go`, `missing_file_repoint.go`, `move_book_file_rows.go`, `narrator_purge_empty.go`, `narrator_split_joined.go`) added beyond 05-tasks and the F5-10 brief, the readings it took where they say nothing, and what F5-18 must do with them. Everything not listed follows the brief as written, and the layout copies F5-08's (`kinds_t6_g3.go`).

## Deviations from the brief

1. **Cores are plain package functions**, not `(p *Plugin)` methods, so R10 is structural. Shells (`(p *Plugin) runX`, `(p *Plugin) xKind`) stay methods. The HEAD-signature wrappers that only tests called (`planMarkMissingFiles`, `planMergeSamePathDupes`, `planMetadataCacheReap`, `planMissingFileRepoint`, `auditMissingFiles`, `classifyMissingRows`, `moveBookFileRows`, `mbfEnv`, `regroupSDKReporter`, `t6g5Progress.Step/Finalize`, `t6g5OpsStore`, `t6g5SeqPool`) are deleted: their tests call the `...Via` cores through env builders in `kinds_t6_g5_envs_test.go`, and the move kind's HEAD-shell tests run `moveBookFileRowsDef().Run`. `t6g5PlanMissingFileRepair` is the former `...Via` form, renamed with the group prefix.
2. **Extra files** beyond the brief's list: `kinds_t6_g5_atoms_test.go`, `export_t6g5_test.go` (the settings.manage scopes are copied because `internal/books` imports this package), `kinds_t6_g5_envs_test.go`, `kinds_t6_g5_native_test.go`, `kinds_t6_g5_units_test.go`, this note, `scripts/deadcode-baseline.txt` (rows removed with the wrappers) and `testdata/fixer_stores_allowlist.txt` (two sink entries removed with `t6g5OpsStore` and the chapters accessor).
3. **Re-signed internal helpers.** Several helpers (the repoint planner, the move-book-file-rows helpers, the regroup snapshot and apply, `applyRegroupGroup`, `mbfPlanOne`, `mbfResolveOwners`, `applyLibraryStateRepair`, `libraryStateRepairScope`, `bookAuthorNamesForSplit`, `libraryStateRepairStore`) now take a narrow reader or reporter instead of `*Plugin` or the wide store. `mbfProgress` is gone: the HEAD move shell sets `env.Progress` from `t6g5MbfHeadProgress`, which logs a failed progress write the way HEAD did. The regroup user-state methods the apply reaches are the narrow `t6g5RegroupUserState`/`t6g5RegroupStateProbe` interfaces; `(*Plugin).t6g5RegroupUserStateFor` is nil-deps-safe. The clone store keeps only the `OpsStore` narrowing its readers need.
4. **Shared batch-write bodies.** `writeBookFileBatch` and `prewriteHeartbeat` (`bookfile_batch_write.go`) are thin wrappers over `writeBookFileBatchVia` and `prewriteHeartbeatVia`, which take a liveness/progress sink; `t6g5WriteBookFileBatch` and `t6g5PrewriteHeartbeat` call the same bodies with the env as the sink. One body carries one set of tests (the abort-after-N-rows rule, the per-row stamp). The report-path helpers are still re-declared as `t6g5` variants, for a later unification.
5. **Clone `icStore` keeps its field names** (`OpsStore`, `ChapterReader`) because existing tests build it with a keyed literal; forwarding methods carry the rest.
6. **Clone mode.** A native preview clears apply/rollback/repair whatever params say; a live run must name exactly one, else it is refused. The native decode refuses only `dry_run` and `dryRun` for clone: `apply`, `rollback` and `repair` are HEAD's own selectors (the shell's `LiveOneOf`), not the run's mode.
7. **Regroup writer** carries only `t6g5RegroupUserState` (`NewUserStateProbe`, `CarryStateThenHardDelete`, `HardDeleteWithoutUserState`), the three calls the empty-book delete makes. The merge store's other methods are not reachable from a native run, and the compiler enforces it: `UserProgress` is no longer on the writer.
8. **Dropped HEAD fields.** `FormerIDs` on four definitions, `Liveness`, `Cancellable`, `Plugin` and the metadata refresh's `0 6 * * *` schedule have no native counterpart here; the native kind takes `sched(kind)` and F5-18 decides.
9. **No kind in this group checkpoints.** None calls `Checkpoint` or `Restore`, so there is no restore test; each ResumeDrop kind is re-run from the start by design.
10. **Identifier prefix.** Every new top-level name carries `t6g5`. Renamed to meet that: `t6g5MbfHeadProgress`, `t6g5RegroupUserState`, `t6g5RegroupStateProbe`, `t6g5ApplyRegroupPlan`, `t6g5PlanMissingFileRepair`. The method that returns the `t6g5RegroupUserState` interface is `(*Plugin).t6g5RegroupUserStateFor`, so it no longer shares its name with its result type.
11. **Fallbacks kept from HEAD.** `t6g5HeadOpID` falls back from the reporter's ID to the run context's; the clone user-state lookup keeps HEAD's fallback.

## Readings taken

- **Resource names.** Only the constants of `pkg/ops/effects.go` are used, written as `string(ops.ResX)` in every `Effects` and as `ops.ResX` in the method table. A coined name DOES compile (an untyped string constant converts to `ops.Resource`), so nothing is claimed of the compiler. `TestT6G5Resources_EveryNameIsAnOpsConstant` checks the values: it parses `pkg/ops/effects.go` for the constants and compares them with the method table, the outside-write list, every kind's write set and the expected write sets in the test tables, and it walks the parsed source of this row's files (`t6g5SourceFiles`, the files that build its kinds, plus `kinds_t6_g5*.go`, tests included), requiring the second argument of every `tasks.Res` call to be `string(ops.<constant>)`. The walk is scoped to this row on purpose: F5-07, F5-08 and F5-09 build their Effects from typed `ops.Resource` helpers (`tasks.Res("books", string(r))`), which a whole-package walk would fail when they stack. Stores with no constant are declared under the nearest one, not coined: `narrators`, `book_narrators` and `chapters` under `books`; `user_preferences` and `user_playlists` under `user_state`; the store's derived secondary keys (`ident:` rows, path and version-group indexes) under the row that owns them, since `indexes` names the search and memdb index set; **`operations` is the undo journal and nothing else**: `opchange:` rows and the merge sibling-move journal (`merge:sibling-journal:<id>`, the undo payload of one merge), while a record keyed on a book or a version group is `books` (owner ruling): `path_history:` rows (a per-book path log, like `book_ver:` history) and the merge `group-redirect` keys that `putGroupRedirects` writes. The merge journal pointer (`RecordJournalPointer`) is a real OperationChange, so `operations`. **Narrator writes (`CreateNarrator`, `DeleteNarrator`, `SetBookNarrators`) are stamped `books`.** The first mapping hides which table a purge or split touches and the second makes playlist-import's whole write set `user_state`; both are accepted (PR body, Review decisions).
- **Known cost of the `user_state` mapping.** Playlist-import now waits behind every `user_state` writer (clone, regroup, merge-same-path-dupes and main's dedup-books, merge-chapter-groups, backfill-itunes-positions), and they wait behind it. The conflict is false (the merge user-state store never touches playlists); correctness is unchanged.
- **Clone declares `files`.** A live clone apply reflinks audio into the library tree (`CloneBookIntoLibrary`, the mixed kind's `Reflink`) and rollback removes the clone files, so clone must not run beside another bytes-on-disk writer (the empty-folder sweep, organize-mess cleanup). **F5-18 obligation:** the plain `os.Remove` calls that delete clone files (mixed-apply cleanup, rollback's file removal and its empty-directory removal in `itunes_clone_into_library.go`) run outside the writer seam and so outside the fence. They must go through the writer, or be covered by the `files` declaration at the point the fence lands; as it stands a fence landing between the last writer call and those removes does not stop them. The report TSVs other kinds write do not count, as `relink-report` declares nothing.

- **Stand-down.** A live run of clone, mark-missing, repoint, move-book-file-rows, purge, split (`t6g5NativeLease`) and metadata-refresh (`t6g5NativeHold`) refuses without a configured scan key ("no scan stand-down key configured") rather than writing unguarded. playlist-import, regroup, repair-library-state, merge-same-path-dupes and metadata-cache-reap take no stand-down, as at HEAD, and a native run of them does not either.
- **Concurrency.** Loops with HEAD `Concurrency: n` become `tasks.Fixed(n, reason)`, the missing-file stat sweeps and the clone repair keep their pools; zero stays sequential.

## Writer stamping contract (method to resource)

F5-18's one books writer must stamp each `t6g5Writer` method with exactly the resources in `t6g5WriterResources` (`kinds_t6_g5_resources.go`), or a live run is refused with `ErrOutsideEffects`. The table is production code, read by the native tests' spy and by the equality test, so test and writer cannot drift: `TestT6G5Resources_TableCoversEveryWriterMethod` keeps it equal to the interface by reflection, and `TestT6G5Resources_EffectsAreTheUnionOfTheirMethods` asserts each writing kind's declared write set equals the union over the methods its writer interface lists plus its reasoned outside writes (`t6g5OutsideWriterWrites`). Every live native test also checks the spy's recorded resources are a subset of the kind's Effects. Because a table that is only compared with itself can be edited to agree (the row, the Effects and the expected set together), the store-level tests in `kinds_t6_g5_storediff_test.go` take their evidence from the store: they snapshot every Pebble key around a native run (all eleven writing kinds: clone apply and rollback, regroup, repair, move, mark-missing, repoint, reap, purge, split, playlist-import and merge-same-path-dupes, the last through a real `merge.Service`; each writer call is also attributed to its own method), name each changed key's registered family (`database.KeyFamilies`), map it to a resource (`t6g5KeyFamilyResource`, fail-closed on an unmapped family), and require the result to be a subset of both the kind's Effects and the resources of the methods the run called. `TestT6G5Native_EveryWritingKindPreviewWritesNothing` runs each writing kind in preview over its live fixture and requires no writer call and no changed key. The union equality is why a kind declares more than its core's own calls suggest: a method's whole call chain counts.

Trace of every method to its store writes: 30 methods, one row each in `t6g5WriterResources`; the table below groups methods whose chains are the same. Store methods all have one implementation, `PebbleStore` in `internal/books/store`.

Round 7 changes the evidence, not the table: the store tests now (a) attribute the keys each writer call changed to that call's method, with nested calls attributed to their own method (CarryStateThenHardDelete's `del` is DeleteBook's), and require them inside that method's row; (b) map `act:` to `activity`, `setting:` to `settings` and `system:journal_clock` to `operations`, and exclude only named store-maintained keys (`t6g5ExcludedKeys`, each with a reason) plus the run's own `act:op:<runID>`; the clone's own undo record is a mapped `user_state` write that cannot count as evidence for a must-write `user_state` (`t6g5SelfRecordKeys`); (c) cover playlist-import and merge-same-path-dupes (the latter through a real `merge.Service`), and run a finished-loser carry through regroup and through the clone rollback so the `CarryStateThenHardDelete` and `CarryStateBeforeHardDelete` rows are each observed writing `books`; (d) seed rows in resources a kind must not write (repair: a metadata cache; reap: a live book, its file row and a live cache). No row changed. Every table row is now observed by a fixture: `CarryStateBetweenLiveBooks` by a clone rollback whose last step fails with a source ABS does not list (the state is carried back onto the live clone), and the `operations`, `external_ids` and `user_state` entries of `MergeBooks` by a same-path merge whose books each have a version-group sibling, an external id and listening state. Three blind spots remain in a before/after key diff, by construction, and no production code was added to the store write path to close them (owner ruling): (1) a write that leaves a key's bytes unchanged is invisible; (2) the delete of a key that was already absent is invisible; (3) a key created and deleted within one call leaves no trace. A row can therefore be too narrow only for writes of those three shapes. Run-time write observation (the F5-18 fence stamping each call with its resources) is where they close.

Resources that changed in round 6: the three `CarryState*` rows gain `books`; new row `SetLibraryStateOrganized` (`books`); `repair-library-state` drops `metadata_cache` (it now calls the narrow method, not ModifyBook, and its store-diff test requires exactly `books`); `path_history` and the merge group-redirect keys are filed under `books`, not `operations`, with no row change (every declaring kind already had `books`). Resources that changed against the round-4 table (round 4 declared fewer): `CloneBookIntoLibrary` gains `authors`, `user_state`, `operations`; `DeleteBook` gains `authors`, `field_states`, `embeddings`, `metadata_cache`, `user_state` and loses `book_files` (it never writes file rows); `DeleteBookFilesByIDs` gains `books`, `fingerprint_index`; `UpdateBook` and `ModifyBook` gain `metadata_cache`; `MergeBooks` loses `book_files`. Kinds whose write set widened as a result: clone (`fingerprint_index`, `field_states`, `embeddings`, `metadata_cache`, `operations`), regroup (`authors`, `field_states`, `embeddings`, `metadata_cache`), repair-library-state (`metadata_cache`, removed again in round 6). `merge-same-path-dupes` keeps `book_files` as a head-parity declaration (`t6g5HeadParityDeclared`, not an outside write): HEAD's own definition declares it and the native kind keeps that capability, though no writer method carries it and nothing on its path writes it.

Confidence: high on every row except the `UpdateBook`/`ModifyBook` cache stamp (medium: conditional on the written fields). The table is deliberately conservative: a composite row such as `CloneBookIntoLibrary` or `MergeBooks` does not list the conditional `metadata_cache`, `field_states` or `embeddings` writes of the ModifyBook, UpdateBook and DeleteBook calls inside it, because the kinds that call them (clone, regroup) declare those names through the methods that carry them directly. Not opened: `identTx.stage` internals, `followUsersLocked`'s full body, `BatchCreateBookFiles` past `stagePIDTransfer`.

Writes made outside the writer that the table does not carry: the report TSVs of reap, mark-missing, repoint, recover-missing-files and merge-same-path-dupes (per-row report files, excluded as above), and clone's three `os.Remove` calls (listed in `t6g5OutsideWriterWrites`, F5-18 obligation above).

## Stacking obligation (not done here)

`ops.ResSyncIdentity` ("sync ids and their pointers on book rows") arrives with F5-06, and `backfill-sync-ids` and `merge-chapter-groups` declare it. This row writes sync identity and files it under `user_state` because the constant does not exist on its base. When the two stack, add `ops.ResSyncIdentity` to:

- the table rows `CloneBookIntoLibrary` (through `merge.FollowVersionHandover`), `MergeBooks` (`MintOrGetSyncID`, `FollowMerge`), `CarryStateBeforeHardDelete`, `CarryStateBetweenLiveBooks` and `CarryStateThenHardDelete` (the follower's sync redirect);
- the kinds clone, merge-same-path-dupes and regroup, and their `t6g5Wants` rows;
- the family map `t6g5KeyFamilyResource` (`sync_item:`, `sync_file:`, `sync_alias_use`), and this note's vocabulary bullet.

Until then dispatch sees `backfill-sync-ids` as disjoint from those three kinds.
