## Spec readings

- **Embed inputs of a package with a `no matching files found` error.** `go list` reports no `EmbedFiles` for such a package, so a second pattern of the same package (say `docs/x.json`) would escape the check. For these packages every `EmbedPattern` is resolved on the file system (`all:` stripped, globbed under the package directory): a pattern naming a listed output is tolerated, a pattern that matches nothing and is not a listed output fails ("matches no file"), and the files of every other pattern are judged against `.dockerignore`. This is the spec's "embed patterns of packages that report ..." made concrete; `test_docs_fails_even_beside_a_listed_pending_output` pins it.
- **Test embeds are not judged.** Only `EmbedFiles` (non-test) is read: the image build runs `go build`, never `go test`, so `TestEmbedFiles` and `XTestEmbedFiles` cannot break it. `testdata` below the root is in the context anyway (`.dockerignore` patterns are anchored at the root).
- **Other embed errors fail.** A package error that mentions `pattern` or `embed` and is not "no matching files found" (an invalid pattern, an embedded directory with no files) is reported; any other package error is left to the compile gates.
- **Which module's list judges which package.** Root packages are judged against `scripts/ci/embed_build_outputs.txt`; core packages against `core/scripts/ci/embed_build_outputs.txt` prefixed with `core/` (03 §3.2 item 4: core's own list), but both are matched against the single repo-root `.dockerignore`, so a core package embedding `core/web/packages/*/dist` content that is not on core's list fails at the root.
- **Dockerfile cross-check.** A "go build stage" is a stage with any `RUN` containing `go build` (continuations joined, comments skipped). A `COPY --from=` counts when its destination, resolved under the stage's `WORKDIR` **at that instruction**, stays inside it; a destination outside (an absolute path such as `/usr/local/bin/x`) is not an embed output. Both `Dockerfile` and `Dockerfile.build-cgo` are compared with the one list, separately.
- **Dockerfile `COPY` form.** Both Dockerfiles already copied core's go.mod and go.sum (commit 88a962140) as `COPY core/go.mod core/go.sum core/`; the brief's literal `./core/` form is applied (identical effect), and a test pins that it precedes `go mod download`.
- **Job condition.** `docker-image` runs when the classifier's `go` or `web` output is true. The brief says "every PR that touches a non-doc file"; a `web/` only change leaves `go=false` and the image embeds `web/dist`, so the web output gates it too (docs-only PRs skip, `merge_group` fails open and runs).
- **Run 2 volume ownership.** A fresh named volume at `/config` (a path the image does not create) is root-owned and the image runs as uid 1000, so the step chowns it once, the way a deployment does. The key lands beside the database because `config.EnsureSecureStateDir` cannot create `/var/lib/audiobook-organizer` for uid 1000 and falls back to the database's directory (checked against a locally built binary: `--db <dir>/x.pebble` puts `.encryption_key` in `<dir>`).
- **`embed_build_outputs.txt` headers.** The root list carries a `#` header (comment lines are ignored by the reader). Core's list is created **empty** (zero bytes, as the brief's acceptance requires), so it cannot carry the four header lines; it is exempt like `core/go.sum` and the baseline files.
- **Docker is not exercised locally.** See the PR's verification notes: the local engine was unavailable, so the image builds and both runs are proved only by `docker-image` on the PR.
