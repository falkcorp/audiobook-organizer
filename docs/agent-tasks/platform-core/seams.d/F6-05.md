# F6-05 seams and coined names

What F6-05 added beyond the spec text of 05-logging §5 ("Live tail"), the readings it took where the brief is silent, the one approved exception to its file list, and what F6-03 (the kernel wiring) must know. The PR is dark: nothing in `core/kernel` declares `core.log.recorded.v1` or calls `logjournal.StartTail`.

## Shape

- `logjournal.TailSpec(otherUser)` is the catalog entry the kernel declares under owner `core`: Realtime, never Durable, `Permission: core:system.manage`, with a `Visible` and a `Redact` that carry the other-user rule. `logjournal.StartTail(l, bus, settings)` registers a second log tap named `journal-tail` (its own goroutine and bounded queue; drops count under that tap name). It is a second tap and not a hook in the journal tap, so F5-15's `tap.go` is untouched and a slow bus costs the journal nothing.
- `logjournal.RecordView` is the wire payload and, since round 2, also the query route's item type: `loghttp` no longer has its own `recordView`. One function builds a view from a stored record (`logjournal.ViewOf`) and one blanks `user_id` (`logjournal.BlankUserIDs`); the route and the tail both call them, so the two cannot drift. `TestJournalTail_SameViewAsQuery` still pins that the stream payload and the route's item agree.
- `StartTail` refuses a second enabled tail on the same `Logging` with `ErrTailStarted` (also after `Stop`: the drop counter that marks the name as taken lives as long as the logger). The check is not atomic, so it guards a sequential second call.
- With authentication off nothing holds `core:system.manage` (it is AuthRequired), so the tail delivers nothing: the same deliberate tightening as the query route.
## What F6-03 must do

- **Declare after the module predicate is collected, before `Freeze`.** `TailSpec` takes the predicate by value, and nil flags nothing. Today the kernel only records `Registrar.LogOtherUserData` (`kernel.consume`: its consumer, the journal, "lands later"). So F6-03 declares `logjournal.TailSpec(pred)` after P7 has collected the module's predicate and before `bus.Freeze()`. Declared earlier with nil, the tail silently never flags another user's line; the topic cannot be declared after `Freeze`.
- **Call `StartTail` after `bus.Freeze()` (and `Open`), not merely "after the bus exists".** A publish before the bus is frozen is rejected ("the bus is not frozen yet"). The bus logs a rejection once per topic, forever, so an early start would also silence the later report of a rejection for another reason. Start it with the journal's own settings, once (`ErrTailStarted`).
- **Size the hub's ring for the tail.** Every journal-level record takes a slot in the hub's one shared ring (`realtime.Options.RingSize`, default 1024, at most 65536). At info level the tail will dominate it and shrink the `Last-Event-ID` resume window of every other realtime topic, such as task progress, to almost nothing under log load. F6-03 sets `RingSize` for this or decides the loss is acceptable; it is outside F6-05's code.
- **Wire the bus's logger to the same `Logging` knowingly.** The bus's drop warning is a log record, so it re-enters the tail. `TestJournalTail_BusWarningsReenterBounded` pins that the loop is bounded: one warning per subscriber per minute, however many events drop, and no deadlock.

## Approved exception: the predicate's input is one normalised record (STOP 2)

The brief says the tail applies the other-user predicate "exactly as F5-19's query route calls it". Measured with a recording predicate, it did not: the route handed the predicate the store's record (typed values, logged order, a repeated key kept), while the tail can only rebuild a record from the wire view (every value text, keys sorted, a repeated key collapsed to its last value). A predicate that switched on `Value.Kind()` could under-flag on one surface, and one that called `Value.Int64()` would panic (the hub withholds on a panic).

The coordinator approved option 2: both surfaces now hand the predicate `log.PredicateInput(rec)`, one function in `core/log/otheruser.go`, so there is one normalisation and not two copies that happen to agree. Its contract is documented on `log.OtherUserPredicate`: text-only values, flat dotted keys, sorted by key, the last value of a repeated key wins.

Files outside F6-05's brief file list that this exception edits:

- `core/log/otheruser.go` (the contract text and `PredicateInput`), with a new `core/log/otheruser_test.go`.
- `core/internal/loghttp/routes.go` (F5-19's file): `q.Hide` calls the predicate through `log.PredicateInput`; and, from round 2 (the coordinator's decision to unify now), the local `recordView` type is gone in favour of `logjournal.RecordView`, and `viewOf` builds through `logjournal.ViewOf` and `logjournal.BlankUserIDs`.

Every production implementation of the predicate was checked first: there is none in the repository. `Registrar.LogOtherUserData` (`core/module/registrar.go`) only stores a predicate a module hands it, and no module registers one yet (06's books module will). The only implementations are test doubles (`namesSelina` and the recording predicates in `core/internal/loghttp` and `core/internal/logjournal` tests, `core/module/module_test.go`), none of which reads a value's Kind or a typed accessor. The 06 books predicate must read attributes as text; `TestPredicateInput` and `TestJournalTail_PredicateSeesSameRecordAsQuery` pin what it will be shown: every field of the record (module, subsystem, level, time, trace and span ids, message, attributes), on both surfaces, and `TestJournalTail_PredicateReadsModuleSubsystemAndLevel` pins that a predicate classifying by those fields filters end to end through the hub.

F5-19 has no seams file in `seams.d`, so the note for its `routes.go` edit lives here.

## Deadcode baseline

The dark tail is unreachable from every main until F6-03 wires it, so `Deadcode Ratchet` listed 11 new identifiers (`StartTail`, `TailSpec`, `TailTopic`, `Tail.Stop`, `Tail.Counters`, `Tail.offer`, `RecordView.record`, `viewOf`, `mayReadUsers`, `tailVisible`, `tailRedact`, all `core/internal/logjournal.`; round 2 renames `viewOf` to `liveView` and adds `ViewOf` and `BlankUserIDs`, which only dark code calls, so the baseline carries those names instead). With the coordinator's approval, and as F5-13, F5-15 and F5-16 did for their dark code, they are added to `scripts/deadcode-baseline.txt` (outside the brief's file list). F6-03 makes them reachable and the pruning bot then lowers the baseline again.
