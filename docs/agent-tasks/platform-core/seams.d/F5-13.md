# F5-13 seams and coined names

F5-13 converts the 45 T7 definitions (44 in `internal/server`, 1 in `internal/scheduler`) to native `books.<ID>` kinds, plus `books.library.scan-full` beside `books.library.scan`: 46 native kinds. They are dark: nothing registers them before the tasks flip (F5-18). This file lists the readings the row took where the brief is silent, the helpers it added, and what later rows build on.

## Seams

- Each package has its own `kinds_t7.go` foundation: `t7Env` (log, progress, cancel, op id, result, items, checkpoint), `t7Hold` and `t7StandDown`, `t7Deps`, `t7Common(head, sched)` and the list function `t7KindList(s, deps, sched)` with a `t7Kinds` method. The scheduler's copy is smaller (it needs one kind) and is a copy, not a shared package: a shared package needs an `internal/arch` layer entry. Drift protection is each package's hand-written `TestT7ServerKinds_MatchHEADDefs` and `TestT7SchedulerKinds_MatchHEADDefs` (expectations are not derived from the helpers) and `TestKindAtomScopes_MatchBooksAtomTable` in each package, which compares the scope table the copy keeps (`t7AtomScopes`) with `books.AtomTable` (an external test: `internal/books` imports both packages, so the table cannot be read from them).
- Every definition is split: `<x>Def()` holds HEAD's literal (so `t7Common` derives title, help, timeout, key, priority, resume, permissions and readiness from it), the HEAD shell's Run calls a shared core, and `<x>Native(deps, sched)` is the native shell over the same core. A core reaches stores and writers only through its env.
- Coarse writer and store methods. Where a definition drives an engine in another package or a Server helper, the core calls one method and HEAD's implementation calls the existing function. F5-18's native writer must implement each, over the run's gated writer:
  - Library, files and batch: `Ready` (the metadata fetch service check, asked right after the stand-down and before anything is reported, as HEAD did), `OpenBatchApply`, `RunQueuedApply`, `OpenAdvance`, `FetchForBookIDs`, `FetchAll`, `EnqueueContinuation`, `RunHarvest`, `FinishHarvest`, `PerformScan`, `PerformOrganize`, `Transcode`, `RecordVersion`, `FetchBookByTitle`.
  - Authors: `MergeAuthors`, `AuthorMergeDone`, `AuthorsResolved`.
  - Dedup: `ScanBookDuplicates`, `ScanSeriesDuplicates`, `FilterReviewedAuthorGroups`, `PreviewSeriesDedup`, `MergeBooks`, `CleanupMergeCandidates`, `CombineBooks`, `ApplySeriesDedup`, `PruneSeries`, `MergeSeries`, `NormalizeSeries`, `InvalidateSeriesCache`, `OrganizeBook`, `WriteBackBooks`, `InvalidateDedupCache`.
  - Reconcile: `RunReconcileScan` (store), `ExecuteReconcile` (writer).
  - Scheduler: `Ready` (store: the fetch service exists; `t7Deps.Store` is set and a native run refuses without it) and `RunUpgrade` (writer).
- The scan kinds (`dedup.book-scan`, `dedup.author-scan`, `dedup.series-scan`) publish their result to the dedup list cache and write an activity row in HEAD. Natively they drop both and return the result from the Task. The cache feed is a flip or handler decision (F5-18), not this row's.
- Native `dedup.series-dedup` Preview reads through the store side: no writer is built and no activity row is written (HEAD wrote one for a preview).
- `dedup.series-normalize` declares `Writes(series)` as HEAD does, but its organize and write-back also write books and files. Kept 1:1 with HEAD (R7); declare the larger set when the write set is next reviewed.
- `t7ScanController` adapts a `t7StandDown` to `dedup.ScanStandDownController`, which `dedup.DedupSeries` and `MergeSeries` take and acquire and renew themselves. HEAD passes the server (which is the controller); a native run passes the adapter over `rc.StandDown`.
- A native run may lose the result when `Run` returns an error: HEAD stored a report and then failed the run (scan-apply, purge, reconcile apply). The kernel may discard a result returned with an error; F5-18 must decide whether those kinds return the result and no error.
- `folder-auto-scan` starts a goroutine that calls `CheckBookDuplicates` after the core returns, as HEAD does. Natively that is a write through the run's writer after the run has ended. Not changed here.
- `diagnostics.ai-analyze` has a 25h HEAD timeout; the kernel refuses a Timeout over `tasks.MaxTimeout` (24h), so `t7Common` clamps it.
- Counter labels that read running counters are dropped natively (the kernel's per-item label is pure), as in F5-11.
- `sdk.NewProgress` now takes a `sdk.ProgressSink` (the one method it calls, `UpdateProgress`) instead of the concrete reporter interface, so a native env can feed it.
- `t7Store` and `t7Writer` are composed from sub-groups (`t7StoreLibrary` into files, AI and batch, and the same for the writer) to stay under the interface-width ratchet (8 elements).
- `internal/books/testdata/tasklint_exempt.d/F5-13.txt` is deleted, as the brief says. The brief's acceptance line "no added or modified entry file" cannot hold: `F5-18.txt` listed `internal/server/batch_apply_refusal.go`, a file F5-13 now fixes, and `TestTasklint_F518ListsOnlyFlaggedFiles` fails on a line for a file with no finding ("delete the line"). That one line is removed (verified: restoring it fails the test).
- The deadcode ratchet: 90 new identifiers (the foundations and the natives, unreachable from every `main` until F5-18 registers them) are added to `scripts/deadcode-baseline.txt` as a sorted union, as F5-09 and F5-11 did.
- `.golangci.yml`: the errcheck exclude list (bucket f, progress and log reporting) gains `t7ProgressReporter.Log` and `.UpdateProgress` in both packages (they return nil unconditionally) and `sdk.ProgressSink.UpdateProgress`, and drops the entries for `extraOpsProgressAdapter`, which this row removed as unused. Without them the errcheck ratchet reads 714 against main's 678. The four `_ = hold.Finish(nil)` discards are `errhandling.MustLog` calls: a lease lost mid-run is worth a log line.
- HEAD's env closes over its Reporter instead of taking method values (`rep.IsCanceled`, `rep.Checkpoint`): HEAD's bodies and tests run with a nil Reporter until the first call that needs one, and a method value on a nil interface panics when it is taken.
- Checkpointing: HEAD has five checkpointing definitions (library.scan, metadata.batch-apply-cached, library.bulk-write-back, metadata.candidate-fetch, catalog.harvest-authors). The env carries no Checkpoint; `t7HeadCheckpointing` adds it in the first four shells, and catalog.harvest-authors sets `env.Checkpoint` in its own shell, saving HEAD's params exactly as HEAD did. The env has no Checkpoint by default because `internal/arch` `TestResumeRestartDefsCheckpoint` reads any def whose Run reaches a Checkpoint call as one that resumes.
- Two resource names were not in `pkg/ops/effects.go`: `ai_scans` (the AI author scan's store, written by `ai.author-scan` and `ai.author-scan-apply`) was coined by this row; `collections` is HEAD's own literal from `collections.refresh-relative-dynamic`. Each is now a constant (`ops.ResAIScans`, `ops.ResCollections`) and is listed in books' `taskResourceKinds` (`internal/books/module.go`). That list has to carry them: the kernel refuses a registration whose kind writes a books resource kind books did not declare, and `TestRegister_DeclaresEveryResourceKind` keeps the list equal to the `pkg/ops` vocabulary.

## Scheduling the kernel cannot express (F5-18 decision 5)

HEAD's write-set gate skips a definition that declares no `Writes`, and its `ConcurrencyKey` can be empty (no key at all). R5 maps an empty key to the zero key, which is `Key(Kind)`, and R7 gives every kind whose body writes a declared write set. Five HEAD definitions rely on the old behaviour on purpose; so do the stand-down holders. `core/tasks` cannot express it, and this row does not hack around that: the declarations are the R5/R7 ones and the differences are listed here for F5-18.

What the kernel does (read, not changed):

- The key is per definition: `executor.go:86-88` sets `x.key` from `Common.ConcurrencyKey`, or `Key(Kind)` when it is zero, and the dispatch gate (`core/internal/executor/dispatch.go`, `gate`) defers a run when any running run has the same `d.key`, before it looks at write sets. There is no per-run key.
- The write-set gate defers a run whose write set overlaps any running run's, including a run of the same kind. `{books, books, ""}` overlaps every `books` ref, so `Subjects` (`SubjectsFunc`, 5T.3.4) narrows a run only against other runs that also narrow to IDs; it cannot get a run past a scan, whose write set is the whole `books` kind.
- `Effects` is required. A `ReadOnly` kind has a writer that refuses writes (`ErrOutsideEffects`), so a kind whose body writes cannot declare none.
- The gate runs before `Run` starts, so a kind that calls `rc.StandDown` is held behind a running run with an overlapping write set before it can reach the call. Nothing exempts a stand-down holder.

Natively, then (HEAD in brackets):

- `metadata.apply-when-scanned` and `library.organize-when-scanned` [no key, no Writes, "MUST run while a scan is running"]: write sets `t7ApplyPathWrites()` overlap `library.scan`'s and `library.scan-full`'s, so a queued apply or organize waits for the whole scan; and every queued run of the same kind runs one at a time (zero key).
- `library.import` [own key `library.import`, "never queues behind a full library scan"]: it runs the scan's `PerformScan`, and its write set is `libraryScanEffects()`, which overlaps the scan's; it queues behind a running scan or scan-full.
- `library.folder-auto-scan` [empty key, "parallel per-folder scans are fine"] and `library.transcode` [empty key, "transcodes can run in parallel"]: the zero key serializes runs of the same kind, and the whole-kind write sets would overlap each other even without it. Both also overlap the scan's write set, so they queue behind a running scan.
- Nine stand-down holders: `metadata.batch-apply-cached`, `metadata.batch-save`, `library.bulk-write-back`, `entities.author-merge`, `entities.author-reclassify`, `ai.author-scan-apply`, `dedup.series-dedup`, `dedup.series-merge` and `scheduler.metadata-upgrade` all declare a write set that overlaps the scan's (`books`, `authors` or `series`). A running `library.scan` therefore holds them at dispatch, where HEAD's acquire quiesced the scan and waited for it to park ("A running scan does not make the op refuse"). The scan is hours long. (`library.bulk-metadata-fetch` also holds the stand-down, but its write set is `operations` and `metadata_cache`, which the scan does not write, so it is not held.)

The same holds, without a HEAD comment that says it was intended, for every other kind in "Writes found" whose set names books, book_files, authors, series, files or activity (for example `library.organize`, `library.ai-parse`, `dedup.book-merge`): HEAD's gate never saw a write set for them, and natively they queue behind a running scan.

Structural options for F5-18, kernel or owner decisions (none is this row's):

1. Let a definition opt out of the static key, or give each run its own. Necessary for the parallel kinds, not sufficient: their write sets still overlap each other and the scan's.
2. Narrow the write set per run with `Subjects` (a book id, a folder). Sufficient only between two runs that both narrow; it does nothing against the scan.
3. Let a stand-down holder pass the write-set gate against the run whose key it stands down (`dispatch.go`, `gate`), so it reaches `rc.StandDown`. This is the only option that restores the nine holders.
4. Make a kind's write set attribution-only (not gating), as 5T.3.4 does for the kernel's data-migration kinds, so the two when-scanned kinds, `library.import`, `library.folder-auto-scan` and `library.transcode` run as at HEAD, serialized by their key alone (with option 1 for the parallel ones). The spec gives this to kernel-registered kinds only.

Until one of these lands, F5-18 should not flip these kinds expecting HEAD's scheduling; the todo fragment carries the decision.
