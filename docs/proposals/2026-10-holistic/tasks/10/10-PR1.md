## Goal
After this PR, a torrent imported through `POST /api/v1/deluge/discover/import` is linked to its book twice: the `BookVersion` created for it carries the infohash in `TorrentHash` (so the existing Pebble index `idx:bv:torrent:<hash>` and tier 1 of discovery work for the first time), and the `BookFile` row carries it in `DelugeHash` (so the deluge-hash memdb index and later cleanup see it). The hash is validated and cross-checked against Deluge before it is trusted. Nothing else about import changes, and no Deluge storage move can be triggered.

## Steps
1. **Request field.** Add `TorrentHash` to `ImportFileRequest` tagged `json:"-"`, with a comment: set only by trusted Go callers, validated and lower-cased by the caller, never bindable from the `/import/file` request body; `ImportFile` checks only its shape and ignores an empty value. In `ImportFile`, if non-empty, reject (return an error before any write) anything that is not exactly 40 or 64 lowercase hex characters, with a package-private check. (`internal/importer` does not import `internal/deluge`, and this PR does not add that dependency; the server test below asserts both validators agree on a table.)
2. **Version.** At `service.go:332` pass `TorrentHash: req.TorrentHash` and `Source: "deluge"` when the hash is set, `"imported"` otherwise (unchanged). A fingerprint match (previously purged or blocked content) stays a logged warning that does not fail the import, but it is checked before `CreateBook` and the hash is then dropped: no version is created for it and the file row gets no `DelugeHash`. A hash that a live version already holds (`versions.LiveTorrentHolder`) is also checked before `CreateBook` and dropped with note `torrent already linked to another book`, but the new book still gets an ordinary `imported` version: `CreateBookVersion` overwrites the one-to-one index, so linking it again would move the torrent away from the book that owns it. An unreadable index drops the hash with note `torrent index not readable`. `ImportFileResponse.TorrentLinked` is true only when the version carrying the hash and the file row carrying it were both written; `TorrentLinkNote` says why not.
3. **File row.** In the `bf` literal set `DelugeHash` to the hash only when step 2 created the version carrying it (`versionLinked`); when the hash was dropped (purged, already linked, unreadable index) or the version failed, the file row gets no `DelugeHash`, so the two halves of the link never disagree in the file row's favour. Do not set `DownloadHash` (a different concept that nothing reads) and do not set `ImportedFromDelugeAt` or `DelugeOriginalPath` (the file has not been copied; the later copy sets them).
4. **Handler.** In `handleDelugeDiscoverImport`:
   - if `req.TorrentHash != ""`, `deluge.NormalizeTorrentID`; a malformed value is `400`;
   - if `versions.LiveTorrentHolder` finds a live version holding the hash, `409` with code `TORRENT_ALREADY_LINKED` and the holder's `book_id`, before any Deluge request and before any book is created (a retry or double POST must not duplicate the book); an index read error is `500`. A discover `content_path` is the whole torrent, so one torrent never legitimately feeds two imports;
   - `client := getDelugeClient()`; if nil, import proceeds unlinked with `torrent_linked:false` and a note `deluge not configured`;
   - otherwise `client.GetTorrentDetailContext(ctx, hash)` with a 15 s timeout derived from the request context: `ErrTorrentNotFound` is `400` (`torrent_hash does not name a torrent in Deluge`); any other error proceeds unlinked with a fixed note, `deluge timed out` for a deadline and `deluge unreachable` otherwise; the upstream error is logged through the app logger and never returned (it names the Deluge URL); never fail the import for that;
   - cross-check: the cleaned `content_path` must equal `filepath.Join(save_path, f.Path)` for some entry `f` of the torrent's `Files` (the route imports one file, so an exact file match is the strong check); no match is `400` (`content_path is not a file of that torrent`). Compare cleaned absolute paths, never raw strings;
   - only a verified hash is placed in `ImportFileRequest.TorrentHash`. Keep the existing `torrent_hash` echo in the response and add `torrent_linked bool` (from `ImportFileResponse.TorrentLinked`, i.e. what was written) and `torrent_link_note string` (omit when empty). The existing permission and the `deluge_discovery_enabled` gate are unchanged.
5. **Do not** add any network call to `ImportToLibraryWith` or to the tag-write guard path: resolving a hash by `save_path` there (as the spec's file table suggests) would put a Deluge round trip and a heuristic match inside every guarded tag write. Rows that already exist without a hash are 10-PR2's job. Report this deviation from spec §4 PR 1 in the hand-back.
6. **Findings to report, not fix** (they change behaviour for every import, so they are the owner's call with their real cost):
   - `CreateIngestVersion` runs at `service.go:332`, before `CreateBookFile` at 397. When it runs, no `book_file` row exists, so its row-link and `file_hash` stamp (`ingest.go:107-140`) find nothing: it logs `no book_file row matched the ingest path; version is orphaned` for every import, `VersionID` stays unset on the file row, and `FileHash` stays empty. Consequence for the cleanup fixer: imported rows are `unverifiable` (no pristine hash) until a hash backfill runs. Cost of fixing: move the `CreateBookFile` block above the `CreateIngestVersion` call and compute `FileHash` there; it changes every import, not only torrent ones, and contradicts the "VersionID deliberately left unset" comment at `service.go:367`.
   - The purge-fingerprint refusal in `CreateIngestVersion` happens after the book row is created. (Addressed for the torrent link in review round 1: `ImportFile` now runs the check before `CreateBook` and never links purged content; the book row itself is still created, as before.)
   - Writing `DelugeHash` without `ImportedFromDelugeAt` puts the row into `GetBookFilesNeedingDelugeImportCore` (`memdb_reads.go:1295`, `pebble_store_bookfiles.go:1119`). The only consumers are manual: `POST /api/v1/discovery/import` (`deluge_discovery.go:117`), the `deluge.centralize` op and `maintenance.bulk-deluge-import` (none is scheduled: `grep` shows no schedule). This is the intended copy model (import in place, copy into the library later, D57); the PR pins it with a test (below) and states it in the changelog fragment.
