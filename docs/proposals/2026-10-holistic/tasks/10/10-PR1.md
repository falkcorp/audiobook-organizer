## Goal
After this PR, a torrent imported through `POST /api/v1/deluge/discover/import` is linked to its book twice: the `BookVersion` created for it carries the infohash in `TorrentHash` (so the existing Pebble index `idx:bv:torrent:<hash>` and tier 1 of discovery work for the first time), and the `BookFile` row carries it in `DelugeHash` (so the deluge-hash memdb index and later cleanup see it). The hash is validated and cross-checked against Deluge before it is trusted. Nothing else about import changes, and no Deluge storage move can be triggered.

## Steps
1. **Request field.** Add `TorrentHash` to `ImportFileRequest` with a comment: validated and lower-cased by the caller; `ImportFile` ignores an empty value. In `ImportFile`, if non-empty, reject (return an error before any write) anything that is not exactly 40 or 64 lowercase hex characters, with a package-private check. (`internal/importer` does not import `internal/deluge`, and this PR does not add that dependency; the server test below asserts both validators agree on a table.)
2. **Version.** At `service.go:332` pass `TorrentHash: req.TorrentHash` and `Source: "deluge"` when the hash is set, `"imported"` otherwise (unchanged). A fingerprint-match refusal from `CreateIngestVersion` stays what it is today, a logged warning that does not fail the import; do not change that.
3. **File row.** In the `bf` literal at line 374 set `DelugeHash: req.TorrentHash`. Do not set `DownloadHash` (a different concept that nothing reads) and do not set `ImportedFromDelugeAt` or `DelugeOriginalPath` (the file has not been copied; the later copy sets them).
4. **Handler.** In `handleDelugeDiscoverImport`:
   - if `req.TorrentHash != ""`, `deluge.NormalizeTorrentID`; a malformed value is `400`;
   - `client := getDelugeClient()`; if nil, import proceeds unlinked with `torrent_linked:false` and a note `deluge not configured`;
   - otherwise `client.GetTorrentDetail(hash)`: `ErrTorrentNotFound` is `400` (`torrent_hash does not name a torrent in Deluge`); any other error (Deluge unreachable) proceeds unlinked with the note `deluge unreachable: <short error>`; never fail the import for that;
   - cross-check: the cleaned `content_path` must equal `filepath.Join(save_path, f.Path)` for some entry `f` of the torrent's `Files` (the route imports one file, so an exact file match is the strong check); no match is `400` (`content_path is not a file of that torrent`). Compare cleaned absolute paths, never raw strings;
   - only a verified hash is placed in `ImportFileRequest.TorrentHash`. Keep the existing `torrent_hash` echo in the response and add `torrent_linked bool` and `torrent_link_note string` (omit when empty). The existing permission and the `deluge_discovery_enabled` gate are unchanged.
5. **Do not** add any network call to `ImportToLibraryWith` or to the tag-write guard path: resolving a hash by `save_path` there (as the spec's file table suggests) would put a Deluge round trip and a heuristic match inside every guarded tag write. Rows that already exist without a hash are 10-PR2's job. Report this deviation from spec §4 PR 1 in the hand-back.
6. **Findings to report, not fix** (they change behaviour for every import, so they are the owner's call with their real cost):
   - `CreateIngestVersion` runs at `service.go:332`, before `CreateBookFile` at 397. When it runs, no `book_file` row exists, so its row-link and `file_hash` stamp (`ingest.go:107-140`) find nothing: it logs `no book_file row matched the ingest path; version is orphaned` for every import, `VersionID` stays unset on the file row, and `FileHash` stays empty. Consequence for the cleanup fixer: imported rows are `unverifiable` (no pristine hash) until a hash backfill runs. Cost of fixing: move the `CreateBookFile` block above the `CreateIngestVersion` call and compute `FileHash` there; it changes every import, not only torrent ones, and contradicts the "VersionID deliberately left unset" comment at `service.go:367`.
   - The purge-fingerprint refusal in `CreateIngestVersion` happens after the book row is created.
   - Writing `DelugeHash` without `ImportedFromDelugeAt` puts the row into `GetBookFilesNeedingDelugeImportCore` (`memdb_reads.go:1295`, `pebble_store_bookfiles.go:1119`). The only consumers are manual: `POST /api/v1/discovery/import` (`deluge_discovery.go:117`), the `deluge.centralize` op and `maintenance.bulk-deluge-import` (none is scheduled: `grep` shows no schedule). This is the intended copy model (import in place, copy into the library later, D57); the PR pins it with a test (below) and states it in the changelog fragment.

## Rollback
Revert the commit. No migration: both columns already exist and are `omitempty`. Rows written while the PR was live keep their `DelugeHash` and version `TorrentHash`; they are harmless and still correct. Setting `deluge_discovery_enabled=false` also disables the route.
