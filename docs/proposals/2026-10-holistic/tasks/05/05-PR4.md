## Goal
After this PR every operation run is also stored as an `opv3:` record with exact per-state and
per-def census indexes, a state-machine audit trail, and the keys the chunk-leasing runner will
use (snapshot, ledger, checkpoint, intent), while every `opv2:` row is still written in the
same Pebble batch so the previous binary can be redeployed at any time. Migration 065 builds
the `opv3:` records from existing `opv2:` rows without changing any op id. No SDK, runner or
HTTP surface ships here.

## Design decision for this PR (one choke point, two families)
Keep the v2 store methods the registry calls today (`InsertOperationV2`, `UpdateOperationV2Status`, `SetOperationV2StatusIfQueued`, `ResetOperationV2ForResume`, `DeleteOperationV2`, ...) as the **write API for v2 vocabulary**, and make each of them stage the `opv3:` projection (run record, indexes, event, counts) **in the same batch**, using a new helper `stageRunV3(batch, prevV2, newV2)` analogous to `stageOpRow`. Add a small set of v3-native methods (`OpsV3Store`, below) for the fields that v2 vocabulary cannot express (`stopping{reason, zombie}`, `wait_reason`, `successor_id`, approval, ledger commits). Those native methods stage the mirrored `opv2:` row through the same `stageOpRow`. Result: there is exactly one place that writes each family, both families change in one `p.opsMu`-serialized batch, and the registry, its 100-plus tests and the fake stores keep compiling. (The upstream brief says "switch the registry's writes to v3 + mirror"; this brief achieves the same end state through the store layer. If the implementer finds a reason to prefer calling `TransitionRunV3` from the registry, say so in the report with the reason; do not do both.)

1. **`internal/operations/state/v3.go`.** Exact API (the table is `state-and-persistence.md` section 1; copy its property columns into `Props` via a second table, do not reuse v2 `Classify`):

```go
// V3 is a run state in the v3 vocabulary (ten states).
type V3 string

const (
	V3Queued           V3 = "queued"            // WaitReason: "" | deps | ready | pause
	V3Running          V3 = "running"
	V3Stopping         V3 = "stopping"          // StopReason: user | timeout | watchdog | quiesce | shutdown; Zombie bool
	V3Interrupted      V3 = "interrupted"       // InterruptedWhy: quiesced | crash | legacy
	V3AwaitingDecision V3 = "awaiting_decision"
	V3Succeeded        V3 = "succeeded"
	V3Failed           V3 = "failed"
	V3Canceled         V3 = "canceled"
	V3TimedOut         V3 = "timed_out"
	V3Dropped          V3 = "dropped"           // SuccessorID optional
)

type Event string // enqueue, wait_cleared, dispatch, return_nil, return_err, stop_requested,
                  // goroutine_returned, boot_sweep, resume, ask, decide_retry, decide_drop, migrate

// Next is the closed transition table of state-and-persistence.md. Anything
// not listed returns an error; the store never writes a transition Next rejects.
func Next(from V3, ev Event, stopReason string) (V3, error)

// Props3 mirrors the v2 Props for the v3 states (Terminal, HoldsSlot, ...).
func ClassifyV3(s V3) Props

// ToV2 is the mirror back-map used while opv2: is dual-written. kind is the run
// kind ("task" | "batch" | "fixer" | "pipeline"); hasLedger is true when a
// chunk ledger exists, because a v2 binary cannot resume it.
func ToV2(s V3, waitReason, interruptedWhy string, hasSuccessor, hasLedger bool, errMsg string) (v2Status string, v2ErrMsg string)
```

   The back-map (all from `state-and-persistence.md` section 4): `queued{deps}` to `waiting_deps`; `queued{ready|pause|""}` to `queued`; `stopping` to `running`; `timed_out` to `canceled` with the message prefix `timeout: `; `awaiting_decision` to `interrupted_ask`; `dropped` with a successor to `interrupted_restart`, otherwise `interrupted_dropped`; `interrupted` to `interrupted_quiesced`, **except** when `hasLedger` is true, then `interrupted_dropped`; `succeeded` to `completed`; `failed`, `canceled`, `running` unchanged. The forward map used by the migration and by the v2 façade is the table in `state-and-persistence.md` section 3 (14 rows plus "anything else"); implement it as `FromV2(status, errMsg string) (V3, why string, ok bool)`. Table-test every row and the round trip `ToV2(FromV2(s))` for every v2 status the registry mints.

```text

opv3:q:{999-prio:03d}:{queued_ns:020d}:{op_id} -> ""   dispatch order; present only for queued with empty wait_reason
```

   Nesting: `opv3:snap:{op}:chunks` sorts inside `opv3:snap:{op}:`; register `opv3:snap:` as the family and note the child in its description, as `keyfamilies.go:30-33` requires. State strings in `ix:state` keys use the v3 names.
   Kept untouched and never re-keyed (R18): `opchange:`, `opchange_by_book:`, `opchange_undecodable:`, `op_result:`, `opsummary:`, `opstate:<id>`, `act:op:`, `op:completion:`, `op:deprev:`, `op:batch:`.

4. **Stage the v3 projection in every v2 method.** In `InsertOperationV2`, `UpdateOperationV2Status`, `SetOperationV2StatusIfQueued`, `ResetOperationV2ForResume`, `DeleteOperationV2` and any other method that calls `stageOpRow` with a changed status (`grep -n 'stageOpRow' internal/database/pebble_store_ops_v2.go`), call `stageRunV3(batch, prev, row)` right after `stageOpRow`. It: converts the v2 row with `state.FromV2`, upserts `opv3:run:`, moves the `ix:state` key, `ix:def` (insert only), `ix:done` (when completed), `ix:parent`, `q` (add/remove exactly as `opv2:q:` is maintained at `:324-340`), appends one `opv3:evt:` row, and adjusts `opv3:meta:counts`. `opv3:meta:counts` is read, adjusted and written under the same `p.opsMu` the v2 methods already hold, so concurrent transitions cannot lose a count. If `FromV2` returns `ok=false` the row maps to `failed` with `FromV2.Status` preserved, and the unmapped count is logged once per process per status string.

5. **Native methods.** `TransitionRunV3` rewrites the record and stages the mirror: it builds the v2 row with `state.ToV2`, stages it through `stageOpRow`, and maintains the `opv2:q:` / `opv2:act:` keys the way `UpdateOperationV2Status` does. `DeleteRunV3` must also run the same deletions `DeleteOperationV2` runs for the mirror. `CommitLedgerV3` never touches `opv2:` (a v2 binary cannot use a ledger). On a terminal transition, `opv3:snap:`, `opv3:snap:...:chunks` and `opv3:ledger:` for that run are deleted in the **same batch** as the transition; the final counters survive in `RunRecord.Progress` (`state-and-persistence.md` 2.1 "Cleanup").

6. **Registry edits (small).**

Reason: under v3 a zombie stays `stopping` (non-terminal, mirrored as `running`) until its goroutine returns, so without this skip the dedupe returns the zombie's id and silently disables the op type, which is exactly the C-3 bug in a new place. Test it (below).
   - `worker.go` zombie branch (05-PR3, `:552-619`): replace the abandonment-time terminal write with `TransitionRunV3(stopping{reason, zombie: true})`; keep `markTerminal`, `publishOpTerminal`, `notifyDepFailed` timing as 05-PR3 left them **only if** that still makes sense with a non-terminal row; if `notifyDepFailed` and `publishOpTerminal` must now wait for the goroutine exit, move them to the exit monitor and say so in the PR body.
