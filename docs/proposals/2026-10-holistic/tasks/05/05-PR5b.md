## Goal
After this PR a resumed Fixer apply reports a row "already applied" (marked, listed in
`FixerResult.Applied`, handed to `AfterApply`, not written again) only when the store holds
history that THIS run wrote for that row's subjects in an earlier attempt: metadata history
rows whose batch id starts `op-<opID>-`, or operation-journal rows (`opchange:<opID>:`) for
the row's book or book_file subjects. A row whose current values equal `Proposed` because
someone else made the same change between the attempts is skipped as `changed_since_plan`,
not counted as the fixer's own. Today (05-PR5) that case is indistinguishable and is reported
applied; the comment in `pkg/ops/fixer.go` `applyRow` says so and points here.

## Context the agent must read first

- `internal/operations/opswriter/writer.go` and `history.go`: where a write's history goes.
  `ModifyBook` records metadata history through `BookHistory` with batch ids
  `<batchPrefix><ulid>`; the v3 run's prefix is `"op-"+opID+"-"` and its source the def id

  `RepointBookFile`, `ModifyBookAuthors` and `Effect` write operation-journal rows
  (`CreateOperationChange`, `OperationID` = the op id). Intents are cleared on success, so
  they are not evidence of a completed write.
- The existing reads: `GetOperationChanges(operationID)` (`internal/database/pebble_store_operations.go`,
  a prefix scan of `opchange:<opID>:`) and `GetBookChangeHistory(bookID, limit)`
  (`pebble_store_metadata.go`, a per-book prefix scan **truncated at limit**). Check whether
  either needs a complete, unbounded variant before relying on it.
- `internal/database/store_width_test.go` (`database.Store` may only narrow) and
  `.golangci.yml` `interfacebloat` max 8: declare any new store surface as its own small

- `scripts/deadcode-ratchet.py` and the "05-PR5 one-time addition" in

## Steps
1. Measure the reads first: for a book with more than 100 history rows, does
   `GetBookChangeHistory` return the run's rows? If it truncates, add the complete read (step 4)
   before anything depends on it.
2. Add `Wrote` to `ops.Writer` with its doc comment (ctx rules as for the other methods), and
   implement it in `opswriter`: a subject counts as written when a journal row under this op
   id names it (book: `BookID`; book_file: `FieldName` naming `book_file:<id>` or the
   `file.<field>:<id>` form `ModifyBookFile` writes), or a metadata history row of its book has
   a `BatchID` with the run's prefix. All subjects must be evidenced.
3. `applyRow`: `irc.Resumed() && refusal == "" && alreadyApplied(planned, fresh) && wrote`,
   with `wrote` from `w.Wrote(irc.Context(), planned.Subjects)`; a read error is the item's
   error (fail, not "applied").
4. Only if step 1 found a gap: the narrow complete read in `internal/database`.
5. Wire the capabilities in `newV3Writer`; update `repairs.Writer` and its surface test.
6. Deadcode: run `make lint-deadcode-ratchet`. New identifiers reachable only through the v3
   runner are unreachable until 05-PR7; do not add them to the baseline without the owner's
   approval (05-PR5 needed two). Prefer placing the reads where a reachable caller already
   exists, and report every new name.
