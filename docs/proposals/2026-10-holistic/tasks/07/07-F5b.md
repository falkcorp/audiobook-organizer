## Goal
A signed-in user opens **Collections** in the sidebar and can: list collections (static and dynamic); create a static collection (name, description, books) or a dynamic one (name, description, a query in the app's one search syntax, sort, limit); edit and delete them; preview or materialize a dynamic collection's members. Users without `collections.manage` see the lists and members but no write control. Every count on the page opens the books it counts. A collection made on the page is returned by the ABS route `GET /api/libraries/:libraryId/collections`, so it shows up in the ABS app. All backend work (owner evaluation, relative dates, add/remove endpoints, `permissions` on auth) is in 07-F5a; this brief is web only.

## Context the agent must read first
- `internal/server/wire_library_routes.go` lines 106-126: the collection block. Reads (`GET /collections`, `GET /collections/:id`) need `PermLibraryView`; `POST`, `PUT`, `DELETE` and `POST /:id/materialize` need `PermCollectionsManage` (`collections.manage`, `internal/auth/permissions.go:65`). Collections are server-wide, not per user.
- `internal/server/handlers/collections.go` (version 1.2.1): `CollectionCreateReq` / `CollectionUpdateReq`, `validateCollectionCreate`, and each handler's status codes (400 bad type or field, 409 name in use or version conflict, 503 search index unavailable on materialize).
  - Create: `{name, description?, type: "static"|"dynamic", book_ids? (static only), query (dynamic, required), sort_json?, limit?}`. The response `data` is the bare `Collection` (not wrapped, unlike playlists).
  - Update (`PUT`): every field optional pointer; `type` cannot change; `book_ids` on a dynamic collection and `query` on a static one are 400.
  - `GET /collections/:id` on a dynamic collection RE-EVALUATES the query for the calling user and refreshes `materialized_book_ids`; `POST /:id/materialize` does the same and answers 503 while the index is closed.
  - List: `RespondWithList` shape `{items, count, limit, offset}`, filter `?type=static|dynamic`.
- `database.Collection` in `internal/database/store.go` lines 563-592: `type`, `book_ids`, `query`, `sort_json` (JSON `[{field, direction}]`), `limit`, `materialized_book_ids`, `version`, `created_by_user_id`.
- `internal/server/handlers/abs/collections.go`: `LibraryCollections` (`GET /api/libraries/:libraryId/collections`) lists both types with `ListCollections("", 500, 0)`; `canManageCollections` gates ABS writes the same way; the ABS update refuses to edit a dynamic collection's membership (409), which is why this page uses the native routes. Tests to copy fixtures from: `internal/server/handlers/abs/collections_test.go` (`abscolHarness`, `abscolFakeStore`, `abscolResults`, `TestCollections_CreateThenListRoundTrip`, `TestCollections_DynamicServesMaterializedMembers`).
- `web/src/services/playlistApi.ts` (version 2.1.0) and `web/src/pages/Playlists.tsx` / `PlaylistDetail.tsx` / `Playlists.test.tsx`: the closest pattern (`jsonFetch` over `apiFetch`, list page with type tabs, create dialog with a "Query (DSL)" field, detail page with a Snapshot button).
- `web/src/components/layout/Sidebar.tsx` (the `menuItems` array, line 92 has Playlists) and `web/src/App.tsx` (lazy imports at line 42, routes at line 368).
- `web/src/components/audiobooks/SearchBar.tsx` and `web/src/utils/queryGrammar.ts`: the app's one RE2 search syntax. Reuse its field list and validation rather than writing a second grammar.
- Query evaluator facts that decide the help text (verified at HEAD):
  - Indexed query fields come from `search.BookDocument` json tags (`internal/search/bleve_index.go`): title, author, narrator, series, series_number, publisher, description, tags, format, genre, language, library_state, isbn10, isbn13, asin, `year`, `duration_seconds`, bitrate_kbps, sample_rate_hz, channels, bit_depth, file_size_bytes, has_cover. `duration` is an alias for `duration_seconds` that takes human units (`duration:>20h`, `20m`, `1h30m`; a bare number is seconds; `internal/search/field_routing.go`).
  - Per-user query fields, filtered in Go for the collection owner (07-F5a): `read_status` (`unstarted`, `in_progress`, `finished`, `abandoned`), `progress_pct` (0-100, numeric ranges), `last_played` (absolute `YYYY-MM-DD` or RFC3339, or relative such as `-30d` after 07-F5a) (`internal/search/bleve_translator.go:43`, `internal/search/per_user_match.go`).
  - After 07-F5a, `date_added` (alias `added`) and `date_modified` are also query fields (absolute or relative dates). `rating`, `itunes_last_played` and `itunes_play_count` are **sort fields only** (`internal/playlist/evaluator.go:215-250`, used through `sort_json`); they are not query fields. The UI must offer them in the sort picker and must not suggest them in the query box.
- **Per-user fields are evaluated as the collection's owner (D75, built by 07-F5a).** A dynamic collection stores its creator's user id (`created_by_user_id`) and is always evaluated as that user, on materialize, on native reads and for ABS, so `read_status`, `progress_pct` and `last_played` mean the owner's reading state for everyone. The page tells the user this (Steps 5).
- **Relative dates (D76, built by 07-F5a).** `last_played:>-30d` (units `d`, `w`, `m`, `y`; a signed offset from now) is part of the one search syntax and is resolved each time the collection is evaluated, so it rolls forward. Absolute `YYYY-MM-DD` still works.
- **Native add and remove books (D77, built by 07-F5a).** `POST /api/v1/collections/:id/books` with `{"book_ids":[...]}` (1 to 500) and `DELETE /api/v1/collections/:id/books/:bookId`; both need `collections.manage`, both answer the updated collection, both answer 409 for a dynamic collection, add answers 400 for an unknown book id, remove answers 404 for a non-member.
- `GET /auth/me` and login carry `permissions: string[]` (07-F5a); `AuthUser.permissions` exists in `web/src/services/api.ts` after 07-F5a merges.
