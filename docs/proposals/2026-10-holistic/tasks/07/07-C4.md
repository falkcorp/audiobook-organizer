# 07-C4: measure the first ten merges after C1-C3 (no workflow change)

| Field | Value |
|---|---|
| Model | sonnet |
| Wave | 0 (runs alongside the next ten merges; start it only when they exist) |
| Size | S |
| Depends on | **Merge first:** 07-C1, 07-C2, 07-C3. 07-C1, 07-C2, 07-C3 merged, plus ten further merges to `main` after the 07-C3 merge |
| Blocks | none briefed (generated from every brief's `Merge first` list on 2026-10-09; do not hand-edit) |
| Owner decisions | D60 |
| Spec | `07-design-decisions-and-modularity.md` §4 row 07-C4 and the "Order" line; appendix A.9 |

## Goal
Prove, with a table, that a merge to `main` now costs one PR-sized run (about 10 minutes) instead of two (39-49 minutes), and that `auto-revert.yml`'s free re-run (`auto-revert.yml:85-97`, `gh run rerun --failed`) is rare. No workflow is changed here. If any job needed a re-run on more than 2 of the 10 merges, find its mechanism (the standing flake rule: a flake is a bug with a cause; never re-run until green).

## Context the agent must read first
- `docs/proposals/2026-10-holistic/07-design-decisions-and-modularity/A-measurements.md` §A.9 (the "before" numbers: PR run 22-24 min, `main` run 39-49 min, the re-run at `auto-revert.yml:85-97` adding about 23 minutes).
- `.github/workflows/auto-revert.yml` lines 60-100 (how attempt 1 is detected and re-run).
- `docs/ci/woodpecker.md` (Woodpecker is a separate, manual-only gate set; it is not measured here).

## Preconditions (check first; stop and report if not met)
1. Find the 07-C3 merge commit: `git log --first-parent origin/main --oneline --grep='shard the short Go test run'`.
2. Count merges after it: `git rev-list --first-parent --count <c3-sha>..origin/main` must be at least 10. If fewer, stop and report the count; do not wait in a loop.

## Steps
1. List the first ten first-parent merges after the 07-C3 merge: `git log --first-parent --reverse --format='%h %cI %s' <c3-sha>..origin/main | head -10`.
2. For each, find its `Continuous Integration` run on `main`: `gh run list --workflow ci.yml --branch main --event push --limit 60 --json databaseId,headSha,conclusion,createdAt,updatedAt,attempt,displayTitle`. Match by `headSha`. A docs-only merge has no run (07-C2): record `no run (docs-only)`; it still counts as one of the ten.
3. For every run record: merge short sha, run id, wall minutes (`updatedAt - createdAt`), `attempt`, conclusion, and the names of jobs that failed on attempt 1 (`gh run view <id> --json jobs --jq '.jobs[] | select(.conclusion=="failure") | .name'`; for attempt 2 pass `--attempt 1`). Also record the wall time of the PR run that preceded the merge (`gh run list --workflow ci.yml --event pull_request --json databaseId,headBranch,createdAt,updatedAt,conclusion` matched by the PR's head branch; use the last run before merge). Also record the longest shard: `gh run view <id> --json jobs --jq '.jobs[] | {name,startedAt,completedAt}'`, compute minutes per job (`completedAt - startedAt`) for the shard jobs from 07-C3, and keep the maximum as a "max shard minutes" column.
4. Write `docs/ci/2026-10-ci-throughput.md` with: the "before" figures quoted from A.9 with their run ids (37865893192 PR 22 min, 37865901335 `main` 45 min); the 10-row table; median and maximum for PR wall and for `main` wall; the count of runs with `attempt` greater than 1; the verdict against the targets (PR under 10 min, `main` one attempt, longest shard under 8 min). The table has a per-run "max shard minutes" column; the third verdict target (longest shard under 8 minutes) is judged on its median and maximum.
5. For any job that needed a re-run on more than 2 of the 10: open its log (`gh run view <id> --log-failed`), identify the test or step, and write the mechanism (not "flaky") in a section of the doc with the file:line of the cause. Open a `todo.d/` fragment for each cause (headerless; see `todo.d/README.md`); do not fix them in this PR.
6. Do not edit any workflow file, baseline or script.

## Tests
- `git diff --stat` shows only `docs/ci/2026-10-ci-throughput.md` and the fragment.
- Every run id in the table resolves: `gh run view <id> --json databaseId --jq .databaseId` for each.

## Acceptance
- [ ] Ten rows, each with a run id or `no run (docs-only)`.
- [ ] Median PR wall and median `main` wall are stated with the command that produced them.
- [ ] The verdict line says met or not met for each of the three targets, with the numbers.
- [ ] Any re-run-prone job has a named mechanism and a `todo.d/` fragment.

## Rollback
Delete the doc. Nothing else changed.

## Guardrails
- Public repo: run ids and short SHAs are fine; no tokens, no internal hostnames or IPs, no emails.
- Report exact counts ("7 of 10 on attempt 1"), never "mostly".
- Worktree rule: `git worktree add ../aorg-07-c4 -b docs/07-c4-ci-throughput origin/main`; never edit main.
- File headers on the new doc; commit `docs(ci): record CI throughput after the sharded run`; `git add` named files only.

## Report format
The table, the three medians/maxima, the verdict, the list of re-run-prone jobs with mechanisms, and anything you could not match to a run.
