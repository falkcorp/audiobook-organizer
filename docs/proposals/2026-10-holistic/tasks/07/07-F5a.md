## Goal
Four backend changes that the Collections page (07-F5b) needs, each with its own tests:
1. **D75.** A dynamic collection is always evaluated as the user who owns it, so per-user fields (`read_status`, `progress_pct`, `last_played`) mean the same thing on materialize, on a native read and for ABS, whoever is signed in. Existing dynamic collections with no usable owner get the first admin.
2. **D76.** The one search syntax gains rolling relative dates (`last_played:>-30d`; units `d`, `w`, `m`, `y`), resolved at evaluation time, for every date field the query path supports; the Search Syntax help documents it.
3. **D77.** `POST /api/v1/collections/:id/books` and `DELETE /api/v1/collections/:id/books/:bookId`: atomic store operations, gated by `PermCollectionsManage`, refused for a dynamic collection.
4. `GET /auth/me` and the login response carry the caller's effective `permissions`, so the web UI can hide write controls.

## Context the agent must read first
- **Owner evaluator (D75).**
  - `internal/server/handlers/collections.go` (version 1.2.1): `evaluate` passes `CallingUserID(c)` to `playlist.EvaluateSmartPlaylist`, so the result depends on who reads. `GetCollection` and `MaterializeCollection` store that result in `MaterializedBookIDs`, and the ABS surface serves it to everyone (`internal/server/handlers/abs/collections.go` `collectionsPageBooks`, which reads the stored set and never evaluates).
  - `database.Collection.CreatedByUserID` (`internal/database/store.go` ~line 584) already exists and both create paths set it (native `CreateCollection`, ABS `collections.go:186`). Its comment says "attribution only; does NOT scope visibility". Visibility stays server-wide; the field gains a second meaning: the evaluating user. Update that comment. Do not add a second owner field unless you find a reason in the code and say so.
  - `internal/playlist/evaluator.go` `EvaluateSmartPlaylist(store, idx, query, sortJSON, limit, userID)` and `applyPerUserFilters`. Smart **playlists** stay per-user by design; do not change them.
  - Users: `database.User` (`internal/database/store.go` ~line 732) has `Roles []string`, `Status`, `CreatedAt`; `ListUsers()` is in `internal/database/iface_user.go`; the canonical admin role id is `auth.SeedRoleAdmin` = "admin" (`internal/auth/seed.go:33`). "First admin" = the active user (`Status` check: read how `Status` values are used, `grep -rn 'Status.*active' internal/database internal/auth`) with the admin role and the earliest `CreatedAt`, ties broken by `ID`. The no-auth fallback caller id is `"_local"` (`CallingUserID`); it is not a user row.
- **Relative dates (D76).**
  - `internal/search/per_user_match.go` `timeFieldMatches`: accepts RFC3339 and `2006-01-02` only, today the only date handling in the query path.
  - `internal/search/bleve_translator.go` (per-user field set at line 43; `duration` human-unit handling at ~231 and `internal/search/field_routing.go` `ParseDurationSeconds`): the model to follow for a shared parse helper.
  - `internal/search/bleve_index.go` `BookDocument` and `bookMappingVersion` (~line 149): the indexed fields. **There is no date field in `BookDocument` today.** `date_added` (alias `added`), `date_modified`, `itunes_last_played` are **sort fields only** (`internal/playlist/evaluator.go:215-250`). So "every date field" has two parts: `last_played` (per-user, matcher) now, and any field you add to the index. The owner's D76 names `date_added`; implementing it as a query field means adding it (and `date_modified`) to `BookDocument` as a Bleve datetime field, bumping `bookMappingVersion`, which makes the index recreate and rebuild at next start (read `mapping_version_test.go` and `bleve_index.go` around `recreatedForMapping`). That is a real production cost (one full reindex); do it, and state the reindex in the PR body and the changelog fragment.
  - `internal/search/query_parser.go`: does the lexer accept `>-30d` (a sign after the operator, a letter unit)? Add a test first; extend the parser if it does not.
  - Help text: `web/src/components/audiobooks/SearchBar.tsx` ("Search Syntax" popover, ~line 497) and `web/src/utils/queryGrammar.ts` (+ `queryGrammar.test.ts`). Also `grep -rniE 'search syntax|last_played' docs README.md` for the user-facing doc and update it.
- **Atomic add/remove (D77).**
  - `internal/database/pebble_store_collections.go`: `UpdateCollection` compare-and-swaps on `Version` but its own comment says the check is **not atomic** inside the process (no lock across Get, compare, Commit). ABS `batchEditCollection` (`handlers/abs/collections.go` ~lines 417-495) does Get, mutate, `UpdateCollection`, so two racing adds can both pass and one is lost. The new store operations must close that race, which is what "atomic" means here.
  - `CollectionStore` interface in `handlers/collections.go`; `MockStore` (`internal/database/mock_store.go`); mockery config `.mockery.yaml` (`make mocks`); the fakes in `handlers/abs/collections_test.go` (`abscolFakeStore`) and the handler tests in `handlers/collections_test.go`.
- **Permissions on auth.** `internal/server/handlers/auth.go`: `AuthUserResponse`, `buildAuthUserResponse` (~line 208), `Login`, `Me` (~line 403); `ChangePassword` (~line 534) already reads the request's effective permissions with `auth.Can(c.Request.Context(), ...)`; `auth.Permission` constants in `internal/auth/permissions.go`. `AuthUser` in `web/src/services/api.ts` (~line 1061) has `roles` only.

## Steps
1. **Owner evaluator.** Add a resolver in `handlers/collections.go`: `evaluatorFor(col)` returns `col.CreatedByUserID` when that user exists (`GetUserByID`), otherwise the first admin (and logs), otherwise an error that the handlers map to 503 "no admin user to evaluate this collection as". `evaluate` uses it instead of `CallingUserID(c)`. The native `CreateCollection` stores the creator and evaluates as that same user, so create-time materialization equals every later one. Re-run the existing handler tests; fix the ones that assumed the caller. The ABS read path keeps serving the stored set without evaluating (it must stay index-independent); the ABS **create** sets `CreatedByUserID` already; make sure an ABS-created static collection is not affected.
2. **Owner backfill** as in Files, with a test over a synthetic store holding: a dynamic collection with an empty owner, one owned by `"_local"`, one owned by a deleted user, one owned by a live user, and a static collection with an empty owner. Expected: the first three get the first admin, the fourth and the static one are untouched, and a second run changes nothing. Include the "first admin" tie-break test (two admins with equal `CreatedAt`).
3. **Relative dates.** Write `ParseDateTerm` and its table test first. Check the parser accepts `>-30d` and `..` ranges; extend it if not. Switch the per-user matcher over, then add `date_added`/`date_modified` to the index as in Files. List in the PR body every date-capable query field after your change (expect: `last_played`, `date_added`, `date_modified`) and every sort-only one (`itunes_last_played`; it lives on `Book` and is not indexed: leave it sort-only and say so).
4. **Matcher edge the page's example depends on.** `perUserFilterMatches` treats a missing state row as a zero-value state, whose status string is empty, so `read_status:unstarted` does not match a book with no row even though the comment at `per_user_match.go:46` says it should. Write the test (a book with no row, a book whose row says `unstarted`, a book `in_progress`) and fix the matcher so `unstarted` matches both of the first two. This is a bug in the matcher, not in the page.
5. **Atomic store ops**, then the two handlers and route registrations, then the 403 route-gating test. Do not change the ABS batch routes in this brief (they keep their Get-mutate-Update shape); say in the report that they still have the intra-process race and that moving them onto the new store operations is a small follow-up.
6. **Permissions** on auth, with the tests.
7. Run the targeted tests, `go build ./... && go vet ./...`, the slog guard and layering tests, `make mocks` (commit the regenerated mocks), then the fragment.
