## Goal
After this PR an install with no `activity_backend` setting runs the Pebble-only activity store. Today the empty value engages the SQLite migration wrapper, and prod stays on Pebble only because of a gitignored `deploy/local.conf`; losing that file would silently re-engage SQLite. An explicit `activity_backend: sqlite` still works until P75 removes the backend.

## Steps
1. Read the files above. Confirm with `grep -n activity_backend internal/config/config.go internal/config/protected_fields.go`. 2. Set the viper default to `"pebble"`. Note that `viper.SetDefault("activity_backend", "")` ALREADY makes `viper.IsSet("activity_backend")` true today (the comment at config.go:2237-2239 says exactly this for `activity_db_path`), so `applyEnvAuthoritativeConfig` already overwrites the blob value with whatever viper returns (now `"pebble"` when the environment is silent). Verify that in a quick test first. Consequently `applyEnvAuthoritativeConfig` will force `c.ActivityBackend = "pebble"` over a persisted blob value. That is acceptable and in fact stronger (a blob can never re-engage SQLite), but it changes what the second test asserts, so update the test and its comment to match what the code now does. Do not weaken the rollback lever: `ACTIVITY_BACKEND=sqlite` in the environment must still select sqlite.
3. In `register.go`, replace the `backend == "pebble"` early return with a check that returns the Pebble-only store unless `backend == "sqlite"`. The slog line at that branch should say which value selected it.
4. Update the two existing tests and add the new table test. The new test must fail on `origin/main` (red) and pass on your branch.
5. Update the two docs and write the changelog fragment (what: new installs and installs that lose their conf file now keep the Pebble activity log; nothing changes for prod).
6. Do NOT touch the SQLite backend files, `ActivityDBPath`, or `ActivityDBMoveOnChange`: P75 deletes them.
