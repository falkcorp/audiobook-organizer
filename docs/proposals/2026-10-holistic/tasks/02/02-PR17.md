## Goal
The Review > Metadata lane loads every reviewable row into the browser and filters it there. This PR adds a server-side query, `view=page`, over the review snapshot the server already keeps in RAM (`reviewSnapshot`, shipped in `d9463d669` and `df23cbe95`): one evaluation per filter yields the page, the count, the chip facets and an ids-only list for "select all N", all keyed by the snapshot generations. Nothing in the web app calls it until PR 18; `view=index` is untouched.

## Steps
1. Create the worktree. Run `go test ./internal/server/handlers/... -run 'MetadataCache|Review' -count=1` first and keep the result as the baseline.
2. Refactor first, with no behaviour change: move the loop that builds `prepared` and `reviewable` (status mapping `no_match`/`matched`->`applied`/`audio_confirmed`->`applied`, the status-rank stable sort, the per-row stale and deferred flags, the single `freshCutoff` clock read) into one function, e.g. `buildReviewableRows(set, now) []reviewableRow`. The `view=index` response must be byte-identical before and after; add a golden test that proves it on a fixture before you start changing anything else.
3. Define `ReviewQuery` and parse it. Parameters (all optional): `q` title text in the Library grammar, parsed like the client's `compileTitleFilter` (a bare value, or `title:` tokens, any negated with `-`; a field other than `title` is a 400 with the same message the client shows) and compiled with `querygrammar.CompileText`; `source` (provider id, compared with the same mapping as `reviewProviderID`); `min_confidence` (0-100, applied to `matched` rows only, as the client does); `hide_applied`, `hide_rejected`, `hide_skipped`, `hide_no_match`; `hide_runtime`; `match_language`; `has_transcription`; `transcription_matched`; `hide_multi_book` with `ungrouped` (comma list of book ids the owner pulled out of a group); `chip` (one of matched, no_match, total, errors, no_candidates, resolved_no_candidates, stale, deferred); `bucket`; `sort`; `limit`, `offset`; `ids=all`. A chip view pauses every other filter except `q`, exactly as `chipRows` does.
4. Before porting `hide_applied`/`hide_rejected`/`hide_skipped`, find where each `rowStates` value is set (`grep -n 'rowStates\|setRowState' web/src/components/review/lanes/useMetadataLane.ts`) and prove what is persisted server-side. Appendix D says these are persisted by the actions, so the overlay sees them. If `skipped` (or any state) is client-only, do not invent semantics: add a `skipped` comma-list parameter like `ungrouped`, keep the state in the lane, and say so in the PR description.
5. Port the runtime filter (`runtimeHiddenBySwitch` = the apply gate's 10 percent rule OR the spine's ten-minute warning), the language rule (an unknown language on EITHER side is a no-op, not a hide) and the multi-book key (`candidateKey`) as Go functions next to the query, each with a table test copied from the TypeScript cases. The multi-book set is computed over the WHOLE filtered set, not the page.
6. Evaluate in ONE pass over the snapshot rows with the live overlay (the same `overlayLiveBooks` call the listing uses, so the overlay is read once per evaluation). Produce an ordered `[]rowIndex`, the facet counts (every chip count plus the count the runtime switch hides) and the total. Slice the page from the list. `ids=all` returns only `{ids, total, generation}` from the same list.
7. Result-list LRU: the last 32 lists, keyed by `(cacheGen, bookGen, normalizedQuery, sort)`; use singleflight so concurrent identical requests share one evaluation. Any write moves a generation and so misses. Expose an unexported evaluation counter the tests assert on.
8. Never block a keystroke on a build: serve the CURRENT snapshot (`h.reviewSnapshot`'s stale-while-revalidate path), at most call `requestRebuild()` (already throttled to one per 45 s). If the overlay would read more than `overlayRebuildThreshold` (2000) books, do what the listing does (ask for a rebuild, serve what you have). Only the first request after a cold start may wait on a build. A test asserts a filter over an unchanged snapshot starts 0 builds (use the builder's counter).
9. Every page response carries `generation` (a string combining `cacheGen` and `bookGen`). Document in the handler comment that PR 18 refuses to apply an ids list whose generation is older than the page it is acting on.
10. Add the response `Cache-Control: no-store` header on `view=page`. Do not touch `view=index`, the `indexView` branch, or the unreviewable-bucket code path beyond extracting shared helpers.
11. Write `review_query_cases.json` (at least 12 cases: each chip, each hide switch, title substring/glob/RE2/negation, min_confidence, language, runtime, multi-book with and without `ungrouped`, sort) using synthetic rows only. For each case derive the expected ordered ids by reading the TypeScript chain, not by running your Go code, and note in the PR description how you checked them.
12. Run the PR 3 conformance corpus through the `q` path: for each corpus case build a one-row snapshot and assert match/no-match equals the corpus.
13. Benchmarks: record ms/op for the four sub-benchmarks at 40,000 rows with `-benchmem`.
