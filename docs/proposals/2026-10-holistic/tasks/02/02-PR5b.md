## Goal
Today `UpdateBook` deletes `metadata_cache:<bookID>` when a write changes the book's title or its author's name (`candidateSearchIdentityChanged`), which is the shape that lost 1,180 candidate rows on 2026-10-06. After this PR the same write keeps the row, stamps it `Stale=true` with the old search fingerprint, and the gate (PR 5a) refuses to apply it while the candidate-fetch selection refetches it.

## Steps
1. Create the worktree. Verify 02-PR5a is on `origin/main`: `grep -n 'CandidateIdentityStale' internal/metafetch/cache.go`. If it is not, stop and report.
2. Add `stageCacheStaleStamp` modelled line for line on `stageCacheASINStamp`, including the lock contract in its doc comment.
3. In the update path, restructure the branch so the three cases are: (a) search identity changed -> take the lock, stamp stale (or drop an unreadable row); (b) else ASIN replaced -> existing stamp; (c) neither. A write can be both a retitle and an ASIN replacement: stamp both on the one row in one rewrite (read once, set `FetchedForASIN` if empty and `Stale`, write once) rather than letting two staged writes to the same key race inside the batch.
4. `candidateSearchIdentityChanged` returns true when `oldBook == nil`; that is the create-like path with no cached row, which `stageCacheStaleStamp` handles as a nil row. Keep it.
5. `cacheRowDeleted` is the variable that makes the caller bump the cache generation after commit; set it from `staged` for the new branch (the row was rewritten), so the review snapshot and the summary index see the change.
6. Leave the book-delete path alone: a deleted book still deletes its cache row (`DeleteMetadataCache` callers). Only the retitle/re-credit write changes.
7. Put the rollback cleanup in the PR description as numbered steps (see Rollback): list the rows flagged stale through the store, then remove them with the existing `DeleteMetadataCache`. Do not ship a new op for it.
