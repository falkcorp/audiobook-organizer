## Steps
1. Create the worktree. Read appendix D section 1 and the spec's PR 15 text twice; the note must reproduce the procedure exactly, not paraphrase it.
2. Create the audit note with the standard Markdown header (file, version 1.0.0, guid, last-edited). Sections: (1) Purpose in two sentences; (2) What to record, three parts below; (3) Tables; (4) Findings (empty); (5) Decision rule.
3. Part 1, Chrome Task Manager (Shift+Esc): for the Review tab's renderer, the GPU process and the browser process, record Memory footprint and JavaScript memory (MB). Put the decision rule in the note: a large figure on the GPU or browser process is not this lane's heap and ends the lane investigation.
4. Part 2, three DevTools heap snapshots (Memory tab, Heap snapshot) on Review > Metadata: (a) idle after first paint; (b) after one `refresh()` (apply one book, let the poll settle); (c) after ten applies in one batch, settled. For each, the table has columns: total JS heap (MB); count of `Array` objects with more than 10,000 elements; retained size of those arrays (MB); retained size of the largest `Map` (the rows-state map) (MB); detached DOM node count.
5. Part 3, Network panel: `view=index` response size (MB) and its `total_count`, so the rows-to-bytes ratio is checked against appendix D's 3.4 KB per row.
6. Decision rule section: if the number of arrays over 10,000 elements is above 1 in (b) or (c), a previous result array is being retained across refreshes; the finding must name the closure that holds it (DevTools Retainers view) and is handed to 02-PR18 as an item to fix in the same rewrite. If the Review renderer is under 300 MB in all three snapshots and the 16 GB is elsewhere, say so and close the lane question.
7. State in the note, in bold: snapshot files are never committed and never attached to an issue (they contain every library title and path; the repo is public). Only figures go in the table.
8. Do not fill any figure yourself and do not call production. Leave every measured cell as `TBD (owner)`.
