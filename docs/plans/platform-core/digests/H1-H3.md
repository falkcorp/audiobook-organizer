# Digest H1–H3 — Hardening cutovers after S10 (one-way, floored, a fresh verified archive first)

Normative digest for implementers. Source order: 09 §9.13 (the stage table and the three release-note texts), §9.2.1 (soaks, trailers, levels), §9.2.2, §9.9; 03 §3.3/R4; 05-storage §5S.3.13, §5S.3.14, §5S.3.7; 05-authn §11.2; 05-config §1.12.5; 05-rbac §6.3; 05-backup §5B.3.9; 12 §12.4.4. No H stage has its own stage table yet: 09 §9.13 says each gets one **when it is planned**, so the "Done when (minimum)" below is a floor, not a full plan, and briefs for H1–H3 stay planning-level until that table exists. H1–H3 move no package, so 04 has no row for them, by design (09 §9.13, 04 §1). Where this file and a spec file differ, the spec file wins and the difference goes in the PR description. `[n]` points to Footnotes.

## 1. Goal

Ship the hardening that the representation-neutral extraction deliberately left out, as three named cutovers on the one-way, floored machinery. Through S10 books' legacy stores keep HEAD's representation; these are the only steps that change it.

| Cutover | What ships | Release ID |
|---|---|---|
| **H1 identity** | sessions and one-time tokens stored hashed; existing sessions, invites and one-time tokens **deleted, not rehashed**; `mck_` keys with canonical scopes; roles and keys holding native scopes (so an ABO role can hold a core-only permission such as `core:metrics.read`); the S4–S10 ambient reach carried over by one rule | `H1` |
| **H2 secrets** | every plaintext blob secret, and the four HEAD-encrypted rows, encrypted into `c/secrets/` with the keyring; blob fields and gap-fill file keys removed | `H2` |
| **H3 auth precedence** | only `enable_auth`, only in the enabling direction | `H3` |

- A release carrying both H2 and H3 uses the one ID `H2H3`, which counts as both. Each ID lands once; moving `release:` to one that has landed, or from an H ID to an S ID, is backwards. `shipped_stage:` order after `S10`: `H1`, `H2`, `H3`, `H2H3` in the order the owner lands them.
- Trailers (09 §9.2.1): flip PR `Stage-Release: <H> flip` (sets `shipped_stage:` and `release:` to the H value together); every content PR `Stage-Release: <H> 1` (`H1 1`, `H2 1`, `H3 1`, `H2H3 1`; `H2H3 flip` for the shared flip). Every commit also ends with `Co-Authored-By: Claude <noreply@anthropic.com>`. Merge with `gh pr merge <n> --rebase`, never squash. A flip can be reverted only before it ships; after that it is one-way.
- **Release notes** (09 §9.13 owns the text; quote verbatim in the release notes and in 05-authn §11.2, 05-config §1.12.5, 12 §12.4.4):
  - H1 (with the one re-login it causes stated beside it): "Backups made before this release still contain sign-in tokens. They no longer work against this server, but restoring such a backup brings them back until they expire; delete those backups or take new ones."
  - H2: "Backups made before this release still contain plaintext third-party secrets. Delete them or take new ones; if the backup directory may have been exposed, rotate those secrets."
  - H3: "With authentication off, Settings can no longer turn it on; set `ENABLE_AUTH=true` or `ABO_CORE_AUTH_MODE=required` and restart."

## 2. Prerequisites

- `S10` has a current soak row, or the previous H release does (the predecessor of an H release is the release `release:` names when its first PR merges). Predecessor row at least 14 days old; `check_soak.py` refuses the flip and every H trailer without it. OWNER work.
- **A fresh verified archive first (H1, H2).** Each runs only once the backup catalogue holds an archive of **this** store (manifest `InstallID` equals `c/storage/install`) whose level stamps are the pre-cutover vector, created within `core.storage.cutover.archive_max_age` (default 24 h) before the cutover boot, with a passing `VerifyOpen` result written after it was created (`<main>.verify.json`). Otherwise the step is deferred (health `storage_step_pending`, log `storage.ErrCutoverNoArchive`, never a boot failure) and the store keeps serving at the old levels. The deferred boot starts no soak clock.
- **No swap set-asides present (H1, H2).** While a restore's `previous/`/`failed/` directories or a reset's beside-itself destinations exist (kept for `core.storage.swap.keep_previous`), the step is deferred (`storage.ErrCutoverResidue`, naming the paths) until the sweep removes them or the operator sets `core.storage.cutover.sweep_set_asides`, with which the cutover boot deletes them first.
- Implicit `RequiresSelfServed`: a level step never runs on the first boot of a new release (this binary must have been ready for `core.storage.self_served_min`, default 1 h), so `make rollback` can still undo a broken release.
- H3 ships with or after the settings family's cutover (05-config §1.12.5): the Basic-gate keys' `HEADAuthOffWritable` rule ends with the earlier of H2 and the settings cutover, which precedes or ships with H3, the three keys together.
- Measured data first: the owner decides each cutover on measured data (key counts, row sizes); 14's Q-D and Q-E are deferred to H1 and H2. All earlier releases from S0 up to the one before the cutover declare both owners `books` and `core`, so every older build refuses the store.
- Worktree per CLAUDE.md; library-scale rewrites follow its concurrency rules (below).

## 4. Contracts (quoted; owner file § cited)

05-storage §5S.3.13 (deferred members):
```go
type Grant struct {
	To       Owner     // "core/<subsystem>"; a module ID is refused
	Prefixes []string  // each resolves inside a claim of the declaring owner
	Keys     []string  // exact keys inside the declaring owner's claims
	Mode     GrantMode // zero rejected
	Cutover  string    // the data migration whose raised phase enables deletes
	Reason   string    // required; boot log, ledger, census
}
type GrantMode uint8 // GrantInvalid, GrantRead, GrantReadDelete (deletes only after the cutover's raised phase)
```
05-storage §5S.3.5 (`UpgradeFloor` as it exists; `Requires` is the deferred addition):
```go
type UpgradeFloor struct {
	Owner        Owner
	Version      int    // the minimum applied version
	InstallFirst string // the STEPPING-STONE release
}
type ErrUpgradeFloor struct { Owner Owner; Have, Floor int; InstallFirst string }
```
05-storage §5S.3.13 cutover shape, a `datamigrate.DataMigration` (05-storage §5S.3.6) of the subsystem: `Breaking`, `BootBlocking`, `RaisesLevel` = the cutover build's supported level for that owner, `Source` = the legacy ranges moved, `After` = the highest step the owning module registers, `Parallelism tasks.Parallelism` required. Fields as declared:
```go
type DataMigration struct {
	ID string; Owner storage.Owner; Description string; Source []storage.Range
	Parallelism tasks.Parallelism; Mode Mode; Compat storage.MigrationCompat; RaisesLevel int
	RewritesInPlace bool; After []storage.StepRef; Barrier int
	Step func(ctx context.Context, kv storage.KV, w *StepWriter) error
	Verify func(ctx context.Context, r storage.Reader) (VerifyReport, error)
}
```
Persisted phases `c/storage/dm/<id>`: `folding`/`folded` (legacy authoritative until `raised`; a resumed fold restarts from legacy rows), `raised` (sidecars first, then one batch stamping the level and recording the backend `native`), `deleting` (legacy rows in chunks with a cursor), `done`. The level is always raised before the first legacy delete. Levels: books `Version` floor `UpgradeFloor{Version: LegacyCap}`; `CheckReader` is the one decision for open, `make rollback` and the updater; fast exits `--print-storage-levels`, `--print-upgrade-floor`.
Soak ledger (09 §9.2.1): `<release> <landing commit> <binary_id> <commit> <since, UTC> <levels> <evidence SHA-256>` written by `scripts/soak_record.py --release <id>`; `<levels>` are `<owner>=<level>` pairs.

## 5. Behaviour rules

**All three (09 §9.13)**
1. **One-way and floored.** Each cutover raises the reader level of every owner it names, so every older build refuses the store; `make rollback` and the updater refuse to swap to one. The floor is the cutover release itself: no binary swap goes below it. Only a restore of the pre-cutover checkpoint or backup goes back. A cutover runs behind the mandatory pre-migration checkpoint (taken in P4a) and the single per-owner level guard.
2. **Owners raised:** H1 raises `books`, plus `core` when it writes `c/auth/`/`c/rbac/` rows; H2 raises `books` and `core` (`c/secrets/`); H3 raises `books` only. The first cutover that raises `core` also lifts books' legacy restore bound `{core, 0}` (backup encryption is built and activated then, 05-backup §5B.3.9); a cutover that raises only `books` lifts nothing. Every guard-aware build from S0 on declares both owners; pre-guard builds are refused through books' legacy projection (`LegacyMaxFormat + 1`).
3. **Soak pass criteria (H):** zero `restore_*` and boot errors since `<since>`; the build's `--print-storage-levels` **and** the store's `<db>.storage-levels` match the expected vector, which is the predecessor row's `<levels>` with exactly the owners its §9.13 row raises strictly above it and every other owner unchanged (a fixed table in `soak_record.py`). No PR writes levels: `ci/stage.txt` holds no `levels:` line; the soak row is the one record. `<since>` is the later of the deploy and the first boot that logged the raised levels (the `boot levels=<vector>` INFO line), so a deferred boot starts no clock.
4. **A cutover that deletes code an older store needs declares an `UpgradeFloor`** naming its stepping-stone release as 09 §9.2.2 does (`UpgradeFloor{Owner: <subsystem>, Requires: [<cutover>], InstallFirst: <cutover release>}`); an archive made before the cutover restores only through a build that still registers it (checked at staging).
5. Library-scale rewrites are a `DataMigration` with its own `tasks.Parallelism` (CPU, fixed or declared sequential with a reason); never a sequential loop. Steps take `ctx` and honour cancellation between batches. Per-owner write locks of the legacy stores are held as at 09 §9.9 across any in-process read-modify-write.
6. Each cutover gets its own stage table, ledger rows and boot-writer rows in 06 §6.5.1's table; any boot-time durable write extends `TestBootCrashMatrix` in the same PR.

**H1 and H2: no old copy in the live directory**
7. Once the rewrite has committed and verified, the cutover boot deletes **every** pre-cutover checkpoint of the store (its own attempt's and every retained or consumed one, with `.migration-checkpoint`) and every old Pebble file under the DB directory, through a forced compaction of the rewritten key ranges and a WAL rotation. A delete is a tombstone and raw tokens sit in keys (`sess:<raw>`, `idx:sess:user:<user>:<raw>`, `invite:<raw>`), hence the compaction. Below that only a restore of the pre-cutover **backup** goes back. Taking, verifying and keeping that archive off the host (the backup directory may sit on the store's disk) is an owner checkpoint of the H1 and H2 deploys.
8. Done-checks plant a canary **before** a fixture upgrade, a restore and a reset, so retained checkpoints and set-asides hold it, run the cutover, and scan every file under the DB directory, `.mediacore-checkpoints/`, `.mediacore-restore/` beside the DB, every recorded beside-itself destination and `<state_dir>/restore/`. They state plainly that archives made before the cutover still hold the old representation; no swap set-aside survives, because H1 and H2 are deferred while one exists (section 2).

**H1 identity (05-authn §11.2, 05-rbac §6.3)**
9. Existing sessions, invites and other one-time tokens are **deleted**, not rehashed, so a raw token in an older archive is dead against the live store; the residual is bounded by the tokens' TTLs. API keys are SHA-256 hashes of high-entropy tokens at HEAD, so an archive exposes no usable key and no key re-issue is asked. Native forms: `mcs_` sessions, `mci_` invites, `mct_` temp-login tokens, `mcb_` bootstrap tokens, `mck_` keys with native scopes derived from each key's effective set; roles gain native scopes; `needs_confirmation`, `SignInRestricted` and native `LastSeen` become stored fields; seed-role operator diff and the lift of `ErrSeedRoleLocked` apply (05-rbac §3.6, §4.8).
10. **Ambient-scope rule (one rule, 05-rbac §6.3):** a role gains `core:self`, `core:metrics.read` and `books:reading` in its native scope set iff it is not `Confined()`; a key gains them iff its **effective** S4–S10 set before Ambient (the owner's role atoms intersected with the expansion of the key's atoms, an empty list meaning the role set) is not `Confined()`; never decided by the key's owner. HEAD's confinement rule (`internal/server/middleware/auth.go:268-297`) stays, so an admin's `["fingerprint.worker"]` key stays confined and every principal's answers are unchanged across H1.

**H2 secrets (05-config §1.12.5)**
11. The books store's plaintext blob secrets and the four encrypted rows (OpenAI key, Google Books key, Hardcover token, Basic password) move into `c/secrets/`, encrypted with the keyring (key IDs, AAD); their legacy copies and the gap-fill file's three keys are removed in the same boot; `legacy.SecretsStore` goes; every remaining `HEADAuthOffWritable` flag on a secret it moves ends (the Basic password and the kept integration secrets). An older build then has no copy to read, which the floor refuses.

**H3 auth precedence (05-config §1.12.5)**
12. **Only `enable_auth` moves, only in the enabling direction:** an operator value that enables auth (`ENABLE_AUTH=true`, `enable_auth: true` in the operator file) beats a stored `false`; a value that disables auth keeps HEAD's precedence (a stored `true` beats it). `HEADAuthOffWritable` is cleared on `enable_auth` only, so the auth-disabled principal can no longer store `core.auth.mode`. Every other `BelowStored` flag keeps HEAD's precedence until a separate owner-decided cutover: a name a shipped deploy file sets unconditionally (compose's `BASIC_AUTH_ENABLED`, `BASIC_AUTH_USERNAME`, `BASIC_AUTH_PASSWORD`) stays `BelowStored` permanently, and a legacy value that weakens a security control (`basic_auth_enabled=false`, `enable_rate_limit=false`) never locks.

## 6. Rollback costs

H stages have **no row in 09 §9.2.1's twelve-row table** (it lists costs that no stored format causes; a cutover is the opposite case). The cost is the floor itself, stated in each stage's release note and in `make rollback`'s refusal:
- Every older build refuses the store (`ErrUpgradeFloor`-class refusal through boot and `CheckReader`); `make rollback` and the updater refuse to swap to a pre-cutover build; the only way back is a restore of the **pre-cutover archive** (`core.storage.cutover.archive_max_age` bounds how stale it may be), which loses everything written since.
- H1: everyone signs in again (sessions and one-time tokens are deleted); an invite issued before H1 is dead; restoring a pre-H1 backup brings raw tokens back until they expire.
- H2: restoring a pre-H2 backup brings plaintext third-party secrets back; the owner rotates secrets if the backup directory may have been exposed.
- H3: a stale `ENABLE_AUTH=false` still loses to a stored `true`; auth-off Settings can no longer turn auth on; no rollback can turn auth off (older builds refuse the store).

## 7. Done-when (minimum, 09 §9.13; commands under `make ci` unless noted)

- `TestHardeningCutoverRefusedByEveryOlderRelease`: every release tag from S0 to the previous one boots on a store stamped by each cutover and refuses at boot and in `CheckReader` (all three).
- **H1, H2:** `TestH1H2_DeferredWithoutFreshVerifiedArchive` (no archive, a stale one, an unverified one and another install's each defer the step with `storage_step_pending` and leave every checkpoint in place; a fresh verified one lets it run). `TestH1H2_DeferredWhileSwapSetAsideExists` (a restore's `previous/` or `failed/` directory, or a reset's beside-itself destination, defers the step with `storage_step_pending` until swept; with `core.storage.cutover.sweep_set_asides` the cutover boot deletes them first).
- **H1:** `TestH1_NoRawTokenOnDisk` (canary session token planted before a fixture upgrade is in no file under the DB directory or a checkpoint directory afterwards); `TestH1_AmbientScopesPreserved` (before/after matrix over every principal kind on `/metrics`, `/api/v1/auth/me`, `/api/v1/auth/sessions` and a reading-state route); `TestH1_ConfinedKeyStaysConfined` (an admin-owned `["fingerprint.worker"]` key, an fp-worker user's key and an empty-effective-set key keep exactly their pre-H1 answers; `TestWorkerKey_NoAmbientScopes` keeps passing); `TestLegacyRoleReachUnchanged` stays green on the legacy routes; the done-check states plainly that archives made before H1 still hold raw session and invite tokens; release note: H1's text.
- **H2:** `TestH2_NoPlaintextSecretOnDisk` (a canary secret planted before a fixture upgrade is in no file under the DB directory, a checkpoint directory or `<db parent>/config.yaml` afterwards); states plainly that archives made before H2 still hold every plaintext secret, valid at its provider; release note: H2's text.
- **H3:** auth enabled through the environment stays on across restarts; `TestComposeEnvKeepsUIBasicGate` stays green; `TestLegacyAuthEnablePrecedenceMatchesHEAD`'s disabling half; release note: H3's text.
- Soak row for each H release: build and store raise exactly the owners its row names; the owner command writes `<levels>`. `scripts/tests/test_check_soak.py` cases: an `H1 flip` PR admitted after `S10`'s row; a `levels:` line in `ci/stage.txt` refused; an exact revert of an `H1 flip` admitted only before a production tag contains it; a deferred H1 boot not starting `<since>` before its `boot levels=` line shows the raised levels.
- Crash safety for the data migration: a crash at every phase and chunk loses no row and deletes nothing before `raised` (`TestCutoverCrashAtEveryPhase`, `TestCutoverRefusesOlderBuild`, `TestCutoverFloorRefusesSkippedStore`, `TestCutoverGrantDeletesOnlyAfterRaised`, `TestUpgradeFloorRequiresDoneStep`, `TestStepClockResetsAfterRollback` per 05-storage §5S.3.13 "when built").
