# Spec review round 3 — dispositions

Inputs: `spec-round-3-{correctness,data-migration,frontend,modules-build,ops-rollback,security,simplicity}.md`.
Totals: **130 findings — 9 BLOCKER, 54 MAJOR, 67 MINOR.** All accepted; several are
resolved by removing the mechanism they target (R3-1). 0 rejected.

## Why round 3 changes course

Blocker counts were 20 → 10 → 9. The residual blockers concentrate in one place: the dual-format rollback machinery
added in rounds 1–2 (identity/config adoption into core keyspaces with same-batch mirrors to legacy rows, side
records, rebuild-every-boot, mirror-disabled keys, Teach-build legacy guards, per-stage claim hand-overs and the
level floors around them). Every round's fix there produced new cross-stage edge cases (DATA3-2, DATA3-3, SEC3-1,
SEC3-2, COR3-1, and in round 2 seven of ten blockers). Per CLAUDE.md "Fix It Right" — the *correct* fix, not the
smallest — the correct fix is to delete the source of the edge cases rather than patch it again.

The premise was checked in code: the current build resolves permissions by exact string match over the role's stored
list (`internal/server/middleware/auth.go:430-455` @748fd787a), so a namespaced scope (e.g. `core:metrics.read`)
stored in a legacy role row grants nothing to an older build (fail-closed). The only widening hazard is empty
API-key scopes ("all role permissions", `internal/server/middleware/auth.go:405-408`), which the new design never
writes.

## Round-3 resolutions (binding; supersede round-1 cross-cutting resolution 5 and round-2 R2-1, R2-2, R2-3)

- **R3-1 One stored format per family during the extraction (decision 13, extended).** Core services that need ABO's
  existing generic data (users, roles, API keys, settings/config blob, ops history, activity) run on **legacy-format
  adapters** over the existing un-namespaced keys, reached through explicit, logged storage grants. There is **no**
  adoption copy into `c/…`, no same-batch mirror, no side records, no rebuild-every-boot, no mirror-disabled keys, no
  claim hand-over between owners and no Teach-build legacy guards during S0–S10.
  - Native-only data is stored **additively in the legacy row** where the legacy format tolerates it (namespaced
    scope strings in role/key lists — ignored by old builds) or in a new **core-only** family that old builds never
    read (e.g. hashed sessions: a rollback costs one re-login, owner Q-D recommendation).
  - New API keys always carry explicit, non-empty scopes, so no row an old build reads can widen.
  - Plaintext secrets move to the encrypted store when first written by the new build and are blanked in the blob
    (owner Q-E recommendation); a rollback then requires re-entering those secrets, which is stated in the release note.
  - **Cutover** (moving a family to a native core keyspace and deleting the legacy one) is **out of the extraction**:
    a later, per-family, one-way, checkpointed step, behind the single per-owner level guard, decided on measured data
    (exactly what 2026-09-18 decision 13 said). Its floor is the cutover release itself.
  - The live security hotfixes in `todo.d/2026-11-04_platform_core_followups.md` (revoked-key re-activation,
    unscoped child keys, `RequireAdmin` scope check, session-token exposure) still ship, independently and early.
- **R3-2 Release gating is one requirement.** Every PR to main passes `make ci` including the extraction gates before
  merge; 09 drops promotion-time gating mechanics; enforcement (branch protection vs. an alternative) is owner
  question Q-I.
- **R3-3 The MOD-2 gate reads non-test imports of every package, including `cmd/*` and the root `main`.**
- **R3-4 State-directory fallback preserved** (OPS3-1).
- **R3-5 SPA segment rule = `TopSegments`/`SPAShared`** everywhere (FE3-1).

What R3-1 keeps from earlier rounds: the single per-owner level guard (now used for real format changes: books'
own migrations and future cutovers), checkpoints before migrations, the min-upgrade-from rule (R2-4), the
revocation journal for restores, never-widen API keys, the native RBAC bounds (SEC-4, SEC2-2) for native routes,
and every non-transition design decision.
